### Publishable privacy attestation + derived-surface identity — `pipeline/day_master_encoder.py`, `pipeline/lf_provenance_sidecar.py`

`_build_day_blur_mask` writes `day_{date}_privacy_attestation.json` (schema `PRIVACY_ATTESTATION_SCHEMA`) beside the day's blur mask, naming all four `REQUIRED_PRIVACY_CLASSES` (`people`, `faces`, `plates`, `vehicle_occupants`) with one of three states each — `verified` / `failed` / `inconclusive` — and a reason (all four are mandatory; a class switched off by config degrades to `inconclusive`, never "not required"). `publishing/dispatch.privacy_hold_reason` holds any delivery whose required classes are not all `verified`, and an absent attestation is a hold too. The encoder writes each day's attestation into the stage dir; Phase D (`_sync_privacy_attestations`, at the publish-plan write) places it -- or, when the stage has none, an explicit `inconclusive` record -- beside the publish plan in the output dir, which is where dispatch reads them (`PrivacyAttestationLoader` globs the plan's directory). Attestations for days not in the plan are deleted there, so a stale `verified` cannot stand in; a non-day attestation there (`enqueue-asset`'s `day_asset_privacy_attestation.json`) is never removed. Copies are content-only (drvfs refuses `copystat`/`utime`).

That closes half the gap: it proves the MASTER was handled correctly. It said nothing about whether a given LF/short/thumbnail actually came from that attested master, rather than a stale, resumed-with-a-different-mask, or hand-placed one — "derived surfaces inherit the blur for free" (see the blur section above) only holds when the surface genuinely is cut from the attested master.

- **The attestation now carries the master's own identity.** `encode_day_master` stamps `master_fingerprint` (the same cheap `size:mtime_ns` identity `master_fingerprint()` computes for the resume-cache gate — never a full hash of the 60 GB master) into the attestation JSON right after the master is promoted to its final path, on EVERY successful return — the fresh-encode path and the cached-master resume shortcut alike (`_stamp_master_fingerprint_into_attestation`, best-effort, never raises; no-ops when no attestation exists, i.e. `--skip-blur`).
- **Long-forms are instrumented end to end; shorts and thumbnails are not yet.** LFs were picked first because they are the primary published deliverable — full duration, largest audience, longest per-video exposure — and already had an operator-facing provenance sidecar (`lf_provenance_sidecar.py`) to extend rather than a new mechanism to invent. Each LF's provenance record now carries `cut_from_master_fingerprint` (read from `per_day_completed[date].master_fingerprint`, populated once at encode time by `build_master_record` — no new fingerprinting) and `master_attestation_verified`: `true`/`false` once `write_lf_provenance_sidecar` cross-checks it on disk against the day's attestation, `null` with a `null_reasons` entry when the check can't be made (no recording date, no per-day record, no attestation on disk, or an attestation written before this field existed). `build_lf_provenance_payload` itself stays pure (state only, no filesystem access) — the disk cross-check is `write_lf_provenance_sidecar`'s job, matching the split `route_stats_sidecar`/`lf_provenance_sidecar` already use.
- **Absent evidence is its own state, on purpose.** A mismatch is recorded, never silently coerced into a pass, and the sidecar never gates an upload on it — same three-state discipline as the attestation's own `verified`/`failed`/`inconclusive`. Whether a mismatch should hold a delivery (mirroring `privacy_hold_reason`) is an enforcement decision left to a follow-up, not decided here.
- **Stills now write one too.** `photos/face_filter.py` learned to SAY what a run could attest (`attestable_privacy_classes`) and `photos/ingest.py` records it per gallery photo in journey frontmatter (`photo_privacy_unattested`) -- but neither produced the machine-readable document `publishing/dispatch.py` reads, whose `privacy_attestations(row)` callback had exactly ONE real implementation, written beside the video day master. So the four-class gate that refuses an unverified video export had nothing to consult for a still. `resizer.PhotoResizer.resize_batch` is the still analogue of that day master -- where the published copy is blurred and written -- and it now writes `photos_privacy_attestation.json` (`PHOTO_PRIVACY_ATTESTATION_NAME`) into the batch dir, in the SAME `{schema, required_classes, classes}` vocabulary, so `privacy_hold_reason` consumes it with no translation; `tests/test_photo_resized_privacy_attestation.py` pins that by feeding the written file straight into the real reader. Per WEEK, not per photo: what a run can attest is a fact about config and detectors, never about one frame. Written BEFORE the first decode, so a batch that dies on photo one still has a record of what was proven about the bytes it did write, and rewritten every run, because a stale `verified` outliving the run that earned it is this section's own cached-evidence bug. A write failure is logged and dropped rather than raised: fail-closed already lives at the reader (`privacy_hold_reason(None)` is a hold), and a record that can abort an export is a record that decides an outcome. **Writes; never gates** -- whether a still export is HELD on an unattested class is a product decision, and nothing here makes it.
- **And each resized export names the photo it was made from.** The attestation beside it is a fact about the RUN -- what config and detectors could attest that week. It could not answer "which source photo is THIS file", and the published copy is not the source: it is centre-cropped, blurred, re-encoded and renamed, so given a Drive link and a complaint nothing on disk led back to the original. `resizer._write_provenance` writes `photos_provenance.json` (`PHOTO_PROVENANCE_NAME`, schema `gms.photo_provenance/v1`) into the same batch dir, one entry per exported file: `exported`, `source`, a cheap `size:mtime_ns` `source_fingerprint` -- the day master's own shape, and for the same reason, since hashing a gallery week would cost more than the resize it records -- and `null_reasons`. A separate file rather than a key in the attestation because merging a per-FILE fact into a per-RUN one makes a single missing photo read like a run-wide failure. Accumulated inside the loop (only the loop knows which of the two write paths each photo took) and flushed on BOTH exits: after the last photo, and in the failure handler before it re-raises, because the bytes that already reached disk are facts a later failure does not unmake. **Records; never gates** -- absent evidence is null-with-reason rather than an omitted entry, since an entry that quietly disappears reads like a photo that was never exported, and a write failure is logged rather than raised.
- **Shorts now carry the identity too.** `lf_provenance_sidecar.write_shorts_provenance_sidecar` writes `shorts_provenance.json` beside `lf_provenance.json`, one entry per rendered short, through the SAME `attach_master_identity_to_record` the thumbnail upload entries use -- not a second comparison that would drift. A separate file rather than a key inside the LF sidecar because a short is not a property of a long-form: a day's shorts outnumber its LFs several times over, and answering "which master did THIS short come from" should not mean walking an LF list. **A short's day comes from its OWN path** (`<stages>/day_<DATE>/shorts/short_<rank>.mp4`, the shape `phase_d_scheduling._per_short_sidecar_labels` already reads rank from), never from its long-form's `per_lf_recording_date`: the path is direct evidence and the recording date is an indirect lookup, and preferring the lookup is how a short gets attributed to the wrong day's master. The LF date is a NAMED fallback, recorded in `null_reasons`, and with neither the day stays `null` and the verdict stays `null` -- never `verified`. Written at the same moment as the LF sidecar (`phase_bc_day_first`), no-op when the run rendered no shorts, and a write failure is logged rather than raised: by then the master is encoded and the shorts exist, so a record that could abort the run would be a record deciding an outcome. **Records; never gates** -- whether a mismatch should HOLD a delivery is still a product decision. Thumbnails were wired earlier, through the same helper (`drive_phases/phase_d_metadata._attach_lf_thumbnails` and its superlong twin), so what remains uninstrumented is resized/transition surfaces, not shorts or thumbnails.
- **Both sidecars name the code that wrote them.** `lf_provenance.json` and `shorts_provenance.json` carry a top-level `code_sha` (HEAD of the package's source checkout, or the commit recorded for a git-ref install, via `health.store.product_sha`), stamped at write time so a resumed run records the code that actually wrote the file. With no git metadata it is `null` and `null_reasons.code_sha` says why; it is never guessed. An inspector proves a corrected render contains a fix with `git merge-base --is-ancestor <fix-sha> <code_sha>`. Tests: `tests/test_provenance_code_sha.py`.
- **`lf_provenance.json` names the camera files each LF was cut from.** Each LF's `source.clips` lists the `VID_*.mp4` chapters whose span overlaps the LF's footage ranges (`name`, `path`, `size_bytes` or `null` when the file is gone, `episode_index`, `offset_s`, `duration_s`), and a top-level `source_clips` holds the sorted unique names across all LFs, so footage reuse across projects can be checked. Derived from `ingest_plan` plus `per_lf_gpx_episode_paths`; a gap (no plan, unpaired GPX, slice-derived episode with no chapters) is a `null_reasons.clips` entry, never an error. The schema version is unchanged: the module documents no bump policy and the fields are additive. Tests: `tests/test_lf_provenance_sidecar.py`.
- **A blur-bypassed day says so, in the same document.** `day_{date}_privacy_attestation.json` had exactly ONE writer, `_build_day_blur_mask`, and that function is gated behind `blur_gate.blur_required` -- so a `--skip-blur` day (or `blur_enabled: false`, the other way to the same place) produced no attestation AT ALL. Publication was still held, because `dispatch.privacy_hold_reason(None)` is fail-closed; what was missing was the CAUSE. An absent file is indistinguishable from a crashed run, a permissions failure, or a directory nothing ever wrote to, and every derived surface's cross-check -- LF, short, thumbnail -- had no document to bind to. `day_master_encoder.write_skip_blur_attestation` now writes one on that path, every required class `failed` with `SKIP_BLUR_REASON`. **`failed`, not `inconclusive`:** this module's `inconclusive` means "nothing ran, so nobody knows", and here nothing ran but we are not in the dark -- blur was turned off deliberately, so the master is KNOWN uncovered and the weaker state would understate a certainty. It never overwrites an existing document, so a resume that reused a blurred master keeps its verified record. Both halves now live behind one name, `finalize_privacy_attestation`, which every successful `encode_day_master` return calls: when they were separate a return path could stamp the master fingerprint and forget the document the stamp needs to live in, which is precisely what the `--skip-blur` path did. **Records; never gates** -- the publication outcome is identical before and after, held either way; this is not a blur gate in disguise.
