## Privacy report per post

- **One reused reader, two callers.** `console/library.py`'s `privacy_status_for_media(media_path, format_, *, site_path=None)` is the single place a media item's privacy status is derived, reusing `_privacy_status`'s recorded strings rather than re-deriving them. `console/pubqueue.py`'s `enrich_rows_with_sidecar` sets `row["privacy_status"]` for the publish-queue detail page (`pubqueue_detail.html`, "Privacy report" section); `cli/handlers/enqueue_plan.py`'s `_privacy_violations` calls the same function to refuse a whole `enqueue-plan --apply` run — upstream of any queue write, alongside the existing media-verification refusal — when any planned item's status is unrecorded or unrecognised (`console/library.py`'s `privacy_status_blocks_publish`).
- **Photo formats (`FORMAT_PHOTO`/`FORMAT_CAROUSEL`) get a real per-item fact.** `photos ingest` records each export's blur outcome on the journey's `photo_blur` frontmatter map (`pipeline/photos/ingest.py`), and `catalog/reader.py` surfaces it as `CatalogEntry.blur_state`. `privacy_status_for_media` resolves the site (an explicit `site_path`, else `console.settings.resolve_site_path()`), reads the catalog, and matches the media item's filename against a photo entry — no resolvable site, or no matching entry, reads as unrecorded (`_PRIVACY_STATUS_UNRECORDED`), the same honest reading as a genuinely-missing record, never a guess.
- **Video formats (`FORMAT_SHORT`/`FORMAT_LONG_FORM`/`None` — the only kind the drive pipeline's `plan_builder.py` builds today) never get a per-item catalog entry** — `catalog/reader.py` leaves `blur_state` `None` for every video row by construction. What IS true and provable: a blur-enabled drive run cannot ship a FINAL that isn't provably blurred (`pipeline/blur_gate.py` hard-fails the day master upstream of every short/long-form cut from it), unless the run passed `--skip-blur` — a run-level flag no delivery/`PublishRecord`/`PipelineState` field records, so this reader has no way to see it from one item. `privacy_status_for_media` therefore reports `_PRIVACY_STATUS_VIDEO_NOT_TRACKED`, naming the upstream gate rather than asserting an outcome for THIS item, and **never blocks** on it — blocking every video delivery (100% of real traffic today) on an architecturally-absent per-item fact would not be a privacy gate, it would be a global refusal.
- **GPS.** No recorded per-item GPS-scrub confirmation is reachable from either a `CatalogEntry` or a `PublishRecord`/`MediaFingerprint` — photo export strips EXIF GPS via a hard gate at write time (a hard gate in the service contract), but that gate leaves no queryable fact behind for a later reader to cite. This report does not claim one; it is scoped to the recorded blur outcome only.
- **Face/plate counts are never surfaced** — `_privacy_status`'s strings report the RECORDED outcome (found/no-regions/skipped/unrecorded/unrecognised), never a count, matching the "counts withheld" requirement.
