## Chapters (`gomoveshift/pipeline/chapters/generator.py`, run in phase_d)

Chapters describe the place sequence, not one label, so they do NOT use the dominant-county reducer. Guards:
- `_strip_null_island_waypoints` drops `(0,0)` cold-start fixes at journey load (keeps the journey if every waypoint is null-island).
- `_rebuild_journey` recomputes `start_date`/`end_date` from surviving waypoints after every strip/trim so the `video_duration / gps_duration` scale and Overpass sampling match on-screen footage.
- **`included_segments` are episode-local, not drive-global** (`_build_included_segments_for_lf`, phase_d): the drive path charts each LF against ONE representative GPX, whose waypoints key from that episode's local 0. The representative episode is chosen by the shared `_pick_representative_episode(segments, gpx_files)` selector (the episode contributing the most **GPX-bearing** segments; ties → lowest global index) — the SAME selector `_build_per_lf_gpx_path_map` uses to resolve the GPX, so callers pass `gpx_files` and the window base and the GPX trace can never come from different episodes (without the GPX-availability filter, an LF whose segment-majority episode lacked GPX built its window from episode A while the GPX came from episode B — wrong `Through:` counties, chapters naming cut footage, region checks false-failing a correct title). So the trim window is built from `LFSegment.start_time`/`end_time` (source-file-local), NOT `original_start_time`/`original_end_time` (drive-global, offset by prior episodes) — otherwise any LF past the drive's first episode gets a window shifted out of the GPX range and silently keeps the wrong stretch or none. Segments from other episodes are dropped (their footage isn't charted by this GPX). The `time_key = wp.timestamp − journey.start_date` trim base already carries the cold-start (effective-offset) correction because the strips reset `start_date` to the first surviving waypoint.
- **An LF spanning several GPX-bearing episodes charts all of them** (`_build_lf_multi_episode_journey`, phase_d_metadata): every episode's trackpoints are projected onto drive-global seconds (`original_start_time - start_time` = the episode's drive offset) and passed as `day_journey` with the segments' drive-global windows as `included_segments` — the superlong day-journey path. The single-representative rule below still applies to a one-episode LF. Regression: an LF once charted a 701 s episode across a 41.5 min LF (scale 3.66x, one intermediate chapter, metadata gate HARD FAIL).
- **Footage clock**: when every trackpoint of the parsed GPX carries `<extensions><gms_media_s>`, `load_journey_and_origin` re-times the journey onto footage seconds and returns the wall-clock instant of footage second 0; the trim window and `_scale_gps_to_video` (first surviving fix's footage second + `gps_time`, then the keep/included piecewise map) key on it, so GPS lock delay and recording gaps inside an episode no longer shift chapters. Partially stamped GPX falls back to basic chapters; unstamped GPX and `day_journey` keep the wall-clock path unchanged.
- **YouTube renderability gate** (`_pad_to_min_chapters`): YouTube renders a chapter block only with ≥`YOUTUBE_MIN_CHAPTERS` (3) timestamps, first at 0:00, each ≥`YOUTUBE_MIN_CHAPTER_GAP_SEC` (10s) apart. Pads the largest inter-chapter gap (only when ≥2× min gap), preferring a real town from `ordered_place_sequence` (chapter names are search terms) over `En route — <place>`. The drive-path hard gate (`_generate_chapters_all_lfs`) fails loud (`CHAPTER-GATE` ERROR) and skips the description embed below the minimum rather than embedding a non-rendering stub.
- **Middle chapters clear the metadata gate's floor by construction** (`min_intermediate_chapters` / `intermediate_chapters` in `generator.py`, which `content_gates.check_metadata_quality` imports for its chapter-density check, so the generator and the gate cannot drift apart): a GPS-bearing LF over 10 min needs `max(1, int(minutes / 15))` chapters that are not Start/Finish. `generate()` merges, counts, and when short calls `_top_up_to_gate_floor`, which re-runs `NominatimChapterSource.fill_interval_chapters` over the SAME geocoded samples `_extract_towns` fetched (`_gps_samples`, one Nominatim session budget) at rising targets — the merger drops a chapter within 60 s of the previous one, so a target equal to the floor can still merge below it. Every added chapter is a real sample's place stamped at that sample's own time; nothing is guessed. When no further sample names one it logs a `chapter floor` WARNING and the gate refuses the LF (fail closed). Motivation: Overpass once returned one town plus three downtown parks all at 705.3 s, `_extract_towns` accepted them (4 ≥ its own minimum of 3), the merger kept one, and the 34-min LF died at the gate (`only 1 intermediate chapter(s) for 34min video (need 2+)`) after a full render. Tests: `tests/test_chapters_gate_floor.py`.
- **Overpass responses cache ACROSS runs** (`overpass_source._shared_cache_entry` / `_load_shared_cache` / `_store_shared_cache`, dir from `paths.gms_overpass_cache_dir()` = the cache home plus `/overpass` (falling back to `~/.cache/gomoveshift/overpass`), `GMS_OVERPASS_CACHE_DIR` override, TTL `OVERPASS_CACHE_TTL_SEC` = 90 days): the cache lives INSIDE `_query_overpass`, so every caller inherits it — including `destination_resolver._default_poi_source`, which passes no `stages_dir` and therefore had **no cache at all** and re-queried the same bbox once per LF on every run. The per-run `_cache_path_for_bbox(stages_dir, …)` copy in `OverpassChapterSource` still exists and is checked first; the shared entry is the layer that survives an `--output-dir` being deleted, which is the normal case when one drive is re-processed for LFs, then shorts, then superlong. Keyed on the **full query text**, not the bbox: the query embeds `named_road_patterns`, so the bbox-only key served one pattern set's answer to another. Entries are written temp-then-renamed (a killed process cannot leave truncated JSON that reads as valid next run), a corrupt or expired entry degrades to a live query rather than raising, and a FAILED query is never written — a cache miss must never be poisoned into a permanent empty answer. An explicitly empty `GMS_OVERPASS_CACHE_DIR` disables caching entirely; `tests/conftest.py::isolate_overpass_shared_cache` sets exactly that for every test, so a mocked `urlopen` can never write a fixture into a developer's real cache nor be served from one. The request User-Agent carries only the project URL unless `GMS_OVERPASS_CONTACT` is set (an e-mail address or URL for whoever runs the install, which is appended to it); operators should set it per the map-data service's usage policy. Motivation: the public endpoint once answered `HTTP 429 Too Many Requests` mid-run because nothing was cached between runs. Tests: `tests/test_overpass_shared_cache.py`. **Still uncached: the coastline query** (`generator.py`, `way["natural"="coastline"]`) posts through `post_overpass_query`, so it gets the same multi-endpoint failover as every other caller, but keeps only a per-run `coastline_<hash>.json` — no shared cross-run cache of its own. `post_overpass_query` also remembers, for the life of the process, the endpoint that last answered successfully and tries it first on the next call (`overpass_source._last_good_endpoint` / `reset_sticky_overpass_endpoint`); a failure there still falls back to the full `OVERPASS_ENDPOINTS` rotation in declared order, so no endpoint is ever skipped or permanently blacklisted.
- **Overpass fails OVER, not just over again** (`OVERPASS_ENDPOINTS`, `_endpoint_is_unusable`, `_retry_after_seconds`). `_query_overpass` walks the endpoint tuple in order, spending at most `OVERPASS_ATTEMPTS_PER_ENDPOINT` (2) on each. What separates the two failure classes is whether waiting could help: a refusal, an unreachable network or a DNS miss (`ECONNREFUSED` / `ENETUNREACH` / `EHOSTUNREACH` / `gaierror`, read off `URLError.reason`) is a verdict about reachability, so the loop moves to the next mirror **immediately** rather than sleeping on a host that already sent a RST; an `HTTP 429` is "later, not never", so it waits out the server's own `Retry-After` (delta-seconds only, clamped to `OVERPASS_RETRY_MAX_SLEEP` = 60s, defaulting to `OVERPASS_RETRY_DELAY` = 5s when the header is absent or unparseable — the HTTP-date form is legal but unused by these mirrors, and mis-parsing it would stall an encode) and retries the same endpoint before failing over. **Every** endpoint's error is logged and accumulated into the final `RuntimeError`, never only the last: `socket.create_connection` walks all of a host's addresses and re-raises just the final one, so two IPv4 `Connection refused` results surfaced as an IPv6 `Errno 101 Network is unreachable` — a message describing a real condition that was not the cause. Tests: `tests/test_overpass_endpoint_fallback.py`.
- **A total Overpass outage degrades to the Nominatim fallback, never to zero chapters** (`OverpassChapterSource.discover_area_pois`): when `_query_overpass` raises the every-endpoint `RuntimeError`, area discovery logs an ERROR naming both the preferred path and the fallback and returns empty, so `ChapterGenerator._extract_towns` runs its capped Nominatim geocoding pass exactly as it does when Overpass answers too few places. The fetch layer stays loud (`post_overpass_query` still raises, every mirror named); the degrade lives at the one consumer that has somewhere else to go, the same shape `destination_resolver._default_poi_source` already had. Motivation: all three mirrors timed out / 504'd, the raise escaped the chapter pass (`CHAPTER-GATE: LF 1 chapter generation failed: Overpass query failed on every endpoint`), the 50-min LF got 0 chapters and Phase D HARD FAILed on metadata quality — while Nominatim had reverse-geocoded the end location seconds earlier. Tests: `tests/test_chapters_overpass.py::TestOverpassTotalOutageDegradesToGeocoding`.
- **The Nominatim fallback samples within half the remaining session budget** (`NominatimChapterSource.geocode_fallback`): when Overpass yields too few places it geocodes at most one sample per 30 s, at most `MAX_GEOCODE_FALLBACK`, and at most half of what is left of `MAX_SESSION_REQUESTS`, at marks spread evenly across the whole drive. The other half stays for the gate-floor top-up's road-label lookups (`reverse_geocode_detailed`, same budget). Sampling one per 30 s from the start let a long LF spend the whole budget in its first half, so the top-up got empty road lookups and the LF fell short of the chapter floor.
- **Both chapter sources map GPS-time ↔ waypoint by REAL timestamp** (`overpass_source.build_spatial_index`, `nominatim_source.geocode_fallback`): each sample mark takes the waypoint whose actual timestamp (elapsed from the journey start) is nearest and carries that waypoint's real elapsed time, NOT the mark time paired with the proportional index. The old proportional pick assumed a uniform GPX sample rate; on a variable rate or a mid-trace dropout it stamped a town/POI at a time the drive wasn't there (the wrong LF-description timestamp).
- **County reconciliation** (`overpass_source.pois_to_locations`): each chapter's county comes from its own nearest geocoded waypoint and is kept iff the resolver voted it, else snapped to `dominant_county`. `resolved_location=None` preserves the legacy first-waypoint stamp.
- Dedup + dead-zone (`gomoveshift/pipeline/chapters/marker_merger.py`): `_collapse_consecutive_duplicates` removes adjacent same-town chapters, comparing a decoration-stripped key (`_strip_chapter_decorations`) rather than the raw title — the route-suffix and terrain-band decorations it used to compare are exactly the ones the lower-third surface strips, so two identical towns split by a band change survived the collapse and burned twice; the 30s head/tail dead-zone clamps a legitimate early/late chapter inward instead of dropping it.
- End-location geocode is budgeted through a run-shared `NominatimChapterSource` (`MAX_SESSION_REQUESTS=50`). On budget exhaustion both fallbacks consult the SAME cache namespace the roads geocoder writes (`detailed`) rather than a namespace it never populates — `reverse_geocode` via a namespace-aware `GeocodingCache.get()` that reconstructs a Location from a warm `detailed` entry, and `reverse_geocode_detailed` via `get_detailed()` — so a budget-exhausted run still serves place-name and road-name chapters from a warm cache instead of silently degrading.
- **Interval-fill fallback carries the earlier passes' guards** (`NominatimChapterSource.fill_interval_chapters`): when passes 1–2 yield too few named places, the gap-fill re-reads the geocoded pool and picks each slot's nearest sample by time — but it routes the picked placename through `is_valid_chapter_placename` (so a tourism/business name can't leak back in as an "Entering X" chapter that the earlier passes would have dropped) and stamps the chapter with that sample's REAL video time, not the synthetic evenly-spaced grid time (grid-time stamping put "Entering X" minutes from when the drive was actually there). **The road substitute is filtered too** (`_road_chapter_label`): when no placename survives, the fallback used to stamp OSM's raw `road` verbatim — `is_valid_chapter_placename` accepts `"I 81"`, `"I 81;US 58"` and `"Deerfield Lane"` alike, so a residential way or an OSM concurrency join burned as a superlong lower third. It now reuses the drive-title road filter (`title_builder._road_passes_quality`, so a residential/service way yields NO chapter rather than a stamped one) and ref splitter (`_road_ref_members`, so `"I 81;US 58"` collapses to its hyphenated primary member), and only the accepted display label enters `used_labels` — a rejected road no longer consumes a slot a real place could have used.
- **Single-video calendar-day attribution buckets by LOCAL day, not UTC date** (canonical `gps_journey.core.models.local_day` = `utc + round(lon/15)h`, imported into `_journey_filter` and shared by `_filter_by_date` and `detect_gps_date_for_location`; `day_grouper` and `generator._longitude_local_start` reuse the same `to_local` primitive). GPX timestamps are UTC but the camera clock (and "the day of the drive") is local, so a continuous local-evening drive crossing UTC midnight would otherwise split across two UTC dates — the majority-date vote then drops the post-midnight half and chapters/end-location describe only part of the drive. Longitude-local solar time keeps one local evening on one day. `_filter_by_date` **hard-fails (`ValueError`)** on a malformed date or a zero-match instead of returning the whole (possibly multi-day) journey unfiltered — on camera-clock skew that fallback sampled OTHER days' waypoints; the raise surfaces upstream of any encode/upload so the operator supplies the correct `--gps-date` or fixes the clock.
- NOTE: chapter timestamp placement on `best_moments` cuts is an index-fraction approximation (exact cumulative-duration remap is a tracked follow-up).

**Legacy/web assembler chapters (`gomoveshift/assembly/assembler.py`, `gomoveshift process` + web `/api/approve`).** This path embeds chapters straight from OCR sign-text (`analysis/ocr.py`) and never touched the drive path's placename guards. Two defences keep OCR garbage out of an embedded MP4 chapter: the county pattern anchors `co`/`co.` to a token boundary (`(?:^|\s)co\.?` — a bare `co\.?` matched inside words, e.g. `tesco express` → `Express County`); and `_create_chapters` routes each candidate placename through `is_valid_chapter_placename` (imported from the chapters package) at the single embed chokepoint, dropping business names / attractions before the irreversible burn. The raw-OCR `UNKNOWN` fallback is not chapter-eligible, so it never embeds.

**Legacy/web assembler encode contract (`gomoveshift/assembly/encoder.py`).** The same `process` / `/api/approve` path renders through `VideoEncoder`, which used to emit codec + CRF + preset and nothing else — no pix_fmt, no profile, no color tags, no bitrate floor — so a render there could ship 8-bit and untagged while `config.output.pix_fmt`/`profile` (both pinned to `LONGFORM_*` by `OutputConfig.model_post_init`) had no reader anywhere in the codebase. `_quality_args` now stamps profile/pix_fmt from those config fields plus the four BT.709 tags and a `-b:v`/`-maxrate`/`-bufsize` floor selected by probed source height, mirroring `color_filters.get_encoding_args` (same constants, same 2160/1080 thresholds; the height is ffprobed once per source and cached). An unprobeable height gets no floor and a warning rather than a guessed number — CRF still governs quality. Separately, `trim_and_encode` now reaches the module's documented stream-copy branch: `_starts_land_on_keyframes` (via `keycut.probe_keyframes`) checks every kept-segment start against the source's real keyframes and, when they all land within `KEYFRAME_TOLERANCE_SEC`, extracts with `-c copy` for a bit-exact result. It is all-or-nothing because `concatenate` joins with `-c copy`, which needs identical stream parameters — mixing copied and re-encoded parts produces a broken file — and an unavailable or failed probe means re-encode, since the lossy answer is always safe. Both call sites previously hardcoded `reencode=True`, so every trim paid a full generation of loss even when the cut needed none. Tests: `tests/test_assembly_encoder_constants.py`.
