## Photo pipeline (`gomoveshift/pipeline/photos/`, `gomoveshift photos …`)

A second, independent pipeline: it posts stills from the site's journey galleries on a daily cadence. It shares the video pipeline's Drive uploader, `ContentLedger` and Metricool CSV primitives, but never touches video state. Two operator phases split by a human review gate — `photos generate` (select + caption) then `photos publish` (resize → upload → schedule → CSV → ledger); `photos batch` runs both with no review step, and `photos cleanup` reclaims artifacts. A separate `photos ingest` feeds developed camera-card stills into the journey galleries the selector later draws from — it is a *producer* of pool photos, not part of the review-gated generate/publish flow.

**Card ingest — `gomoveshift photos ingest` (`ingest.py`).** Photo input used to be journey frontmatter only; ingest closes that at the source end. A resource preflight (`preflight_photo_ingest`) runs at the top of `ingest()` — before the first decode or gallery write — gating free disk on the gallery dir (2 GB) and a **develop-sized** RAM floor (4 GB: the float64 grade transient of a full-resolution frame is several concurrent copies of the frame, about 2 GB at typical sensor sizes, where the publish preflight's 1 GB floor is resize/upload-sized), surfacing shortfalls as `PhotoIngestError` so the CLI reports them instead of tracebacking. It discovers every supported still on a card (recursively, stable name order), develops each, exports it into the journey's gallery dir, and *registers* the new filenames in the journey's day/location group so the selector picks them up unchanged. It is **idempotent and content-aware**: `gallery_filename` is the source stem lower-cased + `.jpg`, each ingest records a SHA-256 of the source bytes in the registering group's `photo_hashes`, and a source resolving to a registered name (bare stem or the day-disambiguated form) is skipped *before any decode* only when its bytes match the recorded hash — a re-inserted card leaves the page byte-identical, while a *different* photo behind a recycled stem (file-counter reset after 9999, a second body, a later day) develops under `<day-date>-<stem>.jpg` (the frontmatter's ISO date token) instead of being silently dropped behind a wrong skip reason. When that day form is also taken by different content, no honest name is left and the card hard-fails naming both; a legacy entry with no recorded hash keeps the skip — never a blind re-develop of a registered name — but is loudly marked unverified. A same-directory RAW + developed-sibling pair (`IMG_0001.NEF` + `IMG_0001.JPG` — standard pair-shooting layout) dedupes at discovery: the RAW develops, the JPEG is reported as skipped with a reason, no failure. Cards are rarely wiped daily, so ingest **partitions by EXIF capture date** (`extract_exif_capture_date` reads `DateTimeOriginal`, never raising — a malformed date counts as missing) after the pair dedupe and *before any decode*. **That reader sees camera RAW.** Pillow cannot open a Nikon `.NEF`, so a Pillow-only reader would read every RAW as dateless and the partition would never fire on a RAW card — the "no readable date" fallback below would be the normal path, and a two-day card would register everything under one `--day`. A RAW is a TIFF container whose Exif sub-IFD sits in front of the mosaic, so when Pillow declines the file the sub-IFD is walked straight out of the container with Pillow's own IFD parser (header seeks only — no demosaic, so the per-file pre-decode cost stands); non-RAW formats still parse through Pillow exactly as before, and a truncated or tag-less container degrades to no tags rather than raising. The partition therefore behaves as designed on RAW: only files whose date matches `--day` develop and register, an out-of-day file is skipped with a reason naming its actual date (registering it would ship a wrong travel date and let its GPS drag the card's single location vote across a county line), and a file with **no** readable date ingests under `--day` with a warning so legacy/EXIF-less cards stay usable. The one-location vote below therefore runs over the in-day survivors by construction. Any other two card files developing to one gallery name (two JPEGs, two RAWs — genuinely different content) hard-fail (`PhotoIngestError`, which always names the offending file/day) rather than silently dropping a photo. Frontmatter round-trips through `journal_publisher` (ruamel, comment-preserving) and is written with `atomic_write_text` **only after the whole card has developed**, so a bad decode or a torn page can't half-register a day (a torn journey page blocks the site deploy). The gallery dir gets the same all-or-nothing outcome: `export_jpeg` still writes per file inside the develop loop, but ingest tracks what this run exported and, on ANY failure before frontmatter registers (a later file's decode, blur, or export failure, an unresolvable location), removes exactly those files before re-raising — pre-existing files are never touched — so a partial card can't strand unregistered residue the idempotency check would never reclaim. An `OSError` from an export (missing/readonly gallery dir) is wrapped into `PhotoIngestError` naming the source file, original as `__cause__`, so it reaches the CLI's handler instead of tracebacking. The whole load → develop → register window runs under a per-journey sidecar flock (`<journey>.md.lock`, `ingest._journey_lock`, reusing the orchestrator run-lock machinery with its stale-PID recovery), so two concurrent ingests of one journey can't lose each other's frontmatter update; a live holder raises `PhotoIngestError` rather than waiting. The same lock is taken by the journal publisher and the site-sync reconciler, so it is mutual (see the lock paragraph below). `photo_count` is re-derived and kept in sync, but only when the key already exists — mirroring the `video_count` contract. Privacy runs **before** the write: each developed frame passes through `blur_faces_for_publish` — the same still-blur entry point the resizer uses, so the two publish surfaces share one region contract (faces ∪ aspect-gated plates ∪ plate-corroborated cabins) — and only the returned array reaches `export_jpeg`, so the gallery dir the website renders can never receive an export that isn't proven blurred; a `FaceBlurError` surfaces as `PhotoIngestError` naming the file with nothing written for it, `--skip-blur` is the only unblurred path (recorded as `IngestReport.blur_skipped` and printed loudly by the CLI, alongside the count of exports that carried a blur), and because the grade has already quantized to uint8 by the time a frame is export-bound, blurring there feeds the detectors exactly the depth they expect while leaving the 16-bit develop chain untouched upstream.

- **One location per card, resolved once and persisted** (`_resolve_location`): the cascade mirrors the drive pipeline's. An operator `--location` is authoritative and registered **verbatim without a geocode**; absent it, the card's own EXIF GPS votes the label. There is no third rung — an unresolvable card *raises* rather than defaulting, because a fabricated label is exactly how a non-US day ships under a US one. It is computed after the whole card develops and before any mutation, so an unresolvable location leaves the journey byte-identical, and it is persisted, never re-derived at a second site (the documented cause of far-road label bleed).
- **Decode provenance, `--redevelop`, `--dry-run`**: every developed export records its `DecodedPhoto.decoder` tag in the journey's `photo_provenance` frontmatter map (`PROVENANCE_KEY`: gallery name → tag, entries only for files this pipeline developed — hand-registered photos carry none), and `IngestReport.decoder_counts` totals the tags so the CLI summary shows at a glance how a mixed decodable+HE card actually developed; a preview-fallback count prints a NOTE naming the remedy. Without the map, filename idempotency permanently pinned a preview-fallback develop — an HE NEF stayed preview-quality forever, even after the true-raw DNG hook was configured. `--redevelop` is the repair: a registered file whose *recorded* provenance is `PREVIEW_FALLBACK_DECODER` develops again and its gallery JPEG is atomically replaced in place, updating the map — never re-registering the name, re-counting `photo_count`, or re-voting the card's location — while true-raw, non-RAW and unrecorded entries keep skipping. `--dry-run` (the photo analog of the drive path's `--label-dry-run`) walks the same discovery → pair-dedupe → EXIF-date-partition → location-resolution code paths, then returns the plan — would-ingest and would-redevelop names, skips with their recorded provenance, the resolved label — with nothing decoded, blurred, exported or written, and the resource preflight skipped since no heavy work follows.
- **Per-photo blur evidence, `photo_blur` (`BLUR_KEY`)**: `blur_faces_for_publish`'s outcome for each *newly ingested* photo (never a redevelop, which reuses an already-registered name) is recorded into the registering group's `photo_blur` frontmatter map in the same update call as `photo_hashes`, so it lands or doesn't land atomically with the rest of that photo's record. Three distinct values, checked off `skip_blur` first rather than the returned region count (a skipped photo never ran detection, so its `0` means "not asked", never "asked and found none"): `BLUR_SKIPPED` when `--skip-blur` shipped this export unblurred, `BLUR_REGIONS_FOUND` when blurring ran and found at least one privacy region, `BLUR_NO_REGIONS` when it ran and found none. A filename absent from the map — every photo ingested before this field existed, plus anything hand-registered outside this code path — is a **fourth**, distinct state: "not recorded", surfaced by `catalog.CatalogEntry.blur_state` as `None` rather than defaulted to any of the three.

- **Cluster-graded develop loop**: the skip/dedupe/date decisions run first and produce the card's to-develop list; a bounded measure pass (`compute_batch_corrections`) then clusters those files by lighting and elects one shared correction per cluster, and the existing per-file develop → blur → export → register loop grades each file with its cluster's params — one file decoded, graded and exported at a time, never a held batch of graded full-resolution frames. A skipped file is never measured, a dry run skips the measure pass entirely (measuring is a decode), a redevelop replacement clusters with the rest of the run (alone it forms a singleton cluster — effectively its own per-photo grade), and a measure-pass decode failure fails the card closed before any export. An injected `develop_fn` (the test seam) bypasses the measure pass and owns its own grading.

- **`--style` — creative look on the gallery masters** (`ingest_style` config default, `photos.style_strength` lever): ingest used to ship only the neutral corrective base grade, so no style ever reached the published site. With a style set, `_develop_styled` bakes the chosen scene-adaptive transform over each cluster's base correction from a **single decode** — the same decoded frame feeds `compute_scene_profile` (scene → `apply_style`) and `develop`, which accepts an already-decoded photo, so there is no second demosaic. The look layer is identical to `photos develop`'s (phase 3 below): the same eleven `STYLES`, the same strength lever. **With no style (the default, empty string) the branch is the pre-existing `develop(source, params, cluster_index)` call — byte-identical to before this option existed**; only an explicit `--style` (or the `ingest_style` config default) opts in, and an unknown name or a strength that is not a finite number > 0 is rejected at the CLI door before any decode (the same validation `photos develop` uses), with `apply_style`'s own `ValueError` as the library backstop. The style rides on top of everything else unchanged — clustering, the per-file OOM contract, the blur-before-export gate, one-location vote, idempotency, and residue cleanup all behave exactly as above. The `develop_fn` test seam owns its own grading and ignores the style.

**Decode + develop (`develop.py`).** `decode` turns RAW (rawpy, `use_camera_wb`, camera-applied orientation), HEIF (pillow-heif) or JPEG/PNG/TIFF (Pillow) into an upright `HxWx3` sRGB array — **16-bit for true-raw decodes** (`_RAW_POSTPROCESS`: `output_bps=16`; `no_auto_bright=True` so measured stats meter the lighting rather than LibRaw's content-dependent 1%-clip gain; explicit sRGB transfer `gamma=(2.4, 12.92)`, replacing rawpy's BT.709 default that contradicted the sRGB claim), uint8 everywhere else, with `bit_depth` reporting honest sensor depth (`white_level.bit_length()`, e.g. 14 for a lossless NEF), never the always-16 container dtype.
An 8-bit array is exactly what `color_analysis.analyze_frame` consumes; a 16-bit one is metered through a uint8 view (`_analysis_rgb` — measurement and the 8-bit-only NL-means run on the view, the latter re-applied to the 16-bit frame as a residual so untouched pixels keep sub-8-bit gradations) and graded from the full-depth original, quantizing to uint8 only at the very end of the float32 grade chain (an 8-bit decode re-floats already-quantized codes — banding in skies/shadows; float64 internals flattened a 20 MP frame to ~500 MB per apply-step copy).
Metering happens at the **video-calibrated analysis scale**: `_frame_stats` area-averages (INTER_AREA) the uint8 view down to `ANALYSIS_MAX_DIM` — the long edge of the video sampler's fixed 160×90 analysis frames the grade thresholds were calibrated on — before `analyze_frame`, because full-resolution per-pixel metering reads sensor noise as chroma and inflates a 20 MP still's measured saturation past what those thresholds were tuned for; the grade itself still consumes the full-resolution frame.
The sky ROI `analyze_frame` meters applies only to landscape frames: the bright-upper-band heuristic assumes dashcam horizon framing, and a portrait still's bright top is usually the subject rather than sky, so a taller-than-wide frame meters whole-frame with `sky_fraction=0` (video samples are always landscape, so video metering is untouched).
Failure is always closed (`PhotoDecodeError`, naming the file), never a half-decoded array.
One deliberate softening: a RAW whose stream LibRaw cannot unpack — Nikon **High Efficiency (HE/HE★) TicoRAW NEFs**, which LibRaw misreports as data-corrupted although the file is intact — falls back to the **full-resolution embedded JPEG preview** when one covers ≥ `PREVIEW_MIN_AREA_RATIO` of the sensor area, so a card ingest survives an HE body instead of dying on its first file.
The fallback re-opens the file (a failed unpack poisons the LibRaw handle for thumbnail calls), applies the camera's LibRaw flip (previews carry no EXIF orientation), and is honest end to end: `decoder="rawpy-preview"`, `is_raw=False`, `bit_depth=8`, plus a loud warning naming the cause and the remedy (shoot Lossless Compressed, or pre-convert to DNG).
No adequate preview → fail closed with that same remediation hint, never LibRaw's misleading "data corrupted" text.
`develop` grades that array by **reusing the video grade engine in its photo mode** — `analyze_frame` → `compute_correction(mode=GRADE_MODE_PHOTO)` → the `_apply_curves` → `_apply_colorbalance` → `_apply_saturation` → `_apply_gamma` chain in the same order the LUT baker uses — the curves step ends with a signed `black_point` tone move (positive lifts the output floor for a matte fade, negative cuts the input floor for crushed blacks; photo styles only, clamped to `BLACK_POINT_MIN`..`BLACK_POINT_MAX` and an exact no-op at zero, so video output and baked LUTs stay bit-identical) — with one photo-develop-only stage riding INSIDE `_grade` between `_apply_saturation` and `_apply_gamma`: a **per-hue HSL** adjustment (`_apply_hsl`) the scalar `CorrectionParams` fields cannot express — three optional length-6 (or length-7, see the orange note at the end of this section) controls (`hue_shift`/`hue_sat`/`hue_lum`) over the fixed anchor hues (red 0°, yellow 60°, green 120°, cyan 180°, blue 240°, magenta 300°), each per-band gain interpolated SMOOTHLY around the wheel (`np.interp` against the anchors made wrap-around, not hard band edges) so no seam shows between bands, and an empty/all-neutral control set is a **bit-identical no-op by construction** (default-OFF); it is deliberately **excluded from `params_to_lut3d_cube`** so every video output and baked LUT stays bit-identical exactly as denoise/sharpen are excluded.
A second photo-develop-only look stage, **split-toning** (`_apply_splittone`), rides `_grade` immediately AFTER `_apply_colorbalance` (before `_apply_saturation`): two independent signed (r,g,b) tints (`splittone_shadow` / `splittone_highlight`, each empty=OFF or length 3) added by a BT.709-luma weight — the shadow tint ramps from full at black to zero by mid-luma (0.5), the highlight tint its mirror, so the two never stack and the midtones stay clean — an empty/all-neutral pair a **bit-identical no-op by construction** and, like the HSL stage, **excluded from `params_to_lut3d_cube`** so video and baked LUTs stay bit-identical.
A third photo-develop-only look, **cross-process per-channel tone curves** (`_apply_channel_curves`), rides `_grade` immediately AFTER the master `_apply_curves` (before `_apply_colorbalance`): an independent ADDITIONAL monotone curve per R/G/B channel (`curve_r`/`curve_g`/`curve_b`, each empty = OFF or a flat list of alternating x,y control points, ≥ 2 points with x strictly ascending), reusing the same monotone-cubic interpolant the master curve uses so one channel's midtones can dip while another's lift (the classic film cross-process); all-empty is **bit-identical by construction** (default-OFF), and it is likewise **excluded from `params_to_lut3d_cube`** so video output and baked LUTs stay untouched.
A fourth photo-develop-only look, the **B&W channel mixer + duotone toning** (`_apply_monomix`), rides `_grade` FIRST of the look stages — immediately AFTER `_apply_colorbalance`, ahead of `_apply_splittone` — because it writes every pixel: it is the film-and-filter step, and every toning stage after it (split-tone, and the chroma stages) then works ON the monochrome frame instead of being wiped by it (see **Split-toned black & white** at the end of this section for why the order moved and what it costs).
`mono_mix` (empty = OFF, else three custom r,g,b luma weights) is the channel mixer — a red-weighted mix is the classic red filter that renders a blue sky dark and red rock bright — deliberately **not normalized**, since a weight sum away from 1 is a legitimate exposure move, though a non-positive sum is rejected outright (it inverts or blacks out the frame); the mixed luma is clipped to [0, 1] and broadcast to all three channels.
`duotone` (empty = OFF, else `(shadow r,g,b, highlight r,g,b)` in [0, 1]) tones through the luma ramp `shadow + luma·(high − shadow)` — sepia, selenium, cyanotype — keying on the `mono_mix` luma when one is set and on BT.709 luma otherwise, so duotone alone still tones the frame's own luma; `duotone_strength` (0..1, default 1.0) lerps that result back toward the plain mono luma and `duotone_mid` bends the ramp through a third mid-luma anchor (a tritone).
Together they are the monochrome control the `mono` style's fixed `saturation_mult = 0` cannot express (one fixed BT.709 rendering: no filter, no toning).
Both fields empty is a **bit-identical no-op by construction** (default-OFF, early `rgb.copy()`), and like the three look stages above it is **excluded from `params_to_lut3d_cube`**, so every video output and baked LUT stays bit-identical — so a still and a video frame of one scene land on the same look apart from the two video-only behaviors photo mode switches off: the unconditional 2-level shadow-lift/highlight-pull floors (they exist only to protect the full→limited 16–235 YouTube squeeze; a still ships full-range sRGB, so its lift/pull come only from the measured ramps, clamped at 0) and full-strength warm-cast neutralization (a warm cast keeps `PHOTO_WARM_CAST_ALLOWANCE` of itself and only the excess is corrected, so golden-hour light survives; cool casts get full authority in both modes, and video — the default `GRADE_MODE_VIDEO` — grades byte-identically to before).
**Reference-image colour match** (`_apply_reference_match`, `photos develop --reference PATH`) is the one look stage that rides `_grade` AFTER `_apply_gamma`, last of all: a Reinhard transfer in CIE Lab — the finished frame is converted to Lab and each of the three channels shifted and scaled until its mean and standard deviation equal a chosen hero frame's — so it must see the completed grade, since any stage after it would pull the frame straight back off the reference.
Deliberately two moments per channel rather than a full histogram transfer: mean and spread carry the reference's tone and cast without importing its tonal quirks onto a different subject.
It recalls a FRAME, not parameters, which is what separates it from a saved look, and it EMULATES that frame, which is what separates it from lighting-cluster sharing (`compute_batch_corrections`), whose shared correction NEUTRALIZES a shoot toward its own measured average.
The six numbers it needs (`reference_lab` = the L,a,b means then the L,a,b standard deviations) are produced by `lab_mean_std` — the single place either side measures, so the two can't drift — through `reference_lab_from_file`, which rides the same bounded `_measure_rgb` decode the clustering measure pass uses and runs ONCE at the CLI door: an unreadable `--reference` fails there naming the path, before a single source photo is decoded, and no per-photo render ever re-reads the file.
A channel with no spread is shifted onto the reference's mean and not scaled (an infinite ratio has nothing to scale) and the per-channel scale is railed at 4×, so a near-uniform frame cannot be blown apart.
Empty is a **bit-identical no-op by construction** (default-OFF, early `rgb.copy()`), it is **excluded from `params_to_lut3d_cube`** like the look stages above, and it is `replace`d onto the STYLED variants only, never `base` or `lut_params` — a `--lut` film emulation stays the film's look, not the operator's hero frame.
Photo mode additionally carries four deterministic, threshold-based **scene guards** that protect deliberate looks the video ramps read as defects (all photo-only; all derived from stats `analyze_frame` already emits, no classifier): a **deliberate-low-key** still (blacks at true black + midtones under the deep-underexposure knee + *intact* highlights — the top end is what separates a silhouette from underexposure, which drags the whole histogram down) has its shadow-lift/gamma response damped by `LOW_KEY_RESPONSE_SCALE` rather than being pulled to gray, while a dark still without intact highlights keeps the full correction; the **Flat/Protune-Log source-profile inference is video-only** (a still is never Protune footage — fog/mist measures exactly like a log profile and the profile gain would saturate the weather); the **mist/fog scene class** (low spread + saturation at or under the same bound the profile detector uses) caps the stacked base+atmospheric contrast at `PHOTO_MIST_CONTRAST_MAX` (the base ceiling) so the veil survives; and a **saturated warm sunset** (mean sat past the pulldown onset *together with* a warm cast ≥ `PHOTO_SUNSET_WARM_CAST_MIN`, the bottom of the golden-hour cast range) skips the saturation pulldown — a neutral/cool oversaturated still keeps it, that being the artifact class the pulldown exists for.
Two photo-only spatial stages ride on top, both **measured-first and ramped, never an on/off cliff**: **denoise** runs on the *source* (before grading amplifies grain) — `params.denoise_strength` authorizes a budget, this frame's measured noise decides how much is spent, so a clean frame returns untouched (noise is estimated from the median of Immerkaer's high-pass response, deliberately *not* variance-of-Laplacian, which scores a clean, finely-detailed frame higher than a noisy one and would smear exactly the frames worth keeping sharp); **sharpen** runs *last*, on the graded output — the unsharp amount ramps down as measured detail (log10 variance-of-Laplacian) rises and is zero at both ends (a crisp frame must not be over-sharpened; a featureless sky/fog frame has no edges to recover).
The operator lever over that ramp is `--sharpen` / `photos.sharpen` (range 0..2, **1.0 by default**): a **MULTIPLIER on the measured amount**, never a replacement for it, so the detail ramp still decides which frames sharpen at all and the knob only says how hard — a hand-tuned constant would over-sharpen the crisp frames and lift grain on the featureless ones, which is exactly what the ramp exists to prevent.
`1.0` short-circuits to the measured amount and is therefore **bit-identical to the automatic-only chain by construction** (the scaling arithmetic is skipped, not merely a no-op); `0.0` turns sharpening off outright; above 1.0 the result is clamped to `SHARPEN_MAX_SCALED_AMOUNT` (twice the calibrated maximum) so an amplified soft frame can't halo.
It applies on the styled surface, the LUT-look surface and the single-photo `develop` path alike, is range-gated at the CLI door and by a `PhotosConfig` validator before any decode, and — being an ALL_CAPS tunable — the ceiling feeds `DEVELOP_ALGO_VERSION` so a retune self-invalidates the reserved develop cache.
Both spatial stages are **resolution-aware**: NL-means wall clock grows linearly with pixel count (minutes at 20 MP), so a frame over `DENOISE_MAX_DIM` on its long edge is denoised on an INTER_AREA downscale — noise is measured on that same view, so the budget ramp matches the noise NL-means actually sees — and the correction is re-applied to the full-depth frame as an upsampled residual; the sharpen ramp's variance-of-Laplacian is metered on a view bounded to `SHARPEN_DETAIL_MAX_DIM` (at sensor scale high-ISO grain reads as crisp detail, and a genuinely sharp 20 MP frame can read soft); and the unsharp radius scales with width above `SHARPEN_REFERENCE_WIDTH` so a full-res frame keeps a perceptually equivalent sharpen after the site's ~5× downscale (a fixed 1.2 px would collapse to ~0.2 px).
At or under every bound all three behaviors are exact no-ops — small frames stay byte-identical to the unbounded chain.
A third, **position-aware** spatial stage rides last of all — the first stage that sees the whole `(H,W,3)` frame rather than the `(N,3)` pixel list `_grade` flattens to: an optional **radial vignette** (`--vignette` / `photos.vignette`, range 0..1, **off by default**) that smoothly darkens each variant's graded corners (applied after sharpen, on both the styled and the LUT-look surfaces, and on the single-photo `develop` path).
It is built on the **reusable spatial seam** `_apply_gain_mask`: a stage measures the frame, returns an `(H,W)` or `(H,W,1)` float **gain**, and hands it here; `_apply_gain_mask` multiplies the frame by that gain (broadcast over the channel axis), clips, and returns uint8.
An **all-ones gain is a byte-identical no-op by construction** (the float multiply is exact for gain 1.0 and every uint8 code), so `--vignette 0` (the default) produces exactly the pre-seam output and a stage that measures "no change" costs nothing.
The vignette's gain comes from `_radial_vignette_mask`, a `VIGNETTE_FEATHER`-power radial falloff computed from **normalized** coordinates (the corners sit at radius 1.0 regardless of frame size), so the look is resolution-independent the same way the sharpen radius's `SHARPEN_REFERENCE_WIDTH` scaling is.
A second position-aware stage, **clarity** (`--clarity` / `photos.clarity`, range −1..1, **off by default**), rides the same seam but runs BEFORE `_sharpen` — broad local contrast first, the fine ~1.2 px detail pass after — on both the styled and LUT-look surfaces and the single-photo `develop` path.
`_clarity_gain` high-passes the **luma channel only** at a large, width-scaled radius (`CLARITY_RADIUS` px at `SHARPEN_REFERENCE_WIDTH`, scaled up on wider frames exactly as sharpen's radius is — broad structure, not edges) and feeds the response back as a per-pixel **ratio** gain (one gain applied to every channel, so hue/saturation are untouched), weighted by a `CLARITY_MIDTONE_KNEE`-shaped midtone window that tapers to ~0 at both ends of the tone range: near-clipped highlights/shadows keep a gain of ~1.0 (halo/clip protection **by construction**) while midtones take the full boost, and `CLARITY_MAX_GAIN` bounds the gain so a dark pixel's small denominator can't blow up.
`--clarity 0` — exactly zero, the default and the only short-circuiting value — early-returns the input, so it is byte-identical to the pre-clarity chain.
A third position-aware stage, **film grain** (`--grain` / `photos.grain`, range 0..1, **off by default**), rides last of all — *after* `_vignette`, because grain is the final emulsion texture laid over every tonal stage including the vignette's corner darkening (real grain sits in the film, not under the lens), and reading the already-vignetted luma lets the darkened corners shed grain for free.
Grain is the **ADD counterpart to denoise's REMOVE**: denoise strips sensor grain from the *source* so grading can't amplify it, `_grain` lays a controlled filmic texture back onto the *finished* frame so film-emulation LUTs don't render sterile-clean.
Unlike vignette and clarity the field is **additive, not a gain** — a single MONOCHROME (luminance) noise field added *equally to R, G and B* (colour grain reads as sensor noise; luminance grain reads as film), so it does **not** ride `_apply_gain_mask`.
The field is luma-**weighted** (`_grain_weight`): a `GRAIN_SIGMA_SCALE`-scaled Gaussian is strongest across the midtones and smoothsteps to ~0 below `GRAIN_SHADOW_KNEE` and above `GRAIN_HIGHLIGHT_KNEE` (tone in 0..1), where real grain is least visible; `amount` scales the sigma.
The particle size is **resolution-independent**, the same promise `_vignette` documents and `_halation` keeps by scaling its radius with the frame width: a grain particle is a physical speck of silver, so a bigger scan of one negative resolves it across MORE pixels.
Drawn one independent sample per output pixel it covered exactly one at every size — the signature of the sensor noise this stage exists to replace — and, being uncorrelated, it averaged away as the frame grew: measured on a sample NEF, one photo at 5600 px carried a SIXTH of the grain it carried at 900 px from the same `--grain` value (sigma 1.83 vs 11.98 at a common viewing size), so the flag named a different look for every export size.
`_grain_field` therefore draws the field on a fixed `GRAIN_REFERENCE_DIM` (1200) grid and resamples it up to the frame (`INTER_CUBIC`), so one particle covers `long_edge / GRAIN_REFERENCE_DIM` pixels; the resample both correlates the samples and drops their variance, so the field is renormalised to unit variance and `GRAIN_SIGMA_SCALE` keeps meaning the same 8-bit sigma it means at the reference size rather than one that quietly decays with the frame.
After it, the same photo measures 8.38 at 5600 px (particles 1 → 4 px wide across 900 → 5600, lag-1 autocorrelation 0.00 → 0.94).
A frame already at or under the reference has nothing to scale and keeps the original per-pixel draw, **byte-for-byte as before** — which covers every contact-sheet panel and the whole existing test surface.
It is **deterministic by construction** — the field comes from `numpy.random.default_rng(GRAIN_SEED)` with a fixed module-constant seed (never global `np.random`, never entropy/time seeding), so two develops of one frame at one amount are byte-identical, which the reserved develop cache and `DEVELOP_ALGO_VERSION` invariants require.
`--grain 0` (the default) early-returns the input, byte-identical to the pre-grain chain.
A fourth position-aware stage, **halation** (`--halation` / `photos.halation`, range 0..1, **off by default**), rides *between* those two — after `_vignette`, before `_grain` — because halation happens in the **emulsion**: it belongs under the film grain and over the lens vignette (the vignette is glass, in front of the film, so corners it has already darkened have less left to bleed).
It is the film highlight bleed: luma above a **measured seed** is ramped to full `HALATION_SPAN` above that seed (so the bleed grows with how far into the highlights a pixel sits instead of switching on at an edge), Gaussian-blurred at `HALATION_RADIUS` px — the radius at `SHARPEN_REFERENCE_WIDTH`, scaled up on wider frames exactly as clarity's and sharpen's are, so a full-res frame keeps the same glow *in proportion to the frame* through the site's downscale rather than collapsing to a thin rim — and **screened** back at `HALATION_STRENGTH` opacity, weighted per channel by `HALATION_RED_BIAS`.
That seed (`_halation_seed`) is **measured off the frame's own tone, never an absolute constant**: it is anchored `HALATION_SEED_FRACTION` of the way from the frame's median to its highlight end (`HALATION_SEED_PERCENTILES`, metered on the same bounded view the sharpen ramp uses — a 20 MP percentile costs a full sort, and sensor speckle must not set the seed), then clamped into `HALATION_THRESHOLD_FLOOR`..`HALATION_THRESHOLD_CEILING`.
That is not a refinement but the difference between working and inert: this grade chain's output on a real NEF tops out near **0.67 luma and never clips**, so a threshold calibrated on a synthetic full-range frame sat above every pixel of every photograph and bled nothing — while passing every blown-frame test.
Anchoring *between* the median and the highlight end is what makes pixels above the seed exist by construction; a bare high percentile is not enough, since it lands *inside* a large uniform highlight where nothing exceeds it and the stage is inert again.
The highlight end is p99.5 rather than the max so one hot pixel cannot set the seed, the floor keeps a dark frame from blooming its own noise (its whole range sits under the floor, so it seeds nothing at all), and the ceiling keeps a blown frame from seeding at the clip point.
`HALATION_SPAN` stays a fixed luma distance rather than a frame-relative one, so a genuinely bright frame still glows harder than a flat one.
Two further deliberate choices.
The glow is **red-biased, not neutral**, because that is the physics: the short wavelengths are absorbed in the upper layers and the anti-halation backing, so what scatters back off the film base is the long end — a blown window in a film frame rims warm, never white, and a neutral bloom reads as a video effect instead.
That bias is the DEFAULT rather than the only option: `--halation-tint R G B` / `photos.halation_tint` (three weights in 0..1, length- and range-gated at the CLI door and by the `PhotosConfig` validator before any decode) replaces `HALATION_RED_BIAS` per channel, so a cyberpunk or neon-noir look can bleed cyan or magenta where film only ever bled red.
Unset is OFF and OFF *is* `HALATION_RED_BIAS` (`_halation_glow` falls back to it on an empty tint), so a develop that never names a colour renders byte-for-byte what it rendered before the knob existed; a tint alone changes nothing either, since the whole stage is still gated on `--halation` being above 0.
And the blend is **screen, not add**, which cannot overshoot: an already-clipped highlight stays exactly where it is and only its surroundings brighten, which is what makes this a glow rather than a global exposure lift.
Like the other spatial knobs it is range-gated at the CLI door and by a `PhotosConfig` validator before any decode, it applies on the styled surface, the LUT-look surface and the single-photo `develop` path alike, and `--halation 0` (the default) early-returns the input, byte-identical to the pre-halation chain.
A sixth position-aware stage, **lateral chromatic aberration** (`--chromatic-ab` / `photos.chromatic_ab`, range 0..1, **off by default**), rides directly on top of that bleed and still under `_grain`: the fringe arrives through the GLASS, so it sits over the emulsion's halation, but the sensor resolves it, so it belongs under the noise floor the grain stands in for.
It is the one look stage that is **geometry, not tone** — glass bends short wavelengths harder than long ones, so an off-axis point lands as three slightly different-sized images, and `_chromatic_ab` reproduces exactly that: one `cv2.remap` grid pair per fringing channel (`_radial_scale_maps`) rescales R by `1 + shift` and B by `1 − shift` about the frame centre, with green untouched as the reference.
The displacement is **zero on the optical axis** (the centre maps to itself, whatever the amount) and grows linearly with radius, which is why the fringe shows in the corners and never in the middle of the frame; the inward-pulled channel reads past the frame edge, where `BORDER_REPLICATE` holds the border colour rather than fringing against invented black.
`CHROMATIC_AB_CORNER_SHIFT` is that corner displacement at amount 1.0 as a **fraction of the half-diagonal**, never a pixel count — the same lesson `GRAIN_REFERENCE_DIM` records: a spatial effect sized in pixels is a different look at every export size, and a 20 MP master downscaled to 2 K has to carry the fringe the 2 K export carries.
It is **deterministic by construction** (no RNG at all — only a geometry derived from the frame's own dimensions), and `--chromatic-ab 0` (the default) early-returns the input, byte-identical to the pre-fringe chain.
A seventh position-aware stage, **scanlines** (`--scanline` / `photos.scanline`, range 0..1, **off by default**), rides between the halation and the grain — the CRT tube is what the emulsion's glow is displayed *on*, and grain stays the last texture of all.
It is a row-periodic darkening on a **soft sine** profile (gain 1.0 at the crest, down by `SCANLINE_DEPTH` in the trough at amount 1.0), laid through the `_apply_gain_mask` seam as an `(H,1)` gain — one value per ROW, broadcast across every column, so the modulation cannot vary along x by construction, and it is deterministic with no rng to seed.
Soft is the design, not a finish: a comb of hard on/off rows carries its energy at the Nyquist limit, so the site's downscale (or a contact sheet) folds it straight into moire.
The line SPACING is anchored to `SCANLINE_REFERENCE_DIM` exactly as the grain field is (`SCANLINE_PERIOD` px at that long edge, ~300 cycles across the long edge, scaled with the export), so one flag value names one line DENSITY at every size rather than one pixel spacing that quietly becomes a different look on each export — the same lesson, pre-applied.
`SCANLINE_MIN_PERIOD` floors it at three rows per cycle: below that the sine cannot be sampled and aliases back into the hard comb it exists to avoid, so a frame far under the reference holds the coarsest line structure it can carry.
`--scanline 0` (the default) early-returns the input, byte-identical to the pre-scanline chain.
An eleventh position-aware stage, the **Orton glow** (`--glow` / `photos.glow`, range 0..1, **off by default**), runs early instead of late: after `_dehaze`, *before* `_clarity`.
It is the darkroom sandwich print — one sharp exposure and one soft, over-exposed one printed together — and one of the two ways this chain can SOFTEN a frame, the other being a negative `--clarity` (below): glow ADDS diffused light over the whole frame, where negative clarity flattens the frame's own broad structure and adds none.
`_glow_bloom` weights the frame by its own tone (brighter pixels contribute more of the soft copy) and blurs that weighted FRAME — not a bare mask, which is what makes the bloom carry local colour instead of laying a white haze over the photograph — at `GLOW_RADIUS` px scaled by frame width exactly as halation's, clarity's and sharpen's radii are; `_glow` then **screens** it back at `GLOW_STRENGTH` opacity, screen rather than add for the reason `_halation` documents (it cannot overshoot, so an already-maxed highlight stays exactly where it is and only its surroundings lift).
The tone the diffusion starts at is **measured off the frame** (`GLOW_SEED_PERCENTILES`/`GLOW_SEED_FRACTION`, on the bounded view the sharpen ramp uses), the `_halation_seed` lesson pre-applied: this chain's output tops out near 0.66 luma and never clips, so an absolute highlight threshold would ship green and inert — mutating the seed to an absolute constant leaves the end-to-end develop assertions passing and reddens only the sub-clipping-tone test.
The ramp runs from that seed to the frame's own highlight end rather than a fixed distance above it (`GLOW_SPAN_FLOOR` stops a flat frame dividing by ~0): where halation wants a genuinely bright frame to bleed harder than a dull one, a whole-frame diffusion has to engage the whole frame either way.
Position is the design, not a detail — glow and *then* re-resolve the detail with clarity and sharpen reads as film, while the reverse smears and reads as haze; dehaze still runs first of all, because it SUBTRACTS the atmospheric veil and running it after a deliberate glow would set the two against each other; `--glow 0` (the default) early-returns the input, byte-identical to the pre-glow chain.

A tenth position-aware stage, **holographic sheen** (`--holo-sheen` / `photos.holo_sheen`, range 0..1, **off by default**), rides over the chromatic aberration and under the scanlines: the foil is a property of the PRINT SURFACE, so it lies over the fringe the glass delivered and under both the tube that displays the print and the emulsion's own texture, which stays last of all.
It is the oil-slick read of a foil print — an iridescent tint whose HUE turns with TONE, so shadows, midtones and highlights each pick up a different cast and the frame shimmers rather than shifting as a whole: `HOLO_TURNS` is how much of the hue wheel that sweep covers from the frame's darkest metered tone to its brightest (under one full turn, so no two tones land on the same cast), `HOLO_PHASE` is where the shadows start on it, and `HOLO_AMPLITUDE` is the per-channel offset at amount 1.0 as a fraction of full scale (~9 codes of 255) — a **sheen**, deliberately an order of magnitude under `--duotone`/`--bw-mix`, which already exist for wholesale recolouring.
`HOLO_CHANNEL_PHASES` sit the three channels 120° apart on that wheel, which is what makes the per-channel offsets sum to **zero at every tone** — the tint is pure chroma by construction, so the stage cannot lift or crush exposure — and the sweep runs over the frame's OWN metered span (`_holo_tone`, `HOLO_TONE_PERCENTILES` on a `HOLO_MEASURE_MAX_DIM` view, with `HOLO_MIN_SPAN` falling back to absolute tone on a flat wall or a whiteout) — the same lesson `_halation_seed` and the dehaze haze floor each record, since an absolute ramp over a chain that peaks near 0.66 luma sweeps two thirds of the wheel on one photograph and a third on the next, so one flag value would name a different look every time.
It is **deterministic by construction** (no RNG at all — the tint at a pixel is decided by that pixel's luma and nothing else, so two pixels of equal tone match wherever they sit in the frame), and `--holo-sheen 0` (the default) early-returns the input, byte-identical to the pre-sheen chain.
A ninth position-aware stage, **glitch** (`--glitch` / `photos.glitch`, range 0..1, **off by default**), rides directly on top of those scanlines and still under `_grain`: the tear is a fault in the SIGNAL being displayed, so it sits over the tube's own line structure, and the grain stays the last texture of all.
The frame is cut into a grid of horizontal BANDS, a subset of them is displaced sideways, and each torn band gathers its three channels at `GLITCH_CHANNEL_SPLIT`-separated offsets — the RGB separation a corrupted stream shows when the planes arrive at different offsets.
It is ONE knob by design rather than three: `amount` drives both the FRACTION of bands that tear (`GLITCH_TORN_FRACTION` at 1.0) and the displacement itself (`GLITCH_SHIFT_RANGE`, a min..max **fraction of frame width** and never a pixel count), so amount 1.0 tears at most a twentieth of the frame sideways at any export size — deliberately conservative, since the picture must still read as the picture and the calibration is an eyeball gate; `GLITCH_BAND_HEIGHT` is the band depth in px at `GLITCH_REFERENCE_DIM`, the anchor the grain field and the scanline spacing take and for the same reason: one flag value must name one band COUNT rather than a pixel depth that quietly becomes a different look on every export (the same lesson).
It is **deterministic by construction** — the tear pattern comes from `numpy.random.default_rng(GLITCH_SEED)` with a fixed module-constant seed, never global `np.random` or entropy — and the stage is a pure horizontal GATHER of existing codes along axis 1, so rows cannot move, no code is ever synthesized, and dtype and range survive without a gate; a band reading past the frame edge holds the border column exactly as `_chromatic_ab` does with `BORDER_REPLICATE`.
`--glitch 0` (the default) early-returns the input, byte-identical to the pre-glitch chain.
An eighth position-aware stage, the **light leak** (`--light-leak` / `photos.light_leak`, range 0..1, **off by default**), sits immediately after `_halation` and before `_chromatic_ab`: a leak is stray light that got past the camera back and exposed the EMULSION, so it belongs with halation's bleed rather than above the lens fringe, and under the grain like every other emulsion effect.
It is one warm radial ramp anchored at a FIXED corner (`LIGHT_LEAK_CORNER`) in a FIXED hue (`LIGHT_LEAK_TINT`), smoothstepped from full at that corner to exactly zero at `LIGHT_LEAK_REACH` of the frame's diagonal away, and screened back at `LIGHT_LEAK_STRENGTH` opacity — so the far side of the frame is untouched by construction rather than by a threshold, and the whole stage is **deterministic** with no rng anywhere (seeded placement variety would be a different feature).
The reach is a fraction of the frame DIAGONAL, never a pixel count — the same lesson `GRAIN_REFERENCE_DIM` records — so one flag value is one look at every export size, and distance is metered in pixels over that diagonal rather than in normalized coordinates, which would stretch the ramp into an ellipse on a wide frame; the blend is **screen, not add**, for exactly the reason `_halation` gives — screen closes a fraction of whatever headroom a pixel has left, so an already-bright area stays put and only its surroundings lift, where a clipped add would slam the whole corner flat against the ceiling.
`--light-leak 0` (the default) early-returns the input, byte-identical to the pre-leak chain; it is range-gated at the CLI door and by a `PhotosConfig` validator before any decode, and it applies on the styled surface, the LUT-look surface and the single-photo `develop` path alike.
A fifth position-aware stage, **dehaze** (`--dehaze` / `photos.dehaze`, range 0..1, **off by default**), runs FIRST of the spatial chain — before `_clarity`, so the local-contrast, sharpen and glow stages work on a corrected frame instead of amplifying the veil.
It is real atmospheric-veil SUBTRACTION via the **dark-channel prior**, deliberately distinct from the bounded S-curve contrast increment `color_correction` also calls dehaze (that one adds punch on a measured haze score and stays exactly as it is; this one removes the veil).
Haze composites as `I = J·t + A·(1−t)` and `_dehaze` inverts it: `_dehaze_airlight` estimates the veil colour `A` as the MEAN colour of the frame's haziest pixels (the top `DEHAZE_AIRLIGHT_PERCENTILE` of the dark channel, averaged rather than the single brightest pixel the published prior takes, so one specular speck cannot set the veil), `_dehaze_transmission` estimates `t = 1 − omega·haze` from the dark channel of `I/A`, and the recovery is `J = (I − A)/max(t, DEHAZE_MIN_TRANSMISSION) + A`; `amount` scales `omega` (`DEHAZE_OMEGA_MAX`), so 1.0 is a strong but not total strip.
Two choices are what make it bite on THIS pipeline's tone rather than on a textbook full-range frame.
`A` is **frame-relative by construction** — on a develop that peaks at 0.66 luma the airlight lands near 0.66, where an absolute constant (or the prior's hard 1.0) would either do nothing or over-correct wildly.
And `haze` is the dark channel measured against **this frame's own haze-free floor** (`DEHAZE_HAZE_FLOOR_PERCENTILE`), not against a literal zero: the prior assumes a clear scene's darkest patch is black, this grade chain never lands there (a real develop's 1st percentile sits near 0.14 luma), so reading the raw dark channel bills every dark object's own colour as veil — on a reference misty-ridgeline NEF that build crushed **29% of the frame under 16/255** at amount 1.0, while the floor-relative one crushes none of it and leaves the 1st percentile exactly where the grade put it (same lesson, same shape of fix as `_halation_seed`).
Dark channel and transmission are metered on a view bounded to `DEHAZE_MAX_DIM`, with the patch a FRACTION of that view's long edge — a full-res min-filter at 20 MP is minutes of wall clock, transmission is inherently low-frequency, and the fraction is what keeps the estimate resolution-independent — then blurred and bilinearly upsampled.
The per-pixel bound `t ≥ 1 − I_c/A_c`, which is exactly the condition for the recovered pixel to stay non-negative and which the un-blurred estimate satisfies automatically, is therefore re-imposed at full resolution afterwards (solved for `DEHAZE_SHADOW_RETENTION` of the darkest channel): the blur/upsample cannot bleed a hazy neighbour's low transmission onto a dark pixel and drive it to black, so shadow non-negativity is restored **by construction** rather than gated after the fact.
`--dehaze 0` (the default) early-returns the input, byte-identical to the pre-dehaze chain; it is range-gated at the CLI door and by a `PhotosConfig` validator before any decode, and it applies on the styled surface, the LUT-look surface and the single-photo `develop` path alike.
The seam is deliberately generic, not hardcoded to any one stage: **`--sky-darken`** is the second stage riding it — `_sky_mask` RENDERS the sky the meter until now only ever measured in order to *exclude* it, and `_sky_darken` turns that mask into a per-pixel gain for `_apply_gain_mask` rather than re-flattening the frame on a parallel path.
The mask mirrors `analyze_frame`'s own reasoning so mask and meter can never disagree about what the sky is: bright pixels inside the upper band (`SKY_ROI_UPPER_FRACTION`, *imported* from `color_analysis` rather than copied, so one retune moves both), and **landscape frames only** — the identical portrait guard, for the identical reason (a taller-than-wide frame gets an all-zero mask, because a portrait still's bright top is usually the subject and silently darkening a head is the failure mode).
"Bright" is **frame-relative**, the same lesson as `_halation_seed` and the dehaze haze-floor: the ramp runs from this frame's median to `SKY_LUMA_SPAN_FRACTION` of the way toward its `SKY_LUMA_PERCENTILES` highlight end, because an absolute threshold tuned on a blown sky selects *nothing* on a develop that peaks at 0.66 luma.
A frame whose median-to-highlight separation falls under `SKY_MIN_CONTRAST` — a forest interior, a flat close-up — is smoothstepped to a zero mask by construction, so a frame with no sky can never have its own noise rendered as one.
Softness is not cosmetic (a hard-edged sky mask is the classic tell of a bad landscape edit): the band ramps by smoothstep over `SKY_BAND_FEATHER` of its depth, and the mask is blurred at `SKY_MASK_BLUR_FRACTION` of the long edge on a `SKY_MASK_MAX_DIM`-bounded view then bilinearly upsampled — resolution-independent, and smooth before the upsample rather than because of it.
It runs with the other gain-mask stages and **before `_vignette`**: pulling the sky down is a subject-region edit, while the vignette is a lens effect that belongs over everything the picture contains.
`--sky-darken 0` (the default) early-returns the input byte-identically, is range-gated at the CLI door and by a `PhotosConfig` validator before any decode, and applies on the styled surface, the LUT-look surface and the single-photo `develop` path alike; `SKY_DARKEN_MAX` holds amount 1.0 at a deep but never black sky.
Sky-saturate is the second lever on this mask and has landed (the note at the end of this section); the graduated ND does NOT ride it — a filter rides straight geometry, not a region (see the `--graduated-nd` note at the end of this section).
Those two masks were each **welded to exactly one effect** (sky → darken, radial → vignette), so no arbitrary colour recipe could ride a region; `masks.py` unwelds them into a **named registry** — `mask_for(name, rgb)` returns one soft `(H,W)` float32 mask in [0,1] computed as a PURE function of the graded frame, and the `MASKS` dict enumerates the legal names so a caller can refuse an unknown one by listing what exists: `sky` (the shipped `_sky_mask`, reused rather than re-derived) and `ground` (its complement), the three feathered luma windows `shadows`/`midtones`/`highlights`, `radial` (the shipped vignette falloff read at amount 1.0 — 1 at the centre, 0 at the corners) `linear` (an angle + span gradient: a bottom-of-frame ground glow at the defaults, a tilt-shift band when paired with its `invert=True` twin), and the two the notes below add, `glints` and `texture`. The dict is the enumeration, never this sentence — `sorted(MASKS)` is what a caller and a reader should both read.
A look's `layers:` is what reaches that registry (see `--look` below): each layer is `{mask: NAME, feather, invert, <colour knobs>}`, its colour chain grades the ALREADY-GRADED frame and the result is lerped through the mask — `out = base + mask * (layered - base)` — so a recipe rides the frame's own regions instead of the whole rectangle.
The luma windows are **frame-relative**, the same lesson `_halation_seed`, the dehaze haze floor and the sky mask's brightness ramp each learned (this chain peaks near 0.66 luma, so an absolute highlight window sits above every pixel of every photograph and the layer ships inert), and they are one smoothstepped ramp *differenced* at `LUMA_EDGES`, which is what makes the three sum to exactly 1 across the tonal range — a layer set covers the frame without a seam — and `midtones` non-negative **by construction** rather than by a clamp; a frame whose measured span falls under `LUMA_MIN_SPAN` holds no structure to partition (a flat wall, a whiteout) and falls back to absolute tone instead of partitioning its own noise.
Every mask is **deterministic** (no RNG, no clock, no global state), **feathered** (`feather` widens or tightens the transition band with 0 and 1 *pinned*, since a feather that lifted a zero region would leak its layer frame-wide) and **resolution-anchored** by construction — positions are normalized coordinates and tone is metered on a `MASK_MEASURE_MAX_DIM`-bounded view, so nothing depends on the pixel count and one name means one look at 1200 px and at 5600 px, `GRAIN_REFERENCE_DIM`'s lesson pre-applied rather than learned again.
The `develop` helpers the registry reuses are imported **inside** its functions, never at module level, so the registry and `develop` can never form an import cycle.
`SKY_LUMA_PERCENTILES`/`SKY_LUMA_SPAN_FRACTION`/`SKY_MIN_CONTRAST`/`SKY_BAND_FEATHER`/`SKY_MASK_BLUR_FRACTION`/`SKY_DARKEN_MAX` and `VIGNETTE_FEATHER`/`CLARITY_RADIUS`/`GRAIN_SIGMA_SCALE`/`GRAIN_SHADOW_KNEE`/`GRAIN_HIGHLIGHT_KNEE`/`GRAIN_SEED`/`HALATION_SEED_FRACTION`/`HALATION_SPAN`/`HALATION_RADIUS`/`HALATION_STRENGTH`/`HALATION_RED_BIAS`/`DEHAZE_OMEGA_MAX`/`DEHAZE_HAZE_FLOOR_PERCENTILE`/`DEHAZE_MIN_TRANSMISSION`/`DEHAZE_SHADOW_RETENTION` — like every ALL_CAPS tunable — feed `DEVELOP_ALGO_VERSION` so a retune (or a reseed) self-invalidates the reserved develop cache.
**Cluster grading**: `compute_batch_corrections` runs the measure pass over a file set and returns one shared `(params, cluster index)` per file — parameters, never pixels — clustering by lighting (`cluster_files_by_lighting`, whose feature is the shared lighting vector plus `CLUSTER_CHROMA_WEIGHT`-weighted r−g / b−g cast terms — golden hour and blue hour at equal luminance must not share one averaged white balance — and which processes files sorted by feature, never input order, so the same set clusters identically however a card enumerates) and pinning **one shared correction per cluster** so a single scene doesn't drift shot-to-shot; its coverage is total by contract (an index the clustering fails to assign raises loudly, naming the file — never a silent drop), its `variance_threshold` default (the `None` sentinel) resolves `photos.cluster_variance_threshold` when set, else `SPAN_SIMILARITY_THRESHOLD` (still one knob — config-overridable, never a drifting copy; an explicit argument always wins), and the measure pass is a bounded decode (`_measure_rgb`: half-size RAW postprocess plus an INTER_AREA bound to `MEASURE_MAX_DIM` — averaging, not striding, so the bounded view meters like the calibrated full decode instead of re-injecting per-pixel noise) since its stats feed clustering only.
`develop_batch` composes it with per-file `develop` calls, decoding twice deliberately since holding a whole set of full-resolution RAW frames in memory is how a large batch OOMs (only the grade pass pays the full demosaic), and the `photos ingest` develop loop is the production consumer (see the cluster-graded bullet above); the standalone per-photo `develop` path stays per-photo by design.
`export_jpeg` builds the output from a bare array, so EXIF (GPS included) is **absent by construction**, not stripped after the fact.
It writes to a temp file and `os.replace`s into place (the resizer's atomic pattern — a failure mid-write leaves no partial gallery master), tags the output with the standard sRGB ICC profile (`srgb_icc_profile`), and encodes at full-chroma 4:4:4 (`GALLERY_JPEG_SUBSAMPLING`) and `photos.gallery_jpeg_quality` (default 92) rather than the social `jpeg_quality` — the gallery master is the archival source the social resizer later re-encodes, so PIL's implicit 4:2:0 and a social-quality master would each pay the generation loss twice.
That ICC tag is **deterministic**: littleCMS stamps the wall clock into the profile header's `dateTime` field (bytes 24:36), so a freshly built profile differed second to second and no two runs of the pipeline produced a byte-equal JPEG for identical pixels; `srgb_icc_profile` now zeroes that informational field (as reproducible-build toolchains do) and is `functools.cache`d, so `export_jpeg` output is byte-reproducible across runs *and* across processes — the property the reserved `DEVELOP_ALGO_VERSION` / cache-key contract assumes.
An explicit `quality=` argument still wins, and a minimal photo config lacking the gallery knob falls back to `jpeg_quality`.
`DEVELOP_ALGO_VERSION` and `develop_cache_key` are a **reserved pair** — implemented, unit-tested, and deliberately unwired (nothing reads or writes a developed-photo cache yet, so ingest re-develops every new file from scratch) — that together form the integrity contract any future cache store must key on: the version is hashed (never hand-bumped) from the *source* of the decode functions and the `_apply_*` grade appliers as well as the develop/spatial ones (decode output is the cached pixels' input, and `GRADE_ALGO_VERSION` covers only the correction producers), plus every serializable ALL_CAPS module constant — float, int, tuple, dict, and ndarray alike, collected by naming convention so an int-valued retune or a noise-kernel edit invalidates without hand-listing — while the key additionally carries the `DecodedPhoto.decoder` tag (blank hard-fails: a preview-fallback and a true-raw develop of one NEF must never share an entry) and the rawpy/LibRaw runtime version, so a decoder-library upgrade can never replay stale pixels.
The stage list inside `_HASHED_SOURCES` is hand-written, and three stages shipped OUTSIDE it — `_scanline`, `_glow` and `_light_leak` each wired a stage into the chain and did not add it to the tuple, so retuning that stage's body would not have moved `DEVELOP_ALGO_VERSION`.
`test_every_spatial_stage_the_chain_calls_is_hashed` closes that class of omission rather than the three instances: it derives the stage list from `_spatial_chain.__code__.co_names` and fails on anything the chain calls that the tuple does not carry, so the next stage is covered the moment it is wired.
**Exposure-bracket detection (`bracket.py`, the HDR path's first half — detection only; nothing merges frames yet)**: `detect_brackets` reads EXIF and returns groups of paths in capture order, pure and deterministic, mutating nothing.
A group needs the same capture date (a bracket never straddles the day a card registers under), neighbouring frames inside `MAX_GAP_S` = 45 s, ISO held constant, `exposure_s` stepping in ONE direction by at least `MIN_STEP_RATIO` = 1.15x, the whole run inside `MAX_SPAN_S` = 180 s, and at least `MIN_BRACKET_FRAMES` = 3 frames.
Every number is tuned against a real hand-stepped sequence (1/320 → 1/1600 at ISO 100 with 35/6/13/2/26-second gaps and one repeated exposure), *not* a textbook AEB burst: a sub-2-second burst window finds nothing in it, the one-direction test is what keeps auto-exposure drift across unrelated frames out of a group that loose a window, the span cap is what stops a golden-hour session chaining into one giant "bracket", and three frames is the floor because at 45 s any two consecutive shots that drifted a third of a stop would otherwise read as a bracket.
A frame repeating its neighbour's exposure is a duplicate — it neither extends the run nor breaks it, and stays ungrouped, like every other file the rule doesn't claim.
Feeding it that hand-stepped sequence yields exactly one bracket (frames 1–4 and 6; frame 5 repeats frame 4's exposure and is its duplicate).
One known non-check remains, for the merge stage to handle: metered-frame-first AEB order (0, −, +), which is sub-second and wants a tight-window pass beside this one rather than a looser shape test here.
**`--hdr` (`photos.develop_hdr`; default off, byte-identical) is the stage that consumes those groups.** `fuse_bracket` decodes the bracket, hands it to OpenCV's `MergeMertens` — *exposure fusion, not tone-mapped HDR*: no response curve, no radiance map, just a per-pixel weighted blend, so the result lands display-referred and every stage after it behaves exactly as on one decode — and returns ONE `DecodedPhoto` the normal chain develops.
It keeps the first frame's path so the scene profile still reads real EXIF, tags its decoder `<decoder>+mertens<N>`, and re-quantizes at the deepest source's own depth (16-bit in, 16-bit out: the tiff16 master is not quietly dropped to 8 bits just because Mertens itself consumes LDR frames).
Exports land under `<first-stem>_hdr_<variant>`, so a fused surface can never overwrite a single-frame develop of that same file, and a bracket's members are **consumed** — they develop once, fused, never also one by one.
`--hdr` with fewer photos than `MIN_BRACKET_FRAMES` is refused at the door, before any decode.
Two properties are bought by construction rather than gated afterwards: the merge is **pinned to one thread**, because OpenCV's parallel stripes move the float rounding (two default-threaded runs over a 20 MP bracket differ on 17% of pixels, max 4.2e-7; pinned they are bit-identical, at 7.7 s against 4.1 s), and a merge that leaves [0, 1] is **mapped in affinely rather than clamped** — the pyramid reconstruction overshoots to 1.48 on a window-over-interior scene, and clamping that flattens the very highlights the darkest frame was shot to hold, while an in-range merge takes the identity map and is byte-identical to a clamp.
**Frames are registered before they merge (default on; `--no-bracket-align` or `photos.develop_hdr_align = false` skips it).** Equal size does not mean aligned: a handheld bracket ghosts. `fuse_bracket` measures each frame's translation against the MIDDLE exposure with OpenCV's median-threshold bitmap method (`createAlignMTB`, on an 8-bit grey view; it compares above/below-median masks, which an exposure change leaves alone) and applies it to the frame at its original precision, before the 8-bit step-down, with `BORDER_REPLICATE` so the shape is unchanged and a 16-bit decode stays 16-bit. Shifts are whole pixels. A shift larger than `BRACKET_ALIGN_MAX_FRACTION` (3%) of the shorter side is more likely a moved scene or a mis-grouped frame than a hand, so that frame is left as decoded rather than smeared. Each frame's result (`dx`, `dy`, `applied`) rides on `DecodedPhoto.bracket_shifts` and is logged at INFO. A tripod bracket measures `(0, 0)` and is bit-identical to the unaligned merge. **Out of scope: rotation and deghosting** (a subject that moved between frames still ghosts).
**Wide input keeps its precision through the merge.** A bracket with any 16-bit decode is handed to Mertens as float32 on OpenCV's 0-255 scale (the warp above already ran at full precision) and the result is quantized straight to 16-bit, with no 8-bit hop; a smooth gradient therefore stays smooth instead of stepping in 8-bit treads. An all-8-bit bracket takes the unchanged 8-bit path and is byte-identical to before. The output is still display-referred exposure fusion, not scene-linear HDR.
Frames that decoded to different sizes are refused, not resampled: that is what a mixed preview-fallback/true-raw bracket off an HE card looks like, and blending them would mean resampling one rendering onto another.
The thresholds now DO reach the cache key — `_develop_algo_inputs` (in `develop.py`) hashes the grouping functions and sweeps `bracket`'s ALL_CAPS constants live into `DEVELOP_ALGO_VERSION` — because with fusion wired they decide which frames merge, and a retune left outside the key would replay a cached photo built from a different set of merged frames with no error anywhere.
The seconds-resolution `extract_exif_capture_timestamp` (`exif_gps.py`) that ordering needs is new alongside it, sharing the hour/date readers' one parse and their per-field never-raise contract.

- **HE→DNG true-raw hook** (`photos.he_dng_converter_exe`; unset probes `HE_DNG_CONVERTER_DEFAULT_PATHS` — the standard Adobe DNG Converter install locations — first existing file wins, so a default-path install needs no config; an explicit config value always wins over the probe, and a probe miss keeps the hook disabled; that resolution rule lives in exactly one function, `develop.resolve_he_dng_converter`, which the `photos astro` preflight below calls too, so an up-front gate can never disagree with the decode path it is gating): before the preview fallback, an unpackable `.nef` is shelled through Adobe DNG Converter — argv-list subprocess, **one invocation per file** (the CLI accepts no wildcards), flags `-c -p1 -cr11.2 -d <dir>`, bounded timeout, exe treated as an opaque path (may be a Windows `.exe` reached through a WSL drive mount; WSL2 runs it directly). A drive-mounted exe is a Windows binary, so its `-d`/source argv are translated to Windows form (`/mnt/<drive>/…` → `<DRIVE>:\…` — the WSL forms make it exit `Invalid destination directory`) while every filesystem check keeps the WSL-side paths; a source or cache path outside a drive mount is invisible to a Windows exe, so the hook warns naming the path and drops to the preview instead of invoking a conversion that must fail. The converter reports errors *silently* (exit 0, no output), so success is judged by the output `.dng` existing non-empty, never by the return code; any miss warns and drops to the embedded preview. The `.dng` lands in `photos.he_dng_cache_dir` (`""` = alongside the source NEF), and a cached one (non-empty, mtime ≥ source) is reused without reconverting. It carries the full Bayer mosaic + camera WB, so it decodes through the normal rawpy branch as `decoder="rawpy-dng"`, `is_raw=True` — a true raw develop, not a preview.

- **ICC-aware PIL decode**: the Pillow branch colour-manages an ICC-tagged source (a Display P3 iPhone HEIC, a wide-gamut TIFF) to real sRGB numbers through `ImageCms` *before* the array grab — otherwise the grade meters and exports wide-gamut numbers as if they were sRGB, desaturated and hue-shifted. A source with **no** profile is assumed sRGB and decodes unchanged. A profile `ImageCms` cannot convert **refuses the photo** (`UnusableColorProfileError`, a `PhotoDecodeError` and `ValueError`): decoding on would leave source-space numbers that `export_jpeg`/`export_tiff16` then tag sRGB, so no master or gallery file is written and `photos develop` prints `! <path>: unusable ICC colour profile (<reason>); no master written -- re-save the photo with a valid (or no) embedded profile and develop it again` and counts it in the failed total (the resizer differs: see Resize below). Every other `decode()` caller refuses it too: `photos ingest` fails the card with `lighting measure pass failed: <path>: unusable ICC colour profile …`, a reel render raises `ReelError`, a timelapse rejects the frame with its reason, and the route-story review pack shows the still as `<name> -- COULD NOT BE READ`. A 16-bit (`I;16*`) TIFF/PNG is lifted through numpy rather than `convert("RGB")` (which *clips* 16-bit values into uint8) and rides the grade chain at full depth like a true-raw decode, with `bit_depth=16`; ImageCms has no I;16 path, and a gray source carries no wide-gamut primaries to correct. `DecodedPhoto.width/height` on this branch are derived from the upright post-`exif_transpose` array, so a portrait frame reports its true dimensions instead of the stored, sideways ones (the raw-preview fallback still reports stored dimensions).

**Scene profiling — style variants, phase 1 (`scene.py`).** `compute_scene_profile` is a pure, deterministic function of one decoded frame (uint8 or uint16 — a 16-bit decode profiles identically to its 8-bit view) plus optional caller-supplied EXIF (`PhotoExif`: iso / exposure_s / capture_hour / capture_utc / solar_elevation_deg — it never reads files), producing a `SceneProfile` computed once per photo; the style library and selector below consume it to pick style variants for the `photos develop` CLI (phase 3 below). It meters through the develop stage's exact calibrated seam (`_frame_stats`: the uint8 view area-averaged to `ANALYSIS_MAX_DIM`, then `analyze_frame`) — never a second metering scale — and every class reuses the grade engine's merged semantics rather than re-inventing thresholds: `exposure_class` (low_key|normal|bright|overexposed) applies the low-key silhouette test verbatim, so a silhouette profiles low_key rather than underexposed-normal, with bright starting at the gamma-pulldown onset and overexposed additionally requiring clipped highlights; `warmth` (cool|neutral|warm) reads the r−g / b−g cast channels with the golden-hour sunset onset as the warm floor, mirrored for cool; `sat_profile` (muted|normal|rich) bands mean saturation with muted at the mist-class bound and rich at the boost ramp's zero point; `haze` (clear|hazy|foggy) gates on the merged mist/fog scene class (compressed spread + muted sat — saturated golden-hour light can never read as veil) and splits it by the dehaze black-point veil factor; `dynamic_range` (flat|normal|wide) bands the white−black spread with flat at the S-curve's full-strength spread; `is_near_monochrome` flags mean saturation at/under `NEAR_MONO_SAT_MAX`. Color readings ride the same metering view: `chroma_headroom` is 1 − the 95th-percentile per-pixel saturation (the grade engine's (max−min)/max basis) — how much saturation push the frame can absorb, low on an already-rich frame; `warm_fraction` is the chroma-weighted share of the warm reds-oranges-yellows hue band (305–60° on the 0–360 circle, wrapping through 0) — each pixel votes with its chroma as the weight so gray pixels never vote, and the fraction is of total chroma weight. `capture_hour` is the EXIF hour carried through untouched for the selector below. **Both call sites populate the EXIF** — `plan_variants` (`develop.py`) and ingest's `_develop_styled` each pass `extract_exif_capture_metadata(decoded.path)`, so real EXIF values reach the profile on real cards rather than being a dead parameter. That extractor reads the same Exif sub-IFD `extract_exif_capture_date` always used (one shared `_exif_sub_ifd` reader, so there is no second EXIF path to drift): ISO `0x8827`, exposure time `0x829A`, and the HOUR of `DateTimeOriginal` `0x9003` — the date reader's behaviour and signature unchanged. It keeps that reader's never-raise contract **per field**: an absent or malformed tag yields `None` for that field alone, never an exception, and a source with no EXIF at all — a PNG/TIFF or a synthesised array — yields an all-`None` record that profiles identically to passing no EXIF. RAW is **no longer** such a source: the reader's TIFF sub-IFD fallback (above) reads a `.NEF` directly, so a RAW card now profiles with its real capture hour (and solar elevation when a track is configured) rather than the all-`None` record it used to yield. When `photos.gpx_dir` supplies a phone track (the `sun_track` dependency's `TrackIndex` / `load_track_index`, parsed once per run into a lazily cached index keyed by the configured dir) and the file carries a UTC anchor (`capture_utc`, from `OffsetTimeOriginal`), the extractor also computes `solar_elevation_deg` at the interpolated position (`sun_track.solar_elevation_deg`) — the selector's golden predicate prefers that measured elevation over the fixed wall-clock window below; without a track or anchor the field stays `None` and selection is bit-identical to the wall-clock behaviour.

**Style library + variant selector — style variants, phase 2 (`styles.py`).** Eleven pure transforms `(CorrectionParams, SceneProfile) → CorrectionParams` — `natural` (identity over the measured photo-mode correction, always the anchor); every other style is a scene-adaptive look identity, never a fixed delta (fixed deltas rendered every variant as the same theme on real photos), and every delta constant is calibrated at look scale — a ×1/×2/×3 strength sweep on a real sample chose the ×2 column (×1 read nearly identical, ×3 too loud), baked into the constants with mono left untouched as already structurally distinct: `vivid` (punchy — `VIVID_CRUSH` black crush, stronger S-curve, saturation push scaled by `chroma_headroom`: full strength on a muted frame, only `VIVID_HEADROOM_GAIN_FLOOR` of it on a rich one, with the `VIVID_SATURATION_FLOOR` additive floor headroom-scaled so a near-cap base still moves, and what the frame can't absorb in chroma it takes as extra contrast ∝ 1−headroom; below `VIVID_RICH_KNEE` vivid's whole intensity — the chroma push, the low-headroom contrast compensation, AND the black crush — rolls off linearly toward zero via one shared `rich_att` factor; an already-saturated close-up (e.g. a red-food frame) would otherwise cartoon on chroma and crush to black on contrast+crush at extreme strength, and the knee sits below every calibration reference so the sweep and bake stay untouched), `moody` (matte/teal — `MOODY_FADE` output-floor fade, cool/teal shadow-mid shift with the `_high` fields counter-shifted toward neutral so the cool sits in the shadows, not globally, desaturated, stronger mids; muted/low-chroma scenes lean tone with deeper fade and contrast but less extra desat, rich frames lean desat; on a `warm` scene — where moody appears only as filler, never its favored scene — the teal WB moves are restrained by `MOODY_WARM_SHIFT_SCALE` so the cool cross-cast reads as a clean desaturated grade rather than mud, the fade/desat/contrast identity untouched, and a neutral landscape stays bit-identical), `golden` (warm-highlight — the warm push concentrates in the `_high` fields over a gentler mid shift, and on a scene that already measures warm (warmth `warm` or high `warm_fraction`) the mid moves scale down by `GOLDEN_WARM_SCENE_SCALE` so an already-golden shot never cooks while the highlight glow keeps the larger `GOLDEN_WARM_HIGH_SCALE` — the warm-highlight glow is the golden identity, and throttling it to the mid scale rendered golden under the distinctness floor from natural, so it was dropped and a muddy filler backfilled exactly where golden fits best; extra highlight pull softens the top end), `mono` (saturation exactly 0.0 with dynamic-range-tuned contrast AND crush: flat DR earns the biggest S-curve and deepest crush, wide the mildest) and `soft` (pastel — `SOFT_FADE` matte fade, gamma up, the S-curve flattened away, desaturated), plus the **white-balance bracket** `daylight`/`cloudy`/`shade` — three cheap declarative transforms that move ONLY the four WB fields over the measured base, giving the operator an instant colour-temperature bracket on the contact sheet: mids shift by `WB_DAYLIGHT_SHIFT` / `WB_CLOUDY_SHIFT` / `WB_SHADE_SHIFT` with blue counter-moving at `WB_BLUE_RATIO` (slightly under a mirror, so the move reads as temperature and not a magenta/green tint) and the `_high` pair following at `WB_HIGH_SCALE`, so the whole frame's temperature moves and no other field drifts — a real bracket AROUND the base rather than a one-sided push (daylight steps cool to the reference-5500K rendering, cloudy warms about a camera preset step, shade twice that), every step well inside `STYLE_WB_CAP` so the rails never clip the ladder's ordering. The trio is scene-independent by construction and deliberately **absent from `_FAVORED`** — the table `select_styles` actually ranks over — so **automatic variant selection is bit-identical to before the trio existed** (a pinned test asserts the full ranking on representative profiles); it is operator-opt-in only, via `--styles daylight,cloudy,shade`, which the CLI accepts and advertises with no code change because it validates against `STYLES`. A second opt-in group, the **matte fade presets** `matte_shoulder` / `matte_knee`, is the one place a style's tone move is a SHAPED curve rather than scalar fields: where `black_point` lifts the output floor of the whole frame LINEARLY, each preset sets `curve_r`/`curve_g`/`curve_b` to ONE identical knot list (`MATTE_SHOULDER_CURVE` / `MATTE_KNEE_CURVE`), which the existing `_apply_channel_curves` runs through the same Fritsch-Carlson monotone-cubic interpolant the master curve uses — a master-shaped fade for **no new applier and no new engine**, and one curve on all three channels means **no colour cast, by construction**. `matte_shoulder` is a rolled TOE over the **shadows and low mids** (the floor lifts 0.11 — ≈28 8-bit levels — at black, still ≈17 levels at x=0.25, decaying to ~0 by x=0.5, so the shadows ride a soft ramp instead of the whole frame washing out; white pins at 1.0, highlights untouched); `matte_knee` is the opposite tonal idea, a compressed SHOULDER over the **upper mids** (identity through x=0.15 so black stays true, then slope falling 1.0 → 0.61 — ≈9 levels down at x=0.45, ≈22 at x=0.6 — rolling the top of the histogram off into a printed white rather than paper white, with a small `MATTE_KNEE_GAMMA_LIFT` holding the mids that rolled top would otherwise darken). **Both knot sets are shaped for the tone each preset actually meets**, because `_apply_channel_curves` runs EARLY in `_grade` — right after the master `_apply_curves`, *before* colorbalance/saturation/gamma — where a real graded frame occupies only about [0, 0.6] (p99 ~0.51–0.58 on the reference NEFs): a first cut whose knee rolled off past x=0.6 was an **identity on a real photo**, rendering ~1.3 mean levels from the shoulder (one preset shipped twice) with the whole suite green, since a style absent from `_FAVORED` is reachable only by explicit request and an explicit style renders verbatim, bypassing the `MIN_RENDERED_DISTINCTNESS` gate by design — so a dedicated test pins the pair's mutual `_rendered_distance` above that same floor. The knots are monotone with x strictly ascending — a non-monotone set inverts the interpolant and destroys tone — and each preset's scalar desat still goes through `_styled`, so the style-layer rails bind exactly as before; the curve carries the identity, not the scalars (shoulder measured 7.1/11.5 rendered levels from `natural` on curve alone against 0.3/1.6 on its scalars alone, and the knee's gamma lift *reduces* its distance from `natural`, being a compensation for the rolloff rather than a second look move). Like the WB trio the pair is deliberately **absent from `_FAVORED`**, so **automatic variant selection is bit-identical to before the presets existed** (a pinned test asserts the full ranking), and it is operator-opt-in via `--styles matte_shoulder,matte_knee`, accepted and advertised with no CLI change because the handler validates against `STYLES`. One real limitation, deliberately not papered over: `_LOOK_FIELDS` — what the `--style-strength` lever scales — holds SCALARS only, so the lever scales a preset's desat/gamma move and carries the baked curve shape through **unscaled** (a knot list has no meaningful linear amplification, and widening `_LOOK_FIELDS` would change every existing style's amplified behaviour; the carry-through is explicit, because rebuilding from `base` alone would silently DROP the shape at any strength but ×1) — and an explicit operator `--curve-r/g/b` replaces a preset's curve outright, operator authority winning as everywhere else. All eleven are registered in `STYLES` (declaration order is the selector's tie-break; the matte pair and the WB trio append after the six ranked styles) and run via `apply_style` (unknown name → `ValueError`). Every output field is clamped, but saturation/WB/contrast rail to STYLE-LAYER caps (`STYLE_SATURATION_CAP` 1.55, `STYLE_WB_CAP` ±0.10, `STYLE_CONTRAST_CAP` 0.20) that deliberately exceed `compute_correction`'s corrective clamps — the renderer is unbounded (`_apply_saturation` is pure luma-preserving chroma scaling and `_grade` accepts any curve), so the corrective 1.25 / ±0.05 / 0.10 values are measurement-layer taste, not math, and a muted scene's base correction already sits near them, which used to collapse every variant into the base grade — and the signed black-point move rails to `STYLE_BLACK_POINT_CRUSH_MAX` −10 … `STYLE_BLACK_POINT_FADE_MAX` +20 — the renderer's full `BLACK_POINT_MIN`/`BLACK_POINT_MAX` authority, all of which the sweep-chosen muted moody fade uses. Shadow/highlight keep the 0–20 band and gamma its 0.9–`GAMMA_MAX` rail; style desaturation floors at the style-layer `STYLE_DESAT_FLOOR` rather than the corrective pulldown minimum, which sits above every look-scale desat target and would flatten moody's muted/rich lean (mono's 0.0 is the one deliberate value under the floor); there is no new filter machinery, every variant renders through the same `_grade` chain. **Strength lever:** `apply_style(name, base, scene, strength=…)` amplifies the whole look — because each style is a delta over the measured base, one factor scales all its fields at once (`base + strength·(styled − base)` over `_LOOK_FIELDS`; denoise/sharpen are metering budgets, not look moves, and ride through). `DEFAULT_STRENGTH` 1.0 returns the transform's own bake untouched (bit-identical, not the float-rebuilt delta); >1 pushes toward renderer authority, <1 softens. The style-layer rails scale WITH the factor (railing an amplified look back to the ×1 caps is exactly what collapsed the variants pre-bake), bounded by hard RENDERER limits that bind at every strength: `SATURATION_HARD_CAP` 2.0, `WB_HARD_CAP` ±0.20, black-point/gamma keep their ×1 rails (already pinned at the renderer clamp), and contrast rails to `_contrast_ceiling` — the largest S-curve offset that keeps `_apply_curves`' four control points monotone-increasing (past it the interpolant inverts and tone is destroyed, not shaped). Amplified moody still floors at `STYLE_DESAT_FLOOR` so it can never desaturate into a second mono; only mono's exact 0.0 sits lower. A non-positive strength raises `ValueError`. `select_styles(scene, count=3)` is deterministic: `natural` first, the rest ranked by per-style suitability scores of the profile (vivid suppressed to the bottom on foggy/near-monochrome scenes, favored only bright-and-clear with `chroma_headroom` ≥ `VIVID_HEADROOM_MIN` to absorb the push, leaning rich-sat, and on a muted scene that fails the favored test penalized by `VIVID_MUTED_PENALTY` — below every unpenalized style, strictly above the suppression floor; moody favored foggy/hazy/low-key; golden favored warm **or** captured in a golden hour; mono favored near-monochrome/foggy and leaning muted+flat; soft favored bright with muted/normal sat and leaning muted or warm — structural difference is worth more when chroma can't differentiate, and the warm lean makes soft the airy alternative that backfills when the warm-favored golden is distinctness-dropped for sitting too close to natural, so a warm close-up gets natural+soft+vivid rather than a muddy moody; a leaning applies only to a not-already-favored style so it never reorders a favored trio, and on a warm rich scene vivid ties soft and wins the declaration tie-break, keeping the golden-hour trio), ties broken by `STYLES` declaration order — same profile, same list, always (misty ridgeline → natural+moody+mono, golden-hour sunset → natural+golden+vivid, bright meadow → natural+vivid+soft, muted overcast → natural+soft+moody, never vivid). **Golden hour by capture time** (`_is_golden_hour` over the profile's `capture_hour`): a frame captured inside `GOLDEN_HOUR_MORNING_START`–`GOLDEN_HOUR_MORNING_END` (05:00–08:59) or `GOLDEN_HOUR_EVENING_START`–`GOLDEN_HOUR_EVENING_END` (17:00–20:59) favors `golden` even when the pixels measure neutral — that is the half of golden the frame can't show, low sun lighting a shaded or backlit subject. Two honest limitations, deliberately not papered over: EXIF `DateTimeOriginal` is camera-**local wall time carrying no timezone**, and the window is a fixed approximation of the low-sun hours that does not move with latitude, season or DST — not a solar calculation, so a high-summer or high-latitude frame can fall on the wrong side of it. `capture_hour` is `None` on every source without capture EXIF and `_is_golden_hour(None)` is False, so **automatic selection is bit-identical to before this rule existed** on those paths (a pinned test asserts the full ranking on six representative profiles). Tests: `tests/test_photo_styles.py`, `tests/test_photo_wb_styles.py`, `tests/test_photo_exif_looks.py`.

**Subject recognition — what the frame is OF (`subject.py`).** The scene profile above measures a frame's LIGHT; nothing said what it was a photograph of, so a 20 s ISO-3200 frame of the Milky Way and a 20 s daylight frame of a waterfall were the same object to this pipeline. `recognise_subject` answers that from EXIF, source grouping and the operator — **no model, no network call at import or at inference**, every rule arithmetic over metadata that is already free and reliable, plus the measurements already computed. The taxonomy is deliberately small and grounded in what this pipeline actually shoots: `astro`, `wildlife`, `portrait`, `long_exposure`, `exposure_bracket`, `landscape`, and `unknown`. **`unknown` is a real answer, never a coerced best guess** — a `SubjectReading` carries `category`, `confidence` (0-1), `source` and the `evidence` strings it used, and the dataclass REFUSES an `UNKNOWN` at any confidence but exactly 0.0 and a named category at 0.0, the same discipline `tracking/schema.py` documents for `Optional[...] = None` (not reported ≠ a measured zero). Evidence runs in descending strength and the first rule that MATCHES answers; nothing matching returns `UNKNOWN_SUBJECT`, never a fallback category, so a daylight frame with no lens metadata is not rounded up to `landscape` just because landscape is the common case. **Source grouping first**: a frame `bracket.py`'s existing detector claims is `exposure_bracket` at `CONFIDENCE_GROUPED`. **Then the EXIF triples**: astro needs a shutter ≥ `ASTRO_EXPOSURE_S_MIN`, ISO ≥ `ASTRO_ISO_MIN` **and** a dark sky, where a measured `solar_elevation_deg` (the GPX track's, ≤ `NIGHT_SOLAR_ELEVATION_MAX`) is authoritative in BOTH directions — with the sun 40° up a long high-ISO exposure is NOT astro however it meters — and the camera-local wall clock plus a low-key frame are the no-track fallback, carrying the lower `CONFIDENCE_MODERATE` for exactly that reason (the same honest limitation `_is_golden_hour` documents: the window does not move with latitude, season or DST). A run of ≥ `ASTRO_SEQUENCE_FRAMES_MIN` astro-like frames inside one session (consecutive captures no more than `SESSION_GAP_S` apart — wider than the bracket rule's gap, since a tracked sky idles between subs) is a **sequence**, worth `CONFIDENCE_SEQUENCE_BONUS` over a lone frame: the Milky Way case one frame cannot show. **Then single-fact optics** off `CaptureOptics` (`extract_exif_focal_length` / `extract_exif_aperture`, both outside `PhotoExif` because nothing in scene profiling meters a lens): a long lens reads `wildlife`, stronger at an action shutter; the classic portrait band at a subject-separating aperture reads `portrait`; a tripod-length shutter at low ISO in bright light reads `long_exposure` — **named for what the EXIF proves, not for what it probably is**, since the pixels were never asked and "waterfall" would be a fabrication with a nicer name; and the wide stopped-down daylight frame reads `landscape` at `CONFIDENCE_WEAK`, the weakest reading on the board. **Operator corrections beat every inference**: `write_subject_correction` persists a `.subject.json` beside the photo (the `.grade.json` pattern), `read_subject_correction` reads it back with the readers' never-raise contract — absent, unreadable, malformed and unrecognised all read `None`, which means "no correction recorded" and is DISTINCT from a recorded `unknown` (the operator looked and could not tell) — and a correction is the only reading that reaches `CONFIDENCE_OPERATOR` 1.0, inference capping at `CONFIDENCE_INFERENCE_MAX`. `recognise_photos` reads a whole card at once, joining bracket membership, session sequences and sidecars, decoding no pixels. **Recognition routes style selection, above a confidence floor.** `styles.select_styles` takes an optional `subject: SubjectReading` fourth input; when the reading's category is in `styles.SUBJECT_STYLE_ROUTING` (currently `astro` → `moody`, evidenced by moody's own `exposure_class == "low_key"` favor; `exposure_bracket` → `matte_shoulder`, evidenced by the bracket grouping itself proving a dynamic range one exposure couldn't hold) **and** its confidence clears `styles.SUBJECT_ROUTING_CONFIDENCE_MIN` (`CONFIDENCE_MODERATE`), the routed style moves to right after `natural` — reordering what follows `natural`, never displacing it. Every other case (no reading, `UNKNOWN`, an unrouted category such as `wildlife`/`portrait`/`long_exposure` whose EXIF proves optics or action but nothing about colour, or a reading below the floor such as `landscape`'s always-weakest one) stays bit-identical to selection with no subject. The CLI `photos develop` auto-select path (no explicit `--styles`) computes the reading per photo and passes it through `plan_variants`/`develop_variants` into `_distinct_styled`. Beside it, `styles.NATURAL_STYLES` / `is_artistic_style` finally name the split the ladder always had: `natural` (always the anchor, and the default for real travel/nature work) and the `daylight`/`cloudy`/`shade` temperature bracket are colour CORRECTION; every other registered style is an artistic RESTYLING, shipped as an additional variant to its own file so the naturally-corrected original is always preserved, and an unregistered name raises rather than being guessed at. Every developed panel's `.grade.json` records `style_kind` (`"artistic"`/`"natural"`, via `develop._style_kind`) so an artistic export is identifiable from the artifact itself, not just at the call site that rendered it — a LUT or named-look panel is never natural correction by definition and reads `"artistic"` without consulting `is_artistic_style`, which only classifies base style names. Tests: `tests/test_photo_subject.py`, `tests/test_photo_styles.py`, `tests/test_photo_grade_sidecar.py`.

**Standalone develop CLI — style variants, phase 3 (`develop_variants` + `gomoveshift photos develop`).** Both functions take the operator look/spatial knobs as ONE frozen `DevelopOptions` record (`options`), grouped spatial / colour-chain / LUT, every field defaulting to its OFF-neutral value — so `DevelopOptions()` is exactly the un-flagged grade, and the next creative knob is a field beside its relatives instead of a 22nd positional on two signatures.
`luts` stays a parameter of its own: it is resolved data (`[(name, Cube), ...]`), not a knob.
The handler packs the record after every flag is resolved and range-gated; no flag name or behaviour below changes.
`plan_variants` is the metering half — decode ONCE (the 16-bit true-raw path, with HE NEFs riding the DNG hook or preview fallback exactly as in ingest), `compute_scene_profile`, the photo-mode base correction through the calibrated `_frame_stats` seam, then per-style params via `apply_style`.
An explicit `--styles` list is operator authority — rendered verbatim, never filtered, never substituted; auto-select (`styles=None`) walks `select_styles`' FULL ranking under a **two-tier distinctness guard**: `natural` always kept first; a ranked candidate whose railed params land within `VARIANT_DISTINCTNESS_EPSILON` of an already-kept variant (`_params_distance` — weighted L1 over the styleable fields, each |Δ| normalized by its rail authority) is dropped as a fast pre-filter WITHOUT rendering (params-identical implies pixel-identical); a params-distant candidate is kept only if `_rendered_distance` — the same small metering view (`_bounded_resize(_analysis_rgb(rgb), DISTINCT_RENDER_DIM)`) graded through the pure `_grade` chain with each params, mean absolute difference in 8-bit levels PLUS `CAST_DISTINCTNESS_WEIGHT` times the norm of the mean per-channel shift about its own mean (so two grades differing only in colour cast are not read as identical), kept renders cached once per walk — reaches `MIN_RENDERED_DISTINCTNESS` against EVERY kept variant. That gate guards AUTO-SELECTED styles only; the look packs meter themselves in their own tests, against plain mean-abs and the same constant.
Params distance alone was a broken proxy: a pastel look's params sit far from natural yet render near-identical on a frame that is already flat and hazy.
Both drop paths warn loudly naming the drop, the variant it collapsed onto and the next-ranked substitute that backfills (rendered drops also name the measured distance); if backfill exhausts the ranking short of 3, it falls back to the original top-3 with a warning — never fewer variants, and always deterministic.
This is what `--dry-run` prints (SceneProfile fields, chosen styles, per-style params table; decodes to meter, writes nothing — the photo analog of `--label-dry-run`).
`develop_variants` renders it: denoise ONCE on the source under the base correction's budget, then each variant grades the shared full-depth array through the existing `_grade` chain (which copies, never mutates) and sharpens its own graded output, yielded one at a time as `(name, DevelopedPhoto)` so the CLI can export incrementally.
`gomoveshift photos develop <path...> --out DIR [--styles s1,s2] [--style-strength K] [--lut NAME|FILE.cube] [--lut-strength K] [--lut-over STYLE] [--lut-auto N] [--hue-shift R [O] Y G C B M] [--hue-sat …] [--hue-lum …] [--split-tone-shadow R G B] [--split-tone-highlight R G B] [--curve-r X Y …] [--curve-g …] [--curve-b …] [--vibrance K] [--border STYLE] [--grade-sidecar] [--dry-run]` validates styles (against `STYLES`, from `--styles` or `photos.develop_styles`) and extensions upfront, exports `<stem>_<style>.jpg` via the atomic gallery-quality `export_jpeg` into `--out` (default `photos.developed_output_dir`; unset + no flag = hard fail), and continues on per-file errors with per-file reasons and a non-zero exit if any failed.
`--style-strength` is the per-run style lever (default `photos.style_strength`, 1.0 = the calibrated bake; ≈2 = extreme) — threaded through `plan_variants`/`develop_variants` into `apply_style` so it scales both explicit and auto-selected variants; a value that is not a finite number > 0 is rejected before any decode, on the resolved flag-or-config value, by `_style_strength_ok` — shared with `photos ingest`.
The lever is the one knob with no upper bound, so it cannot use the `lo <= v <= hi` form every sibling gate uses, and that form is exactly what refuses NaN for free (NaN loses every comparison).
Spelled `strength <= 0` the gate waved NaN through to `CorrectionParams`, and the render then silently produced a different grade than the flag or `photos.style_strength` asked for, with no error on any path — a `photos.style_strength: .nan` in `config.yaml` (YAML spells NaN natively) reached the same place.
Infinity is refused with it: the style rails saturate by roughly x2 — past that, x3, x10 and x1e9 all render the SAME pixels — so an unbounded lever buys nothing but a value that cannot be printed, compared, or recorded in a `.grade.json` sidecar.
`develop.STYLE_STRENGTH_DEFAULT` mirrors `styles.DEFAULT_STRENGTH` (the styles→scene→develop import cycle forbids importing it; a test pins the two equal).
`--contact-sheet` additionally writes `<stem>_contact.jpg` per photo for style tuning: a labeled grid composed in-process by `compose_contact_sheet` from the frames `develop_variants` yields (never re-read from the exported JPEGs) — each panel area-downscaled under `CONTACT_PANEL_WIDTH`, labeled with its style name in PIL's built-in font on a dark strip, shipped through the same atomic sRGB-tagged `export_jpeg`.
The sheet does **not** land in `--out`, and cannot be made to: `--out` takes the masters, `photos.contact_sheet_root` takes the sheet, always, with the run's `--out` basename as the subfolder under it (so two packs developed side by side keep their sheets apart without needing a clock).
A sheet is a REVIEW artifact, and written beside the masters it would follow the develop into whatever scratch dir or temporary path the run happened to use — the operator would never see the one thing they asked to look at.
The root defaults to `<gms_data_home()>/contact-sheets` when `photos.contact_sheet_root` is unset, and is created on demand. An explicitly configured root whose parent directory does not exist (for example an unmounted review volume) is refused at the CLI **door**, before any decode: refusing there costs nothing, while failing at write time costs the whole render and still has nowhere to put the sheet.
`--contact-cols N` wraps the panels into rows of N (each row sized to its tallest panel, its own label strip above), so a large style set stays openable instead of a one-row strip that widens without bound; absent the flag every panel stays in one unbroken row, bit-identical to the pre-wrap layout.
`--dry-run` never writes a sheet, and a photo with a failed variant gets none — the sheet lands only after every variant exported.
`--lut NAME|FILE.cube` (repeatable) renders each supplied external `.cube` 3D LUT (the `pycube-lut` package's `load_cube`/`apply_cube`) as an extra film-emulation variant — a real Kodachrome/Portra look the `CorrectionParams` model, having no per-hue control, can only approximate — applied over the **natural (base) grade** — or, with `--lut-over` below, over a styled one — (`apply_cube(_grade(denoised, base), cube, lut_strength)`, that underlay graded once and shared) then sharpened, kept in `VariantPlan.lut_looks` (with `VariantPlan.lut_strength`) separate from `styled` because a LUT is a fixed table the **style-strength** lever must NOT scale.
`--lut-strength K` (default `photos.lut_strength`, 1.0 = full-strength LUT, 0.0 = no LUT, clamped to 0..1) is the LUT's OWN opacity lever — one global value blended over every `--lut` look inside `apply_cube` (`out*K + input*(1-K)` in normalized float, so 1.0 is byte-identical to the pre-lever full-strength output and 0.0 is a passthrough); ≤0/>1 rejected before any decode.
It is threaded through `plan_variants`/`develop_variants`, distinct from `--style-strength`, which only scales `CorrectionParams` styles.
`--lut-over STYLE` (default `photos.lut_over`, `""` = OFF) is what makes a film look **composable**: every `--lut` look is applied over THAT style's correction instead of the neutral base — `apply_cube(_grade(denoised, apply_style(lut_over, base, scene, strength)), cube, lut_strength)` — so "Portra over moody's matte" is one flag instead of unbuildable.
The params are computed exactly as a styled variant's, through the same `apply_style` at the same resolved `--style-strength`, so the **style lever DOES scale the grade under the LUT** (the LUT table itself still scales with nothing but `--lut-strength`), and they ride `VariantPlan.lut_params`.
Unset is **byte-identical by construction**, not by luck: `develop_variants` grades the underlay ONCE from `lut_params or base`, so the default path renders the same single base grade it always did — no second grade, no rounding drift.
Scope is one style and nothing else — the operator per-hue / split-tone / per-channel-curve / vibrance / mono fields still never ride the LUT surface (they are `replace`d onto the styled variants, never onto `base` or `lut_params`), so a composed look stays a faithful film emulation over a real look identity rather than an operator-tinted one.
That isolation is **pinned rather than remembered**: eleven colour knobs were added one at a time, each relying on its author recalling the rule, and a leak would be invisible (a slightly operator-tinted emulation renders fine).
`tests/test_photo_lut_over.py` sets each knob in turn and asserts the LUT look is byte-identical on RENDERED pixels — not just in `lut_params`, so a leak in `develop_variants`' render branch is caught too — while asserting the styled variant DID move, so the check cannot pass vacuously.
A sync test over `DevelopOptions.__dataclass_fields__` fails when a new field is left unclassified, forcing its author to decide and prove whether it rides the LUT surface.
A composed look is a DIFFERENT surface from the base-graded one, so it is renamed `<lut>_over_<style>` (`IMG_0123_portra_over_moody.jpg`): two develops of one photo cannot overwrite each other on disk or read as the same panel on a contact sheet, and `--dry-run` names the composed look and says the style strength reaches it (the name and that line are unchanged when the flag is unset).
The style name is validated against `STYLES` at the CLI door before any decode — the same gate `--styles` uses, listing the available names — with a `PhotosConfig` validator on the config default beneath it (which checks the name against `config.PHOTO_LUT_OVER_STYLES`, a literal mirror of `styles.STYLES`, so the validator itself imports nothing from the pipeline package) and `apply_style`'s own `ValueError` as the library backstop.
A spec matching a `photos.luts` config key is that named look (variant named for the key), else a filesystem path (variant named for the file stem); the CLI resolves and validates every `.cube` upfront (a malformed one fails the whole invocation, not once per photo) and LUT looks **ADD** to the style variants — combine with `--styles natural` for a LUT-only develop.
The operator supplies the `.cube` files; none are bundled.
`--lut-auto N` (default `photos.lut_auto`, `0` = OFF) makes the choice **automatic and scene-adaptive** — the LUT-side answer to `select_styles`, because hand-picking from an ~80-cube library per photo does not scale.
A `.cube` is an opaque table, so each candidate is **characterised** first (`characterize_cube`) — on **the frame's own graded pixels**, never a synthetic 0–1 lattice.
That distinction is the whole feature: a graded photo here occupies roughly luma 0.14–0.66 and never blows out (measured `p99` 0.52–0.67 across the reference NEFs), so a cube's shadow rolloff — built to sit near 0 for full-range footage — lands in the MIDDLE of a real histogram where a 0–1 measurement cannot see it.
Characterised over 0–1 a film-emulation LUT read as a mild `contrast_gain` 1.08 and won on a sample landscape frame; it crushed **51.6% of that frame to near-black** and dropped the median from 74 to 13.
`plan_variants` therefore grades a `LUT_PROBE_DIM`-bounded metering view once (`_grade(_bounded_resize(_analysis_rgb(rgb), …), base)`) and passes it in; each candidate is pushed through `apply_cube` once and reduced to four statistics — `warm_shift` (mean R−B added), `contrast_gain` (output luma spread ÷ input's), `saturation_gain` (mean (max−min)/max ÷ input's) and `crushed` (share of the frame the cube pushes under `NEAR_BLACK` or over `NEAR_WHITE` that was not already there), an identity cube reading 0 / 1 / 1 / 0 exactly.
Deliberately **not** cached: the traits are a function of the frame too, and one selection pass measures each candidate exactly once anyway.
`score_lut` scores those traits against the `SceneProfile`, and **every axis scores as distance from the target the scene wants**, never "more of what it wants is better": a signed demand let the most extreme cube on the demanded axis win outright — on the same 35-cube library a rich scene picked the one B&W cube, because zero chroma maximizes "a rich frame wants less saturation".
The targets, each with its rule in one comment beside it: warmth 0 on every scene except a measured-cool one (which wants `COOL_SCENE_WARM_TARGET` of warmth back), so an already-warm frame cannot cook under a warm LUT — the same restraint `_golden` applies, gated on the same `GOLDEN_WARM_FRACTION_HIGH` already-warm test, with over-warm penalized harder (`WARM_COOK_WEIGHT`) than over-cool (`WARM_CHILL_WEIGHT`); contrast `1 + CONTRAST_TARGET_SPAN × demand`, demanded by a flat or veiled frame and negatively by a wide-range or low-key one that would lose its shadows; saturation `1 + SATURATION_TARGET_SPAN × demand`, driven by `chroma_headroom` (which IS how much push the frame can absorb) plus the muted/rich lean, so a muted frame absorbs a saturating LUT and a rich one takes a gentle desat rather than a mono conversion.
On top of taste sits the **crush guard**: past `LUT_MAX_CRUSH` (10% of the frame killed) a candidate takes `CRUSH_SUPPRESSED` and sinks below every intact one however well it reads, and the linear `CRUSH_WEIGHT` term still ranks the least-bad first when every candidate crushes — so "picks a cube that destroys the photo" is structurally impossible rather than a matter of taste.
Selection is **deterministic by construction**: `score_lut` is a pure function of (cube, scene, frame) and ties break by NAME, so one profile, frame and candidate set always yield ONE ordered list — what the reserved develop cache requires.
Scoring needs both the `SceneProfile` and the graded frame, so the pick happens in `plan_variants`, not the handler: the handler resolves the whole CANDIDATE SET and hands it over as `luts`; `plan_variants` scores and truncates.
Composition rule with explicit `--lut` specs: the candidates ARE those specs when the operator named any ("pick the best of these"), and every `photos.luts` entry otherwise ("pick the best of the library"); an N larger than that count is rejected at the CLI door naming both numbers, and a negative N at the door and in a `PhotosConfig` validator.
Each pick is renamed `<lut>_auto` (`IMG_0123_portra_auto.jpg`; `<lut>_auto_over_<style>` when composed with `--lut-over`) so an automatic look is identifiable on disk, and `--dry-run` prints every winning score beside the scene line it was scored against, on `VariantPlan.lut_auto_picks` — an automatic choice the operator cannot audit is worse than a manual one.
`0` is the manual path **byte-identical by construction**, not by luck: `plan_variants` skips the block entirely, so `luts` renders verbatim under its own unsuffixed names.
**`load_cube` reads three intake formats**, so the large free film-sim ecosystem is reachable without hand-conversion, and normalizes all three into one 3D `Cube` — `apply_cube` sees exactly one input shape and is untouched.
(1) The Adobe 3D `.cube` (`LUT_3D_SIZE`) is the reference path, **unchanged**: same parse, same R-fastest fold into an `[r, g, b]` table, pinned by a test asserting the identical `size`/table/domain.
(2) A **HALD CLUT PNG** is dispatched on the `.png` suffix (case-insensitive) *before* the text read — a PNG through `read_text()` raises `UnicodeDecodeError`, which is not a `CubeError` — and read through Pillow to an `HxWx3` array.
Its geometry is *derived, never trusted*: a level-`n` HALD is a square `n**3` px image holding a cube of size `S = n**2`, so `S` is the integer cube root of the pixel count, and a non-square image, a pixel count that is not a perfect cube, or `S < 2` each fail closed rather than read a truncated table.
Pixel order is the same R-fastest row-major the `.cube` data rows use, so both formats share one `_table_from_rows` fold.
(3) A **1D tone-curve `.cube`** (`LUT_1D_SIZE` — three independent per-channel curves) is no longer rejected: it becomes the equivalent **separable** 3D cube, `table[i,j,k] = (curve_r[i], curve_g[j], curve_b[k])`.
It is **resampled first** (`np.interp` onto a fixed `LUT_1D_TO_3D_SIZE` = 33 grid) rather than expanded at its own length, because the 3D table costs the *cube* of the 1D length — a common 1024-entry curve would mean a ~10⁹-entry table — and a tone curve is smooth by nature, so a 33-point resample is visually lossless at ~36k entries.
`DOMAIN_MIN`/`DOMAIN_MAX` and the fail-closed row-count check apply exactly as on the 3D path.
Every failure mode across all three stays a `CubeError` naming the path.
`--hue-shift` / `--hue-sat` / `--hue-lum` (defaults `photos.hue_shift`/`hue_sat`/`hue_lum`) expose the in-grade per-hue HSL engine: each is six values over the fixed anchor bands red/yellow/green/cyan/blue/magenta (0/60/120/180/240/300°), or seven with orange (30°) second — shift in degrees, sat/lum multipliers (1.0 = neutral) — and is `dataclasses.replace`d onto **every styled variant's params** (`natural` included) after `apply_style`, so `_grade`'s in-chain `_apply_hsl` renders it.
An empty/unset band is OFF and **bit-identical by construction** (the neutral params path is untouched).
The handler is the upstream gate: `_resolve_hue_band` enforces the empty-or-six-or-seven length (argparse takes `nargs='+'`, which cannot say "6 or 7"), a `PhotosConfig` validator repeats it, and a range guard (shift ∈ [-180, 180], sat/lum ∈ [0, 5]) rejects alongside it — all before any decode, threaded through `plan_variants`/`develop_variants`.
The move is deliberately **NOT** applied to `base`, so the `--lut` looks stay faithful film emulations rather than operator-hue-tinted.
`--split-tone-shadow` / `--split-tone-highlight` (defaults `photos.splittone_shadow`/`splittone_highlight`) expose the in-grade split-tone engine the same way: each a signed length-3 (r,g,b) tint (argparse `nargs=3` plus an empty-or-three `PhotosConfig` validator and a range guard ∈ [-0.5, 0.5], both rejecting before any decode), `dataclasses.replace`d onto every styled variant's params but never `base`, empty/unset OFF and bit-identical, threaded through `plan_variants`/`develop_variants`.
`--curve-r` / `--curve-g` / `--curve-b` (defaults `photos.curve_r`/`curve_g`/`curve_b`) expose the in-grade cross-process per-channel tone curves the same way: each is a flat list of alternating x y control points (`nargs='+'`, ≥ 2 points, x ascending in [0, 1]) `dataclasses.replace`d onto every styled variant's params (never `base`), rendered by `_grade`'s in-chain `_apply_channel_curves`; empty/unset is OFF and **bit-identical by construction**.
The handler is the upstream gate (even-length / ≥ 2 points / strictly-ascending x / x ∈ [0, 1], with a `PhotosConfig` validator and the `CorrectionParams` `__post_init__` beneath), rejecting before any decode.
`--vibrance` (default `photos.vibrance`, range 0..2) exposes the in-grade low-sat-weighted chroma boost the same way — a single float (`type=float`, `0.0` = off, bit-identical) `dataclasses.replace`d onto every styled variant's params (never `base`), rendered by `_grade`'s in-chain `_apply_vibrance`; the handler resolves flag-beats-config and range-guards ∈ [0, 2] before any decode, threaded through `plan_variants`/`develop_variants`.
`--border STYLE` (default `photos.border`) adds a presentational frame at the EXPORT step only — a pure `_add_border` pad-and-paste over the finished frame, never fed into the grade and never applied to the contact-sheet panels (a review artifact): `none` (the default) returns the frame UNCHANGED so the exported bytes stay byte-identical, `white`/`black` lay an even matte on all four sides, and `filmstrip` frames the shot in black with wider top/bottom bars carrying evenly spaced white sprocket holes.
It is the RUN's border, and the only thing that overrides it for a single export is a `--look-variant` whose own recipe names one (below).
`--format {jpeg,tiff16}` (default `photos.develop_format`, argparse `choices` + a `PhotosConfig` validator mirroring `EXPORT_FORMATS` as a literal, both gating upstream of any decode) picks the master container, and — unlike `--border` — it is NOT purely an export-step op: a 16-bit master cannot be manufactured after the fact, since an 8-bit render upsampled into a wider container is a wider container and not more depth.
`tiff16` therefore threads a `depth` into `develop_variants`, which quantizes `_grade` to uint16 instead of uint8; every stage downstream (`_dehaze`/`_clarity`/`_sharpen`/`_sky_darken`/`_vignette`/`_halation`/`_grain`, `_add_border`, and `apply_cube`, which now returns its input's dtype) reads the frame's full-scale code off `_peak` and rounds back through `_requantize`, so the whole chain runs in the frame's own depth — and at 8 bits `_peak` IS 255.0, which is what keeps the default JPEG path byte-identical.
`export_tiff16` writes a deflate-compressed 48-bit `<stem>_<variant>.tif` tagged with the same deterministic `srgb_icc_profile` bytes the JPEGs carry (the chain's working space IS sRGB — a wide-gamut/ICC decode is converted before grading, so a P3 tag would relabel the numbers rather than widen them) and REFUSES a uint8 frame outright, which is what makes fake depth impossible by construction rather than by convention; the contact sheet stays an 8-bit review JPEG, fed a `_analysis_rgb` downconversion.
Thickness is a fraction of the long edge (`BORDER_FRACTION`), so the frame is resolution-independent, and the whole op is deterministic.
The style set (`develop.BORDER_STYLES`) is gated upstream twice before any decode — argparse `choices` on the flag and a `PhotosConfig` validator on the config default (which mirrors the tuple as a literal so the validator itself imports nothing from the pipeline package; a test pins the two together).
Deliberate scope: grading is PER-PHOTO (no clustering — that is ingest's batch contract), and outputs are **local operator working files, never the public site tree** — the publish/ingest paths keep their blur gates, this surface has none.
`--grade-sidecar` (default `photos.grade_sidecar`, OFF) answers "what numbers made this frame?": the exact grade a photo landed on was never recorded, so a frame the operator liked could be looked at but neither reproduced nor transferred to another photo.
On it, each export gets `<stem>_<variant>.grade.json` beside the JPEG (`write_grade_sidecar`, called from the CLI export loop right where `_add_border` is applied — never inside `_grade`/`plan_variants`, so the grade chain is untouched) holding the full `dataclasses.asdict(CorrectionParams)` that graded THAT variant (the authority on its colour chain), the whole live `DevelopOptions` record read off the dataclass rather than a hand-kept knob list that goes stale — spatial `vignette`/`clarity`/`grain`/`halation`/`sharpen` included — the `measured` amounts the ramped denoise/sharpen stages actually chose, a `lut` block (cube name, `lut_strength`, `lut_over`) on a LUT surface only, and provenance: `DecodedPhoto.decoder`, `DEVELOP_ALGO_VERSION` and `develop_cache_key`.
Reading that reserved pair for provenance **does not wire the reserved cache** — no cache entry is read or written anywhere, and the pair stays deliberately unwired.
`correction_params_from_sidecar` rebuilds the params exactly (JSON has no tuple, so the tuple-defaulted fields are coerced back).
The write is the same temp-file-then-`os.replace` `export_jpeg` uses, so a crash can never leave a half-written record next to a good JPEG, and a failed write is **logged loudly and swallowed** — the export is the product, the sidecar metadata, and metadata must never cost a photo.
JSON is sorted-key with Python's shortest round-trip floats, so two develops of one frame produce byte-identical sidecars: the JPEG is byte-reproducible and a wandering key order would undo that property for the pair.
OFF writes nothing and the exported bytes are unchanged.
`--look NAME` (default none) is the other half of that pair: the sidecar records what a frame WAS, a **`photos.looks`** entry declares what you WANT.
`photos.looks` is a registry of NAMED knob combinations (`{filmish: {styles: moody, style_strength: 1.4, vignette: 0.35, grain: 0.2, split_tone_shadow: [0.0, 0.03, 0.08]}}`) keyed by the develop FLAG names — and the surface is every `look=True` row of `config.PHOTO_KNOBS` (`LOOK_KNOBS`), so "moody at 1.4 with a teal split-tone and light grain" otherwise meant retyping eight flags exactly, correctly, a week later.
**Precedence is explicit flag > look > bare `photos.<knob>` default**, and it is structural rather than a rule each resolution has to remember: `_apply_look` runs BEFORE any knob is resolved and FILLS ONLY the flags argparse left `None`, so an explicitly-passed flag is already non-`None` and survives untouched, an unset one takes the look's value, and a knob the look does not carry stays `None` and falls through to the config default in the `flag if not None else photos.<knob>` line it always used.
Every resolution, range gate and `DevelopOptions` field below is therefore reached by exactly the path the flags take, so `--look filmish` and its knobs spelled out as flags render **the same bytes** — the property the operator is actually promised.
The valid key set (`config.LOOK_KNOBS`) is a **literal local to `config.py`, and must stay one**: `Config.load` runs at MODULE IMPORT time — `longform_metadata` builds `DEFAULT_SEO_STORAGE`/`DEFAULT_CREDENTIALS_DIR` off `get_config()` at module import — so a validator that imports `gomoveshift.pipeline.*` re-enters a half-initialised package and **every** command touching the pipeline dies with an unrelated `ImportError` naming `GOLDEN_COLUMNS`, nothing that points the operator at their config file.
Deriving the set from `DevelopOptions.__dataclass_fields__` at validation time did exactly that: one configured look cost the whole CLI, and a lazy import cannot help when the load itself is import-time work.
`border` mirrors `BORDER_STYLES` as a literal for the same reason.
What keeps the literal honest is the **sync test**, which may import `DevelopOptions` freely (test-time imports are outside the cycle): it asserts every `DevelopOptions` field is nameable in a look (via `LOOK_ALIASES` — every `PHOTO_KNOBS` row carrying an `alt`, i.e. the names argparse spells differently: the three `splittone_*` → `split_tone_*`, `mono_mix` → `bw_mix`, `reference_lab` → `reference`, and the two run-owned geometry knobs `straighten_angle` → `straighten` and `crop_rect` → `crop`) AND that every look knob is a real develop flag whose argparse default is `None` — the fill-if-unset precedence rides that default, so a future knob landing with a non-`None` one, or with no `LOOK_KNOBS` entry, fails there instead of silently ignoring the look.
`LOOK_RANGES` holds the scalar gates.
Both sibling validators (`lut_over`, `social_aspect`) follow the same rule: they check literal mirrors in `config.py` (`PHOTO_LUT_OVER_STYLES`, `PHOTO_SOCIAL_ASPECTS`) and import nothing from the pipeline package.
An unknown knob or an out-of-range scalar fails at config LOAD naming the look and the key (a look that only fails once a render reaches the bad knob costs a batch of decodes to find); an unknown `--look` is refused at the CLI door listing the built-in and configured names as SEPARATE tagged groups (`built-in: …; configured: …`, `none` for an empty group), before any decode.
Names resolve out of `{**BUILTIN_LOOKS, **photos.looks}`, so **the operator's config wins a name collision** — an override must survive an upgrade that ships a built-in preset of the same name.
`BUILTIN_LOOKS` (`pipeline/photos/looks.py`) is the in-box half of the registry: plain data, importing neither `gomoveshift.config` nor anything heavy, keyed by the develop FLAG names (`split_tone_shadow`, `split_tone_midtone`, `split_tone_highlight`, `bw_mix`, `reference`, plus the run-owned `straighten` and `crop` a look is refused — the `LOOK_ALIASES` seven), which is the single easiest way for a preset to fail `LOOK_KNOBS` validation.
It is split into per-pack dicts (`_ELECTRONIC` / `_CINEMATIC` / `_MASKED`) merged into one public table **deliberately, and must stay split**: the packs are authored independently and appending to one shared dict would make their edits conflict outright.
A pack lands only once its presets are calibrated — every preset needs a strength sweep against a reference card that no hermetic test can stand in for — and the test that walks the table (every knob in `LOOK_KNOBS`, every scalar inside its `LOOK_RANGES` gate, the whole table through the real `PhotosConfig` validator) is the gate each landed pack passes.
`_ELECTRONIC` is the after-dark four: `cyberpunk` (teal shadows and magenta highlights via the split-tones, a crushed toe, a magenta bloom), `synthwave` (violet shadows climbing to a pink highlight over the lifted `matte_shoulder` base, plus grain and vignette), `chrome` (cool at BOTH ends, every hue but blue and cyan drained, clarity and sharpen pushed) and `neon_noir` (curves crushed low-key, the warm end drained, a cold bloom off the signage).
Each names its own base `styles`, so `--look NAME` renders ONE deterministic variant rather than an auto-selected spread, and `--halation-tint` is what lets that bloom read as neon instead of film red.
Two of the four were recalibrated on the first real landscape frame they were ever rendered on, and both failures are the same shape — a recipe tuned against hermetic synthetic frames, which span the full tonal range this grade chain never reaches.
`synthwave` originally used `duotone`, which is `shadow + luma·(high − shadow)` and therefore REPLACES every pixel's colour with a point on a two-colour ramp with no strength lever: on a photograph the sky, the ridges and the cloud all resolved to one flat magenta, so it is now split-tone plus a hue push, which reaches the same palette while the frame keeps its own colour (the missing lever now exists as `duotone_strength`; the recipe is unchanged, since retuning it is a taste call and needs a sweep).
`neon_noir`'s toe sat at 0.12 and crushed a real frame to near-black; it sits at 0.22 now, because low-key has to keep the subject readable to be a look rather than a failure.
`neon_edge` was left ALONE for the opposite reason: its `highlights` mask is every pixel above 2/3 luma, so on a landscape it covers the whole sky, and softening the amplitude only trades the look away (halving it measured 3.03 rendered distinctness against the 5.0 floor) — what that scene needs is a mask that selects small bright regions, which `glints` now is and the note at the end of this section records it moving onto.
The same pack carries the ARTIFACT three, the first recipes in the box to use any of the spatial stages `--glow` / `--light-leak` / `--chromatic-ab` / `--holo-sheen` / `--scanline` / `--glitch` shipped: `vhs` (a `scanline` tube structure over a `chromatic_ab` fringe, chroma smeared down and the toe lifted onto `matte_shoulder` — tape never reaches black), `glitch_pop` (a cyberpunk split-tone pair on a `vivid` base torn by `glitch`, the signal fault) and `leaked_film` (a tungsten split-tone plus `halation`, fogged from the corner `light_leak` owns).
Amounts stay conservative on purpose — the picture still has to read as the picture — so a strength sweep tunes a knob rather than rescuing a look.
Because each is NAMED for a stage, `tests/test_photo_artifact_looks.py` renders every preset a SECOND time with that ONE knob stripped (as an operator-config look, through the same CLI door) and measures the structure only that stage can make — a windowed spectral line in the row-mean luma for `vhs`, a minority of rows displaced sideways for `glitch_pop`, a warm corner lift the opposite corner does not get for `leaked_film`; anchored on the natural grade instead, all three pass with the artifact knob deleted outright, since the base style and the colour knobs alone carry them there.
`tests/test_photo_electronic_pack.py` renders all four through the real CLI door on a synthesized frame and pins what an eyeball cannot re-check on every change: `MIN_RENDERED_DISTINCTNESS` from the natural grade AND from every pack-mate, byte-identical re-renders, and each look's colour direction measured against its OWN base style — anchored to natural instead, a preset whose colour knobs were deleted outright still passes.
Unconfigured is inert and byte-identical by construction — both halves default empty, the validator returns before the import, and no `--look` means `_apply_look` never runs.
`--look-variant NAME` (repeatable, like `--lut`) is the OTHER axis: `--look` is a defaults layer, so exactly one look applies per run and two candidates can never be compared side by side — which is the contact sheet's whole reason for existing.
Each `--look-variant` renders that look as its own panel over the base grade its own `styles` names (the note at the end of this section), or over the natural base grade when it names none, kept in `VariantPlan.look_variants` as `(look_<name>, that look's own DevelopOptions)` and rendered where the `lut_looks` panels are; the `look_` prefix keeps a look from colliding on disk with a style or a LUT of the same name, and is what the sidecar reads `look: {name}` back out of, so a sheet audits back to the recipe that drew each panel without threading a list.
`look_variant_options` builds each record once at the CLI door — the run's resolved options with that look's knobs replaced on top (`LOOK_ALIASES` maps the flag vocabulary onto the field names, YAML lists become tuples) — so a panel carries the look's colour chain AND its own spatial amounts and two looks differing only in grain still compare, while keys one panel cannot own as a knob (`format`, the `--lut` surface, and `reference`, which names a FILE the door already measured) stay the run's — `styles` is not a knob but the panel's own base grade, carried separately below.
`border` is the one knob a look owns WITHOUT owning it through that record: it is an export garnish rather than a develop knob, so it is no `DevelopOptions` field at all and is instead kept at the door as a `look_<name> -> style` map the export loop reads (`look_borders.get(name, border)`), which is how `polaroid`, whose white matte IS the look, renders as a panel with the matte rather than silently without it.
A look naming no border is absent from that map and falls back to the run's `--border`, exactly as the styled and LUT panels do, so one run can put a look's own matte beside `--border`'s on the same contact sheet.
A look sets its knobs straight onto `args`, past both the argparse `choices` and the `PhotosConfig` validator, so the resolved run-level style AND each look's own are re-gated against `BORDER_STYLES` at the door (`_bad_border` names which one carried it) — a bad style is refused before any decode instead of raising out of `_add_border` once per photo, mid-batch, with the decodes already paid for.
Grading a neutral base through the resolved record there is the upstream gate — a malformed split-tone or curve is refused at the door, not per photo mid-batch — and an unknown name hits the same tagged refusal `--look` does; the two flags compose in one run, and an empty list is byte-identical by construction (no panel renders).
Look panels are NOT filtered by the rendered-distinctness gate, exactly as `lut_looks` are not: that gate guards AUTO-SELECTED styles, and a named look is the same operator authority an explicit `--styles` list is.
One look key is not a flag value but a list: **`layers:`** — masked colour recipes (`[{mask: sky, hue_sat: [...]}, {mask: ground, split_tone_shadow: [...]}]`), the seam that connects the look registry to `masks.py`, and the only way any colour knob on this surface stops being whole-frame.
`_layered` runs between `_grade` and `_spatial_chain` on the styled and look-variant surfaces (never the LUT looks — a masked layer is still a colour move, and a film table renders the film's look, not the operator's), composing each layer over the running frame in list order so a later layer sees, and meters its mask on, what the earlier ones left.
Layers are **colour and tone only by construction** (tone knobs came later — see the `LAYER_TONE_KNOBS` note at the end of this section): a spatial stage is a property of the whole rendered frame — a vignette that stopped at a horizon is a bug, not a look — so `check_layers` refuses a spatial knob in a layer at config LOAD, along with an unknown mask name (listing the legal ones), a non-positive `feather`, a non-boolean `invert`, a layer with no `mask` and one carrying no knob at all (it would render nothing).
That gate is shared with the `--layers JSON` flag at the CLI door, since the flag path never passes the config validator; `LAYER_MASKS` mirrors the `MASKS` registry as a literal for the same import-cycle reason `LOOK_KNOBS` mirrors the flag names, with a sync test pinning the two.

**White balance is a local move too (all six `white_balance_*` axes, `layer="colour"`).** Every other colour knob could already ride a mask, but the one an operator reaches for first could not: "warm the ground, leave the sky alone" is the commonest local correction in a landscape frame, and expressing it meant two renders and a composite outside the pipeline. Nothing in the renderer changed to allow it — `_look_params` derives a layer's colour chain from the field names `DevelopOptions` and `CorrectionParams` **share**, all six axes were already on both records, and `_grade` already routes them through `_apply_colorbalance`. The capability was fully built and fenced off at the door by one missing flag per registry row, since `check_layers` refuses any key `LAYER_KNOBS` does not carry. All six flip together: `white_balance_g`/`_g_high` have no whole-frame producer, so omitting them would have been easy and silently wrong. **The additive/replace subtlety does not reach a layer**: `_wb_shifted` ADDS whole-frame because a look grades over the measured base and replacing would discard `compute_correction`'s cast correction, but `_layered` lays each layer over a fresh `CorrectionParams()`, so the base is zero and the number written is the number applied — pinned by an equivalence against a direct `_grade` through a full-select mask, which would diverge by exactly the cast if a layer ever started from the run's measured params. `config.py` is not in `_HASHED_SOURCES`, and no shipped look or default render changes: an empty layer list still returns the frame untouched without reaching a mask. Tests: `tests/test_photo_layer_white_balance.py`.
No `layers` is the shipped path **byte for byte and by early return** — `_layered` returns its input before importing a mask, so nothing meters, and the whole seam is invisible to every run that does not name one; the `.grade.json` sidecar records the resolved list off the live `DevelopOptions`, so a rendered sheet audits back to the recipe.
The record/review switches (`--grade-sidecar`, `--contact-sheet`, `--dry-run`) are deliberately NOT look knobs: a look is the creative grade, not how a run reports itself.
Scope is recall alone — there is no "save these flags as a look" writer, which would mean editing the operator's own `config.yaml`.
The `_CINEMATIC` pack is the first one filled: `teal_orange` (the blockbuster split, with the skin-adjacent red/yellow `hue_sat` anchors held BELOW 1.0 so faces keep their own colour instead of following the highlights orange), `bleach_bypass` (silver retention — colour drained by a flat 0.4 `hue_sat` with the contrast put back as one hard S shared by all three channels, so it bleaches rather than merely greys), `cross_process` (three INDEPENDENT channel curves, which is the whole point: a split-tone pair cannot pull green-cyan shadows and yellow highlights onto different axes), `cinestill` (tungsten split-tone plus `halation` at the SHIPPED red bias — that bias is the look, so `halation_tint` is deliberately left unset — and grain) and `polaroid` (lifted matte toe, warm cast, slight desat, and `border: white`, the one preset carrying a presentational knob).
None of the five pins `styles`, so a look layers onto whichever variants the scene picks rather than overriding the operator's choice of them; `tests/test_photo_cinematic_pack.py` renders each one through the real CLI and holds every preset to the same `MIN_RENDERED_DISTINCTNESS` bar two auto-selected variants must clear to both ship — against the natural grade AND pairwise against its four siblings, since five names that render as one look are four wasted names.
The `_MASKED` pack is the mask engine's payoff — every preset is `layers` and nothing else: `split_world` (a cooled sky over ground warmed the other way, riding `sky` and its own complement `ground` so the two meet with no seam), `neon_edge` (a magenta/cyan tint through `glints` ONLY, so the lit SIGNS read as light rather than as a filter over the whole photograph), `vignette_wash` (the radial falloff INVERTED to drain and cool the edges plus its non-inverted twin holding the centre warm — the colour half of what a vignette does to tone, which no spatial knob expresses) and `golden_ground` (a warm lift ramped in over `linear`'s default bottom-half gradient, so the sky above it is untouched exactly).
Each recipe is written in channel curves rather than split-tones wherever it must bite regardless of where its region's tone sits — a split-tone is keyed to ABSOLUTE luma and lands nowhere on a region the frame's own span happened to put in the middle — and the fifth, `subject_pop`, rides `texture` (below), which is what keeps it from being the centre/edge split `vignette_wash` already is.
`tests/test_photo_masked_pack.py` renders the pack through `develop_variants` rather than the CLI door the sibling packs use, because these assertions are about EXACT complements and the exported JPEG quantizes in 8×8 blocks — a block straddling a mask boundary would move pixels no layer touched — and it pins per look that the region a mask names moves while the complement moves the other way or not at all, alongside the same `MIN_RENDERED_DISTINCTNESS` bar both sibling packs ship under.
The four pack suites between them name every preset in the box, and `tests/test_photo_look_packs_cover_the_table.py` is what keeps that true rather than remembered: `_CINEMATIC` and `_MASKED` are pinned whole by their own suites (`tuple(_MASKED) == PACK`), but `_ELECTRONIC` is split across the electronic and artifact suites and NEITHER pins the union — it asserts only `set(PACK) <= set(_ELECTRONIC)` — so a look added to that family would ship, pass the config validator, reach `--look`'s help and render in no test, which is exactly how the artifact three arrived before their own suite was written. It renders nothing itself: it asserts the four packs' union is exactly `BUILTIN_LOOKS`, that no pack names a look the table has dropped, and that no look is rendered by two suites; a fourth assertion runs the same check against a fabricated table with one unrendered name, so the gate is proved able to bite rather than merely observed passing.
Tests: `tests/test_photo_develop_cli.py`, `tests/test_photo_grade_sidecar.py`, `tests/test_photo_looks.py`, `tests/test_photo_look_variants.py`, `tests/test_photo_look_packs_cover_the_table.py`.

**Ken Burns reel (`reel.py` + `gomoveshift photos reel <stills...> --out FILE.mp4`).** Stills → one 1080×1920 H.264 MP4, a slow pan-zoom over each still and a hard cut between them (no audio, no crossfade, no captions). Its own subcommand rather than a `develop` flag: it renders video and takes its pixels from `route_story.hud._load_still` (decode + `grade.grade_still`, the same cached graded still the route-story cards and the insert engine use), so a still looks identical on every surface; the reel adds only the pan-zoom and encode, and changes no `photos develop` output. Two pieces. `plan_motion(source_size, output_size, duration, fps, index)` is **pure** — the per-frame crop rectangles and nothing else, no ffmpeg and no I/O — so the motion is unit-testable exhaustively: every rect carries the output aspect *exactly* (width is derived as `height * aspect`) and sits inside the source *by construction* (the base window is stepped down by `math.nextafter` until `base * aspect <= src_w`, and each offset is a fraction of the slack the zoom opens), never by a later clamp. Easing is smoothstep, so the move starts and stops from rest; even-indexed stills push in while odd ones pull out, so a six-still reel alternates instead of droning. Defaults: `REEL_SECONDS_PER_STILL = 3.0`, `REEL_FPS = 30`, `REEL_ZOOM = 0.12` (12% over 3 s ≈ 4%/s — a drift, not a lurch), pan `0.35 → 0.65` of the slack (through centre, never hugging an edge), `REEL_CRF = 18` / `preset slow` (a held still shows banding a moving frame hides). `render_reel` crops+resizes with cv2 and pipes raw `rgb24` frames to ffmpeg over **stdin** rather than using the `zoompan` filter — the easing stays ours and reproducible from the planner alone; `assembly.encoder.VideoEncoder` is not reused because every one of its methods takes a video *file*, never a raw stream. Determinism: `cv2.setNumThreads(1)` for the whole render (same pin as the Mertens fuse), which makes two runs over the same stills produce a **byte-identical container**, asserted as such in `tests/test_photo_reel.py`. Gates are at the door, before a byte is decoded or encoded: an empty path list, any unreadable still, and an `--out` whose directory is missing or unwritable each fail naming the problem. Local working output like `photos develop` — not the blur-gated publish path. **Colour.** The frames arriving over stdin are *true full-range* rgb24 while the encode is 4:2:0 YUV, so the RGB→YUV hop is stated rather than inherited from swscale defaults: `REEL_RANGE_FILTER` = `scale=in_range=full:out_range=tv:out_color_matrix=bt709,format=yuv420p,setparams=…`, and the four `LONGFORM_COLOR_*` constants are stamped on the stream so the file describes what was actually written. `format=yuv420p` is what makes `scale` negotiate YUV as its output (otherwise the range/matrix options apply to an RGB→RGB no-op), and the trailing `setparams` is load-bearing: filtered-frame properties beat the `-color_*` output options at the encoder, so without it primaries and transfer ship `unknown` however the command line reads. The command is built by the pure `build_encode_cmd`, and `tests/test_photo_reel.py` verifies the *conversion* as well as the tag — a black/white still must come out coded 16-235, because a tag that disagrees with the pixels is worse than no tag.

**EXIF-GPS location + endpoint-anchored geocode cap (`exif_gps.py`).** Photos carry their fix in EXIF, not GPX, so `derive_location_from_photos` mirrors `gopro_gps` rather than adding a second geocoder: `extract_exif_gps` reads the GPS IFD (malformed rationals and out-of-range fixes are discarded, and it *never raises* — one bad photo can't abort a batch), the surviving coordinates are emitted as a synthetic GPX, and that is handed to `derive_location_from_gpx(photo_mode=True)`. This keeps the label **voted over the dominant county** (never a bare centroid, which lands on the wrong side of a county line), keeps Nominatim the only geocoding host with the shared cache, and lets a degraded geocoder yield *no* label rather than a fabricated one that could flip a non-US set to a US one. The synthetic GPX lives in a tempdir and is deleted after use; the published JPEG's GPS is stripped separately by the resizer.

- **Endpoint-anchored geocode cap** (`_MAX_GEOCODE_ANCHORS = 16`): each fix is one rate-limited ~1 s Nominatim request, so a 2000-photo card would otherwise spend ~33 min resolving a single label and hammer the geocoder. `_sample_anchor_coords` bounds the distinct requests to 16 regardless of card size — at or below the cap every fix is an anchor (a label byte-for-byte what the full set would elect); above it, exactly 16 indices are sampled with `round(i·(n−1)/(k−1))`, which **pins the true first and last photo** (a naive `range(0, n, step)` skips the last and loses the end-of-trip location) and dedupes identical coordinates. Even spacing makes each anchor a nearest-anchor vote for an equal-size run of neighbours, so the vote still reflects where the day was spent; ~3× the video path's five samples, because a photo set spans more distinct places than one drive.

**Phase 1 — `PhotoOrchestrator.generate_batch`.** `PhotoSelector.select_batch` walks journeys in weighted round-robin (weight ∝ journey photo count, interleaved one slot per pass, sequential by day within a journey), skipping anything in `posted_photos`/`face_filtered_photos`. A GENUINELY exhausted pool (every photo posted or face-filtered, no pending holds; `--count < 1` is rejected at argparse and again in `select_batch`) resets the rotation once and retries iteratively (never recursively) — an empty selection from any other cause (files missing on disk, runtime face filtering, outstanding holds) never wipes the posted-photos ledger or holds and falls through to the count-match gate below. `filter_faces` routes each candidate through `should_withhold_photo` in `face_filter.py` and skips — but does not permanently blacklist — a hit; with blur on (the default) that withholds only unreadable photos, since faces are blurred on the resized copy instead, so detect-and-skip applies only under `--skip-blur`. `CaptionGenerator.generate_batch` then takes the voice style from `ThemeRotator` and writes `<week>_captions.yaml` for the operator to hand-edit and set `reviewed: true`.

- **Selection count-match gate**: `select_batch` raises when it would return fewer than `count` (greppable `PHOTO-CONTRACT`) unless `allow_shortfall=True`. A near-exhausted or heavily face-filtered pool used to return a short batch silently, shipping a thinner week; the raise lands upstream of captions (LLM spend), Drive upload and the CSV. The photo analog of the shorts-shortfall gate.
- **Caption YAML is never clobbered**: `CaptionGenerator.ensure_week_unwritten` hard-fails with `FileExistsError` when `<week>_captions.yaml` already exists. The orchestrator checks it *before selection* (so a doomed run takes no photo holds and burns no LLM spend); `generate_batch` keeps it as a backstop for direct callers. Photos are marked posted at selection, so regenerating over an existing review file destroys both the hand-reviewed captions and the fresh photo set — neither is recoverable. The operator moves or renames the file to regenerate.
- **Per-caption generation provenance** (`generation_provenance.GenerationProvenance`, wired into `CaptionGenerator.generate_batch`): each `PhotoCaption.provenance` records what actually produced it — the model invoked, `RECIPE_VERSION` (a hash of the static prompt-instruction blocks, so it can't go stale from an edited prompt), the metadata keys fed into the prompt (`evidence`), attempts spent (1 + retries), wall-clock `duration_s`, and which validated fields passed/failed. A batch-level `model`/`generated_at` used to be the only record, making a caption a fallback produced (`_fallback_caption`, silent metadata sentence) indistinguishable from one the LLM actually wrote — `fallback_used`/`fallback_reason` close that gap. No dollar cost is recorded: the caption call goes through the local CLI, which reports no per-call price; inventing one would be worse than omitting it. No fabricated confidence score either — `validation_passed`/`validation_failed` are the honest substitute. A batch saved before this field existed loads with `GenerationProvenance.not_recorded()` (`.recorded is False`), a state deliberately distinct from "recorded, `fallback_used=False`" — collapsing the two would launder missing data into a clean bill of health.
- **Generate-path hold release**: selection persists per-photo holds (`pending_photos`) before captioning, so every caption-phase exit must either ship the batch or return this run's holds — a leaked hold is a permanently unselectable photo. Any caption-phase failure (LLM call, parse, count mismatch) releases exactly the just-taken holds before re-raising, and a selection the caption phase drops (empty metadata) has its hold released at generate time, since publish's release/commit only ever sees `batch.captions`. Operator recovery for past leaks: `photos release <week>` releases an unpublished batch's holds via its captions YAML and refuses a published one (those photos are spent, not held).
- **Atomic state**: `PhotoSelectionState` writes through `_atomic_write.atomic_write_json` and the review YAML through `atomic_write_yaml`, so an interrupted run can't leave a truncated rotation state or a half-written review file.
- **Fail-closed state load**: `PhotoSelectionState.load` raises `PhotoSelectionStateError` on a corrupt or schema-incompatible state file (bad JSON, unreadable, unknown/renamed field) instead of silently substituting an empty state — the file is the posted-photos consumption ledger, and a silent reset re-offers the entire shipped back catalog as new. A genuinely absent file (first run) still yields fresh state. Escape: `--reset-selection-state` on `photos generate`/`photos batch` explicitly accepts the wipe, archiving the old file aside as `<name>.corrupt-<timestamp>` (never deleting it) before selection runs.

**Phase 2 — `PhotoOrchestrator.publish_batch`.** Refuses an unreviewed batch unless `force=True`. A **photo preflight** (`preflight_photo_run`) then gates disk/RAM *before the first irreversible step* (resize copies, Drive upload), reusing the drive path's `check_disk_space`/`check_ram` primitives with the same raise-on-shortfall semantics but lower thresholds (2 GB free / 1 GB RAM, vs the drive path's 50 GB / 2 GB — a photo batch writes a few hundred MB, not ~60 GB masters, so the drive floor would only false-fail a healthy volume); it also surfaces any leftover unbooked-ledger marker (below) so a prior silent booking miss can't turn into a silent double-book. A **publish count-match gate** (the photo analog of the shorts-shortfall gate, mirroring the selection gate above) then hard-fails with `PhotoPublishShortfallError` when any caption's source photo has vanished — fewer publishable photos than the batch captioned, or zero, used to drop silently and a caption-less batch would "publish" a header-only CSV, mark itself published and export; a batch truncated to zero by slot availability hard-fails the same way. Then:

1. **Resize** (`PhotoResizer.resize_batch`) — scales to `photos.target_width` (default 1080) maintaining aspect ratio, with an optional **social target aspect** (`photos.social_aspect` / `--social-aspect` on `photos publish` and `photos batch`; `square`, `4:5` or `9:16`, `""` = off and the default): the largest **centred** rectangle of that ratio is trimmed from the frame — after `_prepare`'s EXIF orientation (cropping the stored orientation would trim a rotated portrait along the wrong axis) and before the width scale — so a landscape still is composed by us rather than by Instagram's/TikTok's auto-crop. It is deliberately **one output per photo, never a variant per platform**: everything below the resizer (upload manifest → Drive links → Metricool CSV → scheduler → `ContentLedger`) is keyed one resized file per selected photo, and fanning out N crops would rewrite that contract across four subsystems. Centre only — no saliency detection, which needs a detector and a model dependency. Unset it is **byte-identical to the pre-crop path by construction** (`aspect_ratio("")` is `None`, so no crop code runs and the byte-copy fast path below stays reachable); set, it also disqualifies that copy fast path, since a cropped frame is no longer the source's bytes. An unknown label is rejected at three doors — argparse `choices`, the `PhotosConfig` validator, and the `PhotoResizer` constructor (before any file is written) — each naming the valid set. `_prepare` applies EXIF orientation (`ImageOps.exif_transpose`), converts through `ImageCms` to sRGB (an unusable source ICC profile skips the conversion: the social JPEG is saved **untagged**, the warning says the colours were assumed sRGB, and that photo's entry in `photos_provenance.json` carries a `color_assumption` note — a social derivative is allowed, a master is not), and drops all source EXIF plus the XMP packet and JPEG comment (Pillow's JPEG save re-attaches `info["comment"]` by default, and GPS can ride either segment even when EXIF is clean). Output is always JPEG with a forced `.jpg` extension so the Drive upload can't advertise a source-derived MIME type it doesn't match. Every re-encoded output is saved with explicit 4:2:2 chroma (`SOCIAL_JPEG_SUBSAMPLING`: cleaner chroma edges than PIL's implicit 4:2:0 at a small size cost for a 1080px upload) and, when its colours were converted or it arrived with no profile, the standard sRGB ICC tag (`srgb_icc_profile`, shared with the gallery export — previously only sources that arrived tagged got one, so developed exports and resizes disagreed). A source whose profile cannot be converted is saved **untagged**, never labelled sRGB: the resizer warns, records `ASSUMED_SRGB_NOTE` on the photo's provenance entry and carries on, where develop refuses the photo. The byte-copy fast path is exempt, since tagging it would mean re-encoding. `_assert_no_gps` re-opens every output — copied or re-encoded — and raises if the GPS IFD survived or the XMP packet / JPEG comment carries GPS markers — location metadata must never reach a public platform. The still privacy blur runs here (`face_filter.blur_faces_for_publish` → `_detect_regions`), carrying the VIDEO blur contract: faces ∪ aspect/area-gated plates ∪ the top `blur_vehicle_cabin_frac` of each plate-corroborated vehicle box (`cabin_region`/`plate_inside` reused from `redactcam`; a COCO "vehicle" with no plate inside it is a billboard/sign misfire, and stills have no ego hood so only the min-height vehicle gate applies) ∪ whole-person boxes gated on `blur_person_enabled`/`blur_person_min_height_frac` (`build_person_detector`/`resolve_person_model`, the video path's own person model, reused per-frame instead of per-timeline) — a person photographed from behind, side-on, at distance, or with an occluded face produces no face box, so before this the still path had no detector covering them at all. The detectors resolve through the same download-once model cache (`analysis.resolve_*_model` → `redactcam.resolve_model`) and `blur_plate_min/max_aspect` band as the video path — `build_image_detectors` is no longer called with hardcoded `None` model paths — and a detector failure raises `FaceBlurError` rather than shipping unblurred (tests stay offline via the `hermetic_still_blur_models` conftest fixture, which stubs `resolve_person_model` alongside the other three). An already-clean sRGB JPEG under the target width (no EXIF, ICC, XMP, or comment) is copied rather than re-encoded; any XMP packet or comment disqualifies the fast copy and routes through the re-encode, which strips both. Output names are journey-slug-prefixed to stop two journeys sharing a bare filename from colliding on their Drive links.
2. **Upload** — `PipelineUploader.upload_photos` into `GoMoveShift/Photos/Daily`, then `verify_uploads` re-uploads any failures.
3. **Schedule** (`PhotoScheduler.schedule_batch`) — one slot per day at `PHOTO_POST_TIME` (EST), skipping days already occupied in the shared `ContentLedger`. The ledger is re-read at schedule time because another process may have booked slots since construction. A `start_date` in the past is clamped forward to today with a warning rather than raising (`publish_batch` passes the *generate* day, so an overnight review legitimately arrives with a past start), and a candidate at or before `now` is skipped entirely — Metricool rejects a past scheduled time and a past ledger booking would be wrong forever. `_validate_range` defensively re-asserts every slot falls inside `[start_date, end_date]`. When `end_date` truncates the run to fewer slots than captions, the caption list is trimmed to match.
4. **CSV** (`PhotoCSVGenerator.generate`) — same 31-column golden reference as shorts, with `YouTube = FALSE` and all YouTube columns blank, `Instagram`/`Facebook Post Type = POST` (not `REEL`), and `TikTok Title` filled. Hashtags are appended to the shared `Text` column rather than parked in `First Comment Text`, which Metricool applies to Instagram only.
5. **Ledger + export** — the published marker + booked slots are persisted to the caption YAML *first*, then each slot is booked as a `photo` `ContentEntry`, theme usage is recorded back to `ThemeRotator`, and the CSV is copied to `GMS_EXPORT_DIR` via PowerShell `Copy-Item` (WSL 9p makes `shutil.copy2` unreliable). Marker-before-booking means no crash point leaves a live booking without its marker: a crash (or failed YAML save) between the old booking-then-save sequence stranded ghost bookings that the re-publish rescheduled a shifted duplicate week around.

**CSV integrity gates**, all upstream of the write:

- **Direct-download media links**: `Picture Url 1` runs through `_drive_link_for_metricool`. The upload manifest holds the `/view?usp=sharing` share link, which returns Drive's HTML viewer page to an unauthenticated pull, so TikTok/Meta attach no image; the `uc?export=download` form returns the bytes. Photos sit far under the virus-scan interstitial bound that keeps `/view` the global default.
- **Formula escaping**: every LLM-derived cell (`Text`, `TikTok Title`, `First Comment Text`) passes through `_escape_csv_cell` to neutralize spreadsheet formula injection (OWASP CSV injection).
- **Missing Drive link** raises before the write — a row with no media is a post Metricool silently drops.
- **Schedule gate**: `_assert_metricool_rows_have_schedule` (shared with the shorts CSV) rejects any row with a blank `Date`/`Time`. `validate_csv` only flags *malformed* dates, so a blank cell passed every prior check and Metricool imported it as an immediate post rather than on its planned drop.

**Ledger booking is best-effort — it never fails a shipped batch** (`_book_slots` → the injected `ledger_booker` → `record_confirmed_upload`). After the CSV is written, each slot books a `photo` `ContentEntry` through `record_confirmed_upload`, which holds `_ledger_lock` — a blocking, reentrant `fcntl.flock(LOCK_EX)` on a `.lock` sidecar — across the whole ledger load→add→save, so two concurrent drives can't lose-update each other's booking (the two-USA-drives no-double-book contract). Called strictly *after* the upload is confirmed, it is deliberately best-effort: any failure logs `LEDGER-BOOKING-FAILED` and returns `False` rather than raising, because a raise here would `release_pending` photos already on Drive and in the CSV, returning shipped stills to the pool. The trade-off is a possible *silent missed booking*, so on a `False` the orchestrator writes a durable `.photo_ledger_unbooked.json` marker (`_mark_ledger_unbooked`, greppable `LEDGER-UNBOOKED`) that accumulates failed slots across runs; the next run's preflight (`warn_if_unbooked_marker`) surfaces it loudly so a missed booking can't quietly become a double-book. The marker write is itself best-effort — a write failure only logs, never raises over a shipped batch — and it is written atomically (`atomic_write_json`), so a crash mid-write leaves the previous marker intact rather than a truncated file that reads back as "nothing unbooked". A republish reuses the first publish's booked slots and re-books them: `ContentLedger.add` keys on `(date, time, content_type)`, so re-booking the same slots is a no-op refresh, and booking unconditionally is what lets a crash between the durable `published=True` save and the ledger write self-heal on the next run (the old `if not republish` guard made that window permanently unrecoverable). Theme usage (`_record_theme_usage`) stays gated on the first publish only — it increments the rotation counts that pick the next voice style, so re-recording on a republish would skew the rotation. The photo engine imports neither `content_ledger` nor `seo_manager` (`tests/test_media_boundary.py`): `PhotoOrchestrator` takes `ledger_booker(rows) -> bool`, `voice_source() -> VoiceStyle` and `theme_recorder(voice, week)` as constructor callables, and `gomoveshift/publishing/photo_run_hooks.py` supplies them (`PhotoOrchestrator(..., **photo_run_hooks())`, wired by the `photos` CLI handler). With no `ledger_booker` wired a publish logs `LEDGER-BOOKING-FAILED` and writes the unbooked marker, exactly as a missed booking does; with no `voice_source` the voice is `FIRST_PERSON`, and with no `theme_recorder` usage is simply not recorded.

**Cleanup** (`PhotoCleanup.plan_cleanup`, dry-run by default) deletes caption YAML, CSVs, resized copies and manifests older than `min_age_days`, but **skips any batch that has not demonstrably published**: a caption file is dropped only when it is both `reviewed: true` *and* has a matching `photo_metricool_<week>.csv`. Reviewed is not published — photos are marked posted at selection, so deleting a never-published batch loses that photo set unrecoverably. A Drive manifest (`photo_gdrive_manifest.json`) honors the `completed: true` gate on **every** deletion path — the resized-dir sweep excludes it rather than deleting it on the CSV gate alone, since an incomplete manifest is the resume record for an in-progress upload. `PhotoOrchestrator.cleanup` runs the whole discover→plan→execute pass under the photo-run lock, so a cleanup can never race a live generate/publish over the artifacts that run is producing. `--week` is validated at argparse as a strict zero-padded `YYYY-MM-DD` — it is used verbatim as a path component (captions YAML, resized dir, CSV name), so a traversal value would otherwise write outside the photo output tree.

**Develop fingerprint coverage.** `DEVELOP_ALGO_VERSION` is stamped into every developed photo's `.grade.json` as provenance, so it has to cover everything that moves those pixels — not only `develop.py`'s own decode/grade/spatial functions. `_develop_algo_inputs` therefore also hashes the composers (`_spatial_chain`, `_layered`, `_look_params`, `look_variant_options` — chain ORDER and masked-layer compositing move pixels as surely as a stage body does), `masks.py` as a **whole module** (its luma windows are lambdas inside `MASKS` that no namespace sweep can reach, so a mask added later is covered with nothing to remember), and the ALL_CAPS sweep over `masks` and `looks` — which pulls in the mask window/geometry constants and `BUILTIN_LOOKS`, read live and serialized with **sorted** keys so a retuned recipe changes the fingerprint while a mere reordering does not. `masks` and `looks` are imported inside the function, like `bracket`: this runs while `develop` is still importing, and `masks` imports back from `develop` inside its own functions to dodge that cycle. Without this, retuning `LUMA_EDGES`, the feather math or a shipped recipe changed masked-look pixels while both renders stamped an identical fingerprint.

**Develop cache key — every input that moves a pixel, or it is not a key.** `develop_cache_key` (still deliberately unwired, still stamped into every `.grade.json` as provenance) originally hashed the source file, the decoder identity, `DEVELOP_ALGO_VERSION` and `CorrectionParams` — but `CorrectionParams` is only the *colour* chain, so every knob `DevelopOptions` carries and `CorrectionParams` does not (`vignette`, `clarity`, `grain`, `layers`, the LUT levers, …), the render `depth`, and the cube a LUT look rendered through all changed the pixels without changing the key: a vignetted frame and a clean one of one photo stamped the SAME key, and every LUT variant is stamped with the shared under-grade's params, so two different `.cube` files collided outright. The key now carries the whole live `DevelopOptions` record (read off the dataclass by `astuple`, so tomorrow's knob is keyed the moment the field exists — no hand-kept list to forget), `depth=` (8 and 16 quantize one grade to different pixels), and the LUT surface as **name plus a hash of the cube's own table** (a name alone is not identity: two packs ship a `portra400`, and cubes get re-exported in place). `options` and `depth` are **required keyword arguments**, not defaults — a caller cannot silently key a spatial render as if it were the clean one — and the cube is taken from the same resolved `luts` the render used, never re-read from disk. The blank-`decoder` hard fail is unchanged. Fixed *before* a consumer exists, which is the only cheap time: a cache wired on the old key would have replayed one variant's pixels as another's.

**A look's LIST knobs are gated at the door, through one table** (`config.check_look_lists`, `LOOK_LIST_RANGES` + `LOOK_CURVE_KNOBS`). `LOOK_RANGES` covers scalars only, so every list a look or a masked `layers:` entry can carry — whatever those two tables name, derived from the `items`/`curve` columns of `PHOTO_KNOBS` rather than listed here — used to reach the render unchecked and raise inside `CorrectionParams.__post_init__`, once per photo, mid-batch, after a batch of decodes had already been paid for; and `__post_init__` checks lengths and curve-x ordering only, never a range. The shapes and bounds mirror the `photos develop` flag gates (`_resolve_hue_band` / `_resolve_tint` / `_resolve_mono` / `_resolve_curve`) as literals — no `config.py` validator may import the pipeline, for the reason `LOOK_KNOBS` documents. All three doors route through the one function: config load (naming the look), `check_layers` (naming the look *and* the layer's mask), and `--look-variant`, which previously had no range gate at all, so the same configured look `--look` refused rendered happily through the variant flag. Empty stays OFF everywhere, and no value's legality changed — only where it is refused.

**Masked layers move TONE, not only colour (`LAYER_TONE_KNOBS`).** A layer may carry `gamma`, `black_point`, `contrast_curve` and `saturation_mult` beside its colour knobs — the local move a mask exists for (lift the shadows under `shadows`, steepen the sky under `sky`), which `layers` could not express while its knob set was colour-only. They are set on the layer's `CorrectionParams` **directly** in `_layered` rather than routed through `DevelopOptions`: `_look_params` derives a layer's colour chain from the field names the two records SHARE, and no tone knob is one, so that round trip drops such a knob *silently* and renders nothing — the second, invisible block that made this more than a gate-lifting edit, pinned in `test_a_tone_knob_cannot_ride_the_colour_round_trip_that_carries_the_rest`. `dataclasses.replace` refuses a name that is no `CorrectionParams` field, so a tone knob that could not render cannot be added here unnoticed, and one home (`config.LAYER_TONE_KNOBS`) feeds both the door and the applier so the two cannot drift. Every bound in `LOOK_RANGES` is read off the applier that renders it — `GAMMA_MAX` and its reciprocal, so darkening has the authority brightening has (`GAMMA_MAX` in `color_correction.py`); `_apply_curves`' `BLACK_POINT_MIN/MAX` clamp, past which a value renders as the edge and lies about what it did (`BLACK_POINT_MIN`/`BLACK_POINT_MAX` in `color_correction.py`); the S-curve's documented span and its `c > 0.001` gate, which is why a NEGATIVE `contrast_curve` is refused rather than silently inert (the S-curve code in `color_correction.py`); and `_apply_saturation`'s chroma scale around luma, where a negative multiplier inverts hue instead of draining it (`_apply_saturation`) — so a value the door accepts is a value that moves the picture, refused at config LOAD naming the look instead of clamped mid-batch. Photo-only by construction: `_layered` is called from `develop_variants` alone (its call sites in `develop.py`), which no video path reaches. Spatial stages stay whole-frame, unchanged — a vignette that stopped at a horizon is still a bug.
**Negative clarity — the softening direction.** `_clarity_gain`'s formula (`1 + amount · midtone · detail / luma`, clipped to `[1/CLARITY_MAX_GAIN, CLARITY_MAX_GAIN]`) has always been symmetric in `amount`: a negative one subtracts the same width-scaled high-pass response instead of adding it, flattening the frame's own broad structure — the texture-softening move (skin, portraits) — with the same midtone weighting and the same highlight/shadow protection. Only the gate was one-sided: `_clarity` early-returned on `amount <= 0`, so negative clarity was structurally a no-op and the glow bloom was the chain's only softening path. The gate now short-circuits on **exactly** `0.0` (the byte-identical no-op is load-bearing and unchanged), and the range widens to −1..1 at all three doors that mirror each other — the `--clarity` argparse gate, `PhotosConfig.clarity`, and `LOOK_RANGES["clarity"]`, which is what lets a look preset carry a softening value. The two softening paths are different looks, not redundant: `--glow` screens diffused light *over* the frame, negative clarity adds no light at all.
**`glints` — the SMALL bright regions, and per-layer mask shape (`masks.py`).** Every other tonal mask is a per-pixel test, so on a landscape whose bright region IS the sky, `highlights` covers a third of the picture and `neon_edge` reads as a magenta sky rather than as signage (measured on a sample landscape; softening the amplitude only traded the look away — halved, it scored 3.03 rendered distinctness against the 5.0 floor). `glints` groups the highlight window's pixels into connected regions first (`connectedComponentsWithStats` on the bounded `MASK_MEASURE_MAX_DIM` view) and fades out any region covering more than `max_area` of the frame, reaching zero at `GLINT_AREA_ROLLOFF`× that — a size ramp, not a cliff at one area — then softens the surviving regions by `GLINT_EDGE_FRACTION` of the short edge and multiplies the highlight weight back in. Region areas and the softening radius are both FRACTIONS metered on the bounded view, so "small" means the same share of the picture at 1200 px and at 5600 px, and the four registry properties (deterministic, feathered, resolution-anchored, range-closed) hold as for every other name. A layer now also carries **the shape params of the mask it names** — `_layered` forwards them to `mask_for`, `MASK_PARAMS` derives the legal set from each mask function's keyword-only signature (nothing hand-kept), and `check_layers` validates a layer's extra keys against the params of that mask specifically, so `angle` (real, for `linear`) on `sky` is refused at config LOAD instead of riding along inert; `LAYER_MASK_PARAMS` mirrors the derived table under the same sync test as `LAYER_MASKS`. `neon_edge` is deliberately NOT retuned onto `glints` here — that recalibration is its own change, the note at the end of this section.
**Look strength (`--look-strength`, `look_strength:` in a recipe)** dials a `--look-variant` panel between the run's own base render and the whole look: `out = base + s * (look - base)`, the same lerp `--lut-strength` lays over a cube and `_layered` lays through a mask. It blends RENDERED pixels, not knobs, because a look is a colour chain *and* its spatial stages — no per-knob scaling halves a grain field and a vignette together (hand-halving one recipe's curve amplitude is how `neon_edge` fell to 3.03 rendered distinctness against a 5.0 floor). The dial is a per-look `DevelopOptions` field, so `--look-strength` is only the run-level default and a recipe's own value wins; range `[0, 1]` is gated at the CLI door and at config load. 1.0 (the default) is byte-identical to the shipped path **by construction**: the blend is skipped entirely, and the base render — the natural grade through the run's own `_layered`/`_spatial_chain` — is computed lazily and at most once per photo, only when some panel asks for less than the whole look.
**Mask combinators (`mask_op`).** A layer may name TWO masks and one operator (`{mask: [highlights, radial], mask_op: intersect, ...}`) instead of a single name, because a scene's real region is often narrower than any registry entry: `highlights` is every pixel above 2/3 luma, which on a landscape covers a third of the sky, while "the highlights INSIDE the centre" is the signage `neon_edge` wants. The three ops are array algebra on the [0, 1] weights — `intersect` = product, `union` = elementwise maximum, `subtract` = `a * (1 - b)` — so each stays range-closed by construction. **Order is pinned** (`mask_for`'s docstring and a test): the RAW pair combines first, THEN `feather`, THEN `invert`, so there is exactly one transition band to soften — the combination's own — and both knobs mean on a pair what they already mean on one mask. Two operands and one operator only: three would want precedence rules, and this is a config file, not an expression language. `check_layers` refuses a list without a `mask_op`, an unknown op, a 1- or 3-element list and a `mask_op` on a string mask at config LOAD and at the `--layers` door, upstream of any decode; `LAYER_MASK_OPS` mirrors `masks.MASK_OPS` under the same sync test as `LAYER_MASKS`. A string `mask` is untouched by the seam — no op, no pair — which is what every shipped look still rides.
**Split-toned black & white** (`_apply_monomix` runs BEFORE `_apply_splittone` in `photos/develop._grade`): the mono conversion writes *every* pixel — a grey, or a point on the `duotone` ramp — so a split-tone applied ahead of it was wiped, and split-toned monochrome (selenium shadows over a red-filter B&W, the most standard darkroom move there is) could not be expressed at all. The mixer now runs first of the colour-look stages and the tone lands ON the grey frame. Invisible to everything shipped: `mono_mix`/`duotone` are empty on every built-in look and every style (`mono` desaturates through `saturation_mult`; it sets no mono control), and both appliers stay excluded from `params_to_lut3d_cube`, so video output and baked LUTs are byte-identical. Two knobs land with it — `--duotone-strength` (0..1, default 1.0 = the shipped hard ramp) lerps the toned result back toward plain monochrome, the lever a duotone lacked when it resolved a whole landscape to one magenta; `--duotone-mid` adds a third anchor at mid luma (a tritone), refused without `--duotone`, where it would render as nothing. One interaction to know: the mixer now sits ahead of saturation/vibrance/HSL, so a style that zeroes chroma (`mono`) flattens a duotone under it exactly as it already flattened a split-tone — pair the mono controls with a colour style (`--styles natural`) instead.
**Green-magenta white balance** (`--white-balance-g`, `white_balance_g` / `white_balance_g_high`) is the other half of what white balance means to a photographer, and the axis a fluorescent or forest-canopy cast lives on: `_apply_colorbalance` used to loop over R and B only, leaving green inexpressible anywhere in the chain (split-tone is luma-keyed, HSL is hue-keyed, neither is a white-balance move). Green is now the loop's third channel, tone-weighted by the same shadow+midtone / highlight ramps its r/b siblings ride, so one signed number in [-0.5, 0.5] takes the frame green (positive) or magenta (negative). It is photo-develop only **by construction**: `compute_correction` never sets either field in either mode, so on every video params they hold their `0.0` default, the neutrality guard still early-returns, the encoder's ffmpeg mirror still pins `gs`/`gm`/`gh` at 0, and `params_to_lut3d_cube` bakes byte-identical cubes (pinned by a hash in `tests/test_photo_wb_green.py`). The `DevelopOptions` field is named **exactly** as its `CorrectionParams` twin, so `_look_params` — which derives the colour chain from the field names the two records share — carries it into look panels with no hand-kept list (a masked `layers:` entry cannot name it yet — `LAYER_KNOBS` is deliberately untouched here); `plan_variants` `replace`s it onto every styled variant and never onto `base`, so a `--lut` film emulation keeps the film's white balance. The CLI door range-gates it before any decode and `LOOK_RANGES` gates a look's value at config load.
**Orange, the seventh HSL anchor.** The band a travel photographer reaches for most — skin, and the sunset/golden-hour range around 20–40° — had no anchor of its own, so moving it meant dragging red and yellow together and taking the whole warm end with them. `hue_shift`/`hue_sat`/`hue_lum` therefore accept **six values or seven**: seven inserts orange at 30° in second place (red, orange, yellow, green, cyan, blue, magenta). The two arities are **not** the same curve — each length carries its own anchor array, and a six-slot control interpolates against exactly the pre-orange anchors, so every shipped `BUILTIN_LOOKS` recipe (all six-slot, none retuned here) renders bit-identically; splicing a neutral orange into a six-list would have re-interpolated and moved their pixels. The arity gate moved out of argparse `nargs` (which cannot say "6 or 7") into `_resolve_hue_band`, still upstream of any decode, and `CorrectionParams.__post_init__` plus the `PhotosConfig` validator accept both lengths and name both in the refusal. The three controls are independent — one may be six slots while another is seven — and `_apply_hsl` stays excluded from `params_to_lut3d_cube`, so video output and baked LUTs are untouched.
**Split-toning tints three tonal ranges, not two** (`_apply_splittone`, `--split-tone-shadow` / `--split-tone-midtone` / `--split-tone-highlight`). The applier's two luma ramps used to meet at 0.5 — the shadow weight fading from 1 at black to 0 by mid-luma, the highlight weight its mirror — which left the midtones at weight 0 on both, so the range where a photograph's tone actually sits (this grade chain peaks near 0.66 luma and never clips) could not be tinted at all. `splittone_midtone` adds the tent that slots exactly into that gap, `clip(1 - |2L - 1|, 0, 1)`: 0 at black, 1 at mid-luma, 0 at white. The three weights now **partition** the range — they sum to 1 at every luma, so the ranges hand off with no seam and never double-count where the ramps overlap. Each tint is empty (OFF) or a signed length-3 (r,g,b) push validated at the config door and at the CLI door (`_resolve_tint`, range -0.5..0.5), reachable from a look (`split_tone_midtone`) and from a masked layer like its two siblings. All-empty stays a bit-identical no-op via the early return, and the applier remains deliberately outside `params_to_lut3d_cube`, so video output and baked LUTs are untouched.
**Grain particle size** (`--grain-size` / `photos.grain_size`, range 0.25..4, **1.0 by default**) is the other half of a film stock: `--grain` says how MUCH silver, this says how COARSE each speck is, so a fine 100-ISO grain and a chunky pushed-Tri-X grain stop being one knob. It is a RATIO on `_grain_field`'s reference grid and nothing else — the grid becomes `GRAIN_REFERENCE_DIM / grain_size`, *inversely*, because a coarser particle means FEWER of them across one negative — so every property above survives it: the fixed `GRAIN_SEED` (deterministic), a grid still derived from the frame's own dimensions (one value, one look at any export size), and the variance renormalisation that keeps `GRAIN_SIGMA_SCALE` meaning one 8-bit sigma. 1.0 is the shipped grid byte-for-byte, on both the resampled path and the cheap per-pixel draw a frame at or under the reference takes; the bounds are reasoned about in `config.LOOK_RANGES` (below 0.25 the grid outgrows every realistic export and the resolution independence dissolves; above 4.0 one speck spans ~19 px of a 5600 px export and reads as mottling).
**Master tone curve (`--curve-l` / `photos.curve_l` / a look's or a masked layer's `curve_l`).** The operator could draw a curve per *channel* (`curve_r`/`curve_g`/`curve_b`) but the *master* tone shape was only ever the fixed four-knot parametric skeleton `_apply_curves` builds from `shadow_lift`/`highlight_pull`/`contrast_curve` — knots at x = 0, 0.25, 0.75, 1.0 and nothing else. Proof the feature was missing: the matte fade presets hand-roll a master by duplicating ONE knot list onto all three channel curves. `curve_l` is that move as a first-class field — empty (OFF) or the same flat `x y x y …` control-point form the channel curves take (even length ≥ 4, x strictly ascending in [0, 1]), evaluated through the same Fritsch-Carlson monotone interpolant (`_monotone_cubic_interp`) and applied identically to R, G and B by `_apply_luma_curve`, so it shapes tone and **cannot introduce a colour cast, by construction**. It runs in `_grade` immediately AFTER the parametric `_apply_curves` and BEFORE `_apply_channel_curves`, so the cross-process per-channel curves keep riding on top of the master shape exactly as they ride on the skeleton — and, like them, it meets a real graded frame in roughly [0, 0.6] (before colorbalance/saturation/gamma), so knots shaped for the top decile are an identity on a real photograph. Gated at the door (handler `_resolve_curve` → `PhotosConfig` validator → `CorrectionParams.__post_init__`, the same three the channel curves pass), it `dataclasses.replace`s onto every styled variant but never `base`/`lut_params` — a film emulation stays the film's look — and is deliberately absent from `params_to_lut3d_cube`, like `_apply_hsl` and `_apply_channel_curves`, so **video output and every baked LUT stay bit-identical**. Empty is a bit-identical no-op via the applier's early `rgb.copy()`, and the applier is in `_HASHED_SOURCES`, so a retune self-invalidates the develop cache. The matte presets deliberately keep their three-channel form for now — switching them is a retune with rendered-output consequences, not a wiring change. Tests: `tests/test_photo_channel_curves.py`.
**Detail-riding mask — `texture` + the `subject_pop` look (`masks.py`, `looks.py`).** Every other named mask keys on tone (`shadows`/`midtones`/`highlights`/`sky`) or on position (`radial`/`linear`), so "where does the picture hold detail?" was unaskable — a busy hedge and the flat sky above it can sit at the identical brightness in the identical part of the frame. `texture` is the local standard deviation of luma (box mean of the square minus the square of the mean, `BORDER_REFLECT`), metered on the same `MASK_MEASURE_MAX_DIM` bounded view the tone masks use and with the neighbourhood expressed as a FRACTION of that view's long edge (`TEXTURE_RADIUS`), so one name means one look at 1200 px and at 5600 px — `GRAIN_REFERENCE_DIM`'s lesson, and the view's INTER_AREA downscale is also what stops sensor grain from reading as detail. The spread is normalized against the frame's OWN high percentile (`TEXTURE_REFERENCE_PERCENTILE`, not its max — one hot pixel must not set the scale) and smoothstepped between `TEXTURE_EDGES`, so "textured" means the same thing on a busy frame and a quiet one; a frame whose spread falls under `TEXTURE_MIN_SPREAD` holds no detail to find (a wall, a whiteout) and selects nothing rather than magnifying its own floor — the same fallback `LUMA_MIN_SPAN` makes for the tone windows. `subject_pop` is the look built on it: the smooth surround (the mask inverted) drained, cooled and flattened toward a haze, the detailed region given contrast around where this chain's tones actually sit plus a vibrance push. `tests/test_photo_masks.py` pins it on a frame whose two halves carry the SAME tonal ramp and differ only in detail, which is what rules out tone and position as the thing being measured; the resolution-anchoring fixture's ridgeline is phased on the frame's width rather than on a pixel count, since a pixel-phased sine is a *different* ridgeline at each size and a detail mask is the first thing to notice.
**One knob, one row (`config.PHOTO_KNOBS`).** A knob used to be declared in up to four places inside `config.py` — `LOOK_KNOBS`, `LOOK_RANGES`, `LOOK_LIST_RANGES`/`LOOK_CURVE_KNOBS`, `LAYER_COLOUR_KNOBS`/`LAYER_TONE_KNOBS` — and every one of them was a densely-packed literal, so several knobs added in parallel all appended to the same four LINES; git cannot merge two edits to one line, so parallel knob branches conflicted every time. Each knob is now one `Knob` row (`name`, `span` for a scalar gate, `items` for a list's length+bounds, `curve`, `look`, `layer`, `alt` for the `DevelopOptions` field argparse spells differently) and **every table above is a comprehension over that tuple** — the derive-don't-list move `masks.MASK_PARAMS` makes by reading each mask's accepted params off its signature, which is why mask additions never conflict while knob additions did. Two knob branches now touch different lines, and a row cannot be half-wired: claiming `layer="tone"` *is* membership in `LAYER_TONE_KNOBS`, there is no second append to forget. The registry is a **literal** and must stay one, for the import-cycle reason `LOOK_KNOBS` documents above — no `config.py` validator may import `gomoveshift.pipeline.*`. `tests/test_photo_knob_registry.py` holds the pre-registry tables as a snapshot (the proof no knob gained, lost or changed a range) and walks every row against every surface it claims. What the derived form made visible at a glance: `split_tone_midtone` and `curve_l` carried no list shape, so `check_look_lists` did not gate them in a look — preserved exactly as it was there, and closed in the note below.
**A look panel's sidecar records the LOOK's knobs, not the run's.** `develop_variants` renders each `--look-variant` panel through that look's own `DevelopOptions` (`look_variant_options` — the run's record with the look's knobs replaced on top), but the CLI handed `write_grade_sidecar` the run's record for every variant it exported. So a panel's `.grade.json` described knobs those pixels never saw, and — because `develop_cache_key` keys off the render options — two looks separated by a spatial knob alone (`grain: 0.2` vs `grain: 0.6`, identical colour chains, therefore identical `params`) stamped one options block and one cache key, reintroducing at the call site exactly what keying the whole `DevelopOptions` record fixed. The handler now keeps `look_options`, the same panel-name-keyed map `look_borders` already is, holding the record each panel actually rendered through; the export loop looks the panel's name up in it and falls back to the run's record, so styled and LUT variants record what they always did. One map, built where the look is resolved — the render and the record it claims cannot drift.
**Every list knob is gated at the door, not mid-batch (`config.PHOTO_KNOBS` rows → `check_look_lists`).** A list knob's shape lives in its registry ROW, and the row is what the gate reads — so four list-valued knobs that shipped *after* that gate existed each slipped it: `split_tone_midtone` and `curve_l` (the gap the registry made visible), plus `halation_tint` and `duotone_mid`, which never carried one. A row with no `items` and no `curve` is a knob `check_look_lists` skips outright, so a malformed value in a configured look passed config load *and* the CLI door and then raised inside `CorrectionParams.__post_init__` — once per photo, mid-batch, after the decodes had been paid for. Each row now declares the bounds that knob's own flag was already enforcing (`_resolve_tint` for the two tints, `_resolve_curve`'s flat `x y x y …` form for `curve_l`, `_resolve_mono`'s three values in [0, 1] for `duotone_mid`), so the two doors agree and **no value's legality changed — only where it is refused**. Pure data: four rows, no new validation code. The guard that stops the next one is the real deliverable — `tests/test_photo_knob_registry.py` reads each knob's own `PhotosConfig` default and fails any `list[float]` knob whose row declares no shape, so a list knob cannot slip the gate this way again.
**The sky mask gains a saturation lever (`--sky-saturate`, range 0..1, **off by default**).** `_sky_mask` renders a region, but only one effect could ride it: `_sky_darken`, the grad-filter half of the landscape move. The polariser half — a deeper blue in the sky and *only* the sky — was inexpressible, since `--vibrance` and `saturation_mult` are whole-frame and the masked `layers:` surface carries no chroma multiplier that keys on tone. `_sky_saturate` is that lever, and it shares the mask (portrait guard, contrast confidence, feathering, all inherited rather than re-derived) but deliberately **not** the `_apply_gain_mask` seam the mask's docstring promised it would: that seam applies a per-pixel SCALAR gain, and scaling all three channels of a pixel by one factor moves chroma and luma together and leaves `(max−min)/max` exactly where it was — a gain provably **cannot** saturate. Saturation is a lerp away from the pixel's own luma, so the stage takes the masked-lerp shape `_dehaze`/`_halation` already use, and it is written as an ADDED chroma term (`rgb + amount·SKY_SATURATE_MAX·mask·(rgb − luma)`) rather than the algebraically equal `luma + mult·(rgb − luma)`: where the mask is 0 the term is exactly `0.0`, so **the ground keeps its bytes by construction** — the same guarantee an all-ones gain buys on the seam, on a different shape — and the sky's TONE is preserved for the same reason the term is chroma-only. It runs immediately after `_sky_darken` and, with it, before `_vignette`: the same subject-region edit, grading the chroma of the sky the darkener has already placed. `--sky-saturate 0` early-returns byte-identically, it is range-gated at the CLI door before any decode, and — as `--white-balance-g` and `--layers` are — it is a **flag/look knob with no `photos.*` default**, so a look names it (one `PHOTO_KNOBS` row gates the value at config load) and nothing else changes. `SKY_SATURATE_MAX` sits far under the grade chain's own 2.0 chroma cap: a doubled sky reads as a poster, not a polariser.
**A recorded grade can be REPLAYED (`photos develop --from-grade PATH.grade.json`).** The sidecar round trip shipped half-connected: `write_grade_sidecar` reached the CLI, `correction_params_from_sidecar` parsed a payload straight back into a `CorrectionParams` — and nothing in the service ever called it, so the pipeline emitted a perfectly re-loadable grade it could never load. `--from-grade` is the read half: `plan_variants` takes a recorded `(variant, params)` pair *in place of* the measured style, so the frame renders the numbers that were approved rather than what this photo happens to meter. That is what lets an approved JPEG proof re-render as a `--format tiff16` master, and one photo's grade transfer to the siblings shot in the same light. **The whole record is restored, spatial knobs included** (`develop_options_from_sidecar`, the `DevelopOptions` twin of the params parser) — a replay that kept only the colour chain would drop the vignette and the grain the operator actually approved and hand back different pixels in silence; `tests/test_photo_grade_replay.py` pins the round trip **byte-for-byte**. `base` is still measured from the frame being rendered, because it is the denoise budget, not the colour chain. Precedence is the one `_apply_look` already establishes — an explicitly passed flag is non-`None` and BEATS the file, everything unsaid comes off it — and the field→flag-dest map is `config.LOOK_ALIASES`, read off the knob registry so a knob renamed there cannot silently stop being replayable. Exactly ONE variant renders, under its recorded name; `--lut`/`--lut-auto`/`--look-variant` alongside are refused rather than rendered off the measured base. The version pair in `provenance` is finally READ: a sidecar stamped with another `sidecar_version` or `DEVELOP_ALGO_VERSION` is **refused, not warned past** — another algorithm version cannot replay to the pixels that proof was approved on, and the sidecar is one develop away from being rewritten. That refusal, and every malformed/foreign-JSON refusal, happens at the door in `_load_grade_sidecar`, before a single photo is decoded.
**A row declares the length(s) its flag accepts, not one exact length (`Knob.items` → `Knob.lengths`).** `items` used to be `(exact length, lo, hi)` and `check_look_lists` tested `len(vals) != want`, a type that cannot say "6 **or** 7" — so when orange shipped as the seventh HSL anchor, `--hue-sat` took seven values, `photos.hue_sat` took seven, `CorrectionParams` rendered seven, and every *look* door refused them: `photos.looks` at config load, a masked `layers:` entry through `check_layers`, and `--look-variant`, all three routing through the one registry row. No built-in look could be retuned onto the anchor, and the `_CINEMATIC` pack's comment described a seven-slot recipe the door would not accept. A row's first `items` slot is now a bare int **or** a tuple of accepted lengths (`((6, 7), 0.0, 5.0)`), normalized once by the `Knob.lengths` property so every door tests membership instead of equality and the refusal names both (`hue_sat needs 6 or 7 values, got 8`). Nothing else moved: seven other list knobs keep their bare int and their exact-length semantics, and no value's legality changed but the two the flag already took. The guard is again the real deliverable — `test_each_list_knobs_shape_is_derived_from_the_flag_that_gates_it` walks the `_resolve_*` call sites in `cli/handlers/photos.py` with `ast`, takes each flag's bounds from the call and **probes its resolver** for the lengths it accepts, then asserts the registry row matches; no length or bound in that test is transcribed, so the door and the flag cannot drift apart again (the `masks.MASK_PARAMS` / `_HASHED_SOURCES` derive-don't-list move). It fails on exactly this bug when run against the old row. No built-in look is retuned onto orange here — that is a taste call; this only makes it expressible.
**`neon_edge` tints the signage, not the sky (`looks.py`).** The recalibration the `glints` note above deferred: the look now names `glints` instead of `highlights`, and **the mask choice is the whole recipe**. On the pack's signage landscape `highlights` weighs 0.48 of the frame and a full 1.0 on the lit sky — 25% of that frame — which the shipped look moved by 21 8-bit levels, i.e. it graded the sky magenta; `glints` weighs 0.15 of the frame and **exactly 0.0** on that same sky, which is now left byte-identical rather than gated back to plausible afterwards. `max_area` is left at the registry default deliberately: a sign there is 1.4% of the frame against that sky region's 25%, so neither is within reach of the calibrated 2% limit and a per-look override would be a second, unmeasured opinion. Two things had to be re-swept with it, and the mask swap alone measured **3.93** whole-frame rendered distinctness against the 5.0 floor — no longer a look at all — where the recalibrated recipe measures **6.38**. First, the curves became a **plateau** (deviation held flat from 0.35 to 0.75) rather than one knot at 0.5 decaying to nothing by 1.0: a glint is the top of the frame's OWN span and lands at a different absolute code on every photograph (0.50 and 0.70 on two cuts of one fixture), so a curve keyed to one tone is a look on one frame and half a look on the next — the same lesson the pack already carries about split-tones, now applied to its own knots. Flat, it measures 39.1 / 39.4 / 41.3 levels inside the region across that range. Second, the amplitude went UP (+0.11/−0.11/+0.13 from +0.08/−0.07/+0.10) — it can afford to shout on a region a twentieth of the old one precisely because it can no longer reach the sky. The pack fixture grew the signage it never had (twelve lit blocks, 1.4% of the frame each, all below the half line so `golden_ground`'s untouched top half stays exact, and deliberately a little DIMMER than the sky so the split under test is size and never brightness), because a landscape whose only bright region IS the sky is the frame this look must leave alone.
**A look may not name the LUT (`Knob("lut", look=False, run=True)`).** `--lut` is an APPEND flag, so its dest holds `None` or a LIST of specs, while `_apply_look` fills each unset dest with the look's raw value — so `photos.looks.vintage.lut: portra` loaded clean, wrote a bare STRING into that dest, and `_resolve_luts` iterated it: the operator got a LUT-resolution failure naming the single letter `p`, with nothing pointing at the look. The LUT selection is the RUN's, exactly as `LOOK_VARIANT_RUN_KNOBS` already reserves `lut_strength`/`lut_over`/`lut_auto`/`reference_lab` from one look-variant panel, so the row now declares `run=True` and `LOOK_RUN_KNOBS` refuses it at config LOAD naming the look and the flag — a real flag refused by name, never as an "unknown knob". Its three siblings stay look-able on purpose: each is a SCALAR with its own `photos.<knob>` default, so a look setting one is just another config layer over whatever the run selected. Bundling a cube INTO a look is a real, deliberately deferred feature (resolve the cube at the door, carry it in a panel-keyed map, apply it between the grade and the spatial chain); this closes the corruption, and `tests/test_photo_look_validation.py` pins the class rather than the instance — no look knob may be an append flag's dest.
**Every white-balance axis has a door, and the operator's value ADDS to the measured one** (`--white-balance-r` / `-b` / `-r-high` / `-b-high` / `-g-high`; as look keys, `white_balance_r`, `white_balance_b`, `white_balance_r_high` and `white_balance_b_high`, beside the `white_balance_g` / `white_balance_g_high` pair the green axis already documents above). `_apply_colorbalance` renders six white-balance fields and exactly one of them (`white_balance_g`) had a flag, a look key and a `DevelopOptions` field — so the whole blue-amber **temperature** axis, the first slider in every comparable tool, was settable from nothing at all. The only way to reach it was to surrender the style choice to `daylight`/`cloudy`/`shade`, three fixed steps (`WB_DAYLIGHT_SHIFT`, `WB_CLOUDY_SHIFT`, `WB_SHADE_SHIFT` in `styles.py`, −0.02/+0.03/+0.06) that also cost the operator `moody`/`golden`/`matte_*`; the evidence it bit is that `cinestill` ("tungsten stock in daylight") and `leaked_film` fake temperature with split-tone pairs instead. The applier needed no change — its loop and its neutrality guard already iterate all three channels — so this is doors only: five `DevelopOptions` fields named **exactly** as their `CorrectionParams` twins (so `_look_params`' shared-name derivation carries them into look panels for free), five `PHOTO_KNOBS` rows, and five `photos develop` flags built from one table. Two things make them unlike the green axis. **They are ADDITIVE, not a replace**: `compute_correction` measures the cast and writes r/b on every photo base (a warm-ground fixture meters `white_balance_r=0.0094`, `white_balance_b=-0.05`, the latter pinned at `CAST_CORRECTABLE_MAX`), so `replace` would silently discard the auto white balance — asking for +0.03 of warmth must mean "the measured cast plus 0.03". `_wb_shifted` adds instead, in `plan_variants` *and* inside `_look_params`, and green rides the same rule because `+` and `=` are the same number on a field no producer sets. **The span is derived, not copied from green's ±0.5**: the operator value lands AFTER `_styled`/`_amplified`, so the style rails never see it and cannot clamp it — `WB_OPERATOR_SPAN` is therefore `WB_HARD_CAP − STYLE_WB_CAP` (`styles.py`) = 0.10, the travel between where the rails hold a style at the shipped x1 strength and the renderer authority that binds at every strength, so a style at its rail plus full operator travel lands *on* that authority rather than past it — robust by construction instead of a late clamp that would lie about what it did. Green keeps ±0.5 because no measurement and no rail touches that channel. Video output is untouched by construction: `color_correction.py` is not edited, no video producer reads a `DevelopOptions`, and a baked cube still hashes to its pre-change digest (`tests/test_photo_wb_axes.py`). Like every colour knob these ride the styled variants and never `base`/`lut_params`, so a `--lut` film emulation keeps the film's white balance; `LAYER_KNOBS` stays untouched, as it did for green.

**Exposure, recovery and Kelvin/tint** (`--exposure-ev`, `--shadow-recovery`, `--highlight-recovery`, `--white-balance-kelvin`, `--white-balance-tint`; `DevelopOptions` fields `exposure_ev`, `shadow_recovery`, `highlight_recovery`, `white_balance_kelvin`, `white_balance_tint`) are range-gated at the CLI door before any decode and, like every colour knob, ride the styled variants only, never `base`/`lut_params`. Kelvin/tint fold into the additive r/b/g axes above. Mechanism: `128-develop-exposure-and-white-balance.md`.
**A mask that selects by COLOUR — `hue` (`masks.py`).** The registry could ask how bright a pixel is (`shadows`/`midtones`/`highlights`), where it sits (`radial`/`linear`), whether it is sky, how small its bright region is (`glints`) and how detailed it is (`texture`) — but never *which colour it is*, so "the foliage", "the actual blue of the sky rather than every bright pixel" and "the red car" were not expressible as regions at all; the chain's only hue-selective control, `_apply_hsl`, is whole-frame by construction. `hue` is a `width`-degree band of the colour wheel centred on `center`, smoothstepped over `HUE_EDGE_WIDTH` degrees straddling each edge. Hue is **angular**, so the distance is measured the short way round (`|((h − center + 180) mod 360) − 180|`) and a red band centred on 0° covers 350° and 10° alike instead of splitting at the seam — the obvious failure mode, pinned by `test_hue_wraps_across_the_seam_so_a_red_band_is_one_band`. A near-grey pixel *has* no colour to name (the angle derived at zero chroma is arbitrary), so a chroma gate fades it out below `min_chroma` and a grey frame selects **exactly nothing** — `texture`'s precedent, never magnifying its own floor. That gate meters the pixel's own saturation (chroma over its peak channel), a RATIO, so it means the same on a dark pixel and a bright one and needs none of the frame-relative span the luma windows do; and because the mask is per-pixel throughout — no statistic, no neighbourhood — it is resolution-anchored by construction. The RGB→hue derivation **matches `color_correction._apply_hsl`'s vectorised block exactly** rather than importing it: that block is welded inside the applier's own HSV round trip over an (N, 3) buffer, with no seam to call and no way to reach it from `masks.py` under the import-cycle rule. `MASK_OPS` composes it with everything already there for free — `{"mask": ["hue", "texture"], "mask_op": "intersect"}` is the detailed greens, `["hue", "shadows"]` the blue in the shadows — with no engine change. Two consequences to expect: `masks.py` is hashed as a whole module into `DEVELOP_ALGO_VERSION`, so this **bumps the develop fingerprint** (correct — a new mask changes what the module can render), and the `--layers` help text now **derives** its mask list from `config.LAYER_MASK_PARAMS` instead of hand-listing it, which is how `glints` and `texture` came to ship weeks apart with neither reachable from `--help`.
**A look panel renders the look, base style included (`look_styles` → `VariantPlan.look_bases`).** Seven built-in looks name their own base `styles` and author their colour knobs to ride *that* base — the `_ELECTRONIC` pack says so, and `tests/test_photo_electronic_pack.py` measures each preset against it. `look_variant_options` keeps only look keys that are `DevelopOptions` FIELDS, and `styles` is a `PHOTO_KNOBS` row but no field, so the contact-sheet surface silently dropped it and graded every panel from `plan.base`, the measured natural correction: `--look cyberpunk` rendered over `moody` while `--look-variant cyberpunk` rendered over the natural base — **two different pictures under one name**, on the one surface whose whole job is picking between candidates. The look's base style now travels in `look_styles`, the third panel-name-keyed map beside `look_borders` and `look_options` (a base style is no more a `DevelopOptions` field than a border is), and is APPLIED in `plan_variants` exactly as a styled variant's is — `apply_style(name, base, scene, strength)`, so the **run's** style lever scales it, the same lever `--lut-over` rides — onto `VariantPlan.look_bases`, which `develop_variants` looks each panel's name up in. A look naming no style is **absent from the map** and grades from `base` as before, so the fallback is bit-identity by construction rather than by a branch; nothing else moves, because the map is read at exactly one call site (`tests/test_photo_look_variants.py` pins the styled and LUT panels byte-identical when a styled look panel joins the run). One panel is one picture, so a look's `styles` must name exactly one KNOWN style — refused at the CLI door where the run's own `--styles` list is refused, not inside `apply_style` once per photo, mid-batch. The seven affected panels need a fresh eyeball proof sheet: their pixels move, on purpose.
**A dial no panel can apply is refused at the door (`--look-strength` on the `--look` path).** The dial exists on a `--look-variant` panel only, and the reason is structural: `look_variant_options` builds a panel's record from the RUN's, so the base render it lerps toward is well defined — the look changed nothing underneath it. `--look` is the opposite move. `_apply_look` FOLDS the recipe into the run's own knobs as a defaults layer, so afterwards nothing can say which knob the look set (an explicit `--vignette 0.6` and a look's `vignette: 0.6` are one value in one slot, and precedence says the explicit one wins), and five of the knobs a look may carry — `styles`, `style_strength`, `lut`, `border`, `format` — are no `DevelopOptions` field at all: they decide which panels exist and how they export, which no pixel lerp can halve. There is no look-free base render on that path, so the dial was accepted, range-gated, recorded into `DevelopOptions` and then read at exactly one place `--look` never reaches (`develop_variants`' `look_variants` loop): `photos develop --look cyberpunk --look-strength 0.5` exported **byte-identical** to `--look cyberpunk`, exit 0, no warning — the knob-that-reports-success-and-does-nothing that refusing at the door exists to prevent. It is refused at the CLI door now, pre-decode, naming `--look-variant NAME` as the way to dial that same look. The gate reads the RESOLVED value, so a recipe carrying its own `look_strength:` used through `--look` gets the identical answer — otherwise the lie moves rather than goes. 1.0 stays accepted everywhere: it asks for the whole look, which is what renders.
**Graduated ND (`--graduated-nd`, `--graduated-nd-angle`) is glass, not a region.** `_sky_darken` *finds* the sky and burns it; a grad ND finds nothing — it is smoked glass in a holder, dark at one edge and clear at the other, and the picture behind it decides what gets held down. So it rides `masks._linear`, the straight smoothstepped ramp already in the registry, at the shared `LINEAR_SPAN`, and turns it into a per-pixel gain on `_apply_gain_mask` exactly as the vignette and the sky burn do. **Direction is the whole failure mode** — `_linear`'s angle 0 ramps toward the RIGHT edge and 90 toward the BOTTOM (`golden_ground`'s ground glow), so a sky-holding grad is the *mirror* of the default, `GRAD_ND_ANGLE = -90`, and the operator's `--graduated-nd-angle` is a TILT off that level, not a raw mask angle (which also keeps `0.0` the neutral default every `DevelopOptions` field must have). The tilt is bounded at ±90 at the flag and at the look door, and that bound is the design, not a courtesy: at `-90 + t` the ramp's reach at the top of the frame is `cos t` and at the bottom `−cos t`, so for every legal tilt the top is darkened *at least* as much as the bottom — the grad swings from the sky through either side and **cannot be turned on the ground at all**, rather than being rendered wrong and caught by inspection. Only two knobs ship: the angle is what the physical object's holder is FOR (a sloping horizon is the common landscape frame, and a fixed-vertical ramp darkens the wrong wedge of it), while a `span` knob's only new capability is the hard-edge grad — a visible seam across the picture, which is the one thing the soft default exists to prevent. Chain position is **after `_sky_darken` and immediately before `_vignette`**: pulling the sky down is a darkroom edit of a subject region, but a filter sits in FRONT of the lens, so it belongs with the optics, ahead of the lens's own corner falloff — and, metering nothing itself, it can never perturb the sky mask that was measured before it. `--graduated-nd 0` early-returns the input at *every* angle, and where the ramp is zero the gain is exactly 1.0, which `_apply_gain_mask` multiplies exactly, so the untouched half of the frame comes back byte-identical **by construction** (a test asserts the lower half code for code). Range-gated at the CLI door and at config load through its `PHOTO_KNOBS` rows before any decode; `_graduated_nd` is in `_HASHED_SOURCES` and `GRAD_ND_MAX`/`GRAD_ND_ANGLE` are ALL_CAPS floats, so a retune self-invalidates the develop cache instead of restamping one fingerprint on two renders. There is no `photos.graduated_nd` config default — like `--white-balance-g` it is a flag/look knob, so a recipe carries it and the run does not have to. Tests: `tests/test_photo_graduated_nd.py`.
**The distinctness backfill can reach every style, not six of eleven (`select_styles`).** `_distinct_styled` asks for `select_styles(scene, count=len(STYLES))` — "give me the whole ladder to back-fill from" — but the selector ranked the `_FAVORED` table only, so it handed back **six of the eleven registered styles**. When four or more of those six collapsed under `MIN_RENDERED_DISTINCTNESS` the walk ran out, warned *"Distinctness backfill exhausted … falling back to the top-ranked … despite near-identical params"* and shipped near-duplicate variants — while the matte pair and the WB trio, five legal calibrated looks that differ STRUCTURALLY from the ranked six (two shaped tone curves and three white-balance steps), were never considered at all. The list now continues past the ranked styles into an **opt-in TAIL**: every registered style no predicate ranks, in `STYLES` declaration order. The tail is APPENDED, never scored into the ranking, so ranked selection is bit-identical **by construction** — every count up to the six ranked names returns exactly what it returned before, including the pinned trios and a penalized or suppressed `vivid` holding rank 6 (scoring the tail at `SCORE_BASE` instead would have sunk a suppressed `vivid` below it — a taste change to three pinned baselines, not this bug). Opt-in still means opt-in for PREFERENCE: nothing here can be auto-*selected* over a ranked style, the group is reachable only after the ranking is exhausted, and the two-tier distinctness guard still judges each tail candidate on rendered pixels like any other.
**The journey lock is mutual, not one-sided (`journal_publisher.journey_lock`).** A journey markdown file has four writers — the photo ingest (`photos/ingest.py`), the drive run's auto-publish merge and its `--replay-pending` cron (`cli/handlers/publish_journal.py`), and the channel reconciler (`site_sync/journey_reconcile.py`) — and each does its own load → mutate → atomic-write, so whoever serializes second writes back a doc that never saw the other's inserts. The ingest already held a `<journey>.md.lock` flock sidecar, but nobody else took it, so it only excluded a second ingest: a drive merge landing mid-ingest still clobbered the photos just registered. The lock now lives beside `load_journey`/`serialize_journey` (one implementation, the orchestrator's stale-PID recovery reused) and **every** writer holds it across its whole window. Failure semantics differ by what the caller has already spent: ingest raises `PhotoIngestError` (nothing irreversible has happened — no decode, no export, so refuse and re-run), while the three drive-side writers pass `skip_if_busy=True` and warn loudly then skip — `run_publish_journal` exits 1 with the retry line the drive hook already surfaces, the replay cron keeps that journey's entries pending rather than consuming what it never wrote, and the reconciler records a `ReconcileResult` warning and re-embeds on the next periodic sync. That asymmetry is the contract: the merge never fails a batch whose uploads are irreversible, and never skips silently.

**A bracket must have gathered different LIGHT, not just a different shutter (`bracket.detect_brackets`).** With `fuse_bracket` wired, a mis-grouped run is silently merged pixels: a depth-of-field sweep — stopping down in aperture priority — steps the shutter in ONE direction at held ISO seconds apart, the entire bracket signature, while the aperture gives back exactly what the shutter took, so the frames differ in focus depth and not at all in exposure. Mertens then blends three depths of field to buy no range. So a closed run is also measured on total light, `exposure_s / f_number²`, which must span `MIN_STEP_RATIO` — the same threshold, no new knob. Aperture is read by `extract_exif_aperture` (EXIF `FNumber`), a bracket-only reader deliberately kept OFF `PhotoExif`: nothing in scene profiling meters aperture. The rule is *not* "aperture held constant", which was the obvious fix and is wrong on real sequences — one hand-stepped bracket opens from **f/9 to f/5.3** while the shutter shortens 2.3 stops, so an equality test would refuse the one real bracket the pipeline has; what survives there is 0.8 EV of genuine range (light span 1.76x), and that is what the test measures. A run where any frame lacks `FNumber` skips the check and groups exactly as before the tag was read. Because `bracket`'s rule and constants are hashed into `DEVELOP_ALGO_VERSION`, this **changes the fingerprint and invalidates cached develops** — correct, and the reason the hash exists: which frames merge is which pixels ship.

**A local adjustment can sit on the subject, not only in the middle (`radial`'s `cx`/`cy`/`size`/`aspect`, `linear`'s `offset`).** `radial` declared no shape params at all, so it was the vignette falloff and only that — 1 dead centre, 0 at the corners — and `linear`'s ramp always topped out AT the frame edge, so between them a masked layer could brighten the middle or run in from a side and nothing else: "warm the subject" was expressible only when the subject happened to stand centre-frame. `radial` now takes a centre (`cx`/`cy`, fractions of the frame, `0.5, 0.5` = the middle), a `size` in multiples of the shipped falloff's own reach, and an `aspect` that stretches the oval across (>1) or down (<1); `linear` takes an `offset` saying how far in from the near edge its ramp tops out, so a gradient can hold a plateau inside the picture. Every value is a **fraction or a ratio, never a pixel** — the registry's resolution-anchored invariant, so one recipe names one oval at 1200 px and at 5600 px (pinned across a 4× pixel count) — and every transition stays the same smoothstep/vignette curve, never a 0/1 cliff. Both are keyword-only, so `MASK_PARAMS` picks them up off the signature with nothing hand-listed, exactly as `angle`/`span` and `max_area` arrived; only the `LAYER_MASK_PARAMS` mirror in `config.py` is updated by hand, under the sync test that exists for it. **At the defaults `radial` delegates to `develop._radial_vignette_mask` unchanged**, so the two shipped looks written on this geometry (`vignette_wash`'s two radial layers, `golden_ground`'s linear one) render byte for byte what they did *structurally* rather than by arithmetic that happens to agree — pinned anyway by a digest of their rendered pixels taken before the change. `masks.py` is hashed as a whole module into `DEVELOP_ALGO_VERSION`, so this bumps it, which is correct: mask geometry moves pixels.

**Astro stacking (`astro_*.py` + `gomoveshift photos astro`).** One night's RAW frames become a stacked master through a fixed chain, and every stage before the stretch stays in **scene-linear light** — `astro_calibrate.decode_linear` (`gamma=(1,1)`, `no_auto_bright`) never applies a display curve — because a dark subtracts cleanly only in linear space (a gamma'd frame's black level is nonlinear in exposure) and the MTF stretch (`astro_develop.stretch`) needs the sensor's full linear headroom to place the background, not a curve that has already compressed it. Each of `paths` and `--darks` may itself be a RAW file or a card directory — a directory argument
expands to its contained RAW files (`RAW_EXTENSIONS`: `.dng`/`.cr2`/`.nef`/`.arw`/`.cr3`), sorted by name,
before anything else runs; an empty directory is a hard error naming it, never a silent 1-file run.
Files and directories mix freely in one invocation. `astro_sequence.detect_sequences` groups the CLI's (expanded) input paths into intervalometer runs by EXIF alone (held ISO, held exposure within `MAX_HOLD_RATIO`, gaps under `MAX_FRAME_GAP_S`) — and deliberately **not** by calendar day, unlike `bracket.py`'s same-date rule above. The elapsed-gap test already separates two shoots either side of midnight, so a date comparison can only ever fire on a pair *inside* the gap window, which happens exactly once a night, at 00:00, on the astro runs this module exists to group. A card shot across midnight at a steady cadence would, under a calendar-date rule, group as two runs split at 00:00, costing the trail master the last minutes of arc and emitting a short stub clip beside it. `chunk_sequence` splits each run into `--stack-len`-sized chunks (default `STACK_LEN_DEFAULT`, span-capped at `MAX_CHUNK_SPAN_S`) — the field-rotation cap: a run left running too long blurs in a sigma-clipped stack from sky rotation alone. Ahead of both — before any grouping, and before any frame is decoded — an **HE→DNG converter preflight** answers once what the per-frame path used to discover lazily. `develop.he_dng_inputs_needing_conversion` lists the *candidates* (lights **and** `--darks`) whose suffix is `.nef` and whose cached `.dng` is missing or stale — a suffix test plus one `stat` each, never a decode — and `develop.resolve_he_dng_converter` resolves the exe once. A converter that resolves ends it there: one line names it and the candidate count, so the operator sees the conversion engaged rather than inferring it from timing, and no probe I/O is paid at all. Only when **nothing** resolves does the gate ask whether the card is genuinely undecodable, and it asks LibRaw rather than the filename: **one** candidate is opened and `unpack()`ed, no postprocess. Opening alone would prove nothing — LibRaw parses an HE header fine, which is exactly why the megapixel peek above works on one — so `unpack` is the predictor, and its `LibRawError` is the TicoRAW signature that justifies refusing (the message names the count, `photos.he_dng_converter_exe`, and the probed default paths). A clean unpack, a file that will not open, or any other failure does **not** refuse: a lossless-compressed card still stacks on a machine with no converter at all, exactly as it did before this gate existed, and an open failure stays the decode path's to report — a preflight must not invent a failure it does not understand. Probing one candidate assumes a homogeneous card (one body, one setting), so the gate establishes "this card's frames do not unpack", never "each listed file individually does not". `--triage-only` decodes too, so it is gated identically; the lazy per-frame path is untouched underneath and its warning remains the backstop for a converter that vanishes mid-run. **`--darks` that cannot calibrate these lights are refused in the same before-any-decode window**, beside the RAM and name-collision gates. `validate_dark_identity` already refuses a mismatched dark, but it ran inside `prepare_frames`, per chunk, *after* that chunk's frames had decoded — so darks wrong for the whole card refused every chunk one decoded chunk at a time and the run could only ever produce nothing. For example, a full card of lights at one ISO handed darks shot at a different ISO would spend hours decoding every chunk, refuse every one, and write no file. The answer is available up front for almost nothing — `read_capture_identity` reads `sizes`/`other` without unpacking the image — so the CLI reads the first light and each dark once, runs the SAME `validate_dark_identity` (read off the calibrate module rather than imported by name, so the preflight and the per-chunk master-dark build can never disagree about what a usable dark is), and refuses naming the disagreeing field and both values (for example `light=3200.0 dark=6400.0`) rather than a bare "darks are wrong" that sends the operator hunting. A dark this gate cannot OPEN does not refuse: an unreadable calibration frame stays the decode path's failure to report, the same posture the HE probe takes toward an unopenable light, and refusing a whole night over one unreadable file is worse than the bug. The per-chunk check remains the backstop for a genuinely heterogeneous card. `preflight_astro_stack` gates disk/RAM **once for the whole run, before the first RAW decode**, sized off the run's LARGEST chunk — the estimate rises monotonically with frame count, so a run whose biggest chunk fits has every shorter chunk fit too. Every chunk's size is known before the loop starts (`chunks` is fully built by then, the same fact the name-collision pass above relies on), and gating per chunk instead lets early chunks decode and stack for a long time before a later chunk is refused for RAM, leaving only the first masters salvaged. The refusal names the largest chunk and — when RAM rather than disk is the binding constraint — the largest `--stack-len` that WOULD fit the RAM free at that moment, re-derived by re-running `chunk_sequence` at each candidate rather than read straight off the estimator: the chunker merges a trailing chunk shorter than `MIN_SEQUENCE_FRAMES` into its predecessor, so the merged chunk can exceed the candidate (on a 15-frame run every `--stack-len` from 11 to 15 collapses to one 15-frame chunk, so an estimator-only answer of 12 would refuse a second time). The per-chunk check remains as a BACKSTOP for free RAM that genuinely falls mid-run on a shared box, and it **skips its own chunk** (`continue`, the same handling a failed chunk already gets) instead of aborting, so masters already stacked survive; a run that produced nothing still exits non-zero via the `written == 0` check. `--trails` is exempt from the run-level gate — `preflight_trail` carries no frame-count term, so it already refuses on chunk 1 with nothing decoded, and there is no `--stack-len` to advise on. The gate's own arithmetic: the CLI reads one frame's sensor megapixels from LibRaw's header alone (`rawpy.imread(...).sizes`, no `unpack()`/`postprocess()` — genuinely not a decode) and `estimate_astro_stack_ram_gb` derives the RAM floor from `frame_count x megapixels` **plus the run's own `--darks` count**, which the CLI passes through rather than leaving at the estimator's no-darks default — `prepare_frames` holds every dark live while `build_master_dark` converts and stacks them, so a gate told zero under-counts exactly when darks are adding the memory (the darks add a fixed memory term that does not depend on the frame count). Its `meteor_reinsertion_enabled` term stays off here on purpose: this path hands `stack_run` no `meteors=` policy, so reinsertion cannot occur and charging its layer would false-fail a run that fits. The frame-count term matters because at the instant `astro_stack.stack()` reaches its blend, two full sequence-equivalent frame lists (`aligned_frames`, `unaligned_frames`) are simultaneously live — banding keeps everything else to a fraction of one frame, but that pair does not shrink. The arithmetic is why `--stack-len`'s default is not portable across camera bodies: 20 frames at 24 MP needs ~13.4 GiB (comfortably under a typical 24 GB box), but 20 frames at 45 MP needs ~25.2 GiB and does not fit — a high-resolution body needs a smaller `--stack-len`, which is why the flag's own `--help` states the arithmetic rather than leaving an operator to meet it as an OOM. `prepare_frames` then calibrates every surviving light (dark-subtract, then a hot-pixel cosmetic pass keyed off the master dark or in-frame outlier stats when `--darks` is omitted) and triages it -- **on `--decode-workers` THREADS, default `DECODE_WORKERS_DEFAULT` (4)**. Threads rather than processes because rawpy/LibRaw's unpack+postprocess and the HE path's DNG-converter subprocess both release the GIL, so they parallelise for real while sharing one address space: per-frame time falls close to linearly with worker count up to 8. Processes would have to pickle each ~250 MB decoded frame back to the parent, paying a copy this gets for free. The pool's results are collected in SUBMISSION order (`executor.map`, never `as_completed`), which is load-bearing rather than incidental -- `frames` and `metrics` are paired positionally, `reference_index` indexes into both, and the CLI names each chunk by its first and last source frame, so a completion-ordered collection would pair every frame with a different frame's triage and mislabel every output. 4 is the default rather than the core count because RAM, not CPU, is this path's binding constraint: each worker beyond the first holds another decoded frame plus its demosaic buffers live, a fraction of a GiB per extra worker at typical sensor sizes. 4 buys most of the speed-up that 8 reaches for a fraction of the extra memory. **`estimate_astro_stack_ram_gb` is told the same worker count** (`_ASTRO_CONCURRENT_DECODE_FRAME_EQUIVALENTS`, charged as 2 decoded-frame-equivalents per EXTRA worker so it scales with megapixels on its own): sizing the gate for serial decode and then decoding on N threads is how a run OOMs past a preflight that passed. That term deliberately does NOT multiply `_ASTRO_RAM_DECODE_OVERHEAD_GIB_PER_MP`, which is a documented residual also absorbing the sigma-clip promotion and baseline interpreter overhead -- multiplying it would charge several GiB per extra thread at typical sensor sizes and refuse runs that fit comfortably, and a gate that refuses a fitting run is as broken as one that waves an OOM through. `--decode-workers 1` restores serial decode and a bit-identical estimate (`astro_triage.measure_frame`: star count, FWHM, and — only under `--detect-meteors` — streaks), picking the **registration reference** as the frame nearest the chunk's middle among those within 5% of the richest star count (`astro_orchestrator.pick_reference_index`; the rule is detailed below) — not simply the first frame, since a run can start before full darkness. `stack_run` registers every other frame against that reference (phase-correlation + RANSAC similarity fit), **correlating over the sky rows only and at `MAX_COARSE_DIM` 1024** rather than the whole frame at 512. Both halves of that are one bug, which on a full-resolution night card discards many of the best frames, every rejection reading `only 0 matched star pairs` — never a marginal count. `match_stars` shifts the frame's stars by the coarse prior and keeps only pairs inside `MATCH_TOLERANCE_PX`, so a prior a few px wrong loses EVERY pair at once rather than degrading gracefully, and two things push it wrong. A landscape frame's foreground — trees, ridgeline — is high-contrast and *stationary* while the sky rotates, so whole-frame phase correlation weights it far above the point-like stars and drags the prior toward zero; `stack_run` therefore passes `register` the same boolean sky mask it already gives `detect_stars` and the photometry pedestal, and `coarse_shift` crops both sides to that mask's row band (`sky_rows`). The crop is deliberately a RECTANGLE, not the mask itself: multiplying the frame by the mask was measured *worse* at every coarse dimension, because zeroing the ground replaces soft foreground texture with a hard, perfectly stationary horizon edge that correlates harder than the trees did — cropping removes the structure from the correlation instead of re-shaping it. Separately, prior accuracy scales with the downscale factor, and 512 is too coarse for a full-resolution frame: on the full-sensor-sized CI fixture the sky-cropped prior lands past `MATCH_TOLERANCE_PX` at 512 (so every pair is still lost) but well inside it at 1024 — which is why the fixture is full-sensor-sized, since a convenient miniature flatters every dimension equally and tests neither half. 1024 is also not slower per pair than 512, and 2048 buys almost no additional pairs. `prepare_reference` caches the cropped, downscaled reference and carries its row band with it, so the cached and live paths can never correlate two different windows. **The stacking path then warps each frame through a lens-corrected remap rather than that 2x3.** A similarity cannot undo barrel/pincushion distortion, so stars smear radially toward the corners however cleanly the fit converged; `stack_run` therefore fits ONE shared lens plus a per-frame rotation on the sphere across the whole chunk at once (`astro_geometry.solve_night`, principal point pinned to frame centre, focal length seeded from the frame width by `LENS_SEED_F_PX_PER_FRAME_WIDTH` and then fitted) and composes each frame's correction into a single `cv2.remap` pair (`astro_lens.build_remap`) -- the same one resample the affine warp already cost. The fit needs every frame's matched pairs before any frame can be warped, so registration and the warp are now two passes rather than one; `register` does not hand its pairs back, so they are re-paired under its own fitted transform at the WIDE tolerance (the outer stars the affine misses by more than a few px are precisely the evidence the lens model exists to use, and a tight window would drop them). **The switch is per frame and gated on measurement, never on the fit having converged**: the lens+rotation model must BEAT the 2x3 on the SAME held-out stars -- even-indexed pairs train, odd-indexed held out, the similarity refit on the train half so both numbers are out-of-sample -- in the outer radial third, by `LENS_WARP_MAX_RESIDUAL_RATIO`, with at least `MIN_LENS_HOLDOUT_OUTER_STARS` held-out outer stars behind each number. A fit that does not converge, a frame `solve_night` described with a homography instead of a rotation, a frame carrying too few matched stars to enter the joint fit (it is left out rather than submitted, since `solve_night` refuses a whole night over one such frame), and a lens residual that only ties the 2x3 all keep the existing affine warp -- a silently WORSE frame is the failure mode the gate exists to prevent. The gate sits upstream of the warp on purpose: read off the stacked image it could only fire after the whole chunk had already been resampled and stacked. `warp_validity` is handed whichever transform actually ran, so coverage still describes the real warp, while `transform_by_index` stays the 2x3 because its consumer is the meteor step, which transforms streak ENDPOINT coordinates rather than pixels. **Trails and timelapse keep the 2x3** -- they do not want a gnomonic sky rotation, and their callers are untouched. Each used frame's chosen model, its refusal reason and both held-out outer-third numbers land in the `.linear` manifest's `registration` entries under `warp` (additive), and the chunk-level record -- seed lens, fitted lens, convergence, refusal reason, and how many frames took each warp -- rides back on `AstroReport.geometry`. Then `stack_run` splits the blend in two: the aligned stack goes through a sigma-clipped MEAN (stars sit on the same pixel across frames, so clipping rejects a satellite/plane streak as a single-frame outlier while a real star survives), the unaligned stack through a per-pixel MEDIAN (the foreground is fixed in sensor coordinates; unaligned stars land at a different pixel each frame and the median discards that minority for free) — and `horizon_mask` blends the two at the sky/ground boundary, either at the operator's `--horizon` fraction or, left unset, from the reference frame's own star-density map (a blurred impulse image of detected-star positions, since a raw density is mostly zero rows between stars). `develop_stack` removes the per-channel gradient, sets black point and the MTF stretch — an optional `sky_mask` restricts BOTH the gradient fit and the stretch's own black point / per-step background reads to sky-only samples, so a bright ground silhouette, lit building or horizon glow in the frame can no longer inflate the whole-frame statistics and crush faint sky signal toward black; `stack_run` passes the SAME boolean sky mask it already gives `detect_stars` and the photometry pedestal, so the shipped path is masked; a degenerate mask raises or warns rather than quietly reverting to whole-frame statistics, and the mask travels on `AstroDevelopResult` so `develop_stack_with_params` replays a meteor layer's gradient fit under it too. `sky_mask=None` (the argument default, used by no production caller) reproduces the original whole-frame statistics exactly — and the result exports as a 16-bit TIFF plus a `.stack.json` provenance sidecar (frames used/rejected, per-frame triage, algo version — same shape as `develop.py`'s `.grade.json`). **Each frame's record carries `shape_verdict` (`astro_triage.classify_shape`) alongside the `fwhm_major_px`/`fwhm_minor_px`/`ellipticity` split** the isotropic `fwhm_px` averages away — sidecar `v4`, additive, every earlier key and shape unchanged; `shape` is `null` (never a faked zero) when no star was measurable. **Sidecar `v5`** adds each used frame's `radial_inlier_residuals_px_in_sample` (center/middle/outer RANSAC-inlier residuals, labeled `in_sample` because they come from the fit itself, not held-out geometry evidence) and `match_yield_by_stage` (`match_progressive`'s per-stage matched-pair counts: `seed`/`wide`/`tighten_10px`/`tighten_4px`/`final`) — additive, every earlier key and shape unchanged. `register()` now refuses a fit outright when its outer sensor third keeps fewer than `MIN_OUTER_THIRD_INLIERS` (8, PROVISIONAL) RANSAC inliers: a transform that only converged near the frame's centre is a fit over part of the sensor, not the whole of it, and the raised error names the actual outer-third inlier count. The `.linear` manifest's `registration` entries mirror the same two fields (schema 4, additive). `fwhm_px` alone cannot separate a fat round star from an elongated one, and that separation IS the diagnosis: `classify_shape` shipped with zero production callers, the pipeline could compute `likely_defocus` on the very first frame of a night, record none of it, and leave the cause to be recovered only after the whole night failed to register. **Meteor reinsertion (`astro_meteors.reinsert`, wired by `stack_run`'s `meteors: MeteorPolicy` argument) defaults to OFF** — a single-exposure streak `astro_triage.classify_streaks` cannot rule out as satellite/aircraft is not positive proof of a meteor, so `stack_run` with no `meteors=` argument at all exports the base master untouched. A `MeteorPolicy(mode="reviewed", allowlist={...})` reinserts only the named `(frame_index, streak_index)` identities; an excessive-candidate guard (`MAX_METEOR_CANDIDATES`, PROVISIONAL) skips ALL reinsertion — allowlisted or not — once a run's meteor-labelled streak count looks like a misclassification storm rather than a real night's meteors, and `mode="auto"` is refused with a typed error until an automatic-classification precision gate exists. Selected layers are developed and composited one at a time (`reinsert`'s streaming form) so a frame with several selected streaks is replayed through the develop chain once, not once per streak, and at most two full-res layers (the one being composited, the one being developed) are resident at a time. The `.stack.json` sidecar's `meteors` block records the posture, candidate count, reinserted count, and skip reason. **The per-frame streak scan is OFF unless `--detect-meteors` is passed**, because it is the dominant cost of triage and this command cannot consume its output: `measure_frame` takes several times longer with the scan than without it (`detect_streak_components` alone is the large majority of a triage), while `detect_stars` is far cheaper and `_measure_star_shapes` is negligible because it is already capped at `FWHM_STAR_SAMPLE_COUNT` brightest stars. Star count, FWHM, shape and `usable` are bit-identical either way — the scan feeds only `classify_streaks` and the sidecar, and this path passes `stack_run` no `meteors=` policy at all, so nothing could be reinserted from it. Skipping records `streaks`/`streak_components` as `None`, never `[]`: an empty list is the positive claim "searched, found none", and conflating the two would let a run that never looked read downstream as a meteor-free night. `classify_streaks` therefore raises `StreakDetectionNotRunError` on unsearched frames rather than returning an empty classification, and `stack_run` refuses outright when a non-`off` `MeteorPolicy` meets frames prepared with `detect_meteors=False` — an `off` policy consumes nothing and skips the classification instead. The sidecar's `streaks` key is `null` on a skipped run. Registration is NOT the bottleneck this flag addresses and never was: `prepare_reference`, `coarse_shift` and a full `register` each cost a small fraction of a second per pair. `--triage-only` runs calibration and triage and reports usable/cloud/dew/decode-failure counts without registering, stacking or writing anything. **`astro_triage.classify_exposure` separates a cap-on frame from a light before either baseline is taken.** An operator who shoots darks at the end of a night and leaves them on the card would otherwise hand the run its "clearest sky": `_cloud_baseline` takes the LOWEST backgrounds in a group, a capped frame has the lowest background physically possible, every genuine light then trips `CLOUD_BACKGROUND_JUMP_RATIO`, and `astro_select` REJECTS a cloud-flagged frame -- silently, and forward across the night, since `update_run_cloud_baseline` carries the clearest condition seen so far into every later chunk. The classifier reads two ratios against the frame's OWN pixel distribution (its median, its `EXPOSURE_SPREAD_PERCENTILE` upper half-width, and its `EXPOSURE_BRIGHT_PERCENTILE` level), so no black level, ISO, exposure time or sensor is baked into either: STRUCTURE asks whether the brightest 0.1% of pixels stands above the frame's own noise at all -- a Gaussian's own 99.9th percentile is 3.09 sigma, simulated capped frames measure 3.0-3.6 and star fields 90-205, so `CAP_ON_STRUCTURE_SPREAD_MAX` (5.0) sits in the empty gap between the populations rather than on a slope -- and LEVEL asks whether the frame still sits at the black floor `astro_calibrate`'s postprocess has already moved to zero, a half-clipped Gaussian reading 0.67 whatever its noise amplitude against 10.0 for flat-but-lit overcast, hence `CAP_ON_LEVEL_SPREAD_MAX` (2.0). The upper half-width rather than the MAD because black-clipping can put over half a capped frame's pixels on the floor, which collapses the MAD toward zero and makes any ratio to it explode (measured 1e-8 against a true 1e-3 on a simulated capped frame); the two percentiles are stride-subsampled to `EXPOSURE_STATS_MAX_SAMPLES`, a full-resolution pass costing about three times what all of triage costs with the streak scan off. Both tests on the cap side -> `cap_on`: `usable=False`, excluded from the cloud baseline AND the dew baseline (a capped frame's `fwhm_px` is 0, which would otherwise zero the opening dew baseline and switch dew detection off for the whole group), and reported in `TriageReport.cap_on_frames` under its own cause -- "you left the lens cap on" and "it clouded over" are different nights and never share a flag. Both on the light side -> `light`. Anything else is `indeterminate`: COUNTED in `TriageReport.indeterminate_frames`, never guessed into a population and never acted on. That is the cap going on MID-exposure (part sky, part black floor, neither a dark nor a clean light) and flat-but-lit overcast; such a frame stays a light everywhere else, the cloud baseline's median-of-3 already being built to ignore one outlier. Routing detected cap-on frames into the master dark is deliberately NOT wired here -- they are kept out of the light path and out of every baseline, nothing more. **Both paths also print the chunk's dominant shape verdict the moment `prepare_frames` returns** — the earliest point at which it exists, and on a full run the last one at which the operator can still stop and refocus instead of stacking a lost night; `--triage-only` is a card check run before committing to a night, so it is the most valuable place for the signal. Only a STRICT MAJORITY of a chunk's frames carrying one non-`indeterminate` verdict prints anything: `indeterminate` is the normal, unremarkable case and a line on every healthy run is noise the one real warning would be lost in, while a single odd frame is not a night's diagnosis. It stays a REPORT, never a gate — `classify_shape`'s thresholds are PROVISIONAL and it touches no `usable`/cloud/dew flag, so a deliberately defocused or otherwise unusual frame is still stacked, never refused. Defocused frames show a large `fwhm_px` at low `ellipticity` (round and fat, so defocus rather than trailing), against a clearly smaller `fwhm_px` on in-focus frames. Every constant in the chain is provisional pending the reference-card tuning pass the module docstrings name; the stacked masters `ingest` normally afterward, so the blur/GPS/location gates apply unchanged on the exported files. Tests: `tests/test_photo_astro_cli.py`.

**The stack sidecar records the darks the master was actually built with.** `astro_sidecar.stack_sidecar_payload` has always accepted `dark_paths` and written it to `inputs.dark`, but `stack_run`'s callsite never passed it, so every run that DID subtract a validated master dark recorded `inputs.dark: []` — the sidecar is the audit record for how a master was built, and it was denying provenance that demonstrably existed (a run with 7 darks wrote a master whose name hash encodes the 7-dark fingerprint — a no-darks run of the same frames hashes differently — beside a sidecar claiming no darks at all). The darks now travel on `PreparedFrames.dark_paths`, set by `prepare_frames` from the run's own `dark_paths` argument, because `stack_run` sees only a `PreparedFrames` and must never re-derive or guess them; `()` is the honest "nothing was subtracted" claim a no-darks run makes. Nothing about dark *validation* changes — `build_validated_master_dark`'s capture-identity gate is still fatal on a mismatch, per-run and never per-dark.


**The stack sidecar records what the frames were RECOGNISED as (`sidecar_version` 6).** A master's audit record said how it was built and never what it was built FROM, so a night where a wildlife card or a bracket set got swept into an astro stack left no trace of the disagreement -- the numbers looked fine because nothing had asked the question. The new `subject` block is `astro_sidecar.subject_payload` run over the same `light_paths` the payload already hashes: `photos/subject.py`'s `recognise_photos` reading, the per-category tally, whether each reading was the operator's (`SOURCE_OPERATOR`) or an inference, and every frame disagreeing with the dominant reading **by name** rather than as a count. It is computed inside the payload rather than taken as a kwarg for the reason `dark_paths` above was not: a caller that can forget to pass it is a run record that can silently omit what it was stacking. **It records; it never gates.** Unreadable path slots, an empty light list and a recognition failure each degrade to an empty block carrying a `reason` string -- recognition costs the operator nothing, and `unknown` stays `unknown` rather than being rounded to astro. Whether a subject mismatch should HOLD a stack is a product decision, not this record's. Additive only: every v1-v5 key and shape is unchanged.
**A run that stacked fewer masters than it had chunks exits non-zero.** Every per-chunk skip above (the mid-run RAM backstop, a decode/calibration failure, a triage or registration refusal) deliberately keeps the run alive so the masters already stacked survive and one unfittable chunk cannot discard the others' work — but the exit status was still `0` as long as ONE chunk landed, so a night that lost 13 of its 14 chunks to the RAM backstop reported exactly what a clean night reports, and an unattended caller (cron, a wrapper script) could not tell a complete night from a near-total failure. `_cmd_photos_astro` now compares the masters written against the chunks planned and, when any are missing, prints the shortfall to stderr and returns `1` — the masters on disk are untouched and the message says so. Non-zero rather than a raise: the work is already durable on disk, there is nothing to unwind, and this handler's convention throughout is a stderr line plus a return code. `1` rather than a new code: `photos astro` returns only `0` or `1` today, and "this run is not a success" is what `1` already means here — `written == 0` keeps its own distinct "No chunk produced a stacked master" message. `--triage-only` is exempt (it writes no master by design). Tests: `tests/test_photo_astro_cli.py`.

**A chunk short on RAM gives up decode CONCURRENCY, not the chunk.** `preflight_astro_stack` takes a `degrade_workers` flag (the per-chunk mid-run backstop passes it; the run-level gate does not) and returns the `decode_workers` count it actually approved, which the CLI then hands `prepare_frames` — so the gate and the decode cannot disagree, the invariant the `decode_workers` parameter exists for. With it set, the gate tries each lower worker count before refusing, and a chunk that still does not fit at one worker is skipped exactly as before. Concurrency is a speed choice and the frames are the product: on a 25-chunk night free RAM fell to 14.7 GB while other jobs ran on the same machine, every chunk wanted **18.20 GB at the default 4 workers**, and **24 of 25 were skipped** — while the same chunks needed **16.80 GB serially** and would have fitted throughout. It picks the LARGEST count that fits, not serial, so a small shortfall costs a small amount of speed. The run-level gate deliberately does NOT degrade: quietly halving an operator's throughput for a whole night is the wrong answer when a smaller `--stack-len` is the honest one, which that refusal already suggests. Tests: `tests/test_photo_astro_cli.py`.

**The chunk's alignment reference is its MIDDLE frame, not its richest one.** `astro_orchestrator.pick_reference_index` (used by `prepare_frames`, and again by `stack_run` when triage rejected the prepared pick) takes the frame nearest the chunk's centre among those within `REFERENCE_STAR_COUNT_TIE_FRACTION` (5%) of the richest `star_count`; outside that band a genuinely richer frame still wins outright, and the old sharper-then-lower-index tie-breaks still order the band. Every frame warps onto the reference, so the reference's POSITION sets the worst-case sky rotation a single fit must absorb — a reference at the end asks the first frame to bridge the chunk's whole span, the middle asks for half — and that span is exactly what `MIN_OUTER_THIRD_INLIERS` measures: past a few minutes of rotation the corner stars leave the search windows, the fit collapses to the frame centre, and the frame is refused. Picking on `star_count` alone was really picking "the latest frame", because star count climbs monotonically as the sky darkens: across a whole night the counts rise steadily, the runner-up frame within a chunk sits within a fraction of a percent of the best, and the reference lands near the end of many chunks. The cost was positional and large — frames far from the reference were rejected for `too few outer-third inliers`, mostly the first and second of a chunk. The failures are not near-misses (many kept **zero** outer-third inliers, so relaxing the floor recovers almost nothing) — the reference was in the wrong place, and the floor was correctly reporting it. `total_frames`, not the surviving count, defines the centre: a triage-rejected frame still occupies its slice of time, so halving the rotation means the middle of the CHUNK. Same reasoning the night timelapse already uses for its tone reference below, on the same argument that a night drifts one way and the middle halves the distance to either end. Tests: `tests/test_astro_orchestrator.py`.

**Chroma denoise at the writer (`astro_develop.denoise_chroma`).** The one kind of noise stacking cannot average away is colour: frames share a sensor's colour response, so per-pixel colour error is correlated across the stack in a way shot noise is not, and a clean 10-frame master still looks speckled. `denoise_chroma` splits each pixel into its grey level and its colour departure from that grey, Gaussian-blurs only the second at `CHROMA_BLUR_SIGMA = 3.0` px, and recombines. Luma is preserved **exactly**, not approximately: the colour planes sum to zero across channels at every pixel by construction and a blur is linear, so the blurred planes still sum to zero and the recombined grey is the original grey. Chroma carries almost no real spatial detail at this scale — nebulosity and dust lanes are broad — so a blur this wide erases the speckle and leaves the picture. On a stacked master, clear sky away from the band loses much of its Lab chroma sigma while its luma sigma is essentially unchanged. It runs **at the writer, not inside `develop_stack`**, and after any meteor layer is composited so the layer is never speckled against a sky that is not: every step `develop_stack` takes is invertible from the numbers it records on `AstroDevelopResult`, which is what lets `astro_contact.recover_balanced` walk a master back to balanced linear, and a blur is not invertible. `AstroReport.chroma_sigma_before`/`_after` record what the step actually changed on each chunk and the per-chunk stdout line prints them, because a cosmetic irreversible step must not alter every master silently. Tests: `tests/test_astro_develop.py`.

**The viewable preview beside every master (`astro_develop.preview_render`).** A `.tif` master is written for the ARCHIVE: `develop_stack` lands its sky at `STRETCH_TARGET_BACKGROUND = 0.12` so nothing clips, faint signal survives on a darker night, and `astro_contact.recover_balanced` can walk the file back to balanced linear. Opened in a file browser that same master reads as a near-black rectangle, which would leave a hand-rendered picture as the only way anyone sees a night's work, with the fix living in a one-off script rather than the pipeline. So `stack_run` writes `<master>.preview.jpg` beside every `.tif`, unconditionally rather than behind a flag (robust by construction: the operator always gets a picture). The render is a percentile black point at `PREVIEW_BLACK_PERCENTILE = 30.0`, a white point at 99.8, an `arcsinh(x·10)/arcsinh(10)` curve and a ×1.35 saturation lift. **The black point sits INSIDE the sky distribution on purpose.** The master is already stretched, so a low black point lifts the background a *second* time: cutting at the 1st percentile returns a washed grey with no picture in it, while cutting at the 30th puts the sky floor well below the band — the separation a viewer is actually looking for. The cost is that the darkest 30% (foreground, and the faintest corner of sky) goes to black, and that is the correct trade for a display render; the `.tif` keeps every one of those pixels. Note that clipping at the Nth percentile blacks out exactly N% of the frame by construction, so "clip less than 2% of the sky" is not a property any percentile black point above p2 can have — the testable property is band-to-floor separation, not absence of clipping. The render is **irreversibly lossy and read by nothing downstream** — no stacking, no photometry, no contact sheet — so no later stage can inherit its choices by accident, and a failed preview is logged and dropped rather than failing a run: the `.tif` is what hours of stacking bought, the JPEG is a convenience. `AstroReport.preview_path` carries it (`None` when the render failed) and the per-chunk stdout line names it. Cropping is deliberately NOT part of it — framing is per-picture taste, not a pipeline decision. Tests: `tests/test_astro_develop.py`, `tests/test_astro_orchestrator.py`.

**Star trails (`astro_trails.py` + `gomoveshift photos astro --trails`).** The same night's frames, rendered as ARCS instead of a frozen sky. Registration is what *removes* trailing, so this path never registers and never averages: `accumulate_max` folds each calibrated frame into a running per-pixel MAXIMUM, so every frame contributes its stars wherever they stood at that moment. That accumulation is **streaming**, and it is the feature's biggest advantage — the blend holds only the accumulator plus the one frame being folded in, so peak memory is O(1) in frame count. Frames reach it as a generator (`_frames`, nested in `astro_trails.render_trail`) and are never collected into a list; `tests/test_astro_trails.py` pins the shape by weakref (exactly one input frame resident at 3 frames and at 30). Consequently `--trails` does **not** chunk: `chunk_sequence` is skipped entirely and each detected intervalometer run renders as one master (`astro_trail_<first>_<last>_<fingerprint>.tif`, the stack path's own naming with a distinct prefix so a trail can never overwrite a stack of the same frames), and the RAM gate is `preflight_trail`/`estimate_trail_ram_gb`, which takes **no** `frame_count` parameter at all rather than inheriting `estimate_astro_stack_ram_gb`'s per-frame slope (memory grows with frame count times megapixels). It charges the three live frame-equivalents plus the *frame-count-independent* RAW-decode and develop-chain terms the stack model already carries, since `decode_linear` and `develop_stack` run here unchanged. `--triage-only` keeps the stack gate even under `--trails`, because triage runs `prepare_frames`, which does hold every decoded frame of the run live. **Dark + hot-pixel calibration matters more here than anywhere else in the pipeline**: a maximum keeps the brightest value each pixel ever took, so one hot photosite in one frame is a permanent bright dot and sensor defects accumulate rather than averaging away — hence `--darks` builds the master dark and hot-pixel map through `astro_calibrate`'s own path (there is no second decode or second calibration in this module; the HE→DNG fallback is the orchestrator's). Arcs come out **dashed**, and that is honest output, not a defect to fix: the unrecorded gap per cycle is `interval − exposure`, which can be large: with an exposure just under the intervalometer setting, every alternate trigger is missed while the exposure and raw write finish, so the realised interval doubles and roughly half of the time goes unrecorded. Nothing interpolates, blurs or otherwise bridges that gap; continuous arcs come from a capture interval matching its exposure, never from invented pixels. No `.stack.json` sidecar ships on this path yet — `stack_sidecar_payload` needs per-frame triage metrics and a `StackResult` a trail render never produces, and a synthesised one would misreport the render. Tests: `tests/test_astro_trails.py`.

**Night timelapse (`astro_timelapse.py` + `gomoveshift photos astro --timelapse`).** The same night's frames again, rendered as the sky MOVING: one video frame per captured frame, an MP4 rather than a master. The design decision that makes or breaks it is that **the whole sequence shares ONE tone**. Per-frame auto-stretch is what makes an amateur night timelapse strobe -- each frame fits its own black point, background white balance and midtone curve, so frame-to-frame differences in sky background and star count swing the stretch and the clip flickers. So exactly one reference frame is developed normally (`develop_stack`) and every frame is then rendered through `develop_stack_with_params` against that same result: background gain, black point, peak normalisation and every stretch `m` come from the sequence, not the frame. Measured over five synthetic 24x24 frames whose sky brightens and whose star field turns over (`tests/test_astro_timelapse.py`), a patch held at one identical input value came out at 190 of 255 in every frame under the shared base and spread across 176-206 when each frame fitted its own -- that 30-level spread is the flicker. **The reference is the MIDDLE frame in capture order.** A night drifts one way (twilight fading, moonrise, dew), so the middle halves the worst-case tonal distance from the base to either end where an endpoint doubles it, and an index costs no survey pass over frames this path deliberately refuses to hold; its price is that one frame decodes twice. **Gradient removal deliberately stays per-frame**, which is `develop_stack_with_params`'s own contract: a light-pollution gradient really does move across a night as the sky turns relative to a town, and `remove_gradient` adds each channel's own fitted-surface MEAN back, so a refit changes the gradient's SHAPE and cannot shift a frame's overall level -- the flicker axis. Its cost is a slow, low-frequency wobble in the sky's shading, the only per-frame degree of freedom left in the chain; freezing the gradient from the reference instead would need `AstroDevelopResult` to record a gradient model, which it does not (an `astro_develop` change, out of scope here). The render is **streaming**, like star trails: frames reach ffmpeg through a generator one at a time, the reference frame's own scene-linear pixels are released the moment its tone is measured, and each developed frame is released before the blocking pipe write -- so a long night never holds every developed frame and peak RAM is O(1) in frame count. `preflight_timelapse` sizes that peak for what THIS path holds rather than reusing the trail gate's number: 27 live bytes per pixel (the frame's own scene-linear float32 RGB at 12, the reference master carried on the base result at 6, the frame just developed at 6, its rgb24 pipe copy at 3, summed rather than maxed as an upper bound) plus the frame-count-independent RAW-decode and develop-chain terms `estimate_astro_stack_ram_gb` already charges, plus the darks. Consequently `--timelapse` does **not** chunk (`chunk_sequence` is skipped and `--stack-len` is ignored): chunking exists for stack RAM and field rotation, and a streaming, never-registered render has neither -- one detected run renders as one clip, `astro_timelapse_<first>_<last>_<fingerprint>.mp4`. The encoder is `reel.build_encode_cmd` unchanged -- one house encode for stills-derived video, libx264 settings and the explicit full-range-RGB -> limited-range-BT.709 colour contract included; only the frame source and geometry differ, and the frame is cropped to even axes (never resampled) because yuv420p demands them. **Duration is honest and stated up front**: one captured frame is one video frame, so 90 frames at 24 fps is 3.75 s of video -- a card of a few dozen frames makes a very short clip, and the CLI prints the arithmetic before the render rather than leaving it to be discovered in the file. 24 fps rather than `reel.REEL_FPS`'s 30 because nothing inside a night frame moves to judder and the lower rate buys 25% more clip from the same frames (3.75 s vs 3.00 s at 90 frames). Nothing pads, duplicates or interpolates a frame to lengthen a clip -- a frame that cannot decode, or that is not the reference's shape, is reported and the clip comes out one frame shorter, the same refusal to invent data that leaves star-trail arcs dashed. `--trails` and `--timelapse` are mutually exclusive at argparse. **`--timelapse-height N` caps the output height (aspect preserved), and it is a rendering COST lever before it is a file-size one.** The per-frame develop dominates this path: `remove_gradient` fits its polynomial over every pixel and the stretch runs through float64 temporaries, so developing a full-sensor frame costs several times what decoding it does -- a full-sensor night of several hundred frames is an hours-long render (the encoder sits starved throughout) that lands a video no player wants. The scale is applied BEFORE develop, which is what buys the time back; scaling after it would shrink only the file. That ordering forces the reference frame and `sky_mask` to scale too, since `base.sky_mask` is what every later frame's gradient is fitted under and a full-size mask against a scaled frame is a shape error rather than a slow path -- the mask resamples INTER_NEAREST (averaging a boolean mask re-thresholds into a DILATED one, fitting the gradient over ground pixels the full-size mask excluded) while pixels use INTER_AREA. It is a CEILING, never a target: a request taller than the frame is ignored rather than upscaling pixels the sensor never recorded, and a negative value is refused upfront beside `--timelapse-fps` rather than surfacing inside `cv2.resize` hours into a render. **It defaults to `TIMELAPSE_HEIGHT_DEFAULT` (2160, 4K) rather than the sensor's own height** — uncapped was the original default and the hours-long render above is what that default cost, against a fraction of that at 2160 for a clip that is already larger than any display it will be watched on. `--timelapse-height 0` is the documented spelling for the full sensor back; the handler maps it to the `scale_height=None` the render already reads as uncapped, so 0 is a no-cap request and never a zero-pixel one. Tests: `tests/test_astro_timelapse.py`.
