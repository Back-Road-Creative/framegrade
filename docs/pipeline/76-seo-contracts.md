## SEO contracts

All construction-correct.
- **Analytics ledger capture** (`longform_metadata._batch_sync_stats`): each `performance_updated` event carries the YouTube Data API stats (views/likes/comments/favorites, `published_at`) it always did, plus — per video, subject to `_ANALYTICS_MAX_VIDEOS`/`_ANALYTICS_RECENT_DAYS` (newest 200 channel videos, or any published within 90 days) — Analytics API v2 fields via `reports().query()`: `estimated_minutes_watched`, `average_view_duration`, `average_view_percentage`, `card_impressions`, `ctr` (from `cardClickRate`, the click-through proxy — see the SEO manager's ANALYTICS_CTR_LIMITATION), `subscribers_gained`. A scope/403/quota failure on the Analytics call is logged as a warning and simply omits those fields for that video; it never fails the Data API sync.
- **Tags/hashtags**: `_optimizer_body` feeds the LF's real route facts so analytics keywords reflect this drive; `_phrase_tags` consumes the optimizer's multi-word phrases (single-word fragments dropped). Before that merge, `_drop_cross_region_location_tags` region-filters the optimizer's tags against this LF's `resolved.regions`: the optimizer merges the channel's top-performing tags with no topical filter, so a county-marked phrase from another region ("County Kerry drive" on a USA LF) is dropped; generic phrases and in-region county phrases survive, and a GPS-less/legacy LF (no regions) drops nothing. Geo hashtags (`#Location`/`#Country`) LEAD so they survive the `[:12]` cap. `_seasonal_tags` adds month/season (northern hemisphere by calendar month).
- **Per-component hashtags** (`gomoveshift/pipeline/social_generator.py`): `"Dingle Peninsula, County Kerry, Ireland — Part 1"` → `["#DinglePeninsula","#CountyKerry","#Ireland"]`. Series suffix never in tags (`_strip_series_suffix`). On Shorts the first (place) and last (state/county) tags are mandatory on FB/IG/TikTok and the YouTube description; limits and length cuts drop generic tags first (docs/pipeline/135).
- **Series-suffix stripping covers BOTH shapes** (`pipeline/_series_utils._SERIES_SUFFIX_RE`): the bare `— Part N` and the `— Part N of M` that `build_superlong_part_title` emits. The regex was originally anchored immediately after the digits, so the `of M` form survived stripping and every one of the ~14 consumers treated it as part of the location — most visibly `region_resolver.derive_region`, which takes the last comma-segment and so matched no country/state/county tail, returning EMPTY for every multi-part superlong title. Same defect class as a tag leak (`"Ireland — Part 1"` reaching the tag list), re-entering through a second suffix shape. Paired change in `title_builder.ensure_unique_titles`: its comparison key re-attaches the deliberate `— Part N of M` suffix after `assemble_final_title` strips it, because that suffix is part of a title's IDENTITY — two parts of one day are different videos, not a collision. Without that pairing the widened stripper collapses a day's parts to one key and the residual-collision bump stacks a second `(Part N)` onto a title that already carries one. Tests: `tests/test_longform_metadata_series_suffix.py::TestPartNofMSuffix`, `tests/test_title_builder.py::TestSuperlongTitleSurvivesDedup`.
- **Units/playlist/country/region-tags consume the resolver** via one shared `region_resolver.derive_region` / `is_us_region`: authoritative off `ResolvedLocation.is_us`/`country_code` when present, label-parsed only as fallback. A trailing US state ⇒ miles/feet + US playlist (strict membership via `title_builder.is_us_state`, so `"IE"` is never a state). A degraded/absent resolver never flips non-US → USA.
- **Playlist auto-assignment** (`gomoveshift/pipeline/playlist_resolver.py`): every LF → exactly one playlist; rules in `config.drive.youtube_playlists.rules`, default `"Unsorted (fallback)"` (the fallback is unlisted and should stay empty; a video landing there is a routing miss surfaced in Studio, invisible to viewers). Format-aware: when `metadata["trim_ratio"]` is present, a `format: "highlights"|"full"` key is derived (same strictly-below `HIGHLIGHTS_TRIM_THRESHOLD` band as the "Highlights from …" title verb) and the highlights rules — matched before the region-only ones — route Ireland/USA highlight-band LFs to `"Ireland Highlights"`/`"USA Highlights"` instead of the Drives playlists; absent `trim_ratio`, region-only routing is unchanged. An explicit `metadata["format"]` overrides the trim-derived value (mirrors the explicit-`region` override) — superlong parts (`external_systems_coordinator._upload_superlong_parts_to_youtube`, which never sets `trim_ratio`) stamp `format: "superlong"` so they route to `"Ireland Superlong"`/`"USA Superlong"` instead of falling through to the region-only Drives rules. `playlists.list` cached to one call per run; those two playlists are auto-created by exact title on first superlong upload (`youtube_uploader._get_or_create_playlist`) — no manual playlist ID/URL setup needed.
- **Daily playlist reconciler** (`gomoveshift/pipeline/playlist_reconciler.py`, `config.playlist_reconciler`): `compute_plan` is the desired-membership diff, pure and dry-run by construction (it calls no API — the caller supplies live membership and gets back planned inserts, insert-only, quota-capped at `max_inserts_per_run`); it will be the ONLY mechanism that ever playlists a short once wired up, since shorts publish via Metricool and the pipeline never learns their videoId at post time. Reuses `channel_manifest.classify` for held/short/stream/real_lf and `region_resolver.derive_region` (plus `title_builder.state_full_name` on the title's trailing comma segment, for the 5 states with their own playlist) for region — never re-derives either. Routes `stream`→`Mountains Cam Archive`, `real_lf`/highlight by region to Drives/Highlights (+ the matching state Drives playlist), `short` by region to Ireland/USA Shorts. An unroutable real_lf/highlight is reported, never guessed into `"Unsorted (fallback)"`; `reconcile`'s summary carries the list as `unrouted` (`video_id`/`title`/`kind`), logs one `UNROUTED:` warning per video and the CLI summary line appends `unroutable=N [id,…]` (both capped at 25, then `… and N more`), so the output names them; resolve one by fixing its title region or adding an entry to the overrides file; `overrides_path` is optional and operator-supplied (a JSON file, videoId → `{region, state}`; none ships and the default is no overrides) and backfills a title the derivation can't read. `backfill_since` bounds orphan-short backfill only. **Superlong routing:** `compute_plan` checks live membership of `PL_IRELAND_SUPERLONG`/`PL_USA_SUPERLONG` FIRST, ahead of classification — a video already live in one is routed there and ONLY there, never also into the region Drives playlist. Membership, not title or duration: a superlong part's classification is plain `real_lf` (it carries no distinct `kind`), and a region-first check would still miss a BARE single-part title, which carries no suffix to key on at all (`build_superlong_part_title` only appends one when `part_count > 1`) — likely the common case, since a day only splits above the 4 h cap. The uploader already placed the video in its Superlong playlist at upload time, so that membership is authoritative and needs no title parsing. The series-suffix stripper handles both suffix shapes (see the series-suffix bullet above), but a bare single-part title still carries nothing to key on. **Highlights + state + overrides routing:** live membership of `Ireland Highlights`/`USA Highlights` is authoritative right after Superlong — such a video is never planned into region Drives (a highlight whose title lacks the `Highlights from` prefix used to be re-added to Drives); a USA highlight keeps its state playlist (title/override state plus any state playlist it is live in); membership in BOTH regions' Highlights is reported unrouted, never guessed. The title parse drops a trailing quality suffix (` in 4K`, a final `| 4K ...` segment) before reading region/state, so `…, TN in 4K` reaches `Tennessee Drives`. The hand overrides (for videos whose titles carry no region token) are an optional operator-supplied JSON file (videoId → `{region, state}`; none ships and the default is no overrides) that `playlist_reconciler.overrides_path` points at; a relative path resolves against the config home (`GMS_CONFIG_HOME`, else the XDG config location, where `config.yaml` lives), not the cwd, and a configured-but-missing file logs a warning instead of silently loading `{}`. A real_lf with no title region and no override takes the region of the ONE family (Ireland Drives/Highlights vs USA Drives/Highlights/state playlists) it is live in (last resort; both/none = unrouted); a usa real_lf always keeps every state playlist it is live in. `compute_plan` also returns `desired` (videoId → sorted playlist titles, for every routed video, including ones the backfill window or insert cap leaves unplanned) so a prune step can diff against it. **Shorts region:** a short's region is never defaulted. In order: (1) its title via `region_resolver.derive_short_title_region` — explicit evidence only: the word Ireland/Irish, 🇮🇪, `County <Irish county>` (Ireland); a state name or USPS code, `<X> County`, 🇺🇸 (USA); strong evidence for both countries is a contradiction and yields nothing; `County <Irish county>` counts only when no capitalised word leads it (`Wythe County Down the Back Roads` is the US `<X> County` tail, ambiguous, blanked and counted for neither country; `County Down` needs a capital D); a `<X> Township` or `I-NN` interstate tag is a US signal; a bare Irish county name (`Roscommon`, `West Cork`; never bare `Down`/`Dublin`/`Tyrone`/`Limerick`/`Waterford`/`Wexford`/`Antrim`/`Mayo`, which are towns on this channel's filming routes — they count only via `County X`, `Ireland` or 🇮🇪; `<Irish county> County` such as `Clare County` is the US word order, ambiguous and counted for neither country; the `<X>` of `<X> County` is any capitalised token, so `McDowell County`/`DeKalb County`/`WYTHE County` read as American) or a seed-gazetteer place (for example a small set of Irish place names; never ambiguous names such as `Derry`/`Emerald Isle`, which are American places too) counts only when the title carries no US signal, so `Clare, Michigan`/`Beaufort County` stay American; (2) the overrides file; (3) the ONE of Ireland/USA Shorts it is live in (both/neither = skip); (4) otherwise reported `unrouted`, never sent to USA Shorts. A title/override region that contradicts live membership wins (that is what moves an Irish short out of USA Shorts), and `desired` carries only that one Shorts playlist. Extend the gazetteer (or the overrides file) for a new place rather than loosening the rules. No offline publish record maps a historic short's videoId to its source region (shorts post via Metricool, which hands back no id; the content ledger's short rows carry a region but no videoId and one distinct title; only the latest drive's per-project tracking file names short ids), so it is not used. Both Superlong playlists are resolved as OPTIONAL (`resolve_playlist_ids(..., optional=SUPERLONG_PLAYLISTS)`): they're auto-created by the uploader on its first superlong upload, so a channel that has never shipped superlong content has neither yet, and that must not hard-fail the nightly run. `reconcile` is the runnable glue : `resolve_playlist_ids` resolves every REQUIRED target title to an id via ONE `playlists.list(mine=True)` scan and FAILS LOUDLY on any missing required title (never creates a playlist — live titles are canonical, a typo forks one), `fetch_live_membership` paginates `playlistItems.list` per resolved target, `compute_plan` runs, and `apply_inserts` executes up to `max_inserts_per_run` `playlistItems().insert` calls — the only mutation the nightly run performs (`--prune`, below, adds `playlistItems().delete`; nothing here ever touches a video or a playlist), and idempotent: it re-checks live membership immediately before inserting, so a re-run skips anything already there. Runnable via `gomoveshift reconcile-playlists` (`cli/handlers/reconcile_playlists.py`; dry-run by default, `--apply` executes, `--credentials-dir` overrides the SOPS creds dir — the client is built from the uploader's creds path, whose stored grant carries the write scope the inserts need). Scheduled: run `reconcile-playlists --apply --prune --max-deletes N` from your scheduler (cron) once a day (for example N=40 = 40 inserts + 40 deletes; `--max-deletes 0` gives an insert-only run; no env var governs nonpublic pruning, config `prune_include_nonpublic` does; the log gets the `Reconcile:` summary, the `Prune:` line and the ledger path once) (fresh quota, run it from the directory your relative `seo.credentials_dir` resolves against, or set an absolute `seo.credentials_dir` or pass `--credentials-dir`), logging the one-line summary; failure logs and continues since a re-run resumes idempotently. **Legacy playlist-id pagination 404:** a channel can carry legacy 13-char playlist ids (e.g. `PLxxxxxxxxxxx`) alongside modern 34-char ids; for those, `playlistItems.list` can let page 1 succeed but raise `HttpError` 404 `playlistNotFound` on the SECOND page — a real, still-existing playlist whose pagination alone is broken, not a missing playlist. `fetch_live_membership` now returns `(membership, unscannable)`: a 404 with a pageToken present logs a warning and adds that id to `unscannable` instead of raising; a 404 on the FIRST page still means the playlist genuinely doesn't exist and propagates unchanged (that failure mode predates this fix and is unaffected). `reconcile` excludes every unscannable playlist's titles from `compute_plan` entirely via `unscannable_titles` — never treats the missing membership as empty, since an empty default would plan duplicate `playlistItems.insert` calls against videos already live there — and reports the count as `skipped_unscannable` in the run summary. **Prune / undo / audit:** `reconcile-playlists --prune` also plans removals, only inside the managed playlists (the routing targets plus `Unsorted (fallback)`; anything else on the channel is never touched). It is dry-run unless `--apply`; on `--apply` the inserts run FIRST, then at most `--max-deletes` (default 150) `playlistItems().delete` calls, each preceded by one flushed JSONL ledger line (playlist id/title, playlistItem id, video id, position, reason) at `<GMS output dir>/reconcile-playlists/<timestamp>-prune-ledger.jsonl` (`--ledger` overrides); the cap is filled in strict class precedence (`deleted`, `unsorted`, `misfiled`, `nonpublic`; within a class by playlist title then position), so private/unlisted removals only take slots left after every other class, pinned by `test_cap_is_filled_in_class_precedence_nonpublic_last`; one exception to "last": a private/unlisted entry in `Unsorted (fallback)` is removed as `unsorted` (first class wins; `test_nonpublic_entry_in_unsorted_is_removed_as_unsorted_not_nonpublic`); a failed delete logs and continues and the run prints `Prune: planned/applied/skipped/deferred/errors` (exit 1 if any error) as its LAST output line, so `tail -1` captures the counts. Without `--prune` an `--apply` never calls `videos.list` or `delete`, and a test pins it (a scheduled run passes `--prune` with a cap; omit `--prune`, or pass `--max-deletes 0`, for an insert-only run). One entry is removed once, under the first class it matches: (1) `deleted` — the video is absent from `videos.list` on the playlist's own ids (batches of 50); NEVER judged by absence from the uploads-derived manifest, which can omit real videos; a lookup that resolves none of its ids raises instead of treating the whole channel as deleted; (2) `unsorted` — every entry in Unsorted; (3) `misfiled` — the video is routed (in `compute_plan`'s `desired`, public, never an unrouted/unknown one) and the playlist is not among its desired ones, except Superlong entries and a usa video's state playlists; (4) `nonpublic` — private/unlisted, on by default via config `playlist_reconciler.prune_include_nonpublic` (`--include-nonpublic`/`--no-include-nonpublic` overrides per run). A SCHEDULED upload (private with a future `status.publishAt`, which the uploader files into its playlist at upload time) is reported by `fetch_video_privacy` as `scheduled`: never nonpublic, never counted deleted, and none of its entries are ever removed (skipped `why=scheduled`), since deleting one leaves it playlist-less at go-live and mis-routes a superlong part (live Superlong membership is `compute_plan`'s superlong proof). Tests: `tests/test_playlist_reconciler_prune.py::test_scheduled_video_entries_are_never_pruned_even_with_nonpublic_on`. Safety: a move's delete is planned only once every desired membership is live or inserted by the same run (otherwise skipped `pending_insert`, so the insert cap paces a large move), and a public video is never left in no managed playlist (`last_managed_playlist`; Unsorted does not count as filed). A playlist that was unscannable is never pruned. `--prune`, `--undo` and `--audit` are mutually exclusive (argparse group, exit 2): an audit can never reach the undo inserts. `--undo LEDGER` re-inserts each ledgered entry at its recorded position (ascending), skipping any video already back in that playlist, so a second undo duplicates nothing; it runs immediately. `--audit` is read-only and prints one `RECONCILE_AUDIT <key>=<count>` line per check: `unsorted_items`, `deleted_entries`, `nonpublic_entries`, `misfiled_entries`, `dual_shorts`, `highlights_in_drives`, `unrouted`, `public_orphans`, `planned_inserts`, `planned_deletes` (counted independently of the removal precedence). `public_orphans` is judged against the manifest, so it inherits that blind spot.
- **Config-driven LF description footer** (`longform_metadata._build_gms_description`): `config.drive.playlist_url_by_region` / `cadence_line_by_region` (keyed by the same `derive_region` verdict as playlist assignment, off the canonical `ResolvedLocation`) + `site_url` render `▶ Full {Region} playlist: {url}`, the cadence line, and `🌍 {site_url}` between the CTA block and the hashtag divider. All keys default empty → footer absent, description byte-identical; `_embed_chapters` still inserts the chapter block after the footer and before the hashtags. Tests: `tests/test_lf_description_footer.py`.
- **End-screen sidecar** (`gomoveshift/pipeline/endscreen_sidecar.py`): `operator_checklist.txt` carries one Studio-editor URL per upload (YouTube has no end-screen API).
- **Related-video worklist sidecar** (`gomoveshift/pipeline/related_video_sidecar.py`): YouTube's Shorts "Related video" field — the only clickable Short→long-form bridge — has no API (Studio desktop only), so Phase D appends one `RELATED VIDEO: "<short title>" → https://youtu.be/<parent-LF-id>` line per short to the same `operator_checklist.txt`, right after the consolidated-CSV build. Lines key on the short's TITLE (shorts have no YouTube id pipeline-side — Metricool posts them); a short whose parent LF has no video id (skip-upload audit) is skipped. Fail-open: emission never fails the batch, same posture as the end-screen sidecar. Idempotent across a resumed/re-run Phase D: a `related_video_worklist_state.json` sidecar (written via `atomic_write_json`) tracks which lines were already appended, keyed on line text, so re-running with the same plan doesn't duplicate operator instructions in `operator_checklist.txt` — and once written that dedup state is authoritative, so a line the operator ticks off/deletes from the checklist after handling it does NOT reappear on a later run with the same plan. A genuinely new short still appends. A missing/corrupt state file degrades to "treat nothing as already emitted" (worst case a duplicate line, never a dropped instruction).
- **Per-LF `trim_ratio`** = `final_duration / Σ unique source-clip durations`, clamped 1.0. At `HIGHLIGHTS_TRIM_THRESHOLD=0.5` drives the title verb, the description hook + always-on `🎬 Final cut` disclosure, and the shorts CSV lead. `trim_ratio==0` is "unmeasured" → `None` (verb stays `"Driving"`, `TRIM-RATIO-ZERO` WARN). The Final-cut disclosure gates on numeric seconds (`_TRIM_DISCLOSURE_MIN_DELTA_SEC=30`), not formatted-string equality.
  - **Index-space**: a segment's `source_file_index` is DAY-LOCAL after `_partition_lf_plans_by_date` remaps it, but `state.file_durations` is DRIVE-WIDE (global episode index). Summing `file_durations[sfi]` with a day-local `sfi` reads a different day's episode on day 2+ of a multi-day drive (single-day is coincidentally correct). `_day_local_source_durations` rebuilds each LF's per-day durations slice (bucketing `file_durations` by `episode_dates`, keyed to the LF's `per_lf_recording_date`) so the durations index in the SAME day-local space as the segments; the fresh-encode compute, the ffprobe resume backstop, and the load-time trim-ratio state migration all consume it, falling back to the drive-wide list when a day can't be resolved.
- **`site_id` resolves from config when a caller omits it**: `LongFormMetadataGenerator.__init__` and `check_youtube_best_practices` both default `site_id=None` and fall back to `config.seo.site_id` — a caller cannot forget to thread the brand's site id through and silently tag events/metadata as `"gomoveshift"`. An explicit `site_id=` argument still wins over config. Tests: `tests/test_site_id_wiring.py`.
