## Superlong part planner

`pipeline/superlong_planner.plan_superlong_parts(stop_mask, *, part_max_duration_sec, split_grace)` is the PLANNING layer for the "superlong" rendition — the whole drive day's moving footage in 1-3 parts, distinct from the RegularLF `full_drive` mode above. It returns `SuperlongPartPlan` (`gomoveshift/models.py`), a type the RegularLF pack/merge/classify machinery must never see.

- **Run integration** (opt-in, `--superlong` / `config.drive.superlong_enabled`, `flag_registry.py` SENTINEL_CLI_WINS row): `day_pipeline._produce_superlong_parts` runs AFTER the regular-LF loop AND the day's shorts — past the shorts postburn OST gate, before `purge_day_intermediates` — in `run_day_pipeline`, never touching `lf_plans`/`num_lfs`, so the publishable day-first output lands before superlong's own 4h/part encode queues behind it. Each part is cut from the day master via the same keycut `extract_and_concat_segments` path as a regular LF, gated pre-burn by `superlong_gate_or_raise` (an OST review gate mirroring the shorts gate: a first pass builds every part's record + burn text with no encode, the gate audits it, then a second pass burns only the parts the gate returned), then OST-burned via `apply_ost`, landing at `<day_dir>/superlong/sl_NN.mp4` — distinct naming from `lf_NN.mp4` so DoD/upload discovery does not pick parts up. An existing non-empty `sl_NN.mp4` is skipped on resume; metadata is still (re)computed on that path since it's independent of the encode. Per-day records (`{"part_count", "records": [...]}`) persist to `state.superlong_parts[date]`, each record carrying `path`/`part_index`/`part_count`/`duration_sec` PLUS the metadata fields below (`title`/`description`/`chapters`/`video_duration`/`has_gps`/`location`) via `_build_superlong_part_metadata`; `cleanup.drop_day_master` additionally keeps the day master until every planned part is final (`expected_superlong_parts`, gated at the `phase_bc_day_first` call site). DoD coverage (`tools/validate_pipeline_output.discover_state_superlong_parts` + a per-artifact duration ceiling on the per-artifact checks) and a pre-upload media-limits backstop (`youtube_uploader._enforce_youtube_upload_media_limits`) are wired. The upload filename guard (`youtube_upload_filename_pattern`, default `^(?:lf|sl)_\d{2}\.mp4$`) admits `sl_NN.mp4` alongside `lf_NN.mp4`. `external_systems_coordinator._upload_superlong_parts_to_youtube`, called from `_upload_lfs_to_youtube` AFTER its regular-LF loop, is what finally reaches the uploader — parts were previously cut/gated but never enumerated into the upload path. It walks `youtube_sidecar.iter_superlong_parts(state)` (composite `"date:part_index"` keys, since a bare `part_index` restarts at 1 every day), resolves each part's `publish_at` via `content_ledger.next_free_superlong_slot` (making that helper live), and reuses `YouTubeUploader.upload_if_needed` UNMODIFIED against a throwaway `SimpleNamespace(youtube_uploads=sidecar_uploads)` so records persist to their OWN `superlong_uploads.json` sidecar (`youtube_sidecar.{load,save}_superlong_sidecar` + `assert_superlong_sidecar_integrity`, checked against `state.superlong_parts` rather than `drive_plan.regular_lfs`) — never `youtube_uploads.json`, which would hard-fail `assert_sidecar_integrity`'s LF plan/index match. Exception policy mirrors the LF loop: `YouTubeQuotaError` propagates (state+sidecar persisted first), everything else logs and skips that one part so an already-finished LF batch is never taken down. Each part's upload also carries `tags` from `longform_metadata._location_tags(location, recording_date)` (same builder a regular LF's tags use) and a `recordingDate` — the part's own day, taken from the `YYYY-MM-DD` prefix of its composite sidecar key — passed through `upload_if_needed(recording_date=...)`, mirroring `_upload_lf_to_youtube`'s `recordingDetails.recordingDate` treatment for a regular LF.

- **Resume completeness.** Superlong has exactly ONE producer and it sits in `day_pipeline.run_day_pipeline`'s tail, so "day complete" on a `--superlong` run means LFs + shorts **and** every planned `sl_NN.mp4`. `phase_bc_day_first.day_superlong_complete` is that predicate — expected count from `state.superlong_parts[date]["part_count"]`, and **no record means incomplete**, since the count is only re-derivable from the day's stop mask inside `run_day_pipeline`. It gates two skips that previously judged a day on LFs+shorts alone: the per-day resume fast-paths in `_partition_batches_by_resume_state`, and `orchestrator_fingerprint.invalidate_phase_bc_if_superlong_incomplete`, which drops `phase_bc_day_first` **and** `phase_d` from `resumed_phases` — necessary because `superlong_enabled` is a flag-registry row that appears in no fingerprint, so nothing else re-enters a checkpointed phase_bc. Re-entry is not a re-encode while the master survives (`encode_day_master` reuses it, LF re-burn is fingerprint-skipped, existing non-empty parts are skipped); with the master already dropped it IS a full re-encode, warned by date at partition time. Shorts have no freshness skip and do re-render. Tests: `tests/test_superlong_resume_completeness.py`.
- **YouTube quota accounting** (`external_systems_coordinator._refuse_if_over_youtube_quota_budget`, called from `_upload_lfs_to_youtube` before the first upload, so it covers the run's pending regular-LF AND superlong-part inserts together): sums pending `videos.insert` + `playlistItems.insert` pairs (one of each per upload) and compares against `config.drive.youtube_quota_daily_budget` (default `10000`), `youtube_video_insert_quota_cost` (default `1600`) and `youtube_playlist_insert_quota_cost` (default `50`) — Google's numbers, not ours, hence configurable rather than hardcoded. Over budget is WARN-only by default (`config.drive.youtube_quota_enforce`, default `False`): the run proceeds and the reactive `YouTubeQuotaError` 403 pause + resume-skip recovers the remainder; setting `youtube_quota_enforce: true` makes an over-budget projection raise `YouTubeQuotaError` up front instead of aborting mid-batch. A non-numeric config value (e.g. a `MagicMock()` test double) skips the check.
- **Upload persistence ordering — `videos.insert` is flushed before the playlist insert** (`youtube_uploader.upload_if_needed` `persist=` callback, supplied by `external_systems_coordinator._upload_lfs_to_youtube` as `save_state`): the record lands in `state.youtube_uploads` and is checkpointed to disk THE MOMENT `videos.insert` returns — the video is live on YouTube and unrecallable at that point — while `assign_video_to_resolved_playlist` runs afterwards and is fallible (the API can return `HttpError 409 … playlistItems … SERVICE_UNAVAILABLE` after the video is already live). `_upload_lf_to_youtube` swallows that error and returns `None`, and the caller loop additionally flushes on that `record is None` path before its `continue`, which previously skipped `save_state` outright and left a live video's id in memory only for the rest of the run (a crash or SIGTERM there — `SystemExit`, uncaught by the phase-level `except Exception` — lost it, and resume re-ran `videos.insert` on already-public content). The flushed record deliberately carries no `playlist_id`: that orphan signature is what routes resume into the playlist-only recovery branch (both ids required to skip), so a failed playlist insert stays recoverable and never fails the run. Tests: `tests/test_duplicate_upload_window.py`, `tests/test_playlist_idempotency.py`.
- **Same `stop_mask` contract as `plan_regular_lfs(mode="full_drive")`**: `stop_mask=None` raises `ValueError` — no silent stops-included plan. The planner does not re-derive unmasked spans; it reuses `regular_lf_planner._full_drive_unmasked_ranges` (passing a synthetic 1 Hz timestamp index since it has no score array), so the two planners can never disagree about which seconds are "kept".
- **Config**: `config.drive.superlong_part_max_duration_sec` (default `14400` = 4h) caps each part's KEPT (unmasked) duration; `superlong_split_grace` (default `0.08`) widens that cap by a fraction so a day just over the ceiling ships as one part instead of an unnecessarily thin extra one. `kept <= part_max_duration_sec * (1 + split_grace)` → exactly one part.
- **Splitting**: when more than one part is needed, `K = ceil(kept / part_max_duration_sec)` and each split point is chosen at a stop-mask boundary (the gap between two unmasked spans) nearest the even `k * kept / K` mark of kept time — never in the middle of a kept range, since keycut's `exclude_mask` never excises masked seconds interior to a kept range. A boundary is accepted only when it keeps both the part it closes AND everything left for the remaining parts within `part_max_duration_sec * (1 + split_grace)`, recomputed fresh at every split (not inherited from prior drift) — that is what makes the cap-violation-impossible guarantee hold by construction. When no boundary satisfies that window (e.g. a single unmasked span longer than the cap on its own), the split falls back to an exact cut at the clamped even mark, bisecting that span.
- Each `SuperlongPartPlan.ranges` is the ordered list of actual (start_sec, end_sec) unmasked spans for that part — never a single merged extent — so a masked gap between two spans inside the same part stays physically excluded downstream. Tests: `tests/test_superlong_planner.py`.
- **Superlong metadata wiring** (`day_pipeline._build_superlong_part_metadata`, called once per part from `_produce_superlong_parts`): `title_builder.build_superlong_part_title(base_label, part_index, part_count, trim_ratio=None)` appends a DELIBERATE `— Part N of M` suffix (distinct from `ensure_unique_titles`'s dedup-only `(Part N of M)`, which now skips a title already carrying it) and reuses `longform_metadata._select_verb`'s honesty threshold rather than hardcoding "Driving". `chapters.generator.superlong_max_chapters(video_duration_sec)` returns `ceil(duration / 900) + 2`, the `ChapterGenerator.generate(max_chapters=...)` override a superlong caller passes so a 4h part's chapter count clears `content_gates.check_metadata_quality`'s `max(1, int(duration/60/15))` intermediate-chapter floor — unreachable under the unraised default cap of 15, which every existing (non-superlong) caller keeps untouched. `base_label` and the metadata `location` field are the SAME string `apply_ost` burns onto the part (single source of truth, never re-derived); `resolved_location` reuses the day's first `RegularLFPlan`'s already-resolved `state.per_lf_resolved_location[idx]` (never re-derived from raw GPX), and `gpx_path` is the first GPS-bearing day episode's GPX — absent on a GPS-less day, which structurally skips chapter generation (`has_gps=False`, the same content-gates no-op regular LFs get). The description embeds the formatted chapter block (`📍 CHAPTERS`) only when there are enough chapters for YouTube to render it (`YOUTUBE_MIN_CHAPTERS`). Tests: `tests/test_title_builder.py::TestBuildSuperlongPartTitle`, `tests/test_superlong_chapters.py` (helpers), `tests/test_superlong_metadata_wiring.py` (wiring + the 4h density-gate proof), `tests/test_day_pipeline_superlong.py` (records carry the fields).
- **Output-space gate** (`preflight.check_superlong_output_space`): run-level `check_disk_space`'s fixed 50 GB floor is meaningless at superlong scale (a 4h part FINAL runs ~70-90 GB at the frozen 40 Mbps 4K profile). `_produce_superlong_parts` calls it right after planning, before any part's concat/OST — the earliest point where the master (bytes/sec source) and part durations both exist, since preflight itself runs before any master. bytes/sec = the day master's actual `st_size / probed_duration` (never an assumed bitrate); needed = bytes/sec × 2 (the raw stream-copied concat and the OST-encoded final it feeds coexist on disk for the whole part encode) × total planned part duration × 1.2 safety. A duration the probe can't measure skips the estimate (logged) rather than raising a misleading space error — the master's own integrity is gated separately in `day_master_encoder`. Tests: `tests/test_preflight.py::TestSuperlongOutputSpace`, `tests/test_day_pipeline_superlong.py::TestSuperlongOutputSpaceGate`.
- **The `*_segments.mp4` concat is an INTERMEDIATE, written without faststart** (`extract_and_concat_segments` pins `faststart=False`; keycut defaults it True). `apply_ost` re-encodes it into the final artifact, which writes its own faststart, and `cleanup` deletes the concat — so a moov rewrite over the whole concat buys nothing. On a superlong part, whose concat is the entire day (~118 GB), that rewrite exceeded keycut's 1800s stream-copy timeout and the part was lost. The keycut call (`extract_and_concat_ranges_with_receipt`, whose receipt is validated by `edit_timeline.load_receipt` — an invalid one makes the function return None) takes no timeout argument, so removing the work is the only lever this caller has. **A part whose concat returns no output now HARD-FAILS the day** — it used to log `superlong part N concat failed` and `continue`, letting the day report its LFs and shorts complete and proceed to Phase D with no part on disk (the silent-superlong-loss class).
- **CLI conflict rejects** (`cli/handlers/drive.py`, same style as `--lf-target-duration`): `--superlong` + `--lf-mode full_drive`, and `--superlong` + `--lf-target-duration`, each exit 2 with an `error: ... incompatible ...` stderr message. Tests: `tests/test_cli_superlong_rejects.py`.
- **Recurring LOCATION lower-thirds** (`ost_applier._prepare_lower_thirds`, burned in the SAME OST re-encode as the opener/end-card — no extra encode generation): `_produce_superlong_parts` has NO override parameter for this (an earlier `place_transitions_by_part` kwarg is GONE from the signature); every part's lower-thirds come from `chapters.marker_merger.chapter_town_events(record["chapters"])` — the SAME `ResolvedLocation`-reconciled chapter pipeline every town-name surface uses (`_build_superlong_part_metadata`, above), never raw GPX — and that is the only production shape, regression-pinned by `tests/test_day_pipeline_superlong.py`. `chapter_town_events` keeps only `"Entering <town>"` chapters, stripping the per-chapter route suffix and terrain-band decoration (`marker_merger._TERRAIN_BAND_SUFFIX`) and excluding the `Start -`/`Finish -` bookends and the synthetic `En route` YouTube-renderability pads (never a real transition). `_prepare_lower_thirds` clamps each event to a `config.drive.superlong_lower_third_duration_sec` (default 8s) window, drops any window overlapping the opener or end-card CTA, and enforces `superlong_lower_third_min_gap_sec` (default 45s) between kept windows; an empty/whitespace label hard-fails (the part-label contract), as does one containing `;` (`OST-INTERNAL-SEPARATOR-LOWER-THIRD-LABEL` — an OSM concurrency join that escaped the chapter road filter; `;` also chains drawtext filters in the filtergraph and `escape_ffmpeg_text` does not escape it). The route-suffix strip is **structural**, not comma-counting: the last comma-part is dropped only when it passes the road-quality gate, because `_format_location` omits the county whenever it is falsy and the old `parts[:2]` rule then burned the route in the county slot (`"Yemassee, US-17"`); a real county never passes that gate. Adjacent duplicates are dropped at BOTH sites — `chapter_town_events` collapses them post-strip, and `_prepare_lower_thirds` drops a repeat of the previously KEPT label, which is the only place that catches a repeat whose intervening label the min-gap rule removed. The min-gap is a strobe limiter, never a dedupe. Kept events persist onto the part's `state.superlong_parts[date]["records"][i]["lower_thirds"]` for review. Tests: `tests/test_ost_superlong_lower_thirds.py`, `tests/test_day_pipeline_superlong.py`, `tests/test_chapter_town_events.py`.
