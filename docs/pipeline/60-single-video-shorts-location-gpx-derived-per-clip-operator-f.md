### Single-video shorts location — GPX-derived per clip, operator fallback

The single-video `gomoveshift pipeline <video>` path (stages `shorts.py` / `social.py`, distinct from the drive `day_pipeline`) now derives **per-clip** location labels: `ShortsAnalysisStage` still calls `PipelineShortsExtractor.extract_and_render(location=ctx.location, location_map=None)`, but `location_map=None` means "derive inside `extract_and_render`" — `_derive_short_location_map` maps each short's window back to GPS time (`VideoToGpsTimeMapper`, seeded with the shared `effective_offset` so a cold-start lead never opens the window on garbage fixes) and votes the modal county through the shared geocoder (`gps_enrichment._make_short_ost_text_fn`), so an end-of-drive short is no longer labeled with the start-of-drive town. Every label (derived or not) then passes the day-first `_gate_short_ost_text` cascade (shorten → `validate_ost` → hard-fit → drive-location fallback), which hard-fails rather than burning garbage. Without a GPX or geocoder the path stays **operator-owned**: every short falls back to the whole-video `--location` (the original whole-video contract). `SocialGenerationStage` reads each segment's burned `location_text` from `shorts_analysis.json` and threads it into `generate_all(per_short_locations=…)`, so social surfaces match the burned pixels by construction. `tests/test_post_processing_stages.py` pins the stage-call contract (`test_single_video_shorts_carry_whole_video_location`, `test_single_video_social_carries_whole_video_location`).
