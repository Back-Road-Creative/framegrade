## Publish cadence resolution (implementation)

Long-form days/time: `config.drive.long_form_publish_days` (weekday 0=Mon..6=Sun) + `long_form_publish_time` (HH:MM EST). Default `[2]` (Wed) + `11:00`. Single resolution point `gomoveshift/pipeline/schedule_constants.py` (`long_form_days`/`long_form_time` accessors; `LONG_FORM_DAYS`/`LONG_FORM_TIME` are monkeypatch targets).

- **Shorts windows** come per-REGION from `config.drive.shorts_publish_times_by_region` (the SINGLE source of truth), default `{ireland: ["08:00","12:00"], usa: {tue: ["14:00","18:00"], fri: ["10:00","16:00"], _default: ["14:00","18:00"]}}`. A region's value is EITHER a flat list (one window set for every drive of that region — Ireland) OR a per-LF-day dict keyed by 3-letter weekday with a `"_default"` fallback (USA). Precedence: explicit `--shorts-times` → `shorts_publish_times_by_region[region]` (via `resolve_shorts_times_for_region`, which mutates `config.drive.shorts_publish_times`, read by `scheduler.from_config`) → flat `shorts_publish_times`. `lf_day` selects the day's window ONLY within that region map; the former `publish_slots.shorts_times` per-day override (which contradicted the region map) was removed. The 6-slot anti-cannibalisation map (08/10/12/14/16/18) IS now encoded: Ireland 08/12, USA Tue 14/18, USA Fri 10/16 — the 2 IE + 4 US daily shorts land with no collision.
- **Per-LF-day long-form time**: `config.drive.publish_slots[day].lf_time` (`sun→14:00`, `tue→16:00`, `fri→15:00`). `--lf-day` derives it; `--lf-time` overrides; an unslotted day (e.g. Wed) falls back to `long_form_publish_time`. (LF time was never given its own data study — these are operating defaults.)
- **`--lf-day` defaults `publish_day` to the same weekday** (an explicit `--publish` still wins) so it can't diverge from `long_form_publish_days` and trip `_check_publish_day`. **Stale `drive_schedule` recomputes on resume** when its saved region ≠ the resolved `state.region` (`invalidate_phase_d_if_schedule_region_stale`).
- **Shorts slots are numbered by the ACTUAL per-LF bucket sizes, not a fixed per-window capacity**: `_build_and_persist_drive_schedule` passes `shorts_counts` (`[len(state.shorts_per_lf[lf.index]) …]`, position-parallel to `regular_lfs`) into `generate_drive_schedule`. Each LF's window then numbers its slots from that LF's cumulative post offset (advanced by the full bucket size, mirroring `_build_social_posts_per_lf`'s `global_index_offset`) and is capped at its bucket size. Since posts and slots both key off `short_index`, and buckets are UNEQUAL (real source-window bucket sizes are restored), the old fixed capacity (`windows/day × LF_PUBLISH_INTERVAL_DAYS`, continuously numbered across windows) let an LF whose bucket ≠ that capacity map a post to a slot physically inside a DIFFERENT LF's window — scheduling a short before its own LF published (small bucket) or after the next LF (oversized bucket). Bucket-aligned numbering keeps every LF's shorts inside its own window. `shorts_counts=None` (no buckets known yet, e.g. an early resume) preserves the legacy numbering.
- **A bucket smaller than the window's full per-day capacity is SPREAD across the window, not front-loaded**: the placement loop used to fill each date to `shorts_per_day` before advancing, so a bucket short of `shorts_per_day × window_days` emptied the whole tail of the window instead of thinning every day — an LF whose bucket landed at 12 (not the full 14) left its window's last eligible day with zero shorts. `_spread_bucket_across_window` (pure, unit-tested) computes each window date's ELIGIBLE identity-slot count (the same `shorts_start < candidate_dt < next_lf_dt` boundary rule the placement loop already applies — an LF's own drop day and the window's shared boundary day both have fewer eligible slots than an interior day) and round-robins the bucket across those caps one slot per date per pass, so no date is skipped to zero while another date still has room. A day's placement is thereby capped by its per-day allowance, never just the window-wide cap; `shorts_counts=None` (legacy path) skips this and keeps the earlier fixed per-day fill. **Consequence**: a partial day (one short posted where the pair normally posts two) is now the NORMAL shape of a spread window's edges, not an exception — see the identity-time exemption note above and `tests/test_scheduler_own_partial_day.py`, which any future re-do of that exemption must keep passing.
- **Run-wide posting-time lock persists across resume**: `generate_drive_schedule` resolves ONE consistent shorts posting-time pair for the whole run (`_select_run_identity_times`: defaults-first, dropping any time booked on ≥50% of the run window, filling shortfall from the least-contested region `slot_pool`) and echoes it on `DriveReleaseSchedule.identity_times`. That pair is resolved ONCE — on the drive's first Phase-D build — and persisted (state + `drive_schedule.json`). Every later `_build_and_persist_drive_schedule` (a resumed run) reads `state.drive_schedule.identity_times` back and passes it as `locked_identity_times`, so the drive reuses its pair verbatim instead of re-resolving from a ledger that now holds its OWN booked shorts (which would contest its own times ≥50% and flip a resumed run onto a different pair). When locked, identity-time slots are also excluded from the per-day collision set — a booking already at a locked time is this drive's own short, not a rival to dodge. `identity_times=None` (legacy schedule) resolves fresh.
- **Next free slot is ONE function**: `content_ledger.next_free_slot(ledger, config, region, content_type="longform", *, after, publish_day, include_today, block_cross_region)` implements the operator contract ("publish to the next free Ireland Sunday"). Cadence = `long_form_days(config)`/`long_form_time(config)` (the values `--lf-day`/`--lf-time` already wrote into `config.drive`; `config=None` falls back to the module attrs for the `apply_config`/monkeypatch contract); it walks forward from `after` to the first candidate whose DATE has no occupying long-form ledger entry. Occupancy is **date-granular** (booked entries carry real `publishAt` times, so exact `(date, time)` keys missed them — the Wed-11:00 phantom-grid double-booking class) and **region-aware**: a same-region entry blocks, a different-region entry does NOT (Ireland Sun / USA Tue+Fri are disjoint audiences; flip with `block_cross_region=True`) — that disjoint-day premise is specific to REGULAR long-form cadence and does NOT hold for every caller built on this function, and a legacy anonymous entry (`region=None`) blocks ALL regions. Consumers: `ContentLedger.get_next_available_slot`'s longform branch delegates to it (single-video metadata + description text now follow config cadence), and `_build_and_persist_drive_schedule` resolves the drive's DEFAULT base date through it (`publish_day=state.publish_day`, `include_today=False` preserving the scheduler's never-today rule; an unreadable/corrupt ledger file RAISES rather than degrading to a collision-blind schedule — only a genuinely free-slot-not-found search within `next_free_slot` still degrades) **only when `state.youtube_uploads` holds no parseable `publish_at`** — a resumed drive with LFs already live anchors to the EARLIEST of its own already-uploaded LFs instead, because by then those dates are booked into the ledger under this same drive and `next_free_slot`'s region-only occupancy check can't see `project_name` to exempt them; an unparseable/missing `publish_at` record is skipped rather than fatal. **The base date is also LOCKED once**: with no explicit date and no uploaded LF, the build reads back the persisted schedule's own `lf_slots[0].date` (no new state field) instead of re-resolving — `_build_and_persist_drive_schedule` runs on EVERY Phase-D entry, so re-resolving let a crash-resume or a plain re-run rebuild the schedule on a different base than `drive_schedule.json` already held, and undercut the rebase pass's own `"fresh"` (<12h → keep) outcome. A missing/legacy/malformed schedule falls through to a fresh resolve. `phase_d` threads `rebased=(rebase_info["action"] == "rebase")` into the build so a DELIBERATE rebase — which clears an already-`None` `start_date` and is otherwise indistinguishable from "never resolved" — skips the read-back. Full priority: explicit `--start-date`/`--lf-publish-date` > earliest uploaded LF > locked `lf_slots[0].date` > `next_free_slot`. **LF 2..N guard**: the scheduler places LF *i* at base + 7*i days, but only the base date is resolved against the ledger, so `_build_and_persist_drive_schedule` also checks every later LF date (`_assert_lf_dates_free`, asking `next_free_slot(any_day=True)` from that date, i.e. the same date-granular, region-aware occupancy) and RAISES `RuntimeError` naming the occupied date and the LF index (`LF 2 of N ...`) rather than shifting silently. Skipped for single-LF runs and for a resumed run with any LF in `state.youtube_uploads` (its own LFs are already booked under the same drive and cannot be told from a rival). The base date (LF 1) is not re-checked: an explicit operator date stays authoritative. **Resume limitation**: a partly uploaded multi-LF run is unguarded for its remaining LFs (a rival booking on a not-yet-uploaded LF date goes unchecked); checking only the not-yet-uploaded dates is a follow-up.
- **Superlong-part slot resolution**: `content_ledger.next_free_superlong_slot(ledger, config, region, *, after, include_today, block_cross_region, horizon_days, project_name, title)` reuses `next_free_slot` (`content_type="longform"`) with candidate weekdays narrowed to `schedule_constants.resolve_superlong_publish_day(config, region, ledger=ledger, project_name=project_name, title=title)` instead of `long_form_days(config)`. The resolver's precedence (an established cadence outranks the region default): (1) an EXPLICIT operator override — `config.drive.superlong_publish_day` differs from its class default `"sat"` (set via `--superlong-day`/`flag_registry` or the operator's own config) — always wins, even over ledger history or a per-region entry; (2) PREVIOUS RELATED VIDEOS — when `ledger` and an identity (`project_name` or `title`) are supplied, the weekday of the most recently booked superlong part sharing that `project_name` (preferred) or, when either side's `project_name` is blank (older rows predate the field), the same base title with the `— Part N of M` suffix stripped: a series already publishing on a given weekday keeps that weekday even when the region map names a different one; (3) LOCATION — a region present in `config.drive.superlong_publish_day_by_region`, when there is no related history (or no `ledger`/identity to check); (4) NEXT OPEN DAY — no related history AND no region entry found: the resolver returns `None` and `next_free_slot`'s new `any_day=True` mode searches every weekday for the next genuinely free slot, rather than defaulting to a hardcoded Saturday. A caller that cannot supply `ledger`/identity (e.g. the read-only schedule report) gets the pre-existing flat-field/region-map behavior unchanged — that safe default is why every prior test in this area stayed green. Because the resolved day is shared rather than disjoint by default (unlike regular LF cadence, Ireland Sun vs USA Tue/Fri) whenever no per-video history diverges it, `next_free_superlong_slot` defaults `block_cross_region=True` — the opposite of `next_free_slot`'s own default — so a day taken by one region is taken for every region, and the superlong slots behave as ONE shared weekly queue that whichever region has content ready fills next. The flat field and every value in the region map are still validated as 3-letter weekday abbreviations in `DriveConfig.model_post_init`. Same ledger, same date-granular occupancy, so a superlong part can also never double-book a day already holding a regular LF.
- **Schedule visibility — `gomoveshift schedule` (read-only)**: `pipeline/schedule_report.build_schedule_report(ledger, config, *, after)` answers "what is scheduled and when does it end" by COMPOSING existing primitives — it adds no second scheduler and mutates nothing. `weekly_longform_capacity`/`designed_days` come from `config.drive.publish_slots` (its size IS the weekly long-form capacity — 3 by default: tue/fri/sun, in Python weekday order); `scheduled_longforms`/`scheduled_shorts_count` from `ContentLedger.get_scheduled`. `scheduled_shorts_count` stays a whole-queue total (the CLI prints it verbatim); `scheduled_shorts_by_region` is the per-region breakdown beside it — one key per region plus an `"unassigned"` bucket for shorts whose `region` is `None`, so a legacy/anonymous entry is never silently attributed to a region and never drops out of the total. The console Schedule tab's journey filter (`console/schedule.py::_filter_report_by_region`) narrows `scheduled_shorts_count` itself to the matched region's bucket the same way it narrows `scheduled_longforms`/`queue_ends` — an unmatched journey filters it to zero, never to the whole-queue figure, and an `"unassigned"` short is excluded from every region-matched view since it can't be honestly attributed to one. `queue_ends` is the LAST booked long-form date — long-forms only, so a trailing short never extends it, and `None` when nothing is booked. Handler `cli/handlers/schedule.py` only renders (`--json` emits the dict verbatim); all computation lives in the unit-tested report function. `next_available` is the availability MATRIX (`_availability_matrix`): one row per (region, designed day) carrying that day's `next_free_slot`, its shorts windows (`resolve_shorts_times_for_region`) and required count (`required_shorts_per_lf` = windows × `LF_PUBLISH_INTERVAL_DAYS`), with `earliest_for_region` marking each region's soonest; region roster = the keys of `shorts_publish_times_by_region`. Three load-bearing choices: (1) the reported time is the day's DESIGNED `publish_slots[day].lf_time` (sun 14:00 / tue 16:00 / fri 15:00) substituted over `next_free_slot`'s flat `long_form_publish_time` (11:00) — reporting 11:00 would name a time the pipeline never publishes at; (2) each candidate day is passed to `next_free_slot` as an EXPLICIT `publish_day`, so the module-level `LONG_FORM_DAYS` mirror — which a drive run narrows to its own `--lf-day` — is never read or written (pinned by a no-mutation test); (3) it stays a MATRIX rather than one row per region, because **no config field binds a region to a weekday** — the "Ireland publishes Sunday" pairing lives only in prose documentation and the free-text `cadence_line_by_region` — so collapsing would assert a binding the config does not contain. Occupancy stays region-aware: booking a region's day moves only that region's row. Each `scheduled_longforms` entry also carries `kind` (`superlong_part` vs `longform`, detected by `title_builder._SUPERLONG_PART_SUFFIX_RE` matching the deliberate `— Part N of M` suffix) — the CLI renders booked lines as `SL`/`LF`. A sibling `next_available_superlong` (`_superlong_availability`, one row per region via `resolve_superlong_publish_day` — the same resolver `next_free_superlong_slot` uses) reports the next free superlong-part slot per region; it is kept OUT of the `next_available` matrix since a superlong day (default Saturday) is never one of the designed weekly days.
- **Release schedule write/failure contract**: `ReleaseSchedule.save` (`scheduler.py`) writes `release_schedule.yaml` through `_atomic_write.atomic_write_yaml` (temp file + `os.replace`), so a crash or full disk mid-write leaves the prior schedule intact instead of a truncated-but-still-parseable file with fewer slots. `stages/schedule.py`'s `ScheduleGenerationStage` reports a genuine failure (write error, or any exception while resolving the publish date / generating slots) as `StageResult(success=False, fatal=False)` — non-fatal because a missing shorts schedule doesn't invalidate the already-produced long-form deliverable, but never silently `success=True`, since that let a broken schedule reach the Metricool CSV generator unnoticed.
- **Content ledger — single store**: `<config.seo.storage_path>/.content_ledger.json` is the only ledger file (`_default_ledger_path` resolves it; never `gms_output_dir()`). A `ContentLedger` instance pins its path at `load()`; no-arg `reload()`/`save()` reuse it, and no-arg `reload()` on a never-loaded instance is a no-op — one instance can never read/write two files.
- **Content ledger — transactional booking**: a ledger entry exists ⟺ the upload is confirmed. All pre-upload writers are deleted (metadata-gen booking in `longform_metadata`, schedule-build booking in `phase_d_scheduling`) — a `--skip-upload` run books NOTHING, so aborted/re-planned runs can't leave phantom slots. LF entries are written by `external_systems_coordinator._book_lf_upload_in_ledger` right after YouTube returns a video id, recording the REAL `publishAt` slot (EST) plus `video_id`/`region`/`title` (`ContentEntry` identity fields; older ledgers without them load unchanged). `project_name` is provenance only — occupancy stays date+region-granular and never reads it (see the `next_free_slot` entry above) — and is threaded as `project_base` from `phase_d`'s `source_dir.stem`-derived value through both LF-loop and superlong-parts booking call sites; `PipelineState` carries no `project_base`/`project_name` field to infer it from, so a caller that omits it logs a WARNING naming the `video_id` and books an empty `project_name` rather than failing the already-irreversible upload. Shorts entries are written in `phase_d._emit_consolidated_shorts_csv` only after the media gate passes (real Drive link per short). Both route through `content_ledger.record_confirmed_upload`: best-effort (a ledger failure logs `LEDGER-BOOKING-FAILED` at ERROR, never fails a live upload) and resume-safe (dedup on `video_id`; shorts dedup on slot key). The schedule-build ledger read for collision avoidance is unchanged — read-only.
- **Content ledger — startup YouTube reconciliation**: YouTube is truth, the ledger is a cache. `content_ledger.reconcile_ledger_with_youtube` runs once per drive run inside `phase_d_scheduling._build_and_persist_drive_schedule` — the single site that turns ledger entries into slot decisions — immediately after the ledger load, before `get_occupied_slots`. Policy: entries WITH `video_id` are kept iff `videos.list` (batched 50 ids, `status,snippet`) finds the video, with the slot rewritten to the actual `publishAt` when it moved, and DROPPED when the video is gone; anonymous (legacy, no `video_id`) future `scheduled` longform entries are dropped when no channel upload (uploads playlist via `channels.list mine=true` → `playlistItems.list` → `videos.list`, capped at the 100 newest uploads ≈ 3–5 read calls/run) is scheduled/published within ±1h of the slot; anonymous PAST entries and shorts entries are untouched; nothing whose slot falls within the next 24h is ever dropped (in-flight grace). The ledger saves only when something changed. Credentials come from the same `_yt_creds` path as the uploader (`_build_readonly_youtube_service`); ANY API/credential failure logs one `LEDGER-RECONCILE skipped` WARN and the run proceeds with the ledger as-is — reconciliation never blocks a run. Escape hatch `--no-ledger-reconcile` (flag-registry sentinel row).
