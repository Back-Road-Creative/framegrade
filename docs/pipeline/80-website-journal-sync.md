## Website journal sync (implementation)

Post-Phase-D hook `_maybe_auto_publish_journal` (`gomoveshift/cli/handlers/drive.py`) → `run_publish_journal` (`cli/handlers/publish_journal.py`) → pure merge in `pipeline/journal_publisher.py`.

- **Slug resolution cascade**: explicit `--auto-publish-journal SLUG` wins; else `config.drive.active_journey_by_region[region]`, where `region` is `_effective_region` (`--region`, else the `region` persisted in `pipeline_state.json`). `--no-auto-publish-journal` short-circuits, and so does a run with YouTube upload off (`--skip-upload`/`--no-youtube-upload`, no `--publish`): nothing was uploaded, so the hook logs one INFO line and the standalone `gomoveshift publish-journal <state>` still works. The whole hook body is wrapped in one `try/except` so a recoverable side-quest never breaks the drive batch; a `--publish` run that resolves neither slug nor site path logs a loud WARNING (with the recovery command) but does not raise.
- **Site path**: `--site-path` else `GMS_SITE_PATH` env.
- **Date-gate + sidecar routing**: `plan_merge` splits uploads on `youtube_uploads[lf].publish_at` into immediate `inserts` (past/none) and `deferrals` (future). Deferrals persist to `pending_journal.json`; `run_publish_journal` takes a `pending_dir` (default `state_path.parent`), and the drive hook passes the durable drive output dir (`<output_base>/<project>`) — NOT the ephemeral ext4 staging that holds `pipeline_state.json`, which the scheduled replay never scans. `run_replay_pending` flushes ready entries write-then-consume (only entries actually written are dropped from the sidecar; missing-file / plan-error / malformed entries stay pending).
- **The sidecar's own read-modify-write is locked too, separately from the journey lock** (`pending_journal.pending_lock`): `merge_pending` and the scheduled replay's post-flush consume both do load → mutate → save on `pending_journal.json`, and a live drive run's `merge_pending` call sits OUTSIDE `journey_lock`'s window at the auto-hook call site. Extending `journey_lock` to cover it would protect the wrong resource — the sidecar is keyed by `pending_base` (the drive output dir), not by `journey_path`, and two different journeys can legitimately share one sidecar. `pending_lock` instead mirrors `content_ledger._ledger_lock`: a blocking `fcntl.flock(LOCK_EX)` on a `.lock` sidecar beside `pending_journal.json` itself, keyed on that resolved path, reentrant per-thread. Serializing the RMW this way also makes `save_pending`'s unlink-on-empty safe — the writer that observes a genuinely empty entry set is no longer racing a concurrent insert. Both this lock and `_ledger_lock` are built from the same `_file_lock.make_blocking_file_lock` factory (each keyed on its own `threading.local` reentrancy state) — same centralisation precedent as `_atomic_write.py` for the temp-file + `os.replace` dance, so a fix to the blocking-flock RMW pattern reaches both sites at once.
- **Superlong-day parts** (`journal_publisher.plan_superlong_merge`): a superlong day gets ONE merge event listing every part in order, never one entry per part — a 4h encode cap must not fragment a day into weeks-apart reader-facing entries (parts publish roughly one/week via `next_free_superlong_slot`). Reads the plan from `state["superlong_parts"]` and upload truth from the STANDALONE `superlong_uploads.json` sidecar (`youtube_sidecar.load_superlong_sidecar`, injected — never `state["youtube_uploads"]`). A day with any part not yet uploaded is entirely omitted (no insert, no deferral — nothing honest to write yet); a day whose parts are all uploaded but not all public reuses the SAME `MergePlan.deferrals`/pending-sidecar mechanism as the LF date-gate above, except every part's deferred entry is stamped with the day's LATEST part `publish_at` (not its own) so `--replay-pending` only flushes the group together — the override is a pending-sidecar gating value only and never reaches the written journey entry (an inserted part always carries its own true `publish_at`). `run_publish_journal` extends the regular-LF plan with this one before the shared error-check/write/pending-sidecar path (step 2's non-empty gate accepts `youtube_uploads` OR `superlong_parts`, since a superlong-only day has no regular LF upload). Tests: `tests/test_journal_superlong.py`.
- **`video_count` invariant**: `apply_merge` recomputes the journey's top-level `video_count` = sum of `days[].videos` after every insert (immediate AND replay/cron) when the key exists — the site's own journey-integrity deploy check hard-fails on a mismatch. Idempotent by `youtube_id` (existing entries never overwritten — humans shorten titles); cross-day collisions error rather than duplicate.
- **Library coupling — `apply_merge` requires a `VideoLibrary`**: the keyword argument is *required*, so an embed cannot be written without the library being considered; omitting it raises `TypeError` rather than silently regressing. Both journey writers pass one (`publish-journal --replay-pending` and `reconcile_journeys`), which is what stops a replayed deferral embedding a long-form the library does not know about. Membership is **not** re-decided here: `VideoLibrary.record_embed` tags the row via `channel_manifest.classify(...)` and routes it through `upsert_videos_yaml`, so `data/videos.yaml` stays a mirror of `real_lf` only — a Short or held clip is embedded in the journey and deliberately *not* added to the library. That is why the site's video-coverage deploy check only warns on an orphan embed: an orphan embed is normally correct. An unparseable duration yields 0 seconds, which classifies as a Short and so fails safe (stays out) rather than injecting a malformed row. The library flushes *before* the journey is serialized — a library row whose embed never landed self-heals, the reverse is the defect this coupling prevents.
- **Routing table — `data/video_routing.yaml` in the site repo**: maps `youtube-id → {journey, date}` and is **authoritative forever** for which journey page a video belongs to. `date` is the **travel** date, not the upload date. Never infer a journey from publish date — that is how a late-published back-catalog clip lands in a wrong or standalone page. Every writer that embeds a video also records its route, so an embed can never outlive the route that reproduces it: a finished drive appends its own LF routes, and `publish-journal` (both the immediate inserts and `--replay-pending`'s flush) records a route for each entry it writes. Back-catalog legs are routed by hand. A routed video that is not yet public defers until it is. **Why this is an invariant and not a nicety**: `sync-site --journeys` can only re-embed or heal ids the routing table knows, so an unrouted embed is invisible to it. Once, a replayed deferral wrote an embed with no route; every later regeneration omitted it, the scheduled journal job's superset guard correctly refused to push a snapshot that would lose it, and the sync stalled for many consecutive runs with no path to self-heal.
- **Whole-channel reconcile**: `sync-site --journeys` walks the public long-form channel (not just this run's uploads) against the journey pages and embeds any public long-form that the routing table assigns to a journey which does not yet list it.
- **A corrupt file is a warning, not a crash** (`reconcile_journeys`): the pass documents that it never raises on a routing/data inconsistency, but it READS and PARSES two kinds of file, and both fail. An unreadable/truncated `video_routing.yaml` ended `sync-site` in a traceback; an unreadable journey markdown aborted the pass part-way — journeys sorted before it were already written, journeys after it were never reached, and the caller got an exception instead of a result saying which. Both now append a `ReconcileResult` warning and skip: the routing file returns an empty result, a journey file skips only itself and the rest of the pass continues. Note the two loaders parse through **different yaml libraries** (`load_routing` PyYAML, `load_journey` ruamel) whose `YAMLError`s do not subclass each other, hence the two separate error tuples — the same trap as in `catalog/reader.py`.
- **`data/videos.yaml` serialization**: `run_sync_site` holds `journal_publisher.journey_lock(videos_path, skip_if_busy=True)` across the whole load → upsert → write window (including the `channel_manifest.json` write, so the two artifacts one run produces never straddle a concurrent writer's own window) — a scheduled sync and a live drive run's own sync can otherwise overlap, and the load→upsert→write race is a last-writer-wins lost update identical in shape to the journal-merge race `journey_lock` already guards. Busy is a recoverable refusal (non-zero exit, message on stderr), never a silent skip reported as success — a cron caller that swallowed a skip would look green while a real row went missing.
- **Region cross-check before routing**: the auto-merge derives each LF's region from its own `ResolvedLocation` and refuses the *whole* run's merge when any LF disagrees with the run's `--region`, rather than filing a USA LF under the Ireland journey. Fix `--region` or split the drive by region and re-run. Indeterminate (GPS-less/legacy) LFs are no-ops.
- **Channel-manifest freshness**: a scheduled reconcile job you run refreshes the site's channel manifest; the site deploy hard-fails when the manifest is older than the freshness window. Staleness is the signal that the scheduled job stalled — loosen the window before disabling the gate.

- **Channel manifest classification — a cam/live title is a stream only above Short length.** `channel_manifest.classify` applies its `cam`/`live` whole-word title rule only when the duration is above the Short ceiling (90 s) or exactly 0 (live and upcoming broadcasts report `P0D`); a clip at or under 90 s is a Short whatever its title says. Before this, the title rule ran first and filed short "Car Cam: <place> 🚗" clips (and a short "… is Live!" promo) as `stream`, so the playlist reconciler routed them to the stream archive playlist and to no Shorts playlist. The manifest's effect is count-only: the site consumes `real_lf_ids` (neither category is in it) and `known_ids` (category-agnostic), so reclassifying stream -> short moves the `counts` figures and the reconciler's *target* playlist, never the site library. The reconciler only ever ADDS to playlists (insert-only, no delete), so nothing moves: a reclassified public video stays in the stream archive playlist where it is already a member until someone removes it by hand. Reclassified Car Cam Shorts are additionally planned into a region Shorts playlist; their titles carry no region token, so an operator-supplied overrides file (`playlist_reconciler.overrides_path`) can pin each by video id to a region (and state for USA) -- without it the title-less default would file non-US ones in USA Shorts, permanently. A video already live in its Shorts playlist plans no insert. The "Car Cam: {location} 🚗" template stays in `anti_spam_gate.LEGACY_TITLE_POOL_RAW` on purpose: no live generator emits it (it is only a retired-pool literal, which the gate refuses if it leaks into a batch unrendered), and `library-hygiene` uses the entry to name the series of the already-published Car Cam Shorts, so deleting it would not stop anything being generated and would only lose that.
- **Channel enumeration — one shared union of the uploads playlist and its format-split siblings.** `channel_manifest.enumerate_uploads(service)` is the only place that lists the channel's videos; `build_channel_manifest` and `library-hygiene`'s `list_uploads` both call it. The plain uploads playlist (`UU<channel>`) is unreliable: it can return repeated ids and never list some real own videos (public and non-public), so those are invisible to the site manifest, the reconciler's manifest-fed targets and hygiene. YouTube also serves per-format siblings made by swapping the `UU` prefix — `UUSH` shorts, `UULF` long-form, `UULV` live — and the function unions all four (plain first, deduped, first snippet wins). Every public video is recovered by the union. Private and unlisted videos can still be missing from every listing, so `enumerate_uploads(service, known_ids=...)` takes ids the caller remembers locally, asks `videos.list(part=snippet)` for the ones not yet listed (50 per call), keeps those whose `snippet.channelId` equals the `channels.list` channel id (a foreign or deleted id is ignored; no `known_ids` means zero `videos.list` calls) and logs one INFO line `known ids recovered N via videos.list, M unresolved`. `build_channel_manifest(..., known_ids=)` forwards it, and both callers default to the seed `site_sync/known_ids.py::FROZEN_KNOWN_IDS` (empty by default; an explicit `known_ids`, even empty, replaces it in `build_channel_manifest`); `library-hygiene`'s `list_uploads` passes the seed unioned with `ledger_video_ids()` (every `video_id` in `<GMS_OUTPUT_DIR>/library-hygiene/*.jsonl`), so `--ids` on a short it once privated no longer refuses the batch as "not on this channel". The seed holds ids that no listing returns; an operator appends the ids of their own non-public videos there as they are found, and the module ships empty. Ledgers and the site's `known_ids` recover part of that set; the seed recovers the rest. Not yet wired (follow-up): `sync_site` passing the site's `data/channel_manifest.json` `known_ids` into `build_channel_manifest`. A listing that returns a repeated id logs `uploads enumeration: playlist <id> returned N entries but M unique ids` at WARNING — the symptom of the blind spot, expected nightly on `UU`. A split playlist that 404s degrades to the plain listing (INFO, skipped); any other HTTP error, or any error on the plain listing, still propagates. Cost: one `channels.list`, a few dozen `playlistItems.list` units (one per page of each of the four listings) and one `videos.list` unit per 50 seed ids per full enumeration. `youtube_adapter._find_existing_upload` keeps its own recent-uploads scan (newest `_SCAN_LIMIT` ids for lost-response adoption; it needs recency, not completeness), and `content_ledger` / `longform_metadata` scan the newest 100 uploads — both left as they are.
