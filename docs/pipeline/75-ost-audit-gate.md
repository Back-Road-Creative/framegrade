## OST audit gate (before the first master encode)

The LF gate is `ost_audit_sidecar.lf_gate_or_raise`: it writes `ost_audit_<date>.json` (real resolved `ost_text`, youtube_title, thumbnail_text = same resolved burn text, recording_date) and raises `OstAuditPendingError` unless one confirmation: `.confirmed` file on disk; `state["ost_audit_passed"][date]` + matching `ost_audit_hash`; or `state["ost_audit_confirmed"]` (`--ost-audit-confirmed`). **Material-change invalidation**: `confirmation_is_stale` reopens the gate when a prior confirmed hash differs materially from the current (hash excludes `generated_at`); `prior_hash is None` is not stale (clean-run bypass works). Module `gomoveshift/pipeline/ost_audit_sidecar.py`.

**Front-loaded**: because every day's per-LF burn text is fully resolved (`per_lf_ost_text_by_date` / pre-seeded state) BEFORE any master encode, `run_all_days` runs `lf_gate_or_raise` for **all** days UPFRONT — writing every day's sidecar and raising ONCE (listing all pending days) before the first `run_day_pipeline` (hence before the first `encode_day_master`). Previously the gate raised per-day only AFTER that day's multi-hour master encode → up to one stop/resume cycle per day; now a single confirmation clears the whole run. The per-day call inside `run_day_pipeline` is retained (same function) and fast-passes on the marker the front-load persisted; the front-load passes the same `output_base` + per-day `location` + per-LF maps as the encode loop so the two hashes match. The shorts burn text — which only exists after per-day short planning — still gets its own parallel per-day pre-burn gate (`shorts_gate_or_raise`; see the Shorts section above); front-loading the shorts audit is a tracked follow-up (its text is not derivable from `per_lf_ost_text_by_date` alone).

### System review (`--ost-system-review`, opt-in per run)

A fourth pass signal at both burn gates (the per-day gate in `day_pipeline.run_day_pipeline` and the front-load `lf_gate_or_raise`), checked only after staleness, the CLI flag, `.confirmed` and the state pass. Phase BC's route-claim check writes `state["ost_system_review"][date]` (`ost_system_review.record_system_reviews`, inside a `finally` so a refusal is recorded too): per LF the exact burn text, verdict (`agree`/`refused`), requested label and reason, plus the LF set and a hash of the day's text, sealed with a digest and stamped `writer: gms-route-claims`, `record_version: ost-system-review-1`. It holds labels and verdicts, never a fix or coordinate.

The gate passes only when `--ost-system-review` was given on THIS run and the record is sealed by that writer, is for this date and exactly this LF set, names no refused claim, agrees on every LF and hashes the exact current payload `ost_text`. Anything else stays pending, and the pending message says why (a refused claim is named). It is read from state only: no file on disk satisfies it, and it never writes `.confirmed`. A pass writes an audit-only copy to `<output_dir>/ost_system_review_<date>.json` and logs its path and hash. Default off: the human gate stays until this path is qualified. Both per-run signals (`ost_audit_confirmed_this_run`, `ost_system_review_this_run`) are reset to this invocation's flags after the resume merge (`reset_ost_opt_ins_after_resume`), so a saved `true` in `pipeline_state.json` never stands in for a flag. Tests: `tests/test_ost_system_review_gate.py`.

#### Shorts and superlong parts

The same flag passes the Shorts gate and the superlong gate, each on its own sealed record: `state["shorts_ost_system_review"][date]` and `state["superlong_ost_system_review"][date]` (`ost_system_review.record_surface_reviews`, `writer: gms-route-claims`, `record_version: ost-system-review-shorts-1` / `ost-system-review-superlong-1`). Each Short's entry is written only after its own clip's route check ran, from that check's outcome (rank, clip window, burned text, requested label, reason); each superlong part's entry comes from that part's `route_claim` and binds the part's burned title and every lower-third with its time. An unsupported label is broadened by the route check, and the record carries the broader burned text and the reason, never the requested label.

A surface passes only when the flag was given on THIS run and its record is sealed by that writer and version for that surface and date, covers exactly the gate's entries, names no refused claim, and hashes the exact text about to burn. A Short whose text was inherited from its LF label (`lf_label`, a GPS-less day) was never measured on its own clip, so it stays pending. A Shorts pass writes `<output_dir>/shorts_ost_system_review_<date>.json` and persists the hash-bound Shorts pass, so a resume is bound to the same text. The superlong gate persists no pass: a resume without the flag parks again (stricter; the resume fingerprint is a separate mechanism). Tests: `tests/test_ost_system_review_surfaces.py`.
