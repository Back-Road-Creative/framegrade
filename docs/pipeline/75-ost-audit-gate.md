## OST audit gate (before the first master encode)

The LF gate is `ost_audit_sidecar.lf_gate_or_raise`: it writes `ost_audit_<date>.json` (real resolved `ost_text`, youtube_title, thumbnail_text = same resolved burn text, recording_date) and raises `OstAuditPendingError` unless one confirmation: `.confirmed` file on disk; `state["ost_audit_passed"][date]` + matching `ost_audit_hash`; or `state["ost_audit_confirmed"]` (`--ost-audit-confirmed`). **Material-change invalidation**: `confirmation_is_stale` reopens the gate when a prior confirmed hash differs materially from the current (hash excludes `generated_at`); `prior_hash is None` is not stale (clean-run bypass works). A stale day is UNCONFIRMED for the current payload: the stored `ost_audit_passed`/`ost_audit_hash` and a marker stamped with the old hash never pass it. It passes only through a route that judges the CURRENT payload: `--ost-audit-confirmed` on this run, or a `.confirmed` marker stamped with the current audit hash; a bare hand-made `.confirmed` does not, and neither does the system review record (below), which stays pending for a stale day even when it re-agrees on the new text. A pass re-binds `ost_audit_hash[date]` (and re-stamps an existing marker) to the current hash, so the next run passes without the flag. With no passing route the gate refuses, leaves the stored hash untouched and names those two routes with the current hash. Module `gomoveshift/pipeline/ost_audit_sidecar.py`.

**Title-only changes and the one-shot flag.** The audit hash covers each LF's `youtube_title` normalised: a part suffix equal to the entry's `part_index`/`part_count` (parsed from that title's own suffix, not from the LF's `lf_parts`) (`— Part k of K`, or the legacy `(Part k of K)`) and the ` (Mon D, YYYY)` suffix `title_builder._drive_dated` builds from the LF's `recording_date` are stripped, and the part numbers are hashed instead (`part_index`/`part_count` are on the payload entry of any LF whose title ends in a part suffix, split or deduped). Re-deriving a title with only those suffixes changed never restales a confirmed day; a changed `ost_text`, base label or part count does. A hash earlier code stored still covers the day when its burn text, base label and part count are unchanged (`ost_audit_sidecar.accepted_ost_audit_hashes`: the normalised hash; the raw `normalise=False` hash; the raw hash of a split day under its deployed `(Part k of K)` titles; and the raw hash of a bracket-dated day under its deployed base titles, the normalised base label plus ` (Part k of K)` where the title has a part suffix, which is how deployed code stored a country or state drive's day before dating), in `lf_gate_or_raise`, in the per-day gate in `day_pipeline.run_day_pipeline` (which now calls `lf_gate_or_raise`, so one route order: this run's `--ost-audit-confirmed`, a marker stamped with a covering hash, the hash-bound state marker, the system review on an unstale day) and in the resume drift check (`state_invariants._check_ost_audit_hash_drift`) alike; a pass on such a hash re-stamps the normalised hash and rewrites the sidecar so disk and stamp agree on the next resume. `--ost-audit-confirmed` is one run's own act: the resume recipe (`health/resume.py`, `write_recipe` and `read_recipe`) never carries it, nor `--fresh`, however spelled: tokens are stripped by the destination the drive parser resolves them to (abbreviations and `name=value` too), so a `health heal` relaunch cannot auto-confirm a changed day. The stale-day message names the day, the audit file to review and the hash a marker must carry; it does not tell an unattended run to pass the flag, and neither does the resume drift message. Two split days sharing one label are dated on the base label and suffixed once; with no measured date that makes them unique `ensure_unique_titles` refuses (`PhaseBCExitContractError`).

**Front-loaded**: because every day's per-LF burn text is fully resolved (`per_lf_ost_text_by_date` / pre-seeded state) BEFORE any master encode, `run_all_days` runs `lf_gate_or_raise` for **all** days UPFRONT — writing every day's sidecar and raising ONCE (listing all pending days) before the first `run_day_pipeline` (hence before the first `encode_day_master`). Previously the gate raised per-day only AFTER that day's multi-hour master encode → up to one stop/resume cycle per day; now a single confirmation clears the whole run. The per-day call inside `run_day_pipeline` is retained (same function) and fast-passes on the marker the front-load persisted; the front-load passes the same `output_base` + per-day `location` + per-LF maps as the encode loop so the two hashes match. The shorts burn text — which only exists after per-day short planning — still gets its own parallel per-day pre-burn gate (`shorts_gate_or_raise`; see the Shorts section above); front-loading the shorts audit is a tracked follow-up (its text is not derivable from `per_lf_ost_text_by_date` alone).

### System review (`--ost-system-review`, opt-in per run)

A fourth pass signal at both burn gates (the per-day gate in `day_pipeline.run_day_pipeline` and the front-load `lf_gate_or_raise`), checked after the CLI flag, `.confirmed` and the state pass, and only for a day that is not stale (a label change after a pass needs a person). Phase BC's route-claim check writes `state["ost_system_review"][date]` (`ost_system_review.record_system_reviews`, inside a `finally` so a refusal is recorded too): per LF the exact burn text, verdict (`agree`/`refused`), requested label and reason, plus the LF set and a hash of the day's text, sealed with a digest and stamped `writer: gms-route-claims`, `record_version: ost-system-review-1`. It holds labels and verdicts, never a fix or coordinate.

The gate passes only when `--ost-system-review` was given on THIS run and the record is sealed by that writer, is for this date and exactly this LF set, names no refused claim, agrees on every LF and hashes the exact current payload `ost_text`. Anything else stays pending, and the pending message says why (a refused claim is named). It is read from state only: no file on disk satisfies it, and it never writes `.confirmed`. A pass writes an audit-only copy to `<output_dir>/ost_system_review_<date>.json` and logs its path and hash. Default off: the human gate stays until this path is qualified. Both per-run signals (`ost_audit_confirmed_this_run`, `ost_system_review_this_run`) are reset to this invocation's flags after the resume merge (`reset_ost_opt_ins_after_resume`), so a saved `true` in `pipeline_state.json` never stands in for a flag. Tests: `tests/test_ost_system_review_gate.py`.

**Placeless drives.** A GPS-less drive run with `--placeless-label` (the backlog row's `placeless_label`) has nothing for route claims to measure. Its label is checked by construction instead: `content_gates.placeless_label_problem` admits only a closed vocabulary that names no place (≤40 chars, letters/spaces/apostrophes). That vocabulary still holds descriptive words (hills, ridges, valleys, fields, fog, snow, winter, morning, back roads...), and a descriptive label is a claim about the footage that nothing measures. So the writer agrees only on a claim-free label: every word in `content_gates.PLACELESS_NO_CLAIM_WORDS` (`placeless_label_claims_nothing`, e.g. "Somewhere On The Road"), true of any drive. An unmeasured LF whose exact burn text is such a `state.placeless_label` gets an `agree` review (reason `placeless label: claim-free words only, makes no place or scenery claim`). A descriptive placeless label ("Through The Quiet Hills", "A Long Morning Drive") gets no review and waits for a person to check it against the footage and create `.confirmed`; the backlog launcher never starts any `placeless_label` row unattended (`health/launch.py`, `placeless_label_skip_reason`, doc 01: give `bracket_gpx` instead), so a placeless drive is only ever a hand run. A measured outcome always wins, any other unmeasured text gets no review, and the flag is still required.

#### Shorts and superlong parts

The same flag passes the Shorts gate and the superlong gate, each on its own sealed record: `state["shorts_ost_system_review"][date]` and `state["superlong_ost_system_review"][date]` (`ost_system_review.record_surface_reviews`, `writer: gms-route-claims`, `record_version: ost-system-review-shorts-1` / `ost-system-review-superlong-1`). Each Short's entry is written only after its own clip's route check ran, from that check's outcome (rank, clip window, burned text, requested label, reason); each superlong part's entry comes from that part's `route_claim` and binds the part's burned title and every lower-third with its time. An unsupported label is broadened by the route check, and the record carries the broader burned text and the reason, never the requested label.

A surface passes only when the flag was given on THIS run and its record is sealed by that writer and version for that surface and date, covers exactly the gate's entries, names no refused claim, and hashes the exact text about to burn. A Short whose text was inherited from its LF label (`lf_label`, a GPS-less day) was never measured on its own clip, so it stays pending. The one exception is the drive's claim-free placeless label (above): an unmeasured Short or superlong part burning exactly that label, with no lower-thirds (a lower-third names a town), gets an `agree` review, and the Short's review carries `place_source: placeless_label` so its inherited text passes. A Shorts pass writes `<output_dir>/shorts_ost_system_review_<date>.json` and persists the hash-bound Shorts pass, so a resume is bound to the same text. The superlong gate persists no pass: a resume without the flag parks again (stricter; the resume fingerprint is a separate mechanism). Tests: `tests/test_ost_system_review_surfaces.py`.
