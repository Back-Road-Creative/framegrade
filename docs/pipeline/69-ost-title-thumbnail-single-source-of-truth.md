## OST / title / thumbnail — single source of truth

`state["per_lf_ost_text"]` is populated in `phase_bc_day_first` from `build_lf_title` BEFORE `ensure_unique_titles` (no `(Part N of M)` in burned pixels). Cascade: `per_lf_ost_text` > `per_lf_locations` > drive-wide `location`. YouTube title (dedup-suffixed) and thumbnail derive from the same source — never let the SEO manager template `: Scenic Drive` over the top.

- **No unmeasured road claim** (`build_lf_title(road_coverage_measured=False)`, the default): no caller measures how much retained time a geocoded road covers, so the cascade drops the road in every shape — single, multi-road and `per_lf_location` suffix — before any title is built: "Port Royal to Lady's Island, SC", never "… via Sea Island Parkway, SC". Place and region text is kept; the title is never refused for it. The via-road quality filter, vote and span rules (`01-per-lf-location-labels.md`) apply only once a caller passes `road_coverage_measured=True` from a measured route. A confirmed GPS loop keeps "Loop" but never the "Scenic" genre word ("Ash County Loop, NC"). The SEO description line (`longform_metadata._seo_search_line`) still names the via-road and is not a reviewed surface yet. Tests: `tests/test_ost_unmeasured_road.py`.
- **Drive-level OST ladder falls through, not off** (`ost_formatter.derive_drive_ost_text`): priority 1 structured `episode_profiles` → 2 already-derived `episode_locations` → 3 GPX-endpoint geocoding. Phase A always passes a non-empty profile list, so a profile priority that returned early on *town-less* profiles would ship an EMPTY drive OST and starve priorities 2-3. The profile branch returns only when it produced a non-empty span/town; profiles that yield no endpoint towns fall through so a state-level span still burns. Priority 3 quality-filters each journey's trace (`filter_high_quality_points`) before `_pick_anchor_waypoint`: the anchor steps only ~20 fixes inward, so a longer stale/null-island head or tail run would otherwise own the drive-wide anchor and burn a wrong label into every downstream consumer (the filter falls back to the raw trace if it would evict everything).

- **YouTube title 100-char clamp** (`longform_metadata._clamp_title_len`): the single site both generators route through; preserves verb prefix + trailing `(Part N of M)` / bare `(Part N)` (`_PART_SUFFIX_RE` matches both, so the channel-dedup bump suffix survives the clamp and the `_build_title` rebuild) and truncates the middle on a word boundary.
- **Episode/drive endpoint towns are named where the GPS starts and ends** (`ost_formatter._resolve_endpoint_name`, shared by `_format_ost_from_route` and `route_profile.build_route_profile`; drive OST priorities 1-2 inherit it): the settlement the start/end waypoint anchor geocodes to (town|city|village, ~20 fixes inward) IS the endpoint. A detected town replaces it only when it is the same place as ANY town/city/village field the geocoder returned (same name after dropping "City of/Town of/Village of", detected spelling kept). A county/township/region name in the town slot is not a settlement, so it never beats a real detected town within 6 km. With no anchor settlement (hamlet/rural), a detected town is used only within `ANCHOR_TOWN_SAME_PLACE_KM` (6 km) of the anchor waypoint, else the county/state label. The old rule kept a detected town up to 50 km away, so a one-sample start town dropped by RouteAnalyzer's 3-minute filter could let a town 25 km up the road name a drive that began elsewhere. A far transit town still loses to the anchor by construction. The demotion of county/township/region endpoints still runs after. Per-LF burned OST/titles (`build_lf_title`) are GPS-anchored separately and unaffected. Already-rendered drives change only on `redrive_ost`. Tests: `tests/test_ost_geocoded_endpoints.py::TestAnchorSettlementBeatsFartherDetectedTown`, `tests/test_route_profile.py::TestEndpointNamedWhereGpsStarts`.
- **Title dedup runs in the FINAL-title namespace** (`title_builder.ensure_unique_titles` + `longform_metadata.assemble_final_title`): dedup inputs are pre-reshape labels but the channel ledger holds assembled final titles and the via-stripping reshape runs after dedup — so in-batch counts and the published-set comparison both key on each label's assembled form (returned values stay labels + suffix). The pre-render review gate's hard duplicate check assembles the OST label the same way (nothing writes the manifest's `proposed_title`).
- **An exact channel collision is a hard failure, not a `(Part N)` rename.** A label unique in-batch (no in-batch duplicate, no superlong `— Part N of M` suffix) whose bare assembled form matches a published title raises `exceptions.PhaseBCExitContractError` naming the live video id — the failure mode is two live videos sharing one title (e.g. "Sampleland Scenic Drive in 4K | Exampletown, ST") because the ledger only ever refreshes as a side effect of Phase D's analytics sync, so a Phase BC that starts before the prior upload's Phase D dedups against a stale `events.jsonl`. `longform_metadata.refresh_channel_title_ledger` (one `playlistItems.list` call, reusing `_yt_creds`/`_sync_youtube_analytics`'s client construction) runs once at Phase BC, right before each `load_published_titles` read, and its `{title: video_id}` result is threaded into `ensure_unique_titles` as `published_title_ids`. Missing/invalid credentials or any API failure degrade to `{}` with a WARNING — never blocks a dry run. Near-misses (an in-batch dedup form, or an already-`(Part N)`-suffixed label, that also collides) keep the existing bump behaviour. The refusal names the id from the run's channel refresh at every dedup site, including the pre-encode demoted-label preview; when the refresh has no entry (degraded run), it reads the local live-catalog snapshot `<storage_path>/live_catalog.latest.json` that `catalog-fetch --known-ids-from-queue` writes — on the refusal path only, any age, never the network. With neither, it says `id=unknown (not in the local live_catalog.latest.json)`.
- **Front-loaded SEO title** (`_front_loaded_title`): `"{Region} Scenic Drive in 4K | {A} to {B}, {ST}"`, targeting the 55-65 char SERP window. Via-road demoted to tags/description. The trim-honesty verb lives only in the description hook + `🎬 Final cut` line, not the title. US drives front-load the full state name; US-ness comes from `ResolvedLocation` when present (a degraded resolver never flips non-US → US). `_build_title` detaches the `(Part N of M)` suffix across the rebuild and re-appends it at the tail (`_PART_SUFFIX_RE`) so same-county LFs stay distinct.
- **Title-text quality gate — upstream of upload** (`quality_gates.assert_phase_d_title_quality`, called in `phase_d.PhaseD.run` right after `_build_metadata_per_lf`): title distinctness (Rule 1, `check_titles_distinct`) and `seo_degraded` (Rule 2, `check_seo_degraded`) are computable from the just-built metadata, so they run BEFORE the irreversible Drive/YouTube upload instead of only at end-of-Phase-D. A duplicate-title or degraded-SEO LF now raises `PhaseQualityError` before publish rather than after the video is already public (the gate runs before the irreversible upload). These two rules are no longer in `assert_phase_d_quality` (which keeps the rules that need upload-/CSV-derived state); escape hatch `--allow-seo-degraded` downgrades Rule 2 to warning-only. Tests: `tests/test_phase_d.py::TestPhaseDTitleQualityGateRunsBeforeUpload`, `tests/test_phase_d_quality_gates.py`.

- **Thumbnail frame picker — one scorer for both surfaces** (`drive_phases/thumbnail_generator.quality_score`): a candidate frame is ranked by `SHARPNESS_WEIGHT` × Laplacian-variance sharpness (saturating at `SHARPNESS_SATURATION`) + `EXPOSURE_WEIGHT` × distance from `TARGET_BRIGHTNESS` + `HIGHLIGHT_WEIGHT` × a blown-highlight penalty (pixels ≥ `BLOWN_LEVEL`, zeroing at `MAX_BLOWN_FRACTION`). The prior rule was brightest-of-3, which on driving footage means glare, a blown sky, or a motion-blurred frame — nothing measured focus at all. `select_best_timestamps` is the single entry point: the drive path ranks its 3 body samples through it and the legacy single-video `ThumbnailGenerationStage` ranks its 20, so the two surfaces cannot drift apart again (the stage's own brightest-wins copy is gone, along with its `WeatherDetector.score_frame_brightness ≥ 400` floor). Sharpness is measured on the extracted JPEG downscaled to `SHARPNESS_MAX_DIM` so a 4K still costs the same as a 1080p one; `probe_frame_brightness` survives as a thin wrapper over `probe_frame_quality`. An unmeasurable candidate sorts last and never wins; all-unmeasurable returns `[]` and each caller keeps its own fallback pick. Tests: `tests/test_thumbnail_frame_quality.py` (including a real-ffmpeg blurred-vs-sharp separation check).

- **LF thumbnail generation gate — upstream of upload** (`phase_d_metadata._generate_lf_thumbnails`, called in `phase_d.PhaseD.run` at §1.9, before the §2/§3 uploads): a generator exception, a `None` return and a failed promotion to `thumbnails/lf_NN.jpg` each raise `RuntimeError`; all three used to be warnings that let a long-form publish with no thumbnail while the run reported success. Attaching the JPG needs a YouTube video ID, so `_attach_lf_thumbnails` stays post-upload at §5b and still records `thumbnail_attach_failed` on the upload entry rather than raising (the video is already public). Tests stub the generator via the autouse `stub_lf_thumbnail_generation` conftest fixture (opt out with `@pytest.mark.real_lf_thumbnail_generation`) — a fake `.mp4` genuinely produces no thumbnail.

- **Superlong-part thumbnails — one PER PART, never the day's LF thumbnail** (`phase_d_metadata._generate_superlong_thumbnails` / `_attach_superlong_thumbnails`, called from `phase_d.PhaseD.run` alongside the LF calls above — generation at §1.9 upstream of upload, attach at §5b post-upload): reusing the day's LF thumbnail was explicitly rejected — a 3-part day would show three IDENTICAL images in subscriptions, worse than YouTube's auto-picked frame. Mirrors the LF gate's two-part shape and hard-fail/soft-fail split exactly: generation raises `RuntimeError`/`ValueError` on any failure (upstream of the irreversible upload), attach records `thumbnail_attach_failed` on the part's OWN `superlong_uploads.json` sidecar entry rather than raising. Iterates `youtube_sidecar.iter_superlong_parts(state)` (composite `"date:part_index"` keys); filename is `thumbnails/sl_<date>_<NN>.jpg` — the `sl_` prefix plus date component makes collision with `lf_NN.jpg` structurally impossible. Title text is the part's burned OST `record["location"]` (never the YouTube title, which already carries its own `— Part N of M` suffix); the part number is stamped separately as the thumbnail SUBTITLE (`Part N of M`) so same-day parts read apart at a glance. A part with no generated thumbnail file, or no `superlong_uploads.json` entry (never uploaded, upload failed, or upload pending), is skipped quietly at attach time — never raises, never attaches the wrong image to the wrong part. Tests: `tests/test_superlong_thumbnails.py`.

- **Thumbnail frame extraction quality** (`thumbnail_text_overlay.extract_frame_from_video` plus the frame probe in `drive_phases/thumbnail_generator`): the extract scales with `flags=lanczos` — swscale's default bicubic softened the 4K→1080 downscale, the same defect already fixed for the shorts crop — and states the range conversion explicitly (`in_range=<LONGFORM_COLOR_RANGE>:out_range=pc`) on both the shipped frame and the measurement probe, instead of leaving the limited-range-video → full-range-JPEG hop to implicit swscale behaviour. Because the probe now measures in the same domain the JPEG lands in, picker scores and shipped pixels agree. Font selection goes through `_font_search_paths`, which puts `ffmpeg_filters.FONT_PATH` (the exact face every `drawtext` burn uses) ahead of the platform lists; the module previously carried its own literal list and tried Arial first, so the same title could render in two faces across two surfaces. Tests: `tests/test_thumbnail_extraction_quality.py`.
- **Waypost owns long-form title selection** (`gomoveshift/pipeline/title_decision.py`). GMS supplies GPS-backed title facts for the retained LF and an assembled factual baseline. Waypost returns a decision with the chosen title and reason; an absent performance snapshot keeps that baseline as `insufficient_evidence`, and absent route facts are recorded as `facts_unavailable`. Phase BC makes and stores the decision before encoding. Phase D uses the stored choice and refuses changed inputs. A title upload requires a decision matching the exact text being sent; historical already-uploaded items remain readable. Tests: `tests/test_pre_render_waypost_decision.py`, `tests/test_title_decision.py`, `tests/test_title_decision_required.py`.
- **Pre-encode Waypost approval for retained GPS LFs** (`phase_bc_day_first._approve_waypost_titles_before_encode`): after the route-claim gate and label reconciliation, Phase BC assembles the same YouTube baseline Phase D would use and calls Waypost once. A Waypost winner that omits a material retained place is excluded in favor of a safe baseline; an unsafe baseline refuses before `run_all_days`. The decision records its input label, OST and a digest of retained-route evidence. Phase D requires that record for a GPS-bearing LF, compares the OST and digest to current state, and supplies the exact approved decision to `LongFormMetadataGenerator.generate`; the generator refuses a baseline change and makes no second title choice. Phase D also refuses metadata that replaced the decision. GPS-less legacy LFs retain the existing decision path. No production `EvidenceSnapshot` is supplied yet, so Waypost records `insufficient_evidence` for eligible route facts and keeps the factual baseline; do not describe it as a measured SEO winner. Tests: `tests/test_pre_render_waypost_decision.py`, `tests/test_final_text_record.py`.
- **GMS-17b: Phase D refuses a long-form title its location evidence does not back** (`location_evidence.refuse_unsupported_title`, called in `phase_d_metadata._build_metadata_per_lf` before `<lf>_youtube.json` is written). A title with an `A to B` claim runs `title_claim_issues` against the LF's `state.per_lf_location_evidence` record; no record, an endpoint never entered (or only `near`), or endpoints against the travel order raise `TitleEvidenceError` and log `TITLE-EVIDENCE E: LF <n> title ... refused: <reason>`. A missing record is a refusal, not a skip. A title with no `A to B` claim is not checked. Consequence: a GPS-less LF, or one whose baseline `A to B` title falls back with `facts_unavailable`, now stops Phase D instead of shipping that baseline. Tests: `tests/test_phase_d_title_evidence_gate.py`.
