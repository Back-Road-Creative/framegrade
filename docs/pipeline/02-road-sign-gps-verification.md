## Road-sign GPS verification (`--sign-verify`; on by default for a GPS-less drive)

Every location surface descends from ONE chain — GPS trace → geocoder → `ResolvedLocation`. When the trace and the geocoder agree with each other but are both wrong (drift, a mislabel, a degraded reverse-geocode), no existing gate can tell: they all read the same chain. Road signs are physical ground truth and the only independent evidence available. This is the structural gap the feature fills — not a better geocoder, a second opinion.

**Advisory evidence, never a location authority, for an LF the camera located.** Nothing in the verifying sign path writes, mutates, or returns a location. The one exception is an LF with zero GPS fixes (below), where the signs are the only evidence there is. It only reports agree / no-signal / conflict against the `ResolvedLocation` the pipeline already computed, so the "one resolved location per LF, computed once" invariant is untouched. Default OFF on a drive with GPS (`config.drive.sign_verify`); the strict escalation is a second opt-in.

**A drive with a GPS-less episode reads its signs without being asked** (`sign_pass.sign_pass_wanted`, the Phase A gate). The camera never located it, so the signs are the only evidence of where it was; `nctopa-2026-03-05-rec0063` (13 chapters, telemetry present, zero locked fixes) rendered with no evidence at all because the pass was opt-in. The operator's decision still wins: a saved `--no-sign-verify` (`state.sign_verify is False`) turns it off, `--sign-verify` turns it on for any drive. On such a day the flat per-day cap gives way to one sample per `config.drive.sign_verify_gpsless_sample_period_s` (default 10 s) of footage — an interstate exit sign is in frame for a few seconds, and 120 samples over a four-hour drive missed most of them — and the reader runs on the GPU when torch sees one (`ocr._cuda_available`; a failed probe falls back to CPU, which is always correct, only slower).

**Requires the optional `signs` extra — `pip install -e '.[signs]'`.** `easyocr` is not a core dependency: it drags `torch`, whose Linux wheel unconditionally bundles the CUDA stack (cuda-toolkit, cudnn, nccl, cusparselt, nvshmem, triton). Measured, that is a 5.5 GB environment versus 834 MB without it — ~4.5 GB that a run without `--sign-verify` never loads. Every import is lazy (`analysis/ocr.py` imports easyocr inside the `easyocr_reader` property; `analysis/sign_pass.py` never imports it at all), so the package is only needed when the pass actually runs, and the whole suite passes without it installed. Reaching the reader without the extra raises a `ModuleNotFoundError` naming the install command rather than a bare missing-module traceback. EasyOCR is constructed with `gpu=torch.cuda.is_available()` (`ocr._cuda_available`), so on a box with a CUDA device the payload torch brings is used; without one the reader runs on CPU — the `gpu` extra exists for onnxruntime-gpu in `redactcam`.

- **Two halves joined by `SignHit`** (`analysis/sign_evidence.py`, plain JSON-native dataclasses that round-trip state with `asdict`/`cls(**value)` like `ResolvedLocation`). The expensive OCR pass is per-DAY in Phase A; the cheap comparison is per-LF at dry-run / phase-BC time when LF spans and resolved models exist.
- **Phase A pass** (`analysis/sign_pass.py::collect_sign_hits`, wired as A6 in `phase_a.py`): days grouped by the real `day_grouper.group_episodes_by_day`, per-episode day-master offsets mirroring `gps_enrichment._build_gps_points_by_date` (same cursor, same `effective_offset`, same in-window clamp). Candidate seconds are MOVING only (`gps_quality.window_median_speed_mps` over a bisect-sliced sub-list — the naive whole-trace call is quadratic), sampled EVENLY and hard-capped per day (`config.drive.sign_verify_max_samples_per_day`, default 120 — the cost governor, bounding native-resolution seeks per day no matter how long the drive is; a GPS-less day's cap is the larger of that and one sample per `sign_verify_gpsless_sample_period_s`). Each survivor gets ONE native-resolution targeted seek; sign ROI comes from `signs.SignDetector` on that same frame (no second decode), then the local EasyOCR entry point on the crop. Runs on raw PRE-blur footage — blur targets faces/plates/occupants, never signs.
- **The pass reports progress and where its samples died.** Per day, `collect_sign_hits` logs at INFO every `sign_pass.PROGRESS_EVERY` (50) sampled seconds: `Sign pass <date>: progress <done>/<total> sampled, <hits> hit(s), <elapsed>s elapsed, ETA <s>s (sampled=… grabbed=… region=… ocr_text=… claims=…)`, and the day's summary line carries the same counters and elapsed time. `SignPassDayStats` counts the stage each sampled second reached — `grabbed` (decoded to a frame), `region` (a sign-shaped region), `ocr_text` (non-empty OCR text), `claims` (at least one place claim; equals the day's hits) — and `run_sign_pass` persists them as `state.sign_pass_stats` (`{date: counters}`, plain JSON) and prints them per day on the A6 line. Why: `nctopa-2026-03-05-rec0063` (2026-11-08) ran 1320 samples at ~7 s each with no log line for two hours and then one `recorded 0 hit(s)`; a separate probe was needed to learn that every frame decoded, 7/16 had a region and 2/16 read text — now the A6 line says that. Tests: `tests/test_sign_pass_progress.py`.
- **The pass is keyed independently of the score cache.** A6 sits BEFORE the score-cache resume gate (the cached `drive_scores.npz` branch) and its early return, guarded on `state.sign_hits_by_date is None`, so a re-scored run with a warm multi-hour scoring checkpoint still back-fills evidence and `PHASE_A_CODE_VERSION` never needed bumping. A resume with `phase_a` CHECKPOINTED never re-enters `PhaseA.run` at all, so the orchestrator's resumed-phase branch calls the same body (`sign_pass.run_sign_pass`, via `drive_orchestrator.backfill_sign_pass_on_resume`) from the resumed state's ingest plan, episode paths and rebuilt GPS traces, and checkpoints the evidence before `--label-dry-run` prints or the pre-encode gates read it. The checkpointed plan is a shallow rehydrate (`IngestPlan.from_dict` leaves `episodes` as the serialized dicts), so the back-fill resolves it through `phase_bc_day_first._resolve_ingest_plan` first — handing the dicts straight to `group_episodes_by_day` drops every episode and reports 0 hits across 0 days without decoding a frame. A GPS-less drive parked past Phase A before the pass was the default gets its signs read on its next resume. A read-but-empty day persists as `{date: []}`, not omitted, so an all-empty drive still reads as read; `{}` (zero days grouped) means nothing was decoded, is never recorded, and a checkpoint already holding one is read again on the next resume. Setup failures propagate to phase_a's warn-and-continue (so a broken environment retries next resume); per-second failures are swallowed (so one bad seek can't kill a multi-hour run).
- **Bucketing keys on `episode_index` + `t_local`, NOT a day-master offset** — the same `(source_file_index, start_time..end_time)` coordinates LF segments already use, so assigning a hit to an LF is an exact span test rather than a reconstruction. `sign_verify.bucket_hits_by_lf` therefore requires an UNPARTITIONED plan: `_partition_lf_plans_by_date` remaps `source_file_index` from global to day-local IN PLACE, and bucketing a global-space hit against a remapped plan misfiles evidence into the wrong LF — precisely the desync class this feature exists to catch. Both consumers rebuild a fresh plan via `_build_drive_plan_from_state` for this reason.
- **Claims** (`ocr.parse_sign_claims`, extending the existing pattern table in place): county (BARE name — no `County` filler, so it compares directly against `regions`/`vote` members), state, town, route. A full state name is a state claim only beside a place claim ("Colleton County South Carolina") or a boundary cue ("Welcome to", "State Line", "Entering", "Leaving", "Welcomes You"); a destination on a guide or distance sign ("Winchester / West Virginia / Exit 310") says where the road goes, not where the camera is, and is no claim. Route values are produced by calling the real `title_builder` road-ref member normaliser, so they cannot drift from the via-road vote form they are compared against. Routes match case-sensitively (a case-insensitive match reads "…ahead in 2 mi" as route `IN-2`). The existing noise guards do the heavy lifting: the capture stop-words kill "County Road 12", the `county council` suffix phrase kills "Kerry County Council", and a lone postal abbreviation is never a state claim on its own.
- **Conflict rule is deliberately conservative** — the same conservatism as the far-road gate, because over-flagging trains operators to ignore the gate. ONLY a state or county claim, in ZERO sampled `regions`, asserted by at least `config.drive.sign_verify_min_corroborating_hits` DISTINCT hits, can conflict. One noisy hit never contradicts GPS. Town and route claims are corroboration-only and can never conflict. Region/vote keys arrive as `"County, State"` from the persisted model but `"County|State"` from `dominant_location`, so the comparator splits on either — a single-format reader would silently no-signal every dry-run LF.
- **Silence is not agreement.** No claims → `no-signal`, a distinct third status. An OCR pass that read nothing must never be reported as corroboration, and an LF with no resolved model (GPS-less / legacy / quorum-degraded) is a no-op rather than a conflict.
- **Surfaces.** `--label-dry-run` (`lf_listing.print_label_dry_run`) prints the evidence beside the county vote it is evidence about, WARNs on conflict with the greppable `SIGN-VERIFY-CONFLICT` tag, and still exits normally — the whole block is wrapped so advisory evidence can never break the label gate. `--sign-verify-strict` adds a sibling of the pre-encode location invariant in `phase_bc_day_first`, at the same call site with the same `RuntimeError` contract, upstream of any encode or upload. The strict gate passes NO geocoder: a hard gate must not turn a Nominatim outage into a blocked encode.
- **Egress posture.** Frame crops never leave the box — the sign path calls the local EasyOCR entry point directly, so a revived Claude OCR fallback could not route a frame off-box. Forward-geocoding an OCR'd town name is allowlisted and already sanitised, and is used only on the advisory surface.
- **A GPS-less LF may take its label FROM the signs** (`analysis/sign_label.py::derive_sign_label`). An LF with zero fixes has no GPS chain to verify; its label used to come from an operator, typed from memory and measured by nothing (`nctopa-2026-03-05-rec0063` burned "Through The Valleys And Ridges" over a divided interstate). The deriver produces the county shape only — `"Colleton County, SC"`, the form `route_claims.region_label` gives a measured county, never a town and never "A to B" — and only when every rule holds: at least `config.drive.sign_verify_min_corroborating_hits` (default 2) hits from DISTINCT seconds name the same county (two reads of one frame are one observation); no other county is named anywhere in the LF (a county-line sign inside the LF means one label would be wrong for part of it, so the operator decides); exactly one state is named; and the LF has no GPS fix at all (one fix and the GPS chain owns the label, signs verify it). Any refusal carries a reason starting `LF <idx>:` for the dry-run. The result is a `SignLabel` with its evidence (hit count, seconds, raw sign texts) for the LF's tier evidence, so the provenance sidecar and the OST system review can see why the LF says what it says. This module only derives. **`--label-dry-run` previews it, suggest only** (`lf_listing._print_lf_sign_suggestion`): beneath each LF's `<no GPS — --per-lf-location override required>` line it prints `sign-derived label (suggest only): 'Colleton County, SC' — copy as --per-lf-location '1=Colleton County, SC'` with the deriver's reason line, or `sign-derived label: none (N sign hit(s))` with every refusing rule (`0 sign hit(s)` prints explicitly — silence is never a label), or `unavailable (<error>)` when bucketing failed; a GPS-bearing LF never gets a suggestion (its `sign evidence` block is the verifier). Nothing is written into the override map or the state and the OST review still needs a person (measured on `nctopa-2026-03-05-rec0063`, 2026-11-08: 1320 A6 samples, 0 hits — exit and destination signs are not county/state claims under this grammar, so the preview printed no label for it). Writing the label into the per-LF override map and the review outcome is a later change. Tests: `tests/test_sign_label_dry_run_preview.py`.
