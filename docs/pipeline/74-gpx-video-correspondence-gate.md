## GPX↔video correspondence gate

Runs in Phase A, upstream of every irreversible artifact, ONLY on the external-provenance path (`Episode.gpx_source`; a whole-episode GoPro GPMF track is frame-aligned by construction → skipped). `gopro_gps.assert_gpx_video_correspondence` raises `GpxCorrespondenceError` (`GPX-CORRESPONDENCE:`) on: start-time `|Δ| < 1h`; span within `max(120s, 0.25×duration)`; embedded ISO-6709 coord within 25 km. Degrade-not-fail: missing inputs never raise, but span/start-time still run whenever inputs exist (the swapped-GPX case). The start-time check compares the GPX's UTC start against `video_creation_time.timestamp()`; `extract_recording_date` parses the container tag as **UTC-aware** (ffmpeg writes it in UTC), so the epoch is host-TZ independent — a naive parse would misread the wall clock as host-local and skew the gate by the host's UTC offset, false-blocking a correct GPX (or false-passing a wrong-drive one).

**Sub-slice variant.** A GPS-split sub-episode carries provenance `gpmf_slice` (set by the splitter and by `extract_and_merge_gpx` on resume). Its GPX is time-windowed out of the parent's own GPMF — never a swapped track — but a gross anchoring/slicing error can still mis-window it, so Phase A runs `assert_slice_gpx_correspondence`: start-time (same 1h tolerance) + a **one-sided** span check (only an *over*-covering GPX raises; under-coverage from a lock-delay prefix or a mid-clip dropout is legitimate partial coverage). No embedded-coord check — a stream-copy slice inherits the *parent's* start-location tag, which is wrong for a later slice. `gps_coverage_window` is a read-only companion: it reports a clip's GPS coverage in video time (anchored on `creation_time`, cold-start anomalies skipped via `effective_offset`), so a nonzero first-fix offset surfaces an unlocked GPS prefix.

**Every episode GPX write is atomic; the pre-set `gpx_path` adoption gate parses, not just stats.** `extract_and_merge_gpx`'s merge write, its `_extract_gpx_time_range` slice write, and `gopro_gps.extract_gopro_gpx`'s per-chapter write all route through `_atomic_write.atomic_write_text` (temp file + `os.replace`), so a crash mid-write leaves the prior file intact instead of truncated. The pre-set-`gpx_path` adoption branch (splitter-set sub-episode GPX, or an operator/resume `external` sidecar) no longer treats `exists() and size > 0` as sufficient — it parses the file and requires ≥1 trackpoint (`_gpx_has_trackpoints`), since a truncated write is still nonzero-size. A sub-episode (`recordings == []`) whose pre-set GPX fails that check has no chapter recordings to re-extract from, so it's a hard `RuntimeError` naming the bad path rather than a silent downstream GPS corruption; a chapter-derived episode instead discards the corrupt file and falls through to normal chapter-GPMF extraction. Tests: `tests/test_gpx_atomic_write.py`.

**Splice correctness at the split points (`_split_episode_at_points`).** Each sub-slice is cut by its own independent `ffmpeg -ss <start> -i src -t <dur> -c copy`. A stream copy cannot begin on a non-keyframe, so ffmpeg silently rewinds `-ss` to the previous source keyframe — slice N stopped at the boundary it was given while slice N+1 began up to one GOP earlier, and after the day concat that footage played twice at every splice. Every *interior* boundary is therefore snapped **forward** onto a real keyframe (`keycut.probe_keyframes` + `snap_start_to_keyframe`) before any slice is cut, which makes the rewind a no-op and lets the slices tile exactly. Forward only: backward is the bug. Two split points inside one GOP land on the same keyframe and are de-duplicated so no zero-length slice is emitted. `probe_keyframes` returning `None` means *unknown*, not *no keyframes* — the boundaries are left as-is with a loud WARN rather than refusing to split a multi-hour episode. This is the same forward-snap discipline the montage trim and day-first LF extraction already use. Tests: `tests/test_episode_splitter_self_consistent.py`.

**Fixes carry their footage second (`gms_media_s`).** Mapping "footage second t" to GPS time as `first_fix + t` was late by the GPS lock delay, and in a multi-recording episode (recordings up to 2 h apart are concatenated, the gap skipped) every short after a stop read GPS from up to 2 h earlier — wrong county, wrong state. `gopro_gps.build_stamped_gpx` now stamps every trackpoint with `<extensions><gms_media_s>` (its position in the episode concat; bare tag `shorts_models.GPX_MEDIA_S_TAG`, namespace-free so it survives gpxpy re-writes), and `extract_and_merge_gpx` advances the per-chapter offset for EVERY chapter, including ones dropped for no GPMF/lock. Wall-clock `<time>` is untouched. `parse_gpx_file` rebuilds a footage clock from the stamps (`timestamp = footage_origin + media_s`, where the footage origin is the first fix time minus its own `gms_media_s`; partially stamped → `GPSError`), `shorts_models.footage_origin` / `effective_offset` return that origin (footage second 0) for stamped files, and the split/slice path uses the stamp instead of `first_fix − creation_time` (slices rebase `gms_media_s` to 0). Unstamped GPX (external sidecars, pre-existing files) keeps the old first-fix behaviour. `PHASE_A_CODE_VERSION` is 2 so scores computed against the old origin are not reused. Tests: `tests/test_gps_media_time_anchor.py`.

**Consumers.** Resume (`gps_enrichment.rebuild_gps_per_episode`), longform (`longform_assembler` segment GPS lookup) and the legacy shorts path (`pipeline/shorts_extractor`) all use `effective_offset`, i.e. the footage origin on a stamped GPX, so a resumed run labels footage exactly as fresh ingest did. `VideoToGpsTimeMapper(footage_clock=True)` (set from `footage_origin(gps_data) is not None`) inverts stop removal only and never stretches a stamped track by the GPS-span/video-duration ratio, which would re-introduce drift across recording gaps. Tests: `tests/test_footage_clock_consumers.py`.
