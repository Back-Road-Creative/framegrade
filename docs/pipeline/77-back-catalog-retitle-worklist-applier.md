## Back-catalog retitle worklist + applier

- `tools/retitle_worklist.py` builds the CSV. With `--compose` (**default ON**) `suggested_title` comes ONLY from the video's GPS evidence record (`location_evidence`, inline in the videos YAML or from an `--evidence` JSONL sidecar of `{"video_id", "record"}` lines): `title_from_evidence` titles the first to the last entered place, `"{first} to {last}, {ST}"` (one place: `"{place}, {ST}"`; endpoints in different states stay `needs-human`). The current title and the YAML's structured fields are never a place source, so a video with no record is `needs-human`. A `duplicate-title` collision is disambiguated with the same `"(Part N of M)"` shape `title_builder.ensure_unique_titles` uses for sibling LFs. Every composed candidate is run through `retitle_apply.evaluate_row` and `title_claim_issues` before it's handed out — a candidate that would be `REFUSED` stays `"needs-human"`. Each row carries its record in the `location_evidence` column. `--no-compose` reproduces the earlier plain (structured-fields-only) output byte-for-byte. `tools/retitle_apply.py --worklist PATH` gates each row's suggested title with the real checks (`content_gates.find_grammar_issues`, `place_corrections.find_denylisted`, 100-char cap, non-empty/non-placeholder) — any failure is `REFUSED` and never applied. Every row must also carry `location_evidence`: the segment's `gomoveshift.pipeline.location_evidence.LocationEvidence` record as JSON (built by `build_location_evidence` from that segment's own GPS fixes; each entered place has a scope `in`/`through`, method, provenance and a stable `evidence_id`). `retitle_apply.evidence_issues` fails closed: no record, an endpoint the trace never entered (or only passed `near`), or endpoints against the travel order is `REFUSED`. The check runs in `dry_run`, not `evaluate_row`, because the worklist runs `evaluate_row` on a candidate before writing the row. `apply_updates` re-checks the record immediately before each push; a row it no longer supports is logged `REFUSED` and never sent. Dry-run by default; `--apply --yes-live` fetches the live snippet, `SKIPPED_STALE`s a row whose live title no longer matches the worklist's `current_title`, else mutates only `snippet.title` (categoryId/tags untouched) via `videos().update`, plus `snippet.description` in the same call when the row carries a `suggested_description`. A description row must also carry `current_description`, the drift check: a live description that no longer matches it is `SKIPPED_STALE`. The suggestion passes the same grammar and denylist gates, plus YouTube's 5000-byte and no-`<`/`>` limits (else `REFUSED`). `retitle_worklist.rewrite_description_place(description, old_place, new_place)` builds that suggestion for a wrong-place Short: a whole-word swap in the text, and every place hashtag (old place, its state, a smashed route tag) replaced by the new place's `_location_hashtags`. It returns `None` (leave the description) when the text never names the old place, or when a place tag can't be isolated. Sequential, one retry, stops on the first API error; every outcome is appended to `<worklist>.audit.jsonl` (`old_description`/`new_description` included on a description row).

### Apply safety

- **Idempotent.** A live title already equal to `suggested_title` (and, on a description row, a live description already equal to `suggested_description`) makes no update call and is recorded `ALREADY_APPLIED`, so a second run over the same worklist makes 0 update calls.
- **Snapshot before write.** Before each update the pre-change live `snapshot_title` / `snapshot_description` are appended to `<worklist>.audit.jsonl` as a `SNAPSHOT` line and fsynced, per row, so a crash mid-run keeps them. Each pushed row then adds one outcome line. `apply_updates` returns outcome records only.
- **Read-back.** After a successful update the snippet is read again (up to 3 reads, `sleep` injectable, because a read right after a write can lag). The live title, and the description when changed, must equal what was sent (whitespace-stripped). Otherwise the row is `VERIFY_FAILED` and the run stops like an API error. Only a verified row is `APPLIED`; its audit line carries `readback_title` / `readback_description`.
- **Reversal worklist.** Every `APPLIED` row appends to `<worklist>.revert.csv` (`--revert-out` overrides): `video_id, current_title` (the new title), `restore_title` (the snapshot), and `current_description` / `restore_description` when the description changed.
- **`--revert PATH`** restores from that file; dry-run unless `--apply --yes-live`. It refuses a file that is not in the reversal format. Per row: live value equal to `current_*` is pushed back to `restore_*` (snapshot and read-back as above); already at `restore_*` is `ALREADY_APPLIED`; anything else is `SKIPPED_STALE`. It does NOT run the place/evidence gates, because it restores the exact prior live text from the snapshot. Its audit log is `<revert file>.audit.jsonl`.
- **Hashtag gate.** `retitle_apply.hashtag_issues` refuses a title whose hashtags are absent from the description the video will have after the write (same rule as `plan_io._assert_consistent`, reusing `hashtags_in`): the row's `suggested_description`, else the live description at apply; dry run reads `current_description` when the row has it, else defers to apply. A refusal at apply is logged `REFUSED` and never sent, so the plan sync cannot later be refused for the same cause.
- **Plan sync.** Each `APPLIED` (and `ALREADY_APPLIED`) row, and each restored row, writes the title now live into the publish-plan sidecar of every published YouTube delivery of that video (`gomoveshift.publishing.plan_title_sync.sync_plan_title`; local file only, re-parsed through `load_publish_plan` before it replaces the old file; one `response_log` `sync_plan_title` row each), so `publishing-status --validate --live-catalog` never reads our own retitle as drift. The queue is `--queue-dir`, else config `seo.storage_path`; a live run with neither refuses before any write. A failed sync never undoes the live write; it warns and names `gomoveshift queue sync-plan-titles --audit <log> --apply`, which replays an audit log's newest `APPLIED` title per video into the sidecars (dry run unless `--apply`; each video is attempted independently, a refusal prints `REFUSED <video_id>: <reason>` to stderr and the run continues, the dry run predicts every refusal by parsing the new title through the plan gate on a temp copy, an already-matching plan reports `already synced`, rc 1 if any refused) — also the path for retitles made before this existed.

## Catalog inventory (`gomoveshift catalog-inventory`)

- `gomoveshift catalog-inventory --live-catalog PATH --out-dir PATH` produces the title-accuracy inventory that feeds the retitle worklist. `--live-catalog` is a `live_catalog.json` (`{"videos": {id: {title, privacy, publish_at, published_at, duration_s, recording_date}}}`) from a read-only `videos.list` pass. Each live video ID is joined to local evidence: LF upload records (`<vid output dir>/*/youtube_uploads.json`), tracking files (`<output dir>/*/tracking/*.json`), the social queue's `deliveries` table (opened `mode=ro`), Waypost `yt_sync_` events and the content ledger. Source paths default from `GMS_OUTPUT_DIR` (also the default video output dir) and `config.seo`; `--vid-output-dir`, `--output-dir`, `--queue-db`, `--events-jsonl`, `--ledger` override them. No input is ever written.
- `gomoveshift catalog-fetch --out PATH [--known-ids JSON]` writes that `live_catalog.json`: it enumerates the channel through the read-only client, then runs `videos.list` in batches of 50. It never writes to YouTube, and its output feeds `catalog-inventory --live-catalog`.
- Each row carries `kind` (`short` when `duration_s <= 180`) and `evidence_tier`: `segment` (an LF upload, delivery or tracking record names the footage), `project` (only the ledger names a project), else `none`. `gomoveshift/catalog/inventory.py` writes `longform.csv`, `shorts-nonpublic.csv` and `shorts-public.csv` (oldest `published_at` first) under `--out-dir` and the command prints the per-slice counts.

## Catalog classification (`gomoveshift catalog-classify`)

`gomoveshift catalog-classify --inventory PATH --out-dir PATH [--kind long|short|all] [--limit N] [--output-dir DIR]` builds the two inputs batch 1 needs and nothing else: a per-video GPS location-evidence record and an A-E class for the live title. Read-only; no YouTube write exists in it. `--inventory` is a `catalog-inventory` slice (`longform.csv`); `--kind` defaults to `long`.

- **Record.** For a row with `project` + `lf_index`, the loader is the resume chain a drive uses: the project's `pipeline_state.json` (`<output dir>/<project>/_stages`, `GMS_INTERMEDIATE_DIR` honored) -> `rebuild_gps_per_episode(state.gpx_files)` -> `_build_gps_points_by_lf(state.drive_plan, ...)[lf]` -> `phase_bc_day_first._build_location_evidence_per_lf` (the Phase D builder, same trace sampling) -> `build_location_evidence`. There is no second GPS reader. Places come only from that record, never from the live title or YAML fields.
- **Classes.** `A`: the title is positively refuted: its endpoints run against the travel order, or an endpoint missing from the record is forward-geocoded (Nominatim, via the handler's `_forward`) to more than `NEAR_KM` (10 km) plus the trace's unobserved reach from every GPS fix, in the state the title names (or, with no state code, one the trace entered); the reason gives that distance. The unobserved reach is the video time past the trace's span plus its largest interior gap, at `REACH_KMH` (120 km/h): fix times are wall-clock, so a missing stretch cannot be placed and could have gone anywhere within that reach. Absence from the record alone is not refutation, since the reverse geocode names a town for few fixes. `B`: the endpoints pass, but one is a place the trace only passed `through` (the record's `in`/`through`/`near` scopes make this checkable), so the title claims a start or end the footage does not have. `D`: every claim passes the check `retitle_apply` applies. `E`: unresolved; the reason names what is missing (no project, no `lf_index`, no GPS points, a trace spanning less than 80% of the video's `duration_s` (it cannot show that a named endpoint is missing; no duration counts the same), no geocoded place, a reverse-geocode lookup that failed for that row (the batch continues; re-run to retry), a title endpoint missing from the record that cannot be located, whose forward lookup failed, that lies within 10 km of the trace or within its unobserved reach, or whose lookup lands in another state (a same-name place elsewhere), a Short with no clip audit entry (see Shorts below), or a title with no `A to B` claim the record can verify; an A/B row with no supportable replacement also lands here). `C` (performance alternatives) is never emitted: it is out of scope for this tool.
- **Shorts** (`--kind short` or `all`, inventory `shorts-public.csv` / `shorts-nonpublic.csv`). A Short is judged against its own clip, not an LF trace. `catalog.classify.load_short_evidence` reads the project's `pipeline_state.json` `short_global_index` (short path -> the global index the inventory's `short_index` carries) and joins it, by the path below the stages dir (`day_<date>/shorts/short_NN.mp4`, so a moved cache still joins), to the entry in `shorts_ost_audit_<date>.json`: the burned place (`ost_text`), the regions the clip's own GPS fixes sampled, and `place_source`. `D`: the title (letters and digits only, so `#SevenMileFord` matches `Seven Mile Ford`) names the burned place or a region (first comma part). `E` with drift: it names none of them; the reason quotes the burned place and the clip regions. `E` without drift: the burned place was inherited from the parent LF (`place_source: lf_label`), or the Short has no project, no `short_index`, or no audit entry. A Short is never `A`: the audit keeps place names, not fixes, so nothing here refutes its place, and no Short reaches `retitle_apply`.
- **Suggestion.** For A/B only, `retitle_worklist.compose_suggested_title` from the record; it must pass `retitle_apply.evaluate_row` and `evidence_issues`, else the row is `E`.
- **Outputs** (sorted by `video_id`): `classification.csv` (`video_id, kind, project, class, reason, live_title, suggested_title`), `evidence.jsonl` (`{"video_id", "record"}`, the `--evidence` format), and `worklist-AB.csv` in the exact `retitle_worklist` column format `retitle_apply --worklist` reads (`video_id, current_title, reason, suggested_title, platform, location_evidence`; no description columns, so a row never touches the live description). `worklist-shorts-drift.csv` (`video_id, project, short_index, live_title, burned_place, clip_regions, reason`) lists the drift Shorts for review; it is not a `retitle_apply` input. The command prints the class counts.

Runbook for batch 1 (keep every output outside the repository, in a dated private directory):

1. `gomoveshift catalog-fetch --out live_catalog.json`
2. `gomoveshift catalog-inventory --live-catalog live_catalog.json --out-dir .`
3. `gomoveshift catalog-classify --inventory longform.csv --out-dir classify/`
   For Shorts: `gomoveshift catalog-classify --inventory shorts-public.csv --kind short --out-dir classify-shorts/`, then review `classify-shorts/worklist-shorts-drift.csv`.
4. Review `classification.csv`, then `python tools/retitle_apply.py --worklist classify/worklist-AB.csv` (dry run: every row should print `APPROVED`).
5. `python tools/retitle_apply.py --worklist classify/worklist-AB.csv --apply --yes-live`
6. The run read-backs each write and appends `classify/worklist-AB.csv.revert.csv`; undo with `python tools/retitle_apply.py --revert classify/worklist-AB.csv.revert.csv --apply --yes-live`.
