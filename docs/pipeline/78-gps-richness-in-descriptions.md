## GPS richness in descriptions

Additive per-LF facts computed in `gomoveshift/pipeline/post_encoding_invariants.py`, persisted to int-keyed state fields, threaded to `_build_gms_description`, rendered country-aware. A missing field just omits its line.
- **Windowed to the LF's included segments** (`_window_journey_to_included_segments`): each fact parses the representative episode's whole GPX (keyed on `per_lf_gpx_path`) but is then trimmed to the LF's INCLUDED segments BEFORE any compute — `phase_d._build_included_segments_for_lf` (episode-local ranges for that same representative GPX; see the `included_segments` bullet above) → `gps_quality.trim_gps_to_clip_timeline`, projecting each waypoint from the GPX's episode-local base anchored at the first *valid* fix — the shared `effective_offset` helper skips a leading cold-start anomaly (null-island / stale-lock run) so the window can't open on the garbage prefix. Without it a best-moments LF (trim ~0.3) shipped the whole episode's distance (inflated-but-plausible, so the speed ceiling misses it) and `🗺️ Through:` listed counties whose footage was cut. An LF with no resolvable segment window keeps the whole trace.
- **Segments windowed in ISOLATION, never bridged** (`_segment_isolated_traces`): the included segments are usually several non-contiguous ranges (a best-moments LF keeps several separate clips). Windowing the whole range list at once concatenates every kept clip into one flat trace, so summing consecutive-point distance/speed folded the straight-line gap BETWEEN two kept clips — footage that was CUT — into `🛣️ Distance:` / `🚗 Pace:`. An LF cut from two distant clips could thus ship a distance several times what its own kept footage measured, the cross-segment jumps making up the rest. `_compute_per_lf_distance`/`_compute_per_lf_speed` now window and sum each range separately so a step never crosses a segment boundary. **Follow-up not yet done**: when an LF has NO resolvable segment window at all (legacy/resume path), the distance/pace still falls back to the whole unwindowed trace and ships as an unscoped number rather than a `🛣️ Full drive: 22 km (14 mi)`-prefixed one. **The description layer gates that follow-up**: `check_description_redundancy` reads `metadata_json["full_drive_stats"]` (a list of `"distance"`/`"speed"`) and hard-fails a `🛣️ Distance:` / `🚗 Pace:` line named there unless it also carries a `Full drive:` scope prefix; unflagged (kept-segment-derived) lines need none. **The generator side is wired**: `_format_distance_line`/`_format_speed_line` and `_build_gms_description`/`generate` (`longform_metadata.py`) now take `full_drive: bool` / `full_drive_stats: list[str] | None` — passing `"distance"`/`"speed"` renders the `🛣️ Full drive:` / `🚗 Full drive:` line and stamps `full_drive_stats` onto the returned metadata dict, so a flagged stat passes the gate by construction; omitting the param is the unchanged kept-segment default. **The call site is wired**: `_build_metadata_per_lf` (`phase_d_metadata.py`) mirrors `post_encoding_invariants._lf_episode_pairs` exactly to detect the unwindowed-fallback case — a `per_lf_gpx_episode_paths` entry for the LF means the number was summed per episode (windowed); its absence falls through to `_build_included_segments_for_lf`, and an empty range list there is the unwindowed whole-trace case those numbers actually came from. That case threads `full_drive_stats=["distance", "speed"]` into `generate()`; a kept-segment LF passes `full_drive_stats=None` (unchanged output).
- **One cleaned trace** (`_cleaned_waypoints`): every per-LF numeric compute fn routes waypoints through `gps_quality.filter_high_quality_points` BEFORE summing (root-cause fix for the "315 mi" class — facts used to re-parse raw GPX). **Plausibility ceilings**: distance whose implied avg speed > `_DISTANCE_AVG_SPEED_CEILING_KMH` (200) or elevation > `_ELEVATION_GAIN_PER_KM_CEILING_M` (150 m/km) is OMITTED (`PLAUSIBILITY-GATE` WARN); a stationary/empty-trace LF is the same tolerated omission. Rejected indices go to `plausibility_rejected` (threaded to completeness invariants as `tolerated_indices`) and persist to `state.per_lf_gpx_omitted` so boundary contracts exclude them; a parse failure still raises.
- **Elevation lines DROPPED from the description** (low SEO value, GPS-noise-inflated on flat drives). Compute fns + `state.per_lf_elevation_gain_m`/`per_lf_elevation_profile` are KEPT (consumed by `gomoveshift/pipeline/route_stats_sidecar.py` + the completeness invariant); the description params are now inert.
- **`🚗 Pace:`** (`_compute_per_lf_speed`): time-weighted avg over non-glitch steps (`> _SPEED_GLITCH_CEILING_KMH` 200 excluded); `_speed_character` bands the std (winding/highway/town/scenic). No completeness invariant.
- **`🧭 Heading:`** (`_compute_per_lf_bearing`): wires `_compass_from_waypoints` on first→last; suppressed for loops (net `< _BEARING_MIN_NET_KM` 2 km). No completeness invariant.
- **`🗺️ Through:`** lists regions passed through (cap 12). Admin granularity is country-keyed via the canonical `region_resolver.derive_region` (`_compute_per_lf_regions`): the per-LF country is resolved off the LF's `ResolvedLocation` (`country_code`/`is_us`) when present, label-parsed (trailing US state ⇒ `usa`) otherwise — so US LFs get STATE-level regions (not county — the label's last comma-component is a state name that no raw last-component parse could match to a country) and Irish LFs normalize to `County <Name>`. **The line never restates the LF's own label** — `_format_regions_line` filters an EXACT match (never a substring: a town-form label legitimately contains its county) and omits the line entirely when nothing else remains. That is what keeps a single-county LF inside `check_description_redundancy`'s 2x location budget: the hook and the `📍 Location:` line already spend both occurrences, so a `Through:` line naming the same region was a guaranteed third. **`🛤️ Route:`** (`_format_route_line`) surfaces `ResolvedLocation.ordered_place_sequence` town-level (≥2 places, head/tail elision beyond `_ROUTE_PLACES_CAP` 8).
- **Above-the-fold SEO line** (`_seo_search_line`): line 2 `"{Region} 4K scenic drive — {A} to {B}."` (full US state name). Same-endpoint guarded; no usable data → omitted. The ` via {Road}` clause is added only when road coverage is measured (next bullet).
- **No road without measured coverage**: road names come from untimed reverse-geocode votes and Overpass matches, not coverage measured over the LF's retained time, so they back no published claim. `road_coverage_measured` (default `False`, and nothing sets it yet) gates every description surface: the SEO line's via-road, the factual body's "drive along {road}", `_enrich_with_route_profile`'s "Roads traveled:" / "on {roads}" lines, its `named_routes` and road tags, and the chapter title's `, {road}` suffix (`MarkerMerger`). Towns, features and states are unaffected. Legacy single-video `stages/chapters.py` is out of scope.
