## Resilience & resource gates (implementation)

- **Staging dir**: `GMS_INTERMEDIATE_DIR` wins; otherwise `<output dir>/<project>/_stages/`, except when the output dir is on a `/mnt/` drive mount, where it is `config.paths.intermediate_folder` or else `<cache home>/<project>/_stages/` (cache home = `$GMS_CACHE_HOME`, else `$XDG_CACHE_HOME/gomoveshift`, else `~/.cache/gomoveshift`; a local disk). **Never `/tmp`** (tmpfs wiped on reboot). Heavy working files (episode concats, `drive_scores`, day masters) route to `state.stages_base`, NOT the output dir — a slow/unstable `--output-dir` mount can't degrade the run. Stale `_stages/` dirs >14 days are cleaned (`cleanup_stale_staging`, never the current run).
- **Preflight** (`gomoveshift/pipeline/preflight.py`): source dir, inputs, output ≥50 GB, staging ≥30 GB, RAM ≥2 GB, ffmpeg/ffprobe on PATH. Staging gate sizes peak at **source × 1.5** (`estimate_peak_cache_gb`). Resume-aware: subtracts completed days' recorded `source_bytes` before the safety factor; a phase_a-done resume passes `ingest_complete=True` and drops to `floor_gb` (no re-ingest occurs).
- **Phase A drive_scores reuse on resume**: cached `drive_scores.npz` is reused when its `_score_inputs_key` (per-episode concat path+size+mtime) matches; corrupt/missing/`--fresh` falls through to re-score.
- **Phase B+C drive_plan.json reuse on resume**: `phase_bc_day_first._load_current_drive_plan` reuses an on-disk plan only when its `plan_code_version` equals `PHASE_BC_CODE_VERSION`; a plan with no stamp or another version is rebuilt from state and saved stamped. Reusing any older plan skipped planner changes such as the GPS-gap mask (a pre-mask plan kept 825 s of GPS gap and the place gate refused the LF before any encode). A rebuild costs no encode; renders are reused by their own fingerprints.
- **`--label-dry-run` / `--list-lfs` never waits on the shared GPU lock**: `drive_orchestrator.run()` only calls `acquire_gpu_lock()` at all when the invocation isn't a labels-only one in `full_drive` mode with no `--preview`/`--phase` (both of those can still reach a real encode, so they still take the lock) — that mode's LF boundaries need real per-second `COL_TIMESTAMP` values but not real composite quality scores, so `PhaseA.run(state, labels_only=True)` skips `UnifiedSegmentScorer.score_file` (the GPU decode) and synthesizes a real-duration score array instead (`_synthetic_score_rows`), and never calls `save_scores` on it (a labels-only run must never poison a later LIVE run's resume-cache check above with fabricated scores). The synthetic array pins `COL_MOTION_ENERGY` to 1.0, not 0 — `build_stop_mask` falls back to optical motion where GPS speed is unmeasurable, and a zero motion value would mask every GPS-less second as a stop, dropping real LFs from the printed labels. A resumed phase_a still prints labels and returns before phase_bc/phase_d, same as a fresh one. A labels-only `best_moments` run still needs real scores for its boundaries, so it still takes the lock but non-blocking (`wait_s=0`) — it fails fast naming the holder rather than silently waiting out `GMS_GPU_LOCK_WAIT_S`.
- **Day-master integrity & preservation**: before deleting a master (~60 GB, ~6h to re-encode) every `shorts/short_NN.mp4` must exist, be non-zero, ffprobe-valid, count-matched — else master stays + ERROR with absolute path. A FRESH encode is gated the moment the master is promoted (`os.replace`) inside `encode_day_master`: one ffprobe of the promoted file against `day_batch.total_duration`, same `DURATION_INTEGRITY_TOLERANCE_S`. That gate used to live only in `build_master_record`, which `run_day_pipeline` calls LAST — after every per-LF OST burn, every short and every superlong part had already been encoded from the bad master; `build_master_record` keeps its own (cheap) assertion so a recorded duration pair is never written uncompared. Cached-master resume validates against recorded `expected_duration`/`master_duration`/`master_fingerprint` (`size:mtime_ns`, not sha256) via `verify_cached_master` when raw episodes are absent — unblocks purging raw episodes; a mismatch (> `DURATION_INTEGRITY_TOLERANCE_S` 2.0s) still raises. The record also carries `encode_algo_version` = `MASTER_ENCODE_ALGO_VERSION`, and a record stamped with a different value is refused (re-encode with `--fresh`). That version is **derived, not hand-bumped**: `"<MASTER_ENCODE_RULE_GENERATION>-<sha256 of the frozen encode constants>"`, where the constants are every `encoding_constants` name prefixed `LONGFORM_` or `AUDIO_` (collected by convention, so a new frozen knob folds in on its own). It was a bare integer through generation 1, which meant a change to NVENC CQ / preset / profile / pix_fmt / bitrate floor / maxrate ratio moved the master's pixels and nothing else — the resume gate revalidated the pre-change master and every LF and short cut from it shipped the old encode. The generation counter stays hand-maintained for rule changes no constant expresses (the attenuate-only audio and privacy-blur waves). `SHORTS_*` is deliberately **out** of the fingerprint: no shorts parameter reaches the master, and a shorts-ladder retune must not cost a ~6 h / ~60 GB re-encode. Mirrors `GRADE_ALGO_VERSION`, which self-derives from the grade math the same way. Tests: `tests/test_stale_artifact_reuse_gates.py`.
- **Stop-removal verification gate** (`gomoveshift/pipeline/stop_verify.py`): `verify_stops_removed` runs in `StopRemovalStage` on the cut output BEFORE the irreversible stage-9 encode — proving the stage removed the stops rather than discovering a silent miss hours later. Only runs when stops were detected (`stops_found > 0`). Three checks raise `StopVerificationError` (greppable `STOP-VERIFY`): (a) **residual re-scan** — re-runs `StopProcessor.detect_stops` on the cut output, raises if any low-motion span ≥ `stop_detection.min_stop_duration` survives (expect zero); (b) **duration reconciliation** — `|output_duration − expected|` must be ≤ `DEFAULT_DURATION_TOLERANCE_S` (3.0s), where `expected = Σ(keep_segment durations)` for hard cuts and `Σ − (N−1)·crossfade_duration` when crossfade overlaps (mirrors `_cut_and_stitch`); (c) **keep-segment structure** — monotonic, non-overlapping, within `[0, source_duration]`. Escape: `--skip-stop-verify` (`config.drive.skip_stop_verify`, NOT_PERSISTED registry row mirrored to config like `--no-audio`). Tests: `tests/test_stop_verify.py`.
- **Montage assembly gate** (`montage_builder.build_montage`): the assembled montage is duration-verified via `PipelineValidator.validate_montage_output` (10% tolerance — `_trim_peak_to`'s keyframe snap moves cut points by up to a GOP) BEFORE it is prepended to the LF and encoded. A montage that fails returns `None`, which `prepend_montage` already propagates so the caller skips the LF rather than publishing a broken one; previously the concat output was returned unchecked and an empty clip extraction or truncated concat only surfaced after the irreversible multi-hour encode. `probe_duration`'s `0.0` failure sentinel is NOT treated as a bad montage (an ffprobe that cannot run says nothing about the file) — it WARNs that the montage shipped unverified and passes.
- **Episode ingest concat is never reused truncated** (`ingest/concatenator.concat_episode`): ffmpeg writes `episode_NN_<date>.partial.mp4` and it is renamed to `episode_NN_<date>.mp4` only on success, so a stopped run leaves nothing at the reused name. A cached concat (from older code, or copied in) is reused only when it probes to at least `_CACHED_CONCAT_MIN_FRACTION` of the episode's summed chapter durations; otherwise it is moved to `<name>.invalid` with a `CONCAT-CACHE-INVALID` WARN and rebuilt. Failure mode: a relaunch reused a moov-less concat a killed run left behind and died in Phase A with "produced ZERO score samples".
- **Montage prepend concat uses the shared runner** (`montage_builder.prepend_montage` → `ffmpeg_runner.run_ffmpeg_quick`): the final `[montage + LF]` stream-copy concat previously ran on a bare `subprocess.run`, so a timeout or crash left a truncated `output_path` on disk for a resume to mistake for a finished LF. The shared runner deletes partial output before raising; the failure is still reported as `None` so the caller's skip-this-LF contract is unchanged.
- **Colour range: the TAG and the SQUEEZE are separate steps, in different files.** `color_filters.get_encoding_args` only *stamps* metadata (`-color_range tv` = limited 16-235, `-colorspace/-color_primaries/-color_trc bt709`) — it describes the pixels, it does not convert them. The actual full→limited conversion is a filter, `scale=in_range=<probed>:out_range=limited` (`single_pass`), whose `in_range` follows the PROBED source range via `_scale_range_token` so a limited-range source is a no-op instead of being double-compressed. Stamping `tv` while feeding unsqueezed full-range pixels is the range mismatch that crushes blacks and clips whites; a comment above the stamp used to claim it "preserved full range", which is the reading that reintroduces the bug.
- **GOP is a fixed 60 frames, not fps-derived**: output is normalised to `30000/1001`, so 60 frames is 2s for every source. `encode_video`'s progress log reads `-g` back out of the emitted args rather than recomputing from the source fps, which used to report 120 for a 59.94fps source.
- **Montage joins are hard cuts, by decision** (`montage_builder`): every montage clip is stream-copied out of the already-graded day master and stream-copy-concatenated, so the joins are lossless and the LF body behind them is never re-encoded. A crossfade needs both sides of each join decoded and re-encoded, which would put a lossy generation on the LF's best footage. The cut-on-the-beat look is the house style, not a missing feature — adding crossfades means moving to a filter-graph render (`drive_assembler._render_montage`) and giving up the generational-loss-free property. `render_verified_template.yaml`, the manual pre-upload shorts checklist, was deleted in the same pass: no code ever read it, and its `audio_20lufs` row contradicted the near-silent `-an` shorts contract that replaced LUFS normalisation.
- **Crossfade-stitch encoder parity** (`StopProcessor._crossfade_stitch`): `stop_detection.crossfade_duration` defaults to 0.5 s, so the legacy single-video path re-encodes the whole cut file through one `hevc_nvenc` xfade stitch *before* the stage-9 master encode — a second full generation. Its quality knobs are read from `encoding_constants` (`LONGFORM_NVENC_PRESET` / `LONGFORM_NVENC_CQ` / `LONGFORM_PROFILE` / `LONGFORM_PIX_FMT`), never hand-written: the previous literal `p5` sat one preset below frozen, and the `-cq` value came from `LONGFORM_CRF` — the *x265* fallback knob, correct here only because both constants happen to equal 18 today. Range follows the source (`_get_color_range`); no pixel conversion happens at this stage. Tests: `tests/test_crossfade.py`.
- **Graceful shutdown**: SIGTERM/SIGHUP → `SystemExit(143)`, KeyboardInterrupt → 130; both let `try/finally` checkpoints land. `_eager_import_state_invariants()` runs early in `run()` so a stale `sys.modules` entry raises at startup, not after hours.
- **NVDEC hardware decode on by default** (`config.drive.use_nvdec_decode`): adds `-hwaccel cuda -hwaccel_output_format cuda` + `hwdownload,format=nv12|p010le` in `single_pass._run_encode_step` (~1.54× on 4K HEVC). Auto-skipped when NVENC is disabled. Fallback: `use_nvdec_decode: false`.
- **Sidecar integrity gate** (`drive_phases/phase_d_gates.py::_run_sidecar_integrity_gate`, top of Phase D, delegating to `youtube_sidecar.py`): `youtube_uploads.json` must have exactly `len(drive_plan.regular_lfs)` entries with matching indices, and — independently, whenever any superlong parts exist — `superlong_uploads.json` (an APPEND-AS-YOU-GO progress log, NOT a complete manifest like the LF sidecar) is checked by `assert_superlong_sidecar_integrity` against `state.superlong_parts`' composite `date:part_index` keys: a PHANTOM sidecar key (one the current plan never produced) always raises `SidecarIntegrityError`, but a MISSING key (plan has it, sidecar doesn't yet — normal mid-upload progress) raises only when the sidecar's recorded `__plan_fingerprint__` (`youtube_sidecar.PLAN_FINGERPRINT_KEY`, stamped by `save_superlong_sidecar`) disagrees with the current plan's — naming the specific sidecar file that failed (`sidecar_path`). The gate only no-ops when there are neither regular LFs nor superlong parts to check — a superlong-only state no longer skips it. Escape: `--force-sidecar-reset` wipes BOTH sidecars, plus the LF state mirror, together (manual only).
- **Audio: attenuate-only near-silent, NEVER a boost** (`gomoveshift/pipeline/loudnorm_measure.py::build_attenuate_filter`): the operator standing rule is that every published video must be practically silent — conversation/songs must not be interpretable at max volume. A loudness *measurement* pass still runs (audio-only decode → `input_i`/`input_tp`), but its stats feed a single non-positive `volume=<=0 dB` gain that pulls the source DOWN to `AUDIO_SILENCE_CEILING_LUFS` and honours `AUDIO_TRUE_PEAK_CAP` — positive gain is impossible by construction (asserted in the helper). The prior `loudnorm=I=-20` **boosted** quiet cab audio up to target, which is exactly how a short once shipped audible speech; a `loudnorm`/normalizing filter is now forbidden and `single_pass._build_audio_filter` / `ost_applier._audio_attenuate_filter` raise if one is reintroduced. One pass over the day master; regular LFs stream-copy from it, `apply_ost` re-attenuates each LF on its OST re-encode. `AUDIO_FILTER_ALGO_VERSION` + `MASTER_ENCODE_ALGO_VERSION` invalidate a pre-fix cached master. **`--no-audio`** encodes the day master with `-an` (no audio stream) so LFs stream-cut from it are fully silent; `apply_ost` probes for the absent stream (`_has_audio_stream`) and burns `-an` rather than attaching an audio filter to nothing. **Drive shorts always ship `-an`** (`render_short_ffmpeg`) — vertical platforms may re-normalize quiet audio back up, and a stripped stream can't be undone. The route-story social cut keeps its attenuated audio despite sharing the same 1080x1920 frame (`route_story_short` rendition) — it is not cabin audio.
- **Long-form loudness HARD FAIL** (`assert_audio_loudness_hard_fail`, via `LongformValidator`): ceiling-only. `check_audio_loudness` raises when integrated loudness is LOUDER than `LONGFORM_AUDIO_MAX_LUFS` or true peak breaches `LONGFORM_AUDIO_TP` (a quieter-than-ceiling file is the GOAL, not a defect — the old two-sided `-20 ±2` window is gone because failing too-QUIET audio is what demanded the boost). A reading is judged only if it covers the file: loudnorm prints its JSON for whatever it decoded, so a measurement whose ffmpeg exited nonzero, or whose last `time=` progress stops more than `_LOUDNESS_COVERAGE_SLACK_SEC` short of the probed duration, is re-taken once and otherwise fails as "measurement incomplete" (for example -42.9 on an LF that re-measures -45.0). `check_momentary_loudness` (speech-intelligibility belt) parses ffmpeg `ebur128`'s per-frame momentary `M:` field and raises when the loudest 400 ms window exceeds `LONGFORM_AUDIO_MAX_MOMENTARY` — a few loud speech words barely move the integrated average but spike momentary loudness; a parse failure degrades to a WARN pass (the integrated gate is primary). Both run UPSTREAM of every upload (`_run_final_validation_gate` ahead of the Upload block). Escape: `--no-audio` (diagnostic — also skips the gate via `config.drive.skip_audio`).
- **File-integrity HARD FAIL** (`assert_file_integrity_hard_fail`, in `_run_final_validation_gate`): a FINAL.mp4 that is missing, under the 1 MiB floor, or ffprobe-unreadable (genuinely corrupt) raises UPSTREAM of every upload. The silent-skip hole is closed — the pre-upload loop used to `continue` past a missing/truncated FINAL, so a truncated LF sailed through all four pre-upload gates and the other LFs' Drive/YouTube uploads proceeded, the corruption caught only by the post-upload quality gate after irreversible uploads; the missing/undersized classes are now recorded as integrity failures directly (no `validate` call on an absent file) and abort the whole run before any upload. `content_safety` blocklist violations escalate the same way. Both mirror `assert_audio_loudness_hard_fail`.
- **Cross-surface location-invariant HARD FAIL** (`content_gates.check_location_invariant`): reconciles each LF's ACTUAL shipped `title` / burned-OST `location` text against the `ResolvedLocation` vote (in `metadata_json["resolved_location"]`). Reading the model's own `dominant_county` would be vacuous — it is a member of `regions` by construction — so the gate extracts the sampled counties from `regions` and HARD FAILs when a county-form shipped label names ZERO of them (genuine far-road desync). Town-form labels and `"A to B"` endpoint towns are checked against town-level truth — `ordered_place_sequence` + `destination`, plus the geometric `trace_verified_places` rescue (see 03) — and HARD FAIL when a town appears in none of it (wrong-town-in-right-county class); with no town-level truth the town-form check is skipped. (The shorts gate no longer mirrors this: a town-form burn there IS checked, unless it is clip-derived — see the shorts OST cascade entry above.) Coverage rule: HARD FAILs when a county holding `>= LOCATION_MATERIAL_SHARE` of the footage is named nowhere in the label (a label may not omit a county with material footage). Escalated via `assert_location_invariant_hard_fail`, runs UPSTREAM of upload. No-op for GPS-less/legacy LFs.
- **Label-quality backstop** (`check_label_quality`, WARN-only): flags a county-only label when `ordered_place_sequence` carried a recognizable settlement (`LABEL-QUALITY:`). A label that OPENS with a preposition/title word ("To Mizen Head, County Cork") is checked first and reported separately as a title-not-a-place problem, never misreported as "county-only" just because it happens to contain the word "County". A label whose lead component (before the first comma) is neither county-shaped nor road-shaped ("Goleen, County Cork") is a settlement, not a bare county, and is not flagged even when that settlement isn't itself in `ordered_place_sequence`; a road-shaped lead ("R591, County Cork", "US-64, Jackson County, NC") still warns. Road-shaped means a route ref (`N71`, `US 64 Business`), a spelled-out route (`Interstate 40`, `NC Highway 28`, `Hwy. 64`), an OSM concurrency ref (`US 64;NC 28`), a name ending in a road noun (Road ... Skyway, Motorway, Beltway), or any name the resolver recorded as a road (`resolved_location` `road` / `road_refs` / `road_votes`). A road spelling none of these recognise is read as a settlement and silenced (the cost is a missed WARN, never a failed run), so a newly seen road shape gets added to `_ROAD_REF_RE` / `_ROAD_WORD_RE`. Always `passed=True` (observability for the robust-by-construction ladder; silent on healthy runs). `ReviewGate.gate_cd` re-surfaces the same verdict (`_label_quality_warning`, since the gate's own log line never reaches the human prompt) and prints it inline under the offending LF's title, plus a one-line count banner directly above the Gate C/D `[y/N]` — still WARN-only, the operator can still approve. Both call sites share one helper, `_label_quality_diagnosis`, so the title-vs-county-only detection can't drift between them again.
- **Answer-file path for every human gate, TTY or not** (`ReviewGate._consume_or_ask`): each gate (A, Preview, B, Pre-Render, C/D) checks `<output_dir>/_gates/<gate_id>.answer` (JSON `{"decision": "approve"|"reject", "note": str, "answered_at": iso}`) before falling back to `builtins.input()`: present → consumed (renamed to `.answer.used`) and its decision resolves the gate with no prompt; absent → `<output_dir>/_gates/<gate_id>.question.json` (`gate_id`, `question`, `choices`, `artifacts`) is written. Gate C/D's confirmation state (`gate_cd_confirmed` + `gate_cd_confirmation_hash`) is written onto `PipelineState` and persisted to `pipeline_state.json` by the orchestrator's normal `_save_state` checkpoint, not by the gate itself. The call then polls for that answer (`_poll_for_answer`, 5s interval) ONLY when `GMS_GATE_ANSWER_TIMEOUT_SEC` is a positive number — unset/`0` (the default) returns `None` immediately (no console will ever answer a truly headless run), so a headless cron/CI/CLI run with no console attached never blocks. When the poll DOES run and no answer arrives, `_consume_or_ask` now RAISES `ReviewFailedError` rather than returning `None` — a question that was written and never answered fails the run, it never lets it silently proceed past the review it asked for (previously Gate C/D's `--no-review` path returned and shipped anyway; the same fix now covers gates A/Preview/B/Pre-Render, which used to call `input()` unconditionally whenever review was left on and crash with `EOFError` on a console job's `/dev/null` stdin). The console container is the one place a console operator can answer a job it launched, so `docker/console-compose.yaml` opts every console-spawned job into polling regardless of `--no-review` (`GMS_GATE_ANSWER_TIMEOUT_SEC` default 21600s/6h, registered in `console/registry/gms_settings.yaml`). A real TTY is unchanged and still falls back to `input()` immediately, never touching the answer-file path. A malformed `.answer` (bad JSON) is left in place with a `.answer.rejected` sidecar recording the parse error, rather than being destroyed — a corrected answer can still be dropped and picked up.
- **Metadata-quality corroboration against the resolved trace** (`check_metadata_quality` gates 4 and 7): both checks consult `metadata_json["resolved_location"]` before calling a surface wrong, because the naive forms contradicted other gates on ordinary multi-county drives. Gate 4 (title/location) compared the title against words lifted from the county-form `location`, so a settlement-anchored title shared zero keywords with it (`Exampletown, ST in 4K` vs `Sample County, Samplestate`) — the exact anchor `check_label_quality` asks for, making the pair jointly unsatisfiable; `_title_names_a_traced_place` now passes the title when it names a place from `ordered_place_sequence` or `trace_verified_places` (word-boundary, same `>=4`-char floor the keyword list uses), and a title naming somewhere off the trace still fails. Gate 7 (chapter cross-check) counted any chapter county absent from the single `location` string as a mismatch, which a genuinely multi-county LF trips by construction; a county present in `regions` now counts as a match, so only a chapter naming a county the drive NEVER sampled fires it — the same sampled-region set and bug class `check_location_invariant` guards. Legacy metadata carrying no `resolved_location` keeps both strict forms. Without this, a multi-county run hard-failed Phase D on most LFs after every encode had already succeeded. Known gap left open: the gate's `Entering <place>, <County>` regex requires the comma, so bare `Entering <County>` chapters are never collected — it drops the chapters that MATCH the episode label and keeps the ones that don't, biasing gate 7 toward failure. Fixing it means moving `route_context._ENTERING_RE` too, or the mirrored parsers drift. Tests: `tests/test_metadata_quality.py::TestResolvedLocationCorroboration`.
- **Grammar gate (preposition-collision splices)** (`content_gates.find_grammar_issues`, consulted by `check_metadata_quality` gate 10, `csv_generator._assert_metricool_rows_have_no_grammar_issues`, and `publishing/plan_gates.py::assert_plan_text_grammar`): string-based and independent of any structured location label. HARD-FAILS a location-template splice that runs an existing preposition into a templated `"To <Place>"` clause (`"drive through To Clonakilty"`, `"Through To Clonakilty"`), a doubled preposition (`"through through"`, case-insensitive), a hashtag that swallows `To` into the place name (`#ToClonakilty`), and any surface whose value opens with a bare preposition (`To |Through |Around |Toward `). Runs on the LF title/description/location/tags, every shorts/TikTok CSV row's title/caption/tag columns (the `YouTube Video Tags` cell is split on `,` and each tag checked individually; upstream of the CSV write, greppable `METRICOOL-CSV-GRAMMAR`), and every publish-plan shorts surface before the plan is built (greppable `PUBLISH-PLAN-GRAMMAR`). `social_generator.SocialGenerator._build_tags` also strips a leading operator title word from each location component (`parse_lf_label`) before deriving phrase and region tags, so a bare-preposition tag ("To Goleen") is not built in the first place. Test: `tests/test_grammar_gate.py`, `tests/test_social_tags_preposition.py`, `tests/test_publish_plan_gates.py`.
- **Perceptual spot-check** (`LongformValidator.check_perceptual_spot` → `assert_perceptual_spot_hard_fail`): the first gate that looks at PIXELS. Every other pre-upload gate reads container/stream metadata, so a final that encoded to a black or frozen picture (a broken concat, a dead NVENC surface) satisfied codec/resolution/bitrate/colour/loudness and uploaded. It samples three `PERCEPTUAL_WINDOW_SEC` windows at 20/50/80 % of the timeline through one `blackdetect=d=0.5:pix_th=0.10,freezedetect=n=0.003:d=2` pass each and parses `black_duration:` / `freeze_duration:` out of ffmpeg's stderr. **The verdict is deliberately asymmetric**: it FAILS only when EVERY sampled window is ≥`PERCEPTUAL_DEAD_WINDOW_RATIO` covered by one black run — a final with no picture, which is a render fault and never footage — and otherwise PASSES while reporting the longest black/freeze runs in `measured_value` plus a greppable `PERCEPTUAL-SPOT` warning past `PERCEPTUAL_BLACK_REPORT_SEC` / `PERCEPTUAL_FREEZE_REPORT_SEC`. A night tunnel is legitimately black and a minute stopped in traffic is legitimately frozen, and the gate runs immediately before an irreversible upload, so a heuristic abort would cost more than it saves. A file that will not probe, a timeout, or an ffmpeg failure degrades to a pass — `file_integrity` already hard-fails a corrupt final, the same don't-double-fail policy as the momentary-loudness belt. `_run_final_validation_gate` takes a `perceptual_check_fn` injection point (default `_default_perceptual_check`, which builds a real `LongformValidator`) so the wiring is testable without the `PipelineValidator` facade growing a passthrough.
- **Encode + colour contract gates on every final** (`longform_validator.color_tag_issues` + `ShortsValidator._check_short_encoding_contract`): before this, NO validator read `color_range` / `color_space` / `color_primaries` / `color_transfer` on any shipped artifact, so the full-range-upload class (a `pc`-range or untagged final that a player renders crushed) was unverified everywhere; and `ShortsValidator` had no pix_fmt / profile / codec check at all, so the exact banded-skies regression (p5 / CQ 23 / 8-bit `yuv420p`, `Main` profile) passed every shorts gate. Both encodes stamp the same SDR flags, so one shared `COLOR_TAG_CONTRACT` map (`LONGFORM_COLOR_RANGE` / `_COLORSPACE` / `_COLOR_PRIMARIES` / `_COLOR_TRC`) drives the long-form gate and the new per-short `short_encoding_contract:` gate, which additionally asserts HEVC + `SHORTS_PROFILE` main10 + 10-bit 4:2:0. Reported forms were confirmed against a real pipeline-produced artifact: `-profile:v main10 -pix_fmt p010le` probes back as `Main 10` / `yuv420p10le`, and the four colour flags probe back as `tv` / `bt709` ×3 — so both `yuv420p10le` and `p010le` are accepted. Fail-closed throughout: an ABSENT tag is the untagged-upload case and is reported, never skipped. The shorts gate is FATAL (not `ADVISORY_GATE_PREFIX`), and the long-form issues land in `video_quality`, which the drive path hard-fails.
- **Encode-contract HARD FAIL** (`assert_video_quality_hard_fail`, in `_run_final_validation_gate`): `video_quality` (codec / resolution / bitrate floor / profile / pix_fmt) and `bitrate_preservation` were the last WARN-only gates on the drive path — a regressed 8-bit, sub-4K, or under-floor long-form logged a warning and shipped, which is the banded-skies regression class. Both measure the FINAL against FROZEN `encoding_constants` values, so neither is a judgment call; failures from the pair collect into one bucket and raise ahead of every upload, mirroring `assert_audio_loudness_hard_fail`. `bitrate_preservation` additionally had to be switched ON: `PipelineValidator.validate` used to append it only when a truthy `source_bitrate_kbps` reached it — a leftover trigger from when the floor was derived from the SOURCE bitrate — and the drive path passed nothing, so the only constants-sourced bitrate check never ran in production. Nothing is threaded through `validate` to switch it on — a flag posing as a measurement is the state this removed, and `tests/test_phase_d_integrity_safety_hard_fail.py::test_drive_path_needs_no_bitrate_sentinel` pins that the drive path passes no `source_bitrate_kbps` at all.
- **Validators fail closed on a partial ffprobe read** (`LongformValidator.check_video_quality` + `ShortsValidator`): every long-form quality check used to be guarded by its own field's truthiness — `if height and …`, `if bitrate > 0 and …`, `if profile and …`, `if pix_fmt and …` — so a probe that returned only some fields SKIPPED those checks and reported a clean pass on a final nobody had verified. Each unreadable field is now an issue in its own right (`… unreadable from ffprobe (fail-closed)`); the gate never certifies what it did not measure. The same flip applies to `_check_short_bitrate`, whose `bitrate <= 0` branch returned `passed=True`; it now fails under its own `short_bitrate_unreadable:` gate, which is FATAL — the `ADVISORY_GATE_PREFIX` (`short_bitrate:`) that demotes a below-floor short to a warning deliberately does not match it, because a short a little under the floor still plays while an unmeasurable encode is simply unverified. The long-form bitrate floors are also constants-sourced now (`LONGFORM_MIN_BITRATE_4K` / `LONGFORM_MIN_BITRATE_1080P`): the former hardcoded 30000/12000 sat BELOW the real 40000/15000, so a final landing between the two numbers passed this gate while failing `check_bitrate_preservation`, which reads `encoding_constants` correctly.

- **Per-file Drive upload idempotency** (`PipelineUploader._upload_file` / `_find_existing_drive_file` / `_ensure_shareable`): the day-first shorts path (`upload_shorts_by_paths`, called via `_upload_lf_shorts_to_drive`) uploads a per-LF path list with no manifest, so a mid-LF failure previously discarded every already-succeeded link and a retry re-created a SECOND Drive file per already-uploaded name (Drive permits duplicate names in a folder). `_upload_file` now runs one `files().list(name=… and folder in parents and trashed=false)` before creating (the filename is escaped via `_escape_drive_query_value` — the Drive query grammar requires `\`/`'` escaping, and an unescaped apostrophe in a geocoded place name would otherwise fail the lookup and silently disable idempotency for that file): a same-named, same-size match is REUSED (the existing file id, no re-upload); a same-named, different-size match (a genuinely re-rendered local file) is replaced IN PLACE via `files().update` on that same file id, never a second `create()`, so a resume can never leave two Drive files sharing a name and a re-rendered local file can never keep silently serving a stale remote copy. **Sharing is (re-)applied on every path** — reused, updated, or newly created — via `_ensure_shareable`, which always attempts `permissions().create()` (cheaper than listing permissions first, since the common create-path already paid that exact call, and a `list()`-first approach would pay an extra call on every single upload) and tolerates an "already shared" error rather than treating it as fatal; this closes a real regression the first version of this fix introduced — sharing only on `existing is None` meant a retry after a prior run's `permissions().create()` failure (file landed, share call raised) returned a "successful" but publicly-inaccessible link. The existing-file lookup fails open (any error, or a response shape that isn't a real Drive listing, is treated as "no match") so it never blocks the underlying upload. **Known limit, accepted**: reuse is decided on name + size, not content — a re-render that happens to produce an identical byte count keeps serving the old remote bytes. Unlikely for video; a checksum comparison would mean hashing the whole file every run, and `files().list` can return `md5Checksum` at no extra API call if this is ever tightened. Deferred: manifest entries for `upload_shorts_by_paths` are still only assembled by the caller after every path succeeds (`_upload_lf_shorts_to_drive` in `external_systems_coordinator.py`) — a mid-LF failure still loses the in-memory link list for files already uploaded on THIS run, though a subsequent retry no longer duplicates them since each file is independently idempotent. Tests: `tests/test_upload_idempotency.py`.

- **Composite segment-score** (`gomoveshift/analysis/unified_scorer.py`): 8-dim, weights sum 1.00 — `motion_energy 0.16 / speed_variance 0.15 / color_vibrancy 0.10 / scene_change 0.10 / sky_ratio 0.05 / golden_hour 0.10 / scenic_score 0.20 / brightness 0.14`. GPS-dependent weights (`speed_variance`, `scenic_score`) redistributed when no GPX.
- **Weather is no longer a scoring signal**. `WeatherDetector._classify` was demoted to return OVERCAST on every branch — frame brightness cannot separate rain from a tunnel, or sun from snow glare — so the 7% weather weight fed the composite a constant `0.6` for every episode, ranking nothing while diluting the signals that do. The weight is deleted and its mass moved to `brightness` (0.07 → 0.14), the per-second measurement of the same lighting phenomenon. The scorer still computes a `weather` signal and `WEATHER_SCORE_BY_CLASS` still maps `sunny/overcast/rainy → 1.0/0.6/0.2`; with no weight, the column is inert (a missing weights key scores 0.0, so a config that still lists `weather` keeps loading). `WeatherDetector` and `score_frame_brightness` are untouched — the detector is a light-level reporter with callers of its own, and restoring a real classifier means restoring the weight in `DriveConfig.scoring_weights`. Note phase A still constructs and runs the detector per episode; that measurement now buys nothing for scoring and is a candidate for removal.

A missing source dir still raises at once. `--dry-run` is unchanged (plan only, no gate, no encode). - **Source-footage contract** (`preflight.check_source_filesystem`): resolves every video entry's symlink, then (a) **refuses** a dangling symlink or a file whose first 4 KiB cannot be read — correctness, no flag bypasses it (`stat` can answer from cache while every read fails with EIO/ENODEV, and an `is_file()` check silently drops dangling links); (b) **warns** `PERFORMANCE:` with the files' real mount and the staging mount when they differ — the documented layout (`~/.cache/gomoveshift/sources/<trip>/` symlinked in from another drive) is a speed cost, not a correctness one. The check compares the files' real mount, not the symlink *directory*'s. Slow reads can collapse the weather measurement, but weather has no score weight and `allow_degraded_weather` is True, so no ranked or rendered output depends on read speed. A "can corrupt mid-run" claim has no evidence behind it: what is recorded is degradation and a stale-symlink reroute (now `check_concat_target_alignment`), and a volume failure (such as NTFS delayed-write errors) hits any layout reading or writing that drive. Write safety stays with the disk-space gates, the validated concat cache and the final file-integrity gate. Tests: `tests/test_preflight_source_filesystem.py`.
